# Audit Log Action Catalog

Each row in `auditLogs` has `action`, `resource`, optional `resourceId`,
optional flat-scalar `details`, and optional `detailsBlob` (JSON-encoded
string for nested payloads). Both `action` and `resource` are validated by
`auditActionValidator` and `auditResourceValidator`, derived from
`auditActions/catalog.ts`. The validators check each column on its own; the
action ↔ resource pairing in the table below is what the writers do, not a
schema rule.

All inserts must go through `recordAuditLog(ctx, {...})` in
`lib/auditLog.ts`. The public `auditLogs.create` and internal
`createInternal` mutations have been removed.

## When to use `details` vs `detailsBlob`

| Use `details`                                | Use `detailsBlob`                                         |
| -------------------------------------------- | --------------------------------------------------------- |
| Flat scalar map (string/number/boolean/null) | Nested objects, arrays, or change-tracking `{ from, to }` |
| Fast indexed reads                           | Free-form payload at the cost of `JSON.parse` on read     |

## Action catalog

The table lists every literal in `AUDIT_ACTION_LITERALS`, in catalog order,
and nothing else. `auditActions/__tests__/catalogDoc.test.ts` fails when the
two disagree.

Rows written by a lifecycle module carry `{ previousStatus, newStatus, applied }`,
where `applied` is `'transitioned'` for a real status change and `'recorded'`
for an idempotent same-state attempt (audited, nothing patched). "Lifecycle
details" below means that shape.

A few literals have no writer in the current code. They stay in the catalog
so rows written by older releases still pass the schema validator. Their rows
say "No current writer" and keep the payload this document listed for them
before ("Earlier doc").

### Operator ramp actions

The `deliverability_ramp.*` actions an operator triggers go through
`delivery/rampControlAudit.ts`, which writes the audit row and a matching
`mixDecisions` row together. Their `details` share
`{ cell, fromShare, toShare, reason, message }` (`message` is the sentence the
ramp timeline shows), followed by the action's own inputs listed above.
`resourceId` is the cell key.

## Extending

To add a new action:

1. Append the literal to `auditActions/catalog.ts` `AUDIT_ACTION_LITERALS`
   (and `AUDIT_RESOURCE_LITERALS` if the action introduces a new resource
   kind). The schema validator and `auditActionValidator` derive from this
   catalog automatically.
2. Add a row to the table above documenting the expected payload. Write each
   literal in full, in backticks, in the first column; one row may list
   several (`topic.created` / `topic.deleted`). The `catalogDoc` test fails
   until the row exists, and also on a row naming an action or resource the
   catalog does not have.
3. Call `recordAuditLog` from the mutation that owns the action.
