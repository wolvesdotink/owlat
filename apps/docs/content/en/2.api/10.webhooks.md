Owlat supports both outbound customer webhooks and inbound provider webhooks.

## Outbound customer webhooks

Configure in **Settings → Webhooks**.

Supported outbound events:

- `email.sent`
- `email.delivered`
- `email.opened`
- `email.clicked`
- `email.bounced`
- `email.complained`
- `contact.created`
- `topic.unsubscribed`

### Delivery notes

- Endpoint must accept `POST`
- Use publicly reachable HTTP/HTTPS URLs
- Private/local network hosts are rejected
- Failed deliveries are tracked and can be retried

### Signature verification

Webhook secrets use the `whsec_...` format and are generated at webhook creation.

Every delivery includes these headers:

| Header                  | Description                                                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-Owlat-Signature`     | `t=<timestamp>,v1=<signature>`: `v1` is the HMAC-SHA256 hex digest of `` `${t}.${X-Webhook-Delivery-Id}.${body}` ``, keyed with your secret |
| `X-Signature`           | **Deprecated.** HMAC-SHA256 hex digest of the JSON payload body alone                                                                       |
| `X-Timestamp`           | Unix timestamp (seconds) when this attempt was sent; the same value as `t` in `X-Owlat-Signature`                                           |
| `X-Webhook-Id`          | The webhook ID                                                                                                                              |
| `X-Webhook-Delivery-Id` | ID of this delivery; the same on every retry, so a receiver can ignore a delivery it has already processed                                  |
| `X-Webhook-Attempt`     | Attempt number of this request, starting at 1                                                                                               |
| `Content-Type`          | `application/json`                                                                                                                          |
| `User-Agent`            | `Owlat-Webhooks/1.0`                                                                                                                        |

Verify `X-Owlat-Signature`. Because its `v1` signature covers the timestamp and the delivery ID as well as the body, a valid signature tells you that `X-Timestamp` and `X-Webhook-Delivery-Id` are the values Owlat sent. Then:

1. Reject the request if `t` is more than 5 minutes away from your server's clock.
2. Ignore a delivery ID you have already processed. A retry carries the same `X-Webhook-Delivery-Id` with a new timestamp and a new signature, and it can arrive after the 5-minute window has passed (see [Retry behavior](#retry-behavior)), so keep processed IDs for at least 24 hours, not just for the window. Record an ID after your handler has succeeded. If handling fails, answer with a non-`2xx` status and do not record the ID, so the retry is processed.

::callout{type="warning" title="X-Signature is deprecated"}
`X-Signature` signs the body only. It does not cover `X-Timestamp` or `X-Webhook-Delivery-Id`, so a receiver that checks it cannot tell whether those headers were changed. Owlat still sends it next to `X-Owlat-Signature` for one more release so existing receivers keep working, and then stops. Move your receiver to `X-Owlat-Signature` now.
::

#### Payload shape

```json
{
	"event": "email.delivered",
	"timestamp": "2026-03-15T12:00:00.000Z",
	"data": {/* event-specific data */}
}
```

The payload's own `timestamp` is when the event was built, and it stays the same on every retry. Check freshness against `t`, not against this field.

#### Verification example (Node.js)

```typescript
import crypto from 'node:crypto';

const TOLERANCE_SECONDS = 300;

function verifyOwlatWebhook(headers: Headers, body: string, secret: string): boolean {
	const timestamp = headers.get('X-Timestamp') ?? '';
	const deliveryId = headers.get('X-Webhook-Delivery-Id') ?? '';
	const fields = new Map(
		(headers.get('X-Owlat-Signature') ?? '').split(',').map((part): [string, string] => {
			const eq = part.indexOf('=');
			return [part.slice(0, eq), part.slice(eq + 1)];
		})
	);
	const v1 = fields.get('v1');
	if (!v1 || !deliveryId || !/^\d+$/.test(timestamp) || fields.get('t') !== timestamp) {
		return false;
	}

	// 1. The signature covers the timestamp, the delivery ID and the raw body.
	const expected = crypto
		.createHmac('sha256', secret)
		.update(`${timestamp}.${deliveryId}.${body}`)
		.digest();
	const presented = Buffer.from(v1, 'hex');
	if (presented.length !== expected.length || !crypto.timingSafeEqual(presented, expected)) {
		return false;
	}

	// 2. Freshness: reject a request signed more than 5 minutes from now.
	return Math.abs(Date.now() / 1000 - Number(timestamp)) <= TOLERANCE_SECONDS;
}

// In your webhook handler:
const body = await request.text(); // the raw body, before any JSON parsing
if (!verifyOwlatWebhook(request.headers, body, webhookSecret)) {
	return new Response('Invalid signature', { status: 401 });
}
// Then skip the event if you have already processed this X-Webhook-Delivery-Id.
```

### Retry behavior

Failed deliveries are retried up to **3 attempts**:

1. Immediate
2. After 1 minute
3. After 5 minutes

Each request has a **30-second timeout**. Endpoints that resolve to private/local network IPs are rejected.

If an attempt is lost before it records an outcome (for example when the backend restarts during the request), Owlat sends it again with the same `X-Webhook-Delivery-Id`, up to three times, and then marks the delivery failed. Deliveries that a release before 0.5.6 left waiting are picked up the same way after the update, unless they have been waiting for more than 24 hours. Those are not sent. They appear in the delivery log as failed, with the error "Abandoned: stuck before the delivery-recovery upgrade".

## Inbound provider webhook routes

These are the endpoints Owlat itself exposes to receive delivery status and inbound mail from its sending provider. They are distinct from the outbound webhooks above, which Owlat sends to _your_ endpoints.

Each feedback-capable sending path has a stable inbound route:

| Route                     | Provider                | When it's used                          |
| ------------------------- | ----------------------- | --------------------------------------- |
| `POST /webhooks/mta`      | Bundled Owlat MTA       | Default for self-host                   |
| `POST /webhooks/ses`      | Amazon SES through SNS  | When SES feedback is configured         |
| `POST /webhooks/resend`   | Resend                  | When configured as the sending provider |
| `POST /webhooks/mandrill` | Mailchimp Transactional | When Mandrill feedback is configured    |
| `POST /webhooks/emailit`  | Emailit                 | When Emailit feedback is configured     |

A request without the signature headers its provider's scheme requires is refused with `401` before its body is read. Except for SES, each route then verifies the signature before it charges the per-provider rate limit, so unsigned traffic cannot use up the limit that real deliveries need. That free verification covers bodies that declare at most 256 KiB. A larger or chunked body (for example a big Mandrill `mandrill_events` batch, up to the 5 MiB cap) is charged before it is read, to a separate limit it shares with every other large unverified request on that route. Under a flood of large junk requests on the same route, such a batch can be answered `429`; the provider retries it later, as it does for any non-2xx answer.

### Bundled MTA route

```http
POST /webhooks/mta
```

For self-hosted deployments, the bundled MTA is the default sending path, so this is the primary inbound route. It handles delivery status, inbound mail, and operational reputation events:

| Event                                                                        | Effect                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bounced`                                                                    | Records the bounce (hard/soft, pre-classified by the MTA) and updates blocklist + contact activity                                                                                                                                                                        |
| `complained`                                                                 | Records the spam complaint and updates blocklist + contact activity                                                                                                                                                                                                       |
| `sent`                                                                       | Marks the send as dispatched                                                                                                                                                                                                                                              |
| `inbound.received`                                                           | Ingests inbound mail (e.g. campaign replies) into the team inbox. **Legacy path**: a current MTA sends this to `POST /webhooks/mta-inbound` instead, which carries the raw message; this route still accepts it for DLQ replays and older MTA binaries, without the bytes |
| `org.circuit_breaker`                                                        | Trips the sending circuit breaker on a high bounce rate                                                                                                                                                                                                                   |
| `ip.blocklisted` / `ip.delisted` / `ip.warming_complete` / `all_ips_blocked` | Surfaces IP reputation changes                                                                                                                                                                                                                                            |

Requests are signed with HMAC-SHA256 over `${timestamp}.${body}`:

| Header                   | Description                                                                                                                                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-MTA-Signature`        | HMAC-SHA256 hex digest                                                                                                                                                                                                                     |
| `X-MTA-Timestamp`        | Unix timestamp (seconds), rejected if more than 5 minutes from server time                                                                                                                                                                 |
| `X-MTA-Length-Signature` | HMAC-SHA256 hex digest over `owlat-mta-length-v1.${timestamp}.${byteLength}`. Lets the raw-message routes read a body over 256 KiB without first charging the rate-limit key shared with unverified requests. Optional; older MTAs omit it |

The shared secret comes from the `MTA_WEBHOOK_SECRET` environment variable. If it is unset, the endpoint fails closed with `503`.

### Team-inbox route

```http
POST /webhooks/mta-inbound
```

Where a current MTA sends `inbound.received`. Same HMAC scheme, same `MTA_WEBHOOK_SECRET`, same 5-minute staleness window as the route above — the verification is one shared implementation.

It exists separately because its body carries `rawBytesBase64`, the entire received message. The shared webhook pipeline caps a request body at 5 MiB **before** authenticating it and answers `413` above that, which the MTA retries and eventually dead-letters; this route has no such cap, so a message up to the 10 MiB the inbound listener accepts arrives intact. The raw message is stored sealed at rest, its attachment leaves are scanned for malware, and the attachments become downloadable from the thread view.

The audit row this route writes is a **digest** of the body plus the envelope identifiers, not a copy of the mail: one Convex document is capped at 1 MiB, so storing the body verbatim would silently fail for exactly the messages that have attachments.

### Resend route

```http
POST /webhooks/resend
```

Resend sends a wider set of provider events, but Owlat **acts on only two of them**:

| Event              | Effect                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| `email.bounced`    | Records the bounce (classified hard/soft from the provider message) and updates blocklist + contact activity |
| `email.complained` | Records the spam complaint and updates blocklist + contact activity                                          |

The other Resend events — `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.opened`, `email.clicked` — are received and acknowledged with `200 {"success": true, "ignored": true}`, but Owlat does not consume them. Send status is recorded at dispatch time, and open/click data comes from Owlat's own tracking pixel and link redirects, not from Resend's counters.

::callout{type="warning" title="No delivered/open/click side effects from the inbound path"}
Do not build integrations that expect the Resend inbound route to drive delivered, open, or click analytics — only bounce and complaint events have any effect. Use the [outbound webhooks](#outbound-customer-webhooks) above to receive `email.delivered`, `email.opened`, and `email.clicked` events.
::

Resend requests are verified using the [Svix](https://www.svix.com) signature scheme:

| Header           | Description                                                                |
| ---------------- | -------------------------------------------------------------------------- |
| `svix-id`        | Message ID                                                                 |
| `svix-timestamp` | Unix timestamp (seconds), rejected if more than 5 minutes from server time |
| `svix-signature` | One or more space-separated `v1,<sig>` HMAC signatures                     |

The signature is verified against the `RESEND_WEBHOOK_SECRET` environment variable (the `whsec_` Base64 secret from your Resend dashboard). If it is unset, the endpoint fails closed with `503`.

### Emailit route

```http
POST /webhooks/emailit
```

Emailit `accepted`, `attempted`, `delivered`, `bounced`, `complained`, `failed`, `rejected`, and `suppressed` events enter the same normalized lifecycle pipeline as incumbent providers. Suppression reasons are mapped into Owlat's closed recipient-safe vocabulary; loaded/clicked events are ignored because first-party tracking remains authoritative.

Requests require `X-Emailit-Timestamp` and `X-Emailit-Signature`. Owlat computes the lowercase hexadecimal HMAC-SHA256 of `<timestamp>.<raw body>` with the full `EMAILIT_WEBHOOK_SECRET` and rejects timestamps outside five minutes. An unset secret fails closed with `503`.

### TLS report route

```http
POST /webhooks/mta-tls-report
```

Inbound TLS-RPT (RFC 8460) aggregate reports. The MTA registers the operator's `_smtp._tls` `rua=` address as a system inbound route that delivers here, and the handler decodes the gzipped report attachment and stores the digest. Same HMAC scheme and same `MTA_WEBHOOK_SECRET` as the routes above, with a 60-second freshness window. A malformed or oversized report is answered `2xx` without being ingested, so the MTA does not retry a permanently bad report.

### DMARC report route

```http
POST /webhooks/mta-dmarc-report
```

Inbound DMARC aggregate (RUA) reports (RFC 7489). The MTA treats Owlat's DMARC report address (`MTA_DMARC_REPORT_ADDRESS`, by default `dmarc-reports@` on the return-path domain) as a system inbound route that delivers here instead of to a mailbox. The handler unpacks the gzip, zip or XML attachment under fixed size limits, parses it without DTD or entity support, and stores it once per reporter and report id. Reports about domains this deployment does not send for are dropped. Same HMAC scheme, `MTA_WEBHOOK_SECRET` and 60-second window as the TLS report route, and the same `2xx` answer for a report that will never parse.

### Bundled-plugin route

```http
POST /webhooks/plugin/{pluginId}
```

Feedback from a bundled plugin transport — one route for every plugin that reports its own outcomes. Unauthenticated and internet-facing by design: the caller is a third-party provider that holds no Owlat session, so every gate fails closed, in order — for a known plugin id, the signature headers its declared scheme needs (`401` before anything is spent), rate limit per plugin id, registration (an unclaimed id is `404` before the body is read), body size, the signature scheme the plugin's contract declares, the operator's authorization for that plugin, and replay by delivery digest.

### GitHub route

```http
POST /webhooks/github
```

Merge notifications for the code-work board. Verifies `X-Hub-Signature-256` against `GITHUB_WEBHOOK_SECRET` and acts only on `pull_request` `closed` events where the PR merged, moving the matching task to `merged`. A request without that header is refused with `401` before it is rate-limited or read. An unset secret fails closed with `503`; an event with no matching task is answered `200` so GitHub does not retry.
