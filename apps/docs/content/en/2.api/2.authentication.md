Secure API access with organization-scoped API keys. Each deployment serves a single organization, so a key is scoped to that one organization rather than to one of several tenants.

## API key format

Owlat validates keys with a live prefix format:

```txt
lm_live_...
```

## Sending auth headers

```bash
curl "https://rest.api.example.com/api/v1/contacts" \
  -H "Authorization: Bearer lm_live_your_key"
```

`Authorization: <api_key>` (without `Bearer`) is also accepted, but `Bearer` is recommended.

## Common auth failures

Each failure carries a code in `data.reason`, so a client can tell them apart
without reading the message: `missing_credentials`, `malformed_key`,
`invalid_key`, `missing_scope` and `too_many_failed_attempts`. A scope error
also names the scope it needs in `data.scope`.

### Missing header (`401`)

```json
{
  "error": {
    "message": "Missing or invalid Authorization header. Use: Authorization: Bearer <api_key>",
    "category": "unauthenticated",
    "data": { "reason": "missing_credentials" }
  }
}
```

### Invalid format (`401`)

```json
{
  "error": {
    "message": "Invalid API key format",
    "category": "unauthenticated",
    "data": { "reason": "malformed_key" }
  }
}
```

### Unknown, revoked or expired key (`401`)

```json
{
  "error": {
    "message": "Invalid API key",
    "category": "unauthenticated",
    "data": { "reason": "invalid_key" }
  }
}
```

A key that does not exist, was revoked or has expired gets the same answer, so
a response never confirms that a key was once real.

### Insufficient scope (`403`)

```json
{
  "error": {
    "message": "This API key is missing the required scope: contacts:write",
    "category": "forbidden",
    "data": { "reason": "missing_scope", "scope": "contacts:write" }
  }
}
```

### Rate limit exceeded (`429`)

```json
{
  "error": {
    "message": "Rate limit exceeded. Maximum 10 requests per second.",
    "category": "rate_limited"
  }
}
```

The limit is a token bucket that sustains 10 requests per second but allows short bursts of up to 15 requests before throttling.

Authenticated responses (including the `429` itself) carry the headers below. A `429` additionally includes `Retry-After`. Authentication failures (`401`) do not include these headers. `X-RateLimit-Remaining` and `X-RateLimit-Reset` are fixed values, not a reading of the bucket, so do not pace requests by them: back off when a `429` arrives, for as long as its `Retry-After` says.

| Header | Meaning |
| --- | --- |
| `X-RateLimit-Limit` | Sustained requests per second |
| `X-RateLimit-Remaining` | `0` on a `429` from this per-key limit, otherwise always one less than the limit, a transactional send limit's `429` included. It is not a count of the requests left |
| `X-RateLimit-Reset` | A Unix timestamp (seconds) one second after the response. It is not when the bucket refills |
| `Retry-After` | Seconds to wait before retrying (on `429` only) |

### Too many failed key attempts (`429`)

```json
{
  "error": {
    "message": "Too many failed API key attempts from this address. Wait for the Retry-After interval before trying again.",
    "category": "rate_limited",
    "data": { "reason": "too_many_failed_attempts" }
  }
}
```

Requests whose key does not authenticate are throttled per client address, so that nobody can try keys without limit. A valid key is never held back by it. This `429` carries `Retry-After` but no `X-RateLimit-*` headers. If you see it, check the key your client sends before retrying.

## Scopes

Each key carries a set of scopes that gate which v1 endpoints it may call. A request with a key that lacks the required scope is rejected with `403 forbidden` (see above).

| Scope | Grants |
| --- | --- |
| `contacts:read` | `GET /api/v1/contacts`, `GET /api/v1/contacts/{id}` |
| `contacts:write` | create / update / delete contacts |
| `events:write` | `POST /api/v1/events` |
| `transactional:send` | `POST /api/v1/transactional` |
| `topics:write` | add / remove a contact on a topic |

Creating a key **requires** an explicit, non-empty scope list — omitting it is rejected, and unknown scope names are rejected too. Pre-existing keys with no stored scopes are treated as having none (deny-all), so grant the specific scopes each integration needs.

## Best practices

- Keep keys server-side only
- Rotate and revoke keys on schedule
- Use separate keys per environment
- Monitor request patterns and failures
