Send published transactional templates to a recipient.

## Endpoint

| Method | Path                             | Purpose                  |
| ------ | -------------------------------- | ------------------------ |
| `POST` | `/api/v1/transactional`          | Queue a send             |
| `GET`  | `/api/v1/transactional/{sendId}` | Read where a send stands |

## Authentication

Both routes require an API key in the `Authorization` header with the
`transactional:send` scope. Requests without a valid key carrying this scope are
rejected with `401`/`403`.

## Request body

Provide either `transactionalId` or `slug`.

```json
{
	"slug": "order-confirmation",
	"email": "john@example.com",
	"dataVariables": {
		"firstName": "John",
		"orderNumber": "ORD-12345"
	},
	"language": "en",
	"attachments": [
		{
			"filename": "invoice.pdf",
			"url": "https://example.com/invoices/12345.pdf",
			"contentType": "application/pdf"
		}
	]
}
```

Fields:

- `transactionalId` or `slug` (required, one of these)
- `email` (required)
- `dataVariables` (optional flat object; each value is a string, number, boolean or `null`)
- `language` (optional language code, e.g. `en`, `de`, `en-US`)
- `attachments` (optional array) — file attachments to include with the email

### Attachments

Each attachment object has the following fields:

| Field         | Type   | Required                  | Description                                      |
| ------------- | ------ | ------------------------- | ------------------------------------------------ |
| `filename`    | string | Yes                       | The file name shown to the recipient             |
| `content`     | string | One of `content` or `url` | Base64-encoded file content                      |
| `url`         | string | One of `content` or `url` | URL to fetch the file from                       |
| `contentType` | string | No                        | MIME type (e.g., `application/pdf`, `image/png`) |

**Limits:**

- Maximum **10 attachments** per email
- Maximum **10 MB** (10 MiB, 10,485,760 bytes) total attachment size, counted as decoded bytes of `content`. Files sent by `url` are fetched later and are not part of this total.
- Send `content` as plain base64 without line breaks. This route accepts a request body of up to 14,081,056 bytes: the 10 MiB budget as base64 plus 100,000 bytes for everything else. Every field other than attachment `content` (including `dataVariables`) must fit in those 100,000 bytes, the same body limit as every other API endpoint. A larger body is rejected with `400` before it is read in full.
- An invalid attachment rejects the whole request before anything is stored, and the files of a request that is refused are deleted.

## Response

Accepted sends return queued status:

```json
{
	"data": {
		"status": "queued",
		"email": "john@example.com",
		"transactionalEmailId": "j57...",
		"slug": "order-confirmation",
		"contactId": "j58...",
		"contactCreated": true,
		"language": "en"
	}
}
```

> `transactionalEmailId` is the id of the **send** created for this request,
> not the template id. Every `email.*` webhook for this send carries it as
> `sendId`, and `GET /api/v1/transactional/{sendId}` reads its status. `slug` is
> the template's slug, also when the request named the template by
> `transactionalId`.

`queued` means the send was accepted, not that it went out. When delivery is
paused for a while (the delivery safety circuit is open, or the mail server
is restarting), the request is still accepted and the send waits. It goes out
when delivery resumes, or fails after four days with an error code that names
the cause: `DELIVERY_HOLD_EXPIRED` or `MTA_UNREACHABLE`. A send that fails for
good fires the `email.failed` webhook once and shows `failed` on the status
route; a send that is only waiting fires nothing.

## Send status

`GET /api/v1/transactional/{sendId}` returns where one send stands. `sendId` is
the `transactionalEmailId` the send call answered with.

```json
{
	"data": {
		"sendId": "j57...",
		"status": "failed",
		"email": "john@example.com",
		"templateId": "j59...",
		"slug": "order-confirmation",
		"language": "en",
		"queuedAt": "2026-11-02T09:00:00.000Z",
		"sentAt": null,
		"deliveredAt": null,
		"openedAt": null,
		"clickedAt": null,
		"bouncedAt": null,
		"complainedAt": null,
		"failedAt": "2026-11-06T09:00:00.000Z",
		"bounceType": null,
		"bounceCause": null,
		"errorCode": "MTA_UNREACHABLE",
		"errorMessage": "The mail server could not be reached before the delivery deadline passed"
	}
}
```

- `status` is one of `queued`, `sent`, `failed`, `delivered`, `opened`,
  `clicked`, `bounced` or `complained`.
- Timestamps are ISO 8601 and `null` until the send reaches that step.
- `errorCode` is set only when `status` is `failed`. Branch on it; the
  message is for people.
- `errorMessage` says why the send did not arrive: the reason of the failure
  when `status` is `failed`, and the receiving server's reply (for example
  `550 5.1.1 User unknown`) when it is `bounced`. It is `null` otherwise, and
  for a bounce whose report carried no text.
- `bounceType` is `hard` or `soft` once a bounce was reported.
- `bounceCause` says who the bounce was about, as the `email.bounced` webhook
  does: `recipient` when the address was refused (a hard bounce blocklists
  it), `sender` when the receiver refused the sending IP or domain (the
  address is kept, so do not suppress it on your side). It is `null` without
  a bounce, and for a bounce recorded by a server version that did not store
  the cause yet.
- `templateId` and `slug` are `null` once the template has been deleted.
- The send's `dataVariables` are never returned.
- An id that names no send created through this API answers `404`
  `not_found`: an unknown or malformed id, and also an email sent by a campaign
  or an automation, or one whose contact was deleted.

To learn about outcomes without polling, subscribe a webhook to `email.failed`,
`email.delivered` and `email.bounced` and match events on `sendId`.

## Idempotent retries

Send an `Idempotency-Key` header to make a send safe to retry after a timeout
or a `5xx`:

```http
Idempotency-Key: 3f0c1d9e-6c2b-4a51-9a3e-2f6d1b7c8e90
```

- The key is 1 to 255 printable ASCII characters without spaces, such as a UUID
  or your own order id. It is scoped to your organization.
- The first request with a key is processed normally. A repeat of the **same**
  request with that key within 24 hours queues nothing, returns the first response
  (same status and body) and carries an `Idempotent-Replayed: true` header.
- Reusing the key for a **different** request (another body or another endpoint)
  is rejected with `409` `conflict` (`reason: "idempotency_conflict"`) and has no
  effect.
- If the contact the first request named has been deleted since, a repeat
  within the 24 hours is rejected with `409` `conflict`
  (`reason: "idempotency_erased"`) and has no effect: the request already ran,
  but its response named the deleted person and is no longer kept.
- A request that was refused (for example `404` or `400`) or failed before it
  was applied stores nothing, so retrying it with the same key runs it again.
- After 24 hours the key can be used for a new request.
- Without the header, every request is processed, as before.

## Language resolution order

1. Explicit `language` in request
2. Contact preferred language (if recipient exists)
3. Template default language
4. Fallback default

## Validation and delivery checks

- The **Transactional API** feature must be enabled under **Settings → Features**;
  while it is off, requests are rejected with `403` (`reason: "feature_disabled"`)
- While sending is suspended or banned on the instance, requests are rejected
  with `403` (`reason: "abuse_blocked"`). The error's `data` also carries
  `status` (`suspended` or `banned`), `since` (an ISO 8601 time, or `null` when
  none was recorded), `detail`, the reason recorded with the suspension (or
  `null`), and `lift`, how it lifts, in the shape of the
  [status](/api/status) endpoint's `sendingHold.lift`. The message says
  whether it lifts by itself. A platform admin can lift it in the operator
  console
- Template must exist and be `published`; a `transactionalId` that names no
  template, including a malformed one, is rejected with `404`
- Template must have rendered HTML content
- Sending domain must be verified
- `dataVariables` are validated against template schema when present
- Every variable the email uses without a fallback (`{{orderNumber}}` rather
  than `{{giftNote|''}}`) must be supplied, unless the email marks it
  **optional**. A required variable that is missing or `null` is rejected with
  `400` naming it; an optional one renders empty, or as its fallback. Mark a
  variable optional in the email's editor, under **Sending > Data variables**
- The send must fit the [transactional send limits](/api#rate-limits), which
  the instance admin sets; a send over a limit is rejected with `429`

## Refusal reasons

A refused send carries a code in `error.data.reason`. Branch on the code, not on
the message: the message is for people and can change. The SDKs expose it as
`reason` (JavaScript) and `getReason()` (Java). New reasons can be added;
treat one you do not know by its status.

| `reason`                 | Status | What to do                                                                                                                       |
| ------------------------ | ------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `feature_disabled`       | `403`  | An admin turns on **Transactional API** under **Settings → Features**.                                                           |
| `abuse_blocked`          | `403`  | Sending is suspended. `data.lift` says if it lifts by itself; a platform admin can lift it in the operator console.              |
| `no_delivery_provider`   | `422`  | The instance has no delivery provider. Its operator configures the built-in MTA, Resend or SES ([Self-Hosting](/developer/self-hosting)). |
| `recipient_blocked`      | `422`  | The address bounced or complained before. Do not retry; remove it under **Audience > Suppressions** only if you know it works again. |
| `template_not_found`     | `404`  | Check the `slug` or `transactionalId`: no template has it.                                                                       |
| `template_not_published` | `422`  | Open the email under **Sending > Transactional** and click **Publish**.                                                          |
| `template_no_content`    | `422`  | The email has no rendered HTML. Open it, save it and publish it again.                                                           |
| `sender_not_configured`  | `422`  | Set a sender under **Sending > Transactional** (**Change** next to **Sends from**) or a default sender under **Settings > General**. |
| `domain_unverified`      | `422`  | The sender's domain is not verified. Verify it under **Settings > Technical > Sending Domains**.                                 |
| `invalid_variables`      | `400`  | A data variable is missing, `null` or of the wrong type; the message names it. Send a value of the type the email declares. A variable you do not always have can be marked optional in the email's editor. |
| `recipient_rate_limited` | `429`  | Too many sends of this email to this address. Retry after `Retry-After`; the instance admin sets the limit under **Settings > API**. |
| `daily_send_limit`       | `429`  | This key reached its daily send limit. Retry after `Retry-After` (the next UTC midnight), or ask the instance admin to raise it under **Settings > API**. |
| `idempotency_conflict`   | `409`  | The `Idempotency-Key` was used for a different request. Use a new key for a new request.                                         |
| `idempotency_erased`     | `409`  | The request already ran, but its contact has since been deleted. Use a new key only if you mean to send again.                   |
