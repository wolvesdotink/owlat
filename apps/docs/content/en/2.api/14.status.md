Check whether your instance can send and, if not, why and what fixes it. The
answer is the same delivery health the web app shows in the sidebar and on the
Delivery hub, so a script, a monitoring job or an AI agent can check it before
a launch instead of finding out from a refused send.

## Endpoint

| Method | Path             | Purpose                    |
| ------ | ---------------- | -------------------------- |
| `GET`  | `/api/v1/status` | Read whether sending works |

## Authentication

The route requires an API key with the `status:read` scope. A key that only
sends or only manages contacts gets `403` with `data.reason` `missing_scope`
until you create one that carries `status:read`. Everything the route returns
is visible to every member of your workspace in the web app. Provider settings
and the Deliverability Center's checks are not part of it. The DNS records each
domain still needs are at [`GET /api/v1/domains`](/api/domains), with the same
scope.

## Response

```json
{
	"data": {
		"level": "error",
		"reasonCode": "sending_suspended",
		"explanation": "Sending is suspended on this instance, so new sends are refused and campaigns hold until it lifts; the sending hold says whether it lifts by itself once the rate behind it recovers, and a platform admin of this instance can lift it in the operator console, while transactional mail already queued is still delivered and a campaign held past its delivery deadline stops without mailing the rest.",
		"fix": { "route": "/dashboard/admin/operator", "who": "platform_admin" },
		"domains": [
			{ "domain": "mail.example.com", "status": "verified" },
			{ "domain": "news.example.com", "status": "pending" }
		],
		"rates": {
			"windowDays": 30,
			"sent": 12000,
			"bounce": { "ratePct": 1.25, "limitPct": 2, "isOver": false },
			"complaint": { "ratePct": 0.42, "limitPct": 0.1, "isOver": true }
		},
		"sendingHold": {
			"status": "suspended",
			"since": "2026-11-20T09:00:00.000Z",
			"detail": "Auto-suspended: complaint rate 0.42% over the 0.1% limit",
			"lift": {
				"mode": "automatic",
				"condition": {
					"trigger": "complaint_rate",
					"domain": null,
					"currentPct": 0.42,
					"limitPct": 0.2,
					"isClear": false,
					"clearsAt": null
				}
			}
		}
	}
}
```

- `level` is `ok`, `warn` (worth a look) or `error` (a serious problem that
  affects or threatens delivery: mail is refused, held or delayed, or a bounce
  rate is past the point where sending is suspended). Whether sending is suspended right now is `sendingHold`, not
  `level`.
- `reasonCode` names the worst problem. When several apply, the most severe
  wins, and among equals a fixed order puts a suspension or ban first. Branch
  on the code; `explanation` is an English sentence for people.
- `fix.route` is the page in your instance's web app where the problem is
  fixed, and `fix.who` says who can do it there: `workspace_admin`,
  `platform_admin` (an admin of the whole instance), `contact_manager` or
  `deployment_operator` (whoever sets the deployment's environment). `fix` is
  `null` when sending is healthy.
- `domains` lists every sending domain with its verification state:
  `registering`, `pending`, `verified` or `failed`. Only a verified domain can
  send.
- `rates` holds the bounce and complaint rates over the last 30 days, in
  percent, next to the limit past which they count against your sending.
  `isOver` is `true` once a rate reaches its limit. `rates` is `null` while
  the window holds no sends, deliveries, bounces or complaints.
- `sendingHold` is set while sending is suspended or banned. It has the
  `status`, `since` and `detail` fields of the `403` a transactional send gets
  while sending is suspended, so a client reads one shape in both places.
  `detail` is the reason recorded with the suspension. `sendingHold` is `null`
  while sending is allowed.
- `sendingHold.lift` says how the suspension lifts, as the delivery hub's
  banner does. `mode` is `automatic` when it lifts by itself,
  `manual_setting` when the instance is set to wait for a platform admin even
  after the rates recover, and `admin` when only a platform admin lifts it (a
  ban, or a suspension a platform admin imposed). For `automatic`,
  `condition` names the metric (`trigger`: `bounce_rate`, `complaint_rate`, or
  `gmail_spam_rate` with its `domain`), where it stands (`currentPct`, `null`
  once no evidence is left in the 30 days) and the line it must fall under
  (`limitPct`). `isClear` is `true` once it is back under the line, and
  sending resumes at the next hourly check. For Gmail, `clearsAt` is when the
  last reading over the line leaves the 30-day window. `condition` is `null`
  for the other modes.

## Reason codes

New codes can be added. Treat a code you do not know by its `level`.

| Code                             | Level   | What to do                                                                                                                                 |
| -------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `healthy`                        | `ok`    | Nothing.                                                                                                                                   |
| `sending_suspended`              | `error` | `sendingHold.lift` says if it lifts by itself; if not, a platform admin lifts it in the operator console.                                  |
| `sending_banned`                 | `error` | Sending is disabled for good until a platform admin lifts the ban in the operator console.                                                 |
| `no_provider`                    | `error` | An admin sets up a delivery provider on the delivery transport page.                                                                       |
| `no_provider_transactional`      | `error` | An admin adds a provider to the transactional route.                                                                                       |
| `no_provider_campaign`           | `error` | An admin adds a provider to the campaign route.                                                                                            |
| `feedback_missing_campaign`      | `error` | The operator sets the campaign provider's bounce and complaint settings in the deployment's environment. Campaigns are refused until then. |
| `feedback_missing_transactional` | `warn`  | The operator sets the transactional provider's bounce and complaint settings. Bad addresses are not suppressed until then.                 |
| `mta_signing_held`               | `error` | Mail from the named domains is held without a usable DKIM key. An admin fixes the key and record on the sending domains page.              |
| `mta_signing_held_unnamed`       | `error` | The same, for a domain the mail server did not name.                                                                                       |
| `mta_degraded`                   | `error` | The built-in mail server reports a problem. An admin checks it on the delivery transport page.                                             |
| `mta_unreachable`                | `error` | Owlat cannot reach the built-in mail server. An admin checks it.                                                                           |
| `mta_stale`                      | `warn`  | The mail server has not reported its health recently.                                                                                      |
| `mta_unchecked`                  | `warn`  | The mail server has not reported its health yet.                                                                                           |
| `ips_all_held`                   | `error` | Every sending IP of a pool is held back, for example on a blocklist. An admin reviews them on the deliverability page.                     |
| `ips_some_held`                  | `warn`  | Some sending IPs are held back and the rest carry the mail at lower volume.                                                                |
| `domain_failed`                  | `error` | A sending domain failed setup or verification. An admin fixes the error shown on the sending domains page and verifies it again.           |
| `no_domain`                      | `error` | An admin adds and verifies a sending domain.                                                                                               |
| `no_verified_domain`             | `error` | An admin publishes a domain's DNS records and verifies it.                                                                                 |
| `domain_pending`                 | `warn`  | A sending domain is still waiting for DNS verification.                                                                                    |
| `sender_missing`                 | `error` | An admin sets a default sender for transactional mail.                                                                                     |
| `sender_unverified`              | `error` | The default transactional sender's domain is not verified. An admin verifies it or picks a sender on a verified domain.                    |
| `warmup_halted`                  | `warn`  | IP warm-up is halted, so campaign volume stops growing until an admin reviews it.                                                          |
| `reputation_critical`            | `error` | A rate is past the critical limit, at which sending is suspended automatically. Stop mailing addresses that bounce or never engage.        |
| `reputation_high`                | `warn`  | A rate is high enough to put sending at risk. Clean the list.                                                                              |
| `reputation_medium`              | `warn`  | A rate is above its limit. Clean the list before the next send.                                                                            |

## Checking it from a job or an agent

The status changes over minutes, not seconds: the built-in mail server reports
its health every two minutes and the rates move with the mail you send. Every
five minutes is plenty for a monitoring job, and more than once a minute gains
nothing. The route counts against the key's rate limit like every other call
(see [Authentication](/api/authentication)).

An agent asked why mail is not going out can read `reasonCode` and
`explanation`, and tell the person which page to open (`fix.route`) and whom to
ask (`fix.who`). To be told about a failing deliverability check or a
suspension instead of asking, subscribe a webhook to
`deliverability.alert_raised` (see
[Webhook Payloads](/api/webhook-payloads)).

With an SDK:

```ts
const status = await owlat.status.get();
if (status.level === 'error') console.warn(status.reasonCode, status.fix?.route);
```

```java
DeliveryStatus status = owlat.status().get();
```
