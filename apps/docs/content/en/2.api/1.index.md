Owlat exposes authenticated API endpoints under your instance's API URL.

## Base URL

Every Owlat install serves its own API. The web app shows the address as **Your
API base URL** under **Settings → API → API quickstart**. It is the
`NUXT_PUBLIC_CONVEX_SITE_URL` the operator set, for example:

```txt
https://rest.api.example.com
```

Authenticated endpoints are currently under:

```txt
/api/v1/*
```

## Authentication

Send your API key in `Authorization`:

```txt
Authorization: Bearer lm_live_...
```

API keys are created in **Settings → API**.

## SDKs

For server-side integrations, use an official SDK instead of raw HTTP calls:

- [TypeScript SDK](/api/sdk) -- `@owlat/sdk-js` for Node.js, Bun, and Deno
- [Java SDK](/api/sdk-java) -- `com.owlat:owlat-sdk` for JVM applications (Java 11+)

## OpenAPI document

Every instance serves the OpenAPI 3.1 document of its own API, without an API
key:

```txt
GET <your API base URL>/api/v1/openapi.json
```

Its `servers` entry is your instance's API base URL, so an API client
generator, an HTTP tool or an AI agent pointed at that one URL learns every
path, scope, schema and example and where to send the requests. Each operation
names the scope its key needs.

The blocks of templates, transactional emails and saved blocks have a schema
of their own, served the same way at `/api/v1/schemas/blocks.json`; see
[Block content](/api/blocks).

The request and response shapes of every `/api/v1` operation are declared once,
in the `@owlat/public-contract` package. The API server validates requests with
it, the TypeScript SDK takes its types from it, and the Java SDK's tests check
the SDK against the document generated from it. The repository holds a copy
with a placeholder server:
[`packages/public-contract/openapi.json`](https://github.com/wolvesdotink/owlat/blob/main/packages/public-contract/openapi.json).

After changing the contract, regenerate the document and commit it with the
change:

```bash
bun run --cwd packages/public-contract openapi
```

CI fails when the committed document is out of date
(`bun run --cwd packages/public-contract openapi:check`).

## Response format

Most endpoints return JSON in this shape:

```json
{
	"data": {}
}
```

Errors use the locked Operation-error envelope — a human-readable `message`, a
closed `category`, and an optional `data` object carrying specifics:

```json
{
	"error": {
		"category": "invalid_input",
		"message": "Human readable message",
		"data": { "field": "email" }
	}
}
```

`category` is one of: `unauthenticated` (401), `limit_reached` (402),
`forbidden` (403), `not_found` (404), `invalid_input` (400), `already_exists`
(409), `conflict` (409), `invalid_state` (422), `rate_limited` (429),
`internal` (500).

A `400` about one input names it in `data.field`. A body field is written the
way the body addresses it: `email`, `dataVariables.name`,
`attachments.0.filename`. A path segment, a query parameter or a header goes by
its name in this reference: `id`, `topicId`, `cursor`, `limit`,
`Idempotency-Key`. An error about the body as a whole (one that names neither
`transactionalId` nor `slug`) carries no `data.field`.

A route that writes answers `422` `invalid_state` with
`data.reason: "workspace_deletion_in_progress"` while the workspace is being
deleted. Nothing is written; retry once the deletion has finished or was
aborted.

A method a path does not support, such as `PATCH /api/v1/contacts`, is not
routed to the API at all: it answers `404` with a plain-text body, not this
envelope.

## CORS

Private API endpoints (`/api/v1/*`) are restricted by the `ALLOWED_ORIGINS` environment variable. Set it to a comma-separated list of allowed origins in the Convex dashboard:

```bash
npx convex env set ALLOWED_ORIGINS "https://app.example.com,http://localhost:3000"
```

Public endpoints (forms, unsubscribe, preference center) allow all origins.

## Rate limits

Authenticated API requests are limited to **10 requests per second** per API key.

Headers:

```txt
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
```

When exceeded, responses return `429` with `Retry-After`. Back off by
`Retry-After`: `X-RateLimit-Remaining` and `X-RateLimit-Reset` are fixed values,
not a reading of the limit ([Authentication](/api/authentication#rate-limit-exceeded-429)
says what each holds).

Transactional sends (`POST /api/v1/transactional`) have two further limits.
The instance admin can raise, lower or switch off each one under
**Settings > API** (`/dashboard/admin/team/api`); a change applies to the next
request. The defaults:

- **5 sends per hour of one template to one address.** Password resets and
  sign-in links to the same person do not need more, and a loop against one
  address stops here. The error's `data.reason` is `recipient_rate_limited`.
  A template that only ever goes to one fixed address (a new-order notice to
  your own shop) can opt out of this limit in its editor.
- **50,000 sends per API key per UTC day.** It bounds what a leaked key can
  send. The error's `data.reason` is `daily_send_limit`, and `Retry-After`
  points at the next UTC midnight. No template can opt out of it.

Both answer `429` with `Retry-After` in seconds. A request that repeats an
accepted `Idempotency-Key` is answered from its first response and never counts
against either limit.

`GET /api/v1/limits` reads both limits as they are set now, with any key. For
the daily limit it also gives the asking key's count: `used`, `remaining` and
`resetsAt`, the next UTC midnight, read from the same counter the send route
checks. A send that lands between your read and your next send counts too, so
treat `remaining` as what was left at the time of the read. While the daily
limit is off, nothing is counted, and the three fields are `null`.

What is left of the per-template-and-address limit depends on the template and
the address, so name both to read it:
`GET /api/v1/limits?email=ada@example.com&slug=password-reset` (or
`transactionalId=` instead of `slug`, as in a send). `recipientSends.usage`
then holds `used`, `remaining` and `resetsAt`, when the count is back to zero.
The allowance refills continuously, so one send frees up before then. Every
key's sends of that template to that address count, so this read needs the
`transactional:send` scope, like the send list. Reading the count does not
change it. An address without a template, or a template without an address, is
refused with `400` naming the missing parameter, and an unknown template
answers `404`. For a template that opted out, or while the limit is off,
`isExempt` or `isEnabled` says so and the three fields are `null`.

```json
{
	"data": {
		"dailySends": {
			"isEnabled": true,
			"limit": 50000,
			"used": 1204,
			"remaining": 48796,
			"resetsAt": "2026-11-24T00:00:00.000Z"
		},
		"recipientSends": {
			"isEnabled": true,
			"limit": 5,
			"windowSeconds": 3600,
			"usage": {
				"email": "ada@example.com",
				"templateId": "k57t3mpl4te0000000000000000000",
				"slug": "password-reset",
				"isExempt": false,
				"used": 2,
				"remaining": 3,
				"resetsAt": "2026-11-23T15:54:00.000Z"
			}
		}
	}
}
```

`usage` is there only when the request names a template and an address.
