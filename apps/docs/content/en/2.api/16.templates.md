Read, write and publish transactional emails and saved blocks. A script can
import the emails of a product moving to Owlat, promote templates kept in a
repository from a staging instance to production, or read an email's variable
schema to check it against the service that sends it.

## Authentication

Reads need an API key with the `templates:read` scope, and writes and
publishing need `templates:write`. Sending (`transactional:send`) grants
neither. A key created before these scopes existed does not have them: create
a new key in **Settings → API** with the scopes it needs.

Transactional emails follow the **Transactional emails** feature: while it is
off, those routes answer `403` with `data.reason` `feature_disabled`. Saved
blocks do not. [Rendering](#render-without-storing) needs only
`templates:read`, since it stores nothing.

## Endpoints

| Method | Path                                           | Purpose                                 |
| ------ | ---------------------------------------------- | --------------------------------------- |
| `GET`  | `/api/v1/transactional-emails`                 | List transactional emails               |
| `POST` | `/api/v1/transactional-emails`                 | Create a transactional email as a draft |
| `GET`  | `/api/v1/transactional-emails/:slug`           | Read one, with its content              |
| `PUT`  | `/api/v1/transactional-emails/:slug`           | Create or replace it by slug            |
| `POST` | `/api/v1/transactional-emails/:slug/publish`   | Publish it                              |
| `POST` | `/api/v1/transactional-emails/:slug/unpublish` | Return it to draft                      |
| `GET`  | `/api/v1/saved-blocks`                         | List saved blocks                       |
| `POST` | `/api/v1/saved-blocks`                         | Create a saved block                    |
| `GET`  | `/api/v1/saved-blocks/:id`                     | Read one, with its blocks               |
| `PUT`  | `/api/v1/saved-blocks/:id`                     | Replace it                              |
| `POST` | `/api/v1/render`                               | Render blocks without storing them      |

The lists come oldest first, a page at a time: `limit` (at most 100, default 25) and the previous page's `pagination.cursor`, until `pagination.isDone`.
They carry no content; read one item for that.

## A transactional email

```json
{
	"data": {
		"id": "k57t3mpl4te0000000000000000000",
		"slug": "order-confirmation",
		"name": "Order confirmation",
		"status": "published",
		"subject": "Your order {{orderNumber}}",
		"defaultLanguage": "en",
		"languages": ["en", "de"],
		"revision": 4,
		"publishedAt": "2026-11-02T09:00:00.000Z",
		"createdAt": "2026-10-30T14:00:00.000Z",
		"updatedAt": "2026-11-02T09:00:00.000Z",
		"blocks": [
			{
				"id": "b-heading",
				"type": "text",
				"content": {
					"html": "<h1>Thanks for your order</h1>",
					"blockType": "h1",
					"fontSize": 28,
					"textColor": "#111827"
				}
			}
		],
		"translations": {
			"de": {
				"subject": "Deine Bestellung {{orderNumber}}",
				"blocks": { "b-heading": { "html": "<h1>Danke für deine Bestellung</h1>" } }
			}
		},
		"dataVariablesSchema": { "orderNumber": "string", "total": "number" },
		"dataVariableExamples": { "orderNumber": "A-1001", "total": 42.5 },
		"showUnsubscribe": false
	}
}
```

- `blocks` are the email's blocks exactly as the editor stores them. A block's
  `content` holds every field of its type; the content check below refuses a
  block with a field missing or of the wrong type. The quickest way to see the
  fields of a block type is to build an email in the editor and read it here.
  Images are URLs: the API does not upload media.
- `translations` holds the other languages: a subject (`null` uses the default
  subject) and the translated text of each block by block id (`html` for text,
  `buttonText` for a button, `alt` for an image). The layout always comes from
  `blocks`.
- `dataVariablesSchema` names the variables a send passes and their type:
  `string`, `number`, `boolean`, `date`, or `array` for a list that a
  [repeated block](/guide/transactional#repeat-a-block-for-a-list) reads. Later
  releases may add types.
- `dataVariableExamples` holds sample data per variable, which the editor
  preview and test sends use: a string for `string`, a number for `number`,
  `true` or `false` for `boolean`, an ISO date such as `2026-11-25` for `date`,
  and for `array` a list of at most 500 entries, each a plain value or a flat
  object of them. Together they stay under 16 KB of JSON. A real send never
  uses them: a request still has to pass every required variable. Store sample
  data, never a real customer's.
- `id` is what a send may pass as `transactionalId`; the routes here take the
  slug.

New fields can appear in later releases. Read the ones you know and ignore the
rest.

## Write

`POST /api/v1/transactional-emails` creates a draft; its body needs a `slug`.
`PUT /api/v1/transactional-emails/:slug` creates the email with that slug if
there is none, and otherwise replaces its editable fields: `name`, `subject`,
`blocks`, `translations`, `dataVariablesSchema`, `dataVariableExamples`,
`defaultLanguage` and `showUnsubscribe`. A field left out of a `PUT` takes its
default (no variables, no translations, `en`, no unsubscribe link), so send the
whole email every time. `dataVariableExamples` is the exception: left out,
each stored example stays while it still matches its variable's type, also
after a retype, and `{}` clears them. An example that does not match its variable's type, or names a variable
the email does not declare, is refused with the field that names it. The
sender, the attachments and the hand-written text/plain body are not part of
the API and keep their value.

A write goes through the same path as a save in the editor: the HTML in text
blocks is sanitised, the email is rendered on the server, a change to a
published email is scanned, and the audit log records the write with the API
key as the actor (`api`).

The answer is the stored email and what the content check found:

```json
{
	"data": {
		"email": { "slug": "order-confirmation", "revision": 5 },
		"issues": [
			{
				"severity": "warning",
				"code": "BUTTON_NO_TEXT",
				"message": "Button block has no text",
				"blockId": "b-button",
				"blockType": "button"
			}
		]
	}
}
```

Warnings and notes do not stop a write. A block with an error does: the write is
refused with `400`, `data.reason` `invalid_content`, the first block at fault in
`data.blockId` and every issue in `data.issues`, and nothing is stored. A `PUT`
of an email the editor saved with such a block is refused the same way until
the block is fixed.

### Export and import

A read is the export: a `PUT` of the `data` of a `GET` to the same slug,
unchanged, stores the same email. The read-only fields in it (`id`, `status`,
`revision`, the timestamps, `languages`) are ignored. To copy an email to
another instance, `GET` it from one and `PUT` it to the other. A block linked
to a saved block names the saved block's ID in `savedBlockRef`, and saved block
IDs differ between instances: create the saved blocks on the target first and
put their new IDs in, or remove `savedBlockRef` to import the content as plain
blocks. A link to a saved block the instance does not have is refused with
`invalid_content`.

### Someone else's edit

Every `GET` and write answers the email's `revision`, also as the `ETag`
header. Send it back as `If-Match` and the write is refused with `409`,
`data.reason` `revision_mismatch` and `data.currentRevision` when the email
changed after you read it, for example in the editor. Read it again and apply
your change to what is there. The revision follows the name, subject, blocks
and translations. A variable added on its own in the editor's variable list
does not move it, so a `PUT` built on an older read replaces such a variable
without a conflict.

```bash
curl -X PUT "$OWLAT_API/api/v1/transactional-emails/order-confirmation" \
  -H "Authorization: Bearer $OWLAT_KEY" \
  -H 'Content-Type: application/json' \
  -H 'If-Match: "4"' \
  --data @order-confirmation.json
```

### A published email

A `PUT` to a published email is refused with `422` and `email_published`
unless it says `?whilePublished=true`. With it, the change goes live at once,
after the content scan: blocked content is refused with `content_blocked` and
nothing changes, and suspicious content moves the email to `pending_review`
until an admin approves it.

## Publish

`POST .../publish` renders the email and runs the content scan. A clean email is
`published`; a suspicious one comes back as `pending_review` and goes live once
an admin approves it; a blocked one is refused with `422`, `content_blocked` and
the scan's `data.scanScore`. Publishing a published email, or one waiting for
review, changes nothing. `If-Match` works here too, so you publish the revision
you checked. `POST .../unpublish` returns the email to draft; sends that name it
are refused until it is published again. An email waiting for review stays
there until an admin decides: unpublishing it is refused with
`email_in_review`.

## Saved blocks

A saved block is one or more blocks that emails link to. Its body is `name`,
`description` and `blocks`, checked like an email's. A `PUT` replaces all
three, and a `PUT` cannot empty a saved block. A change to the blocks reaches
every email that links the saved block, as an edit in the editor does: the
emails are rendered again in the background, and a published email's new HTML
is scanned before it goes live. That change replaces the linked copy in each
email, so edit a linked block through its saved block, or remove its
`savedBlockRef` to keep your own version.

## Render without storing

`POST /api/v1/render` takes blocks and answers with what this instance would
make of them, without storing anything. Use it to check an email before you
write it, or to get HTML you can screenshot.

```json
{
	"subject": "Your order {{orderNumber}}",
	"previewText": "Arriving {{deliveryDay}}",
	"blocks": [
		{ "id": "b-heading", "type": "text", "content": { "html": "<h1>Thanks, {{firstName}}</h1>" } }
	],
	"translations": { "de": { "subject": "Deine Bestellung {{orderNumber}}", "blocks": {} } },
	"language": "en",
	"dataVariables": { "orderNumber": "A-1001", "firstName": "Ada", "deliveryDay": "Thursday" },
	"darkMode": true
}
```

- `kind` is `transactional` (the default) or `template` for a marketing
  template, whose variables are contact fields filled when a campaign sends it.
- Without `dataVariables`, `html`, `text` and `subject` are what a save of
  these blocks would store, byte for byte: the same sanitising, the instance's
  brand kit and the same renderer. Every conditional and repeated block is in
  it once, and variables are left as written.
- With `dataVariables` (transactional only), the email is composed as a send
  with that data would compose it: conditions and repeats resolved, variables
  filled. `sendRefusal` holds the error a send would answer for these
  variables (a wrong type, a missing variable), and `missingVariables` lists
  the ones used without a fallback that the data leaves out. Add
  `dataVariablesSchema` to check the types.
- `language` picks the translation to answer with, falling back to the default
  language as a send does. A translation stores no text body, so `text` is
  `null` for one unless the email is composed.
- `issues` lists what the content check of a write finds, each with the id of
  its block. A block with an error is refused with `400` `invalid_content`,
  as a write is.
- Mail clients apply an email's dark styles themselves, so `html` does not
  change with `darkMode`. `darkMode: true` adds `darkHtml`: the same HTML with
  the email's own dark-mode rules always on, as a client in dark mode that
  honours them shows it. Clients that recolour an email by themselves, such as
  the Gmail app, are not modelled.
- `health` scores the HTML from 0 to 100 (higher is better):
  `compatibility` and `outlookSupport` from how well mail clients support the
  top-level blocks, `accessibility` from contrast, alt text and heading order,
  `deliverability` from size, text, images and links, and `overall` as their
  weighted mean. `analysis` holds the figures they read, and
  `recommendations` what pulled a score down.

Nothing is written: no email, no audit entry, no content scan. The same body
limit applies as for a write, and a render that would not fit in a stored email
is refused with `content_too_large`.

To see one stored email as a real send would compose it, use a
[dry run](/api/transactional#dry-run) of the send instead.

## Limits

- A request body may be up to 1 MB. A stored email holds its blocks, its
  translations and the HTML rendered for each language; an email that would
  not fit is refused with `400` and `content_too_large`.
- Writes and publishing share a per-key limit of 60 a minute, with bursts of
  30, apart from the request limit and the send limits. Past it, the answer is
  `429` with `data.reason` `template_write_rate_limited` and `Retry-After`.
- Renders and dry runs of a send share another per-key limit of 60 a minute,
  with bursts of 30. Past it, the answer is `429` with `render_rate_limited`.

## Refusals

| Status | `data.reason`                 | Meaning                                              |
| ------ | ----------------------------- | ---------------------------------------------------- |
| `400`  | `invalid_content`             | A block has an error; `data.issues` lists them       |
| `400`  | `content_too_large`           | The email would not fit in one stored record         |
| `400`  | `invalid_variables`           | A render's list would build an email over the limit  |
| `403`  | `missing_scope`               | The key lacks `templates:read` or `templates:write`  |
| `403`  | `feature_disabled`            | Transactional emails are turned off                  |
| `409`  | `slug_taken`                  | Another email has the slug                           |
| `409`  | `revision_mismatch`           | The email changed after the revision in `If-Match`   |
| `422`  | `email_published`             | The email is live; send `whilePublished=true`        |
| `422`  | `email_in_review`             | The email waits for an admin's review                |
| `422`  | `default_language_change`     | The default language cannot change while translated  |
| `422`  | `content_blocked`             | The content scan refused the content                 |
| `422`  | `html_render_pending`         | A saved block it uses changed and is still rendering |
| `429`  | `template_write_rate_limited` | Too many template writes from this key               |
| `429`  | `render_rate_limited`         | Too many renders and dry runs from this key          |

A malformed field is a `400` that names it in `data.field`, such as `slug`,
`blocks` or `dataVariablesSchema.total`.

## Not in the API yet

Uploading images and files, the email's sender and attachments, deleting
emails and saved blocks, and marketing templates are only in the web app.
