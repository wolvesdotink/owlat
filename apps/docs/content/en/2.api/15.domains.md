---
title: 'Domains API'
description: 'List the sending domains and the DNS records each still needs, and ask for a fresh check of one.'
---

List your sending domains with their verification state and every DNS record
each one needs: where to publish it, the value, and what the last check found
there. A script or an AI agent finishing sender setup can read what is left to
publish without opening the web app.

## Endpoint

| Method | Path                               | Purpose                                    |
| ------ | ---------------------------------- | ------------------------------------------ |
| `GET`  | `/api/v1/domains`                  | List sending domains and their DNS records |
| `POST` | `/api/v1/domains/{domain}/verify`  | Ask for a fresh DNS check of one domain    |

## Authentication

The list needs an API key with the `status:read` scope, the same scope as the
[Status API](/api/status), which names each domain's verification state. A key
without it gets `403` with `data.reason` `missing_scope`. Every member of your
workspace sees the same records on the Sending domains page; provider tokens
and stored error messages are not part of the answer.

A check needs the `domains:verify` scope. It is a scope of its own because a
check rewrites the domain's stored state and can move a verified domain
towards `failed`, so a key that only reads the status cannot start one. Keys
created before the scope existed do not have it: create a key with it and
give that key to the integration.

## Response

```json
{
	"data": [
		{
			"id": "k57d0main0000000000000000000000",
			"domain": "news.example.com",
			"status": "failed",
			"lastCheckedAt": "2026-11-21T07:30:00.000Z",
			"records": [
				{
					"purpose": "dkim",
					"type": "CNAME",
					"host": "s1._domainkey.news.example.com",
					"value": "s1.dkim.owlat.example",
					"priority": null,
					"state": "wrong",
					"foundValue": "old.dkim.example.net",
					"optional": false
				},
				{
					"purpose": "dmarc",
					"type": "TXT",
					"host": "_dmarc.news.example.com",
					"value": "v=DMARC1; p=none",
					"priority": null,
					"state": "missing",
					"foundValue": null,
					"optional": false
				}
			]
		}
	]
}
```

- `status` is `registering`, `pending`, `verified` or `failed`. Only a verified
  domain can send.
- `records` lists every record to publish: `spf`, each `dkim` key, `dmarc`,
  and `mail_from` for the return-path host that receives bounces. It is empty
  while the domain is still being registered.
- `host` is the record's full name. A `mail_from` record can sit on a
  return-path domain outside your domain, so publish it where `host` says.
- `priority` is set for an `MX` record and `null` otherwise.
- `state` is what the last check found: `found` with the expected value,
  `wrong` (a record is there with another value, shown in `foundValue`),
  `missing`, or `unchecked` (no check has run yet, or DNS gave no answer).
- `optional` is `true` for a record the domain does not need: the optional
  second DKIM key (Ed25519, `k=ed25519`) a domain on the built-in MTA can
  carry. Its `state` never decides `status`, so don't count it as missing.
  `false` for every other record.

The list is not paged: an instance has a handful of sending domains.

## When the states change

The states come from the last check, at `lastCheckedAt` (`null` before the
first). Owlat re-checks every domain that was verified once each day. A domain
that is still being set up is re-checked while its row on the Sending domains
page is expanded, or when you ask for a check.

## Ask for a check

After publishing records, ask for a fresh check of the domain by its name or
its `id`:

```http
POST /api/v1/domains/news.example.com/verify
```

```json
{
	"data": {
		"id": "k57d0main0000000000000000000000",
		"domain": "news.example.com",
		"status": "failed",
		"lastCheckedAt": "2026-11-21T07:30:00.000Z",
		"requestedAt": "2026-11-23T15:30:00.000Z"
	}
}
```

- The answer is `202`: the check runs in the background, because looking up
  every record against a slow nameserver can take longer than a request may.
  `status` and `lastCheckedAt` are the state before the check.
- Poll `GET /api/v1/domains` until the domain's `lastCheckedAt` is at or after
  `requestedAt`, usually within seconds. Every check of the domain that reaches a
  verdict moves `lastCheckedAt`, so it may be another check that landed first, such as one
  the Sending domains page started; either way the states are fresh. When DNS gives no answer at all, the
  check changes nothing and `lastCheckedAt` stays where it was; ask again
  later.
- One check per domain per minute, whichever key asks. A second request sooner
  gets `429` with `Retry-After` and `data.reason` `domain_check_rate_limited`.
- A name or id that is no sending domain of this instance gets `404`. A domain
  that is still being registered has no records to check yet and gets `409`
  with `data.reason` `domain_registering`.
