This is the plugin author's path from an empty directory to a contribution running in a deployment. It assumes a checkout of the Owlat workspace; see [Installing & Operating](/developer/plugin-operations) for the operator's side.

## 1. Scaffold the package

```sh
bun run plugins:prepare     # build the plugin-kit contracts once
bun run owlat-plugins create hello-owlat --name @acme/owlat-plugin-hello-owlat
```

Replace `@acme` with an npm scope you can publish to. Step 6 publishes the package, and the default name, `@owlat/plugin-<id>`, is in the Owlat project's own scope.

`owlat-plugins` is the plugin CLI. It exists in an Owlat checkout after `bun install`, and `bun run owlat-plugins` runs it from any directory of the checkout.

`create` writes files only — it never installs, imports, or executes anything, is idempotent on re-run, refuses to clobber a file whose content differs, and rolls back every file and directory it created if any write fails.

Defaults: package name `@owlat/plugin-<id>`, directory `examples/plugins/<id>`. Override with `--name` and `--dir`; preview with `--dry-run`.

To keep the plugin in its own repository, pass a `--dir` outside the checkout, for example `--dir ../hello-owlat`. The package is then self-contained: it depends on `@owlat/plugin-kit` from npm at the checkout's kit version (`^<version>`), its `tsconfig.json` and `vitest.config.ts` point nowhere else, and its `lint` script runs `oxlint` from its own dependencies. Run `bun install` in it before step 5. Step 6 for such a package starts at `bun publish` in its folder, and its README lists the commands. The tree below is the default, inside the checkout.

```text
examples/plugins/hello-owlat/
├── package.json          # private, depends on @owlat/plugin-kit (workspace:*)
├── tsconfig.json         # extends the workspace base config
├── vitest.config.ts      # aliases @owlat/plugin-kit to its sources
├── README.md
└── src/
    ├── manifest.ts       # the definePlugin declaration
    ├── index.ts          # re-exports the manifest
    └── __tests__/manifest.test.ts
```

## 2. Declare the manifest

The manifest is the whole contract. The host derives permissions, feature flags, the settings form, and the generated composition from this data **without executing plugin code**, so keep it a static, data-only declaration.

```ts
import { definePlugin } from '@owlat/plugin-kit';

export const helloOwlatPlugin = definePlugin({
	id: 'hello-owlat',
	version: '0.1.0',
	capabilities: ['plugin-storage:read', 'plugin-storage:write'],
	// Storage capabilities REQUIRE a flag: access must be revocable at runtime.
	flag: { default: false },
});

export default helloOwlatPlugin;
```

`definePlugin` preserves literal TypeScript inference and validates at runtime, throwing `PluginManifestError` with a list of `{ code, path, message }` issues. Two sibling forms exist for tooling: `validatePluginManifest(value)` returns `{ ok, manifest | issues }` and never throws, and `parsePluginManifest(value)` throws.

Validation rejects unknown fields, accessor properties, malformed identifiers, duplicate capabilities or env vars, invalid budgets, unsafe export paths, and unknown contribution buckets. It inspects references as **data** and never invokes them.

### Rules the validator enforces

- A contribution bucket requires both its capability *and* an explicit `flag`. You cannot ship a contribution an operator has no way to turn off.
- `plugin-storage:read` / `plugin-storage:write` require an explicit `flag` for the same reason.
- `llm:invoke` requires an explicit `flag` **and** a valid `llmBudget.dailyUsd` (> 0, ≤ 1,000,000, at most six decimal places).
- A feedback webhook's `signature.secretEnvVar` must also be listed in `flag.requiredEnvVars`. The route it feeds cannot verify anything without the secret, so enablement — not every individual delivery — is where its absence has to be caught.
- Ceilings: 64 capabilities, 64 required env vars, 256 entries per contribution bucket, 64 settings fields.

## 3. Add contributions

Every contribution is a data descriptor whose executable half lives at one **condition-independent package export**, for example `./gate`. Codegen verifies the export exists without running it and emits the static import. List each one in the package's `package.json` `exports` as one string, for example `"./gate": "./src/gate.ts"`, and give the module a default export: the generated composition imports it by default import.

The manifest below is a separate example plugin, `preflight`. In your scaffold, add the parts you need to `src/manifest.ts` and keep its default export. The example's import brings in `definePlugin` together with the capability constants the manifest lists.

```ts
import {
	definePlugin,
	PLUGIN_AUTONOMY_GATE_CAPABILITY,
	PLUGIN_CRON_CAPABILITY,
	PLUGIN_NAV_ITEM_CAPABILITY,
	PLUGIN_SETTINGS_PANEL_CAPABILITY,
	PLUGIN_WORKER_CAPABILITY,
} from '@owlat/plugin-kit';

export const preflightPlugin = definePlugin({
	id: 'preflight',
	version: '1.0.0',
	capabilities: [
		PLUGIN_AUTONOMY_GATE_CAPABILITY,
		PLUGIN_CRON_CAPABILITY,
		PLUGIN_NAV_ITEM_CAPABILITY,
		PLUGIN_SETTINGS_PANEL_CAPABILITY,
		PLUGIN_WORKER_CAPABILITY,
		'llm:invoke',
	],
	// Contributions REQUIRE an explicit flag: an operator must be able to turn
	// the plugin off without a redeploy.
	flag: { default: false, requiredEnvVars: ['PREFLIGHT_API_KEY'] },
	// `llm:invoke` additionally requires a hard daily budget in USD.
	llmBudget: { dailyUsd: 1.5 },
	contributes: {
		sendGates: [
			{
				id: 'preflight',
				label: 'Pre-send preflight',
				module: { exportPath: './gate' },
				timeoutMs: 15_000,
			},
		],
		crons: [
			{
				id: 'refresh-rules',
				label: 'Refresh preflight rules',
				module: { exportPath: './cron' },
				schedule: { intervalMinutes: 360 },
				timeoutMs: 60_000,
			},
		],
		navItems: [
			{
				id: 'dashboard',
				section: 'administration',
				name: 'Preflight',
				href: '/dashboard/admin/instance/plugins/preflight',
				icon: 'coolicons:radar',
			},
		],
		settingsPanels: [
			{
				id: 'settings',
				name: 'Preflight',
				href: '/dashboard/admin/instance/plugins/preflight',
				icon: 'coolicons:radar',
			},
		],
	},
	settingsSchema: [
		{
			kind: 'boolean',
			key: 'holdOnFail',
			label: 'Hold sends that fail preflight',
			default: true,
		},
		{
			kind: 'secret',
			key: 'vendorApiKey',
			envVar: 'PLUGIN_VENDOR_API_KEY',
			label: 'Vendor API key',
			required: false,
		},
	],
});
```

A `navItems` entry's `section` must be one of the **core sidebar section keys** — `inbox`, `postbox`, `chat`, `assistant`, `send`, `audience`, `knowledge`, `administration`, `preferences`. A plugin cannot create a section, and the host drops an entry naming an unknown one fail-closed, so a wrong key silently never renders. Existing plugins that still target the former `settings` key are attached to `administration` during the compatibility window.

The `icon` of a `navItems` or `settingsPanels` entry is a coolicons token, `coolicons:<name>`, with a name from [coolicons.cool](https://coolicons.cool). `bun run plugins:codegen` compiles the named icons into the web build, so a name coolicons does not have fails the build, and any other prefix (such as `lucide:`) fails manifest validation.

Every bucket and its semantics are listed in the [Contribution Reference](/developer/plugin-contributions).

## 4. Write the modules

A module implements one small interface and receives **host-mediated services only** — never a Convex context, database handle, tenant id, scheduler reference, or an environment variable it did not declare.

```ts
import type {
	PluginAutonomyGateInput,
	PluginAutonomyGateModule,
	PluginAutonomyGateResult,
	PluginAutonomyGateServices,
} from '@owlat/plugin-kit';

/** A gate may object or stand aside. There is deliberately no "approve" result. */
export const gate: PluginAutonomyGateModule = {
	async evaluate(
		input: PluginAutonomyGateInput,
		services: PluginAutonomyGateServices
	): Promise<PluginAutonomyGateResult> {
		if (services.signal.aborted) return { outcome: 'objection', reason: 'preflight cancelled' };
		if (input.draftBody.includes('http://')) {
			return { outcome: 'objection', reason: 'draft contains a plaintext HTTP link' };
		}
		return { outcome: 'no-objection' };
	},
};

export default gate;
```

Background work gets an abort signal, a logger, and — when `llm:invoke` is declared, granted, and within budget — the attributed host LLM dispatch:

```ts
import type { PluginCronModule, PluginCronServices } from '@owlat/plugin-kit';

export const cron: PluginCronModule = {
	async run(services: PluginCronServices): Promise<void> {
		// Cancellation is cooperative: the host aborts `signal` at the declared
		// timeout and stops waiting either way.
		if (services.signal.aborted) return;
		const summary = await services.llm.generate({
			tier: 'fast',
			prompt: 'Summarise this week of deliverability tips in one sentence.',
		});
		services.logger.info('refreshed preflight rules', { length: summary.text.length });
	},
};

export default cron;
```

### What each module receives

A module gets the arguments its interface in `@owlat/plugin-kit` names, and nothing else:

| Bucket | The host calls | Besides the input, the module gets |
| --- | --- | --- |
| `sendTransports` | `parseExtras(input)`, `send(params, extras, config)`, `buildDispatchExtras(context)` if you define it, and `buildSystemMailExtras(context)`, which a transport declaring `deduplicatesOnIdempotencyKey: true` must define | `send` alone gets `config`: the values of the environment variables this transport declared, for the instance the send is addressed to |
| `sendTransports` feedback webhook | `parseEvents(rawBody)` | nothing |
| `sendTransports` domain identity | `registerDomain(domain, config)`, `checkDomain(domain, config)` | `config` in the same shape as `send`'s, always for the transport's default instance |
| `agentSteps` | `execute(input)` | nothing |
| `draftStrategies` | `generate(input, services)` | `services.llm` |
| `sendGates` | `evaluate(input, services)` | `services.signal` |
| `automationSteps` | `execute(input, config)` | the step's configuration, parsed by your `parseConfig` |
| `crons` | `run(services)` | `services.signal`, `services.logger`, `services.llm` |
| `navItems`, `settingsPanels` | nothing: they are data | — |

`services.llm` dispatches only while the manifest declares `llm:invoke`, the operator has granted it, and the plugin's daily budget has room. The buckets the host accepts but does not call yet are listed in the [Contribution Reference](/developer/plugin-contributions#declared-and-catalogued-but-not-yet-invoked).

Plugin storage, a scheduler and a shared `PluginContext` are not shipped. The kit exports their types, but no host passes them to a module, so a plugin cannot keep state between runs or schedule follow-up work today. [Capabilities, Grants & Trust](/developer/plugin-capabilities#planned-storage-scheduling-and-a-plugin-context) lists what is planned.

::callout{type="warning" title="Design for denial"}
Any hosted call can be denied at the last moment — the flag may have flipped, the grant may have been revoked, an env var may be missing. Write modules so that a `PluginHostError` or a timeout leaves no half-applied state; the host applies the contribution's declared safe fallback regardless.
::

## 5. Test the plugin

Contribution modules are ordinary TypeScript, so they test as units with vitest. Always assert the manifest itself: `parsePluginManifest` is the same validator codegen runs, so a manifest test fails the build before a broken package can be composed.

```sh
bun run --cwd examples/plugins/hello-owlat test
bun run --cwd examples/plugins/hello-owlat typecheck
```

The reference plugins are the worked examples, one per tier: `examples/plugins/escalation-guard` (Tier 1 — agent step, draft strategy, automation trigger/step/condition, webhook event, nav and settings entries), `examples/plugins/slack-approvals` (Tier 2 — a connected app with a restrict-only hold gate), and `examples/plugins/deliverability-lab` (Tier 3 — a sandboxed seed-list job, plus a Tier-1 gate, cron and UI).

`examples/conformance` then replays all three through the real host, codegen and CLI — clean install, add, remove, disable, upgrade, and a full pipeline replay — so a contract change breaks the gallery in the same commit.

::callout{type="danger" title="Never use vitest's globals via bun test"}
Run tests with `vitest`, not `bun test`. The workspace's vitest setup is what makes the suites meaningful.
::

## 6. Bundle it

Codegen bundles a plugin only when it is installed at the workspace root from a package registry and pinned in `bun.lock` with its integrity hash. That is a supply-chain rule: the build contains exactly the artifact that was published, never a folder that can change under it. The package `create` wrote is a folder in this workspace, so bundling it means publishing it first. If you run `add` on it directly, `add` refuses and prints the steps below with your package's names filled in.

From the checkout root:

```sh
cd examples/plugins/hello-owlat
npm pkg delete private      # a registry refuses a private package
bun publish --access public # writes real versions for workspace:* and catalog:
cd -
mv examples/plugins/hello-owlat ../hello-owlat
bun add --exact @acme/owlat-plugin-hello-owlat@0.0.0
bun run owlat-plugins add @acme/owlat-plugin-hello-owlat
bun run plugins:codegen
```

- `bun publish` publishes to npm unless you configure another registry. Codegen accepts any registry, so a registry on your own machine is enough to try a plugin before you release it: see [Trying a plugin before you release it](#trying-a-plugin-before-you-release-it).
- The folder has to leave the checkout before `bun add`: Bun links a workspace folder in place of the published package of the same name, and codegen refuses a linked package. Keep developing the plugin in its new place or in a second checkout. Its `tsconfig.json`, `vitest.config.ts` and `lint` script still point into an Owlat checkout by relative path.
- `0.0.0` is the version `create` wrote. For a later release, run `npm pkg set version=<version>` before `bun publish`, then `bun add --exact` that version.

`add` edits the checked-in `plugins.config.ts` and prints the capability diff the change introduces. `codegen` verifies package identity, lockfile integrity and realpath containment, imports only the manifest entry, and rewrites the generated composition files. Commit `package.json`, `bun.lock`, the config **and** the generated files together, then rebuild and deploy. The build installs the plugin from the lock, so a commit without the first two cannot build it.

The plugin now exists in the deployment but does nothing: its feature flag is at its declared default and its capabilities are ungranted until an operator acts.

## Trying a plugin before you release it

Codegen has no path that skips a registry, but the registry does not have to be public. Verdaccio in a container is the shortest setup:

```sh
docker run -d --name verdaccio -p 4873:4873 verdaccio/verdaccio:6
npm adduser --registry http://localhost:4873/ --scope=@acme --auth-type=legacy
```

`npm adduser` asks for a user name, password and email. Any values work: the account exists only in this registry. It also writes `@acme:registry=http://localhost:4873/` to `~/.npmrc`, so from then on Bun publishes and installs every `@acme` package through Verdaccio. Run step 6 as written. Verdaccio passes every other package through from npm.

- Don't commit the `package.json`, `bun.lock` and generated files from this install. The lock points at `localhost:4873`, which a deployment build cannot reach.
- Verdaccio keeps each version once. Before publishing a change, run `npm pkg set version=<next>` in the plugin's folder and install that version.

To go back to the public registry for `@acme`:

```sh
npm config delete @acme:registry
docker rm -f verdaccio
```

## Publishing checklist

- The manifest's default export path is one condition-independent root export, so Bun, Convex, Nuxt SSR, and the browser build all resolve the same manifest.
- No `postinstall` or side effects at import time — codegen imports the manifest entry.
- Every contribution's `module.exportPath` is a real, exact package export.
- `flag.requiredEnvVars` lists only variables a shipped module actually needs; a missing required variable blocks enablement.
- Version bumps follow semver; the `@owlat/plugin-kit` major you build against is your compatibility line.
