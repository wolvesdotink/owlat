This guide covers day-to-day maintenance of your self-hosted Owlat instance. For initial setup, see [Self-Hosting](/developer/self-hosting).

## Updating

Owlat supports three ways to update: **in-app**, **CLI**, or **manual**. All three do the same thing under the hood — pull the pinned compose template for a tagged release, apply it, and redeploy Convex functions.

### Convex images moved (0.6.14)

Convex moved its images from the `get-convex` organization on GitHub's registry to `convex` (for example `ghcr.io/get-convex/convex-backend` is now `ghcr.io/convex/convex-backend`), and the old repositories no longer allow anonymous pulls. Releases up to 0.6.13 name the old repositories, so on those releases every command that pulls a Convex image fails with `denied`: `docker compose pull`, a first start of the `dashboard` profile, or a restore onto a new host. Containers that are already running, and a `docker compose up -d` that finds the images on the host, keep working.

From 0.6.14 on, Owlat ships the Convex images itself, as `ghcr.io/wolvesdotink/convex-backend` and `ghcr.io/wolvesdotink/convex-dashboard`, pinned to one Convex build per release. The in-app update and `owlat upgrade` to 0.6.14 switch to them without any extra step. A manual update is Option C below with version 0.6.14. The `convex-data` volume is used as it is. `CONVEX_BACKEND_VERSION` and `CONVEX_DASHBOARD_VERSION` are no longer read; delete them from `.env`.

To stay on, or roll back to, 0.6.13 or older, point that release's compose file at the new repositories before you pull. It is the same image under its new name:

```bash
sed -i 's#ghcr.io/get-convex/#ghcr.io/convex/#g' docker-compose.yml
docker compose pull
```

`owlat upgrade --version` to 0.6.13 or older cannot do this edit for you, so it fails at the pull and the running release keeps serving. Roll back by hand instead.

### Owner-only .env

`.env` holds every deployment secret. `owlat setup`, `owlat env`, the web setup wizard, the sending-provider editor and the updater make it owner-only (mode `600`) each time they write it. They refuse to write when they cannot: when the file belongs to another account, or when the install directory is on a filesystem that does not keep Unix permissions. The error names the file, and the file is left as it was.

An existing install keeps its current mode until one of those tools next writes `.env`. To secure it now, run this in the install directory as the owner of `.env`:

```bash
chmod 600 .env
ls -l .env .env.backup.* 2>/dev/null
```

`.env.backup.<timestamp>` files are copies the legacy bash wizard (`owlat setup --legacy`) made of an earlier `.env`, and they hold the same secrets. Run `chmod 600` on them too, or delete the ones you no longer need.

If a write fails with `could not make it owner-only`, the account doing the write does not own `.env`. On a default install the setup container creates `.env` as root, and the updater can only change the mode of a file root owns, so give the file back to root: `sudo chown root: .env && sudo chmod 600 .env`.

### Data migrations in the app

Some releases convert data that is already stored. Platform admins run these migrations from **Settings → System & Updates**, in the **Data migrations** card. The card lists every migration the installed release can run, grouped by the release that introduced it, including the unfinished ones of releases you skipped. It reads the migrations' own progress records, so it shows the same state after an in-app update, after `owlat upgrade`, and after a migration you ran from the CLI.

Each migration shows one of these states:

- **Pending**: it has never run on this deployment. **Waiting** means it starts only after another migration has completed.
- **Running**: it is working through its tables in the background, with the rows checked and changed so far.
- **Completed**: it has finished. Running again skips it.
- **Failed**: a step of it failed. The card shows the error.
- **Interrupted**: it has not made progress for a while (15 minutes for most migrations), for example because its background job was cancelled.

**Run pending migrations** starts every pending migration whose prerequisites have completed and resumes the failed and interrupted ones from their last recorded page. Migrations that wait for another one start by themselves once it has completed. The button only starts the work: the migrations continue in the background, and you can leave the page and come back. Completed and running migrations are never started again, and while one admin's run is in progress the button is unavailable to everyone, so two admins cannot start competing runs. If a migration fails or stops making progress, the run starts no further migrations and the card names the one that stopped it. Migrations that are already running carry on until they finish. Fix the cause and run again.

A migration that a later release depends on is marked **Must complete before you update past …**. While one is unfinished, the System page holds back **Update now** and names it, and the in-app update refuses the update. `owlat upgrade` and manual updates do not check this. A later release that removes old data cannot be deployed while that data is still there: the function deploy fails and the previous release keeps running. Run the migration and update again. If the release you want to reach needs an intermediate release first, its release notes say so: update to that release (`owlat upgrade --version <intermediate>`), let its migrations complete in this card, then update again.

The sections below keep the CLI command for each migration. Use them to run a migration without the web app or to recover one by hand. Migrations from before 0.6.6 (0035 to 0052) do not record their progress, so they are not in the card and are run from the CLI only.

### Chat attachment privacy migration

When upgrading an instance that has used chat, keep user traffic restricted while deploying the security update and running the following migration. From `apps/api`, with the intended deployment configured, run:

```bash
npx convex run migrations/0044_private_chat_media:run
```

Wait for completion before restoring access. The migration is paginated and safe to rerun after an interruption. It restores the private tag on media referenced by chat messages, including files whose tag was removed, and applies it to every media record referencing the same stored blob. It also covers tagged uploads that were never posted. The returned `updated` count becomes zero on a second run.

Previously shared marketing files posted in chat are conservatively made private too. Review those files and upload a separate copy for the shared library where needed. The update and migration prevent future library exposure; they cannot retract previously downloaded copies or storage URLs that were already disclosed.

### Performance migrations (0046 to 0049)

The release after 0.6.4 moves often-written counters, list counts and message bodies into their own tables. The app does not wait for these migrations: until they have run, it reads the new rows and falls back to the old fields. Once the release has settled, run them from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0046_split_hot_rows:run
npx convex run migrations/0047_denormalize_thread_rows:run
npx convex run migrations/0048_backfill_counters:run
npx convex run migrations/0049_move_message_bodies:run
```

- `0046_split_hot_rows` copies the feature flags, the instance counters and each mailbox's used storage into their own rows.
- `0047_denormalize_thread_rows` copies the newest message's snooze and the Reply Queue trigger's sender and subject onto each conversation.
- `0048_backfill_counters` starts counting the label, section and new-mail badges, the campaign, template and automation status filters, and subscriber growth. The counting continues in the background after the command returns. `npx convex run migrations/0048_backfill_counters:status` shows how far it is. Until a count is ready, the app counts it the old, slower way.
- `0049_move_message_bodies` moves the inline text and HTML of existing messages into their own table, sealed as before.

All four are idempotent and can be run again after an interruption. After `0049` has run, a backend rolled back to 0.6.4 or earlier shows the moved messages without their inline body, so run it only once you are staying on the new release.

### Deep body search cleanup (0051)

If deep body search (Settings → General → Mail search) was ever turned on and is now off, run this once after updating, from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0051_clear_residual_search_bodies:run
```

It starts the background sweep that clears the stored body excerpts, the same sweep that turning the switch off starts. It does nothing while deep body search is on, joins a sweep that is already running, and is safe to run again. Progress (`status`, `scannedCount`, `clearedCount`) is on the `mailBodySearchPurges` row in the Convex dashboard.

### Finishing earlier account deletions (0052)

Account deletion now runs as a tracked job that also removes the login itself (password, sessions, passkeys, two-factor secret), private assistant conversations and uploaded mail archives, and marks a request completed only after checking that the data is gone. Requests that an earlier release marked completed may still have left some of that behind. Once the release has settled, run from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0052_reerase_legacy_account_deletions:run
```

It reopens a completed request only when exactly one login with the request's address exists, that login is older than the request, and it has no profile and no organization membership. It counts the requests it cannot match that way and leaves them as they are. The erasure then continues in the background; `npx convex run auth/erasure/lifecycle:status '{"requestId": "…"}'` shows its progress and any error. The migration is idempotent.

### IMAP folder membership (0054)

The IMAP server used to read every message in a folder to work out message numbers, on every command that names messages, so a one-message command in a 100,000-message folder read 100,000 messages. The backend now keeps a compact list of each folder's message UIDs, and the IMAP server reuses it until the folder changes. Folders created after the update are covered from the start. Existing folders are covered by migration 0054, which the backend starts by itself: every 10 minutes it checks the migration, starts it if it has never run, and resumes it if it has not moved for an hour. To start it sooner, run from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0054_backfill_folder_membership:run
```

The list for each folder is built in the background after the command returns; `npx convex run migrations/0054_backfill_folder_membership:status` shows how many folders are ready, and reports `completed` once all of them are. Until a folder is ready, the IMAP server reads it the old, slower way, so nothing waits on this. The migration is idempotent: run it again after an interruption and it continues where each folder stopped. If building one folder's list fails three times in a row, the migration stops and shows as failed under **Data migrations**, naming the folder and the error, and the backend no longer resumes it by itself. Fix the cause, then run it again. `'{"rebuild": true}'` builds every list again from the messages; while it runs, the IMAP server reads each folder the old way again until that folder's list is rebuilt. If a rebuild is interrupted, run the command again without arguments: it resumes the rebuild rather than switching to an ordinary pass (`status` shows `isRebuild: true` for a rebuild). `'{"restart": true}'` is refused while a rebuild is unfinished.

Update the backend before the IMAP container, as the in-app and CLI updates do: the new IMAP server calls functions the previous backend does not have.

### Backend and IMAP server versions

The IMAP container calls the backend directly, so the two have to speak the same version of that interface. The supported skew:

- Update the backend first, then the IMAP container. The in-app update and `owlat upgrade` do both, in that order.
- The IMAP server may run at most one release behind the backend.
- It is never newer than the backend. A newer IMAP server waits, logs `Update the backend first` and retries, and starts serving once the backend has been deployed. The manual path below deploys the backend in step 3, before step 4 recreates the IMAP container.
- An IMAP server older than the backend supports is refused. One that reports its version (every release after 0.6.7) does not start: it logs both versions and `Update the IMAP container`, and exits. A running one stops at its next successful report, usually within 5 minutes of the backend update. A report that fails is only logged, and the server keeps serving until a later one gets through. IMAP servers from 0.6.7 and older do not report, so they keep running, but the backend refuses their logins once it no longer supports them.

Every IMAP server released after 0.6.7 reports its release to the backend when it starts and every 5 minutes. To check which IMAP servers ran in the last 7 days, open **Settings → System & updates** (the **Worker versions** card), or run from `apps/api` with the intended deployment configured:

```bash
npx convex run mail/imap/serverRegistry:status '{"days": 7}'
```

It lists each server with its release, wire version, last report and whether the backend still serves it. IMAP servers from 0.6.7 and older do not report; their logins show up as `legacyImapSeenAt`. Before updating to a release whose notes say it drops support for an older IMAP server, check the status, bring every older IMAP container up to the release your backend runs now (including any still on 0.6.7 or older), and only then update. An older IMAP server left running is not stopped at once. Its new logins are refused, and so are its calls that the change affects, before they change anything. Sessions it already had open can still make the calls the change did not touch, writes included: `STORE`, `COPY`, `MOVE`, `APPEND`, and `FETCH` marking a message `\Seen`.

### Worker versions

Mail sync, the MTA and the code worker report their release and wire version too, when they start and every 5 minutes; each replica reports for itself. Each service has its own wire version, so MTA wire 2 and IMAP wire 2 are unrelated. The **Worker versions** card on **Settings → System & updates** lists, per service, the builds that reported in the last 7 days, whether the backend still serves each one, and a note when more than one wire version of a service reported in that time. From `apps/api`, with the intended deployment configured:

```bash
npx convex run maintenance/workerRegistry:status '{"days": 7}'
```

A data migration that removes something an older worker still uses waits under **Data migrations** until every worker of that service runs the version it needs. It says which service it waits for. It starts once no older worker has reported for 15 minutes and a current one has. Update the older containers, or stop them; a run started from the card starts the migration by itself once they have moved. Workers from releases before they reported their version are not seen, so keep following the update order above.

### IMAP folder names and hierarchy

The IMAP server lists nested folders under their parents (`Work/Clients`) instead of side by side, and answers a LIST by its reference and pattern as RFC 3501 defines it. There is nothing to run: stored folder names are unchanged, and the web app shows them as before. What IMAP clients see changes once, so a client may need to refresh its folder list (in Thunderbird, **Subscribe…** then **Refresh**) to find folders it had cached under their old flat names.

- A folder's IMAP name is its path, the names of its parent folders and its own joined with `/`.
- A new folder name cannot contain `/`. An existing name with a `/`, or one mirrored from a provider whose delimiter is not `/`, is shown as `∕` (U+2215 DIVISION SLASH) so it stays one level. A `∕` already in a name is shown as `⧵∕`, and a `⧵` (U+29F5) as `⧵⧵`, so every folder keeps a name of its own.
- `INBOX` in any case means the inbox over IMAP, so a top-level folder other than the inbox named `Inbox`, `inbox` or another spelling of it could not be opened. Such a folder was created before these names were refused, or mirrored from a provider. It is now listed as its name, a `⧵` and its internal id, such as `Inbox⧵k57c…`. Creating, renaming or deleting other folders never changes that name. It stays the same as long as the folder's own name, role and place in the folder tree do: renaming it, moving it below another folder or giving it the inbox role gives it a different IMAP name. `Inbox` itself still opens the inbox, the web app still shows the folder's own name, and a folder called `Inbox` below another folder keeps its name.
- The server no longer advertises `LIST-EXTENDED`, `LIST-STATUS` and `SPECIAL-USE`, whose extended LIST forms it never implemented. Clients read subscriptions with `LSUB` and message counts with `STATUS` instead. The `\Sent`, `\Drafts`, `\Trash`, `\Junk` and `\Archive` attributes are still sent on every LIST.

### Repeated block ids in saved emails (0055)

Before 0.6.7, duplicating a Container, Hero, Columns or Accordion block in the email editor gave only the copy itself a new id; the blocks and accordion sections inside it kept the original's ids. In the sent email, clicking a section header in the second copy of an accordion opens or closes the section in the first, and one translation applies to both copies of a block. To repair templates and transactional emails saved before the fix, run from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0055_repair_repeated_block_ids:run
```

It gives every repeated id after the first a fresh one and copies that block's translations to the new id, so both copies keep the text they show today and can be translated separately from then on. Emails without a repeated id are not changed. A repaired email's HTML is rendered again in the background, the same way as after a saved-block edit; until then it sends with its current HTML, and publishing waits for the render. An editor tab still open on a repaired email has to reload before it can save. Progress (`status`, `scannedCount`, `changedCount`) is on the `0055_repair_repeated_block_ids` row of `migrationRuns` in the Convex dashboard. The migration can be run at any time, resumes after an interruption, and is safe to run again.

### Withdrawing confirmation tokens after an opt-out (0057)

A global opt-out now withdraws the contact's outstanding double opt-in confirmation link. Contacts who opted out before that change may still hold the link they had then. Once the release has settled, run from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0057_withdraw_opted_out_confirmation_tokens:run
```

It withdraws the confirmation token of every opted-out contact whose token was issued at or before the opt-out, and keeps a token issued after it (a later signup that waits for confirmation). The walk continues in the background; progress (`status`, `scannedCount`, `changedCount`) is on the `migrationRuns` row `0057_withdraw_opted_out_confirmation_tokens` in the Convex dashboard. Running it again resumes an unfinished pass and does nothing once it has completed.

### Scoping saved replies (0060)

Snippets were per mailbox; saved replies belong to a person or to the team. Every reader works out a snippet's new scope from its mailbox, so nothing waits on this migration, but it writes that scope onto each row so the rows are found by their owner and their team. Once the release is deployed, run from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0060_saved_reply_scopes:run
```

A snippet in a personal mailbox becomes its owner's personal reply; a snippet in a team inbox becomes a shared reply limited to that inbox. Both keep their mailbox, so browser tabs opened before the update keep finding them. A snippet whose mailbox no longer exists is left as it is and its id logged. Progress (`status`, `scannedCount`, `changedCount`) is on the `migrationRuns` row `0060_saved_reply_scopes` in the Convex dashboard. Running it again resumes an unfinished pass and does nothing once it has completed.

### Send-time profiles from past campaigns (0064)

"Optimized per contact" scheduling learns each contact's usual reading hour from new opens and clicks as they arrive. To give contacts who engaged before the upgrade a profile straight away, run from `apps/api` with the intended deployment configured:

```bash
npx convex run migrations/0064_backfill_send_time_profiles:run
```

It rebuilds each contact's profile from their latest 60 campaign sends, and the organization's hour histogram from the same events. Only campaigns that already left automated opens and clicks out of their statistics count, so Apple Mail Privacy Protection fetches and scanner clicks from older campaigns are not learned. The walk continues in the background; progress (`status`, `scannedCount`, `changedCount`) is on the `migrationRuns` row `0064_backfill_send_time_profiles` in the Convex dashboard. It can run at any time: until it finishes, contacts without a profile get the organization's usual hour or the start time. Running it again resumes an unfinished pass; `'{"restart": true}'` rebuilds everything.

### Team Inbox response history (0065)

Response analytics for the Team Inbox read each conversation's first-reply and resolve times, which conversations from before 0.6.8 do not carry. The analytics page starts this back-fill the first time an owner or admin opens it; to run it yourself, run in `apps/api` against the target deployment:

```bash
npx convex run migrations/0065_backfill_thread_response_metrics:run
```

It sets each conversation's first-reply time from its earliest sent reply or follow-up, then each resolved or closed conversation's resolve time from the audit log. It runs in the background and nothing waits on it; progress (`status`, `scannedCount`, `changedCount`) is on the `migrationRuns` row `0065_backfill_thread_response_metrics` in the Convex dashboard. Running it again resumes an unfinished pass and does nothing once it has completed (`'{"restart":true}'` starts over).

### Clarification question provenance (0066)

Reply Queue and Answer mode questions used to store where they came from as one English sentence. Since 0.6.10 they store the sender domain, and the web writes the "Based on an email from …" line in the reader's language. Migration 0066 converts the questions saved before that. 0.6.11 removes the old field from the schema, so **0066 must have completed before you update to 0.6.11**. On 0.6.10, run it in `apps/api` against the target deployment:

```bash
npx convex run migrations/0066_backfill_clarification_origin:run
```

It walks every mail thread, then every Answer mode session, and replaces each old sentence with the sender domain it names. The trust line reads the same before and after. It runs in the background; progress (`status`, `scannedCount`, `changedCount`) is on the `migrationRuns` row `0066_backfill_clarification_origin` in the Convex dashboard. Running it again resumes an unfinished pass and does nothing once it has completed.

Before you update to 0.6.11, run it once more from the start. A question that 0.6.9 was still working on during the update to 0.6.10 can be saved with the old sentence after the first pass has gone past its thread. Wait until nothing that started before the 0.6.10 update can still be running (an action runs for at most 10 minutes, so an hour after the update is enough), then run:

```bash
npx convex run migrations/0066_backfill_clarification_origin:run '{"restart":true}'
```

Update to 0.6.11 once that pass shows `status: "completed"` with a `completedAt` after you started it, in the dashboard or with `npx convex data migrationRuns`. If a question with the old sentence is left, the 0.6.11 update stops at the function deploy: Convex checks every stored row against the new schema and refuses a schema that one of them does not match. 0.6.10 keeps running; run the restart again and retry the update. An install on 0.6.9 or older updates to 0.6.10 first (`owlat upgrade --version 0.6.10`), runs both passes there, and then updates to 0.6.11.

### Option A: In-app update (recommended)

Platform admins see an "Update available" notification at **Settings → System & Updates** when a new version is released. Click **Update now**, confirm, and the web app will:

1. Download the pinned `docker-compose-<version>.yml` from GitHub Releases
2. Dispatch it to the updater sidecar
3. Pull new images, snapshot the Convex and Redis data and the configuration, redeploy Convex functions, then recreate containers
4. Verify the new version is live, and roll back to the snapshot if it is not (see [The snapshot and automatic rollback](#the-snapshot-and-automatic-rollback))

The page polls container health and auto-reloads once the update is complete. Total time: typically 2–5 minutes.

Two containers are deliberately left out of step 3, because the update runs _through_ them: the **updater** itself, and the **docker-socket-proxy** that carries its Docker API calls. Recreating either one stops the command performing the update, halfway down the list of services. So the updater hands its own replacement to a short-lived helper container that starts once the update has been reported, and the socket proxy — a third-party image whose configuration only changes when an Owlat release changes it — is left to the host. If a release note says the proxy's stanza changed, run `docker compose up -d docker-socket-proxy` in your install directory afterwards (or just `owlat upgrade`, which does a full `docker compose up -d`).

### Option B: `owlat upgrade` CLI

Installed to `/usr/local/bin/owlat` by every provisioning path — the one-liner installer, the desktop setup wizard, and a manual `scripts/owlat quickstart`:

```bash
owlat upgrade                     # to latest
owlat upgrade --version 1.2.3     # to a specific version (useful for rollback)
```

The CLI drives the same updater sidecar the in-app flow uses.

Release candidates (`X.Y.Z-rc.N`) are published as GitHub prereleases so a release can be tested before it ships. Neither the in-app update, `owlat upgrade` without `--version`, the installer nor the desktop app's own updater picks one up. To try one, update a test instance to it by name, for example `owlat upgrade --version 0.7.0-rc.1`. Its stable release is published from the same commit, so updating the test instance to `0.7.0` afterwards is an ordinary update.

::callout{type="info" title="`owlat: command not found`?"}
Older installs provisioned by the desktop wizard or a manual `git clone` never got the `/usr/local/bin/owlat` symlink — only the one-liner installer created it. Restore it with:

```bash
sudo /opt/owlat/scripts/owlat install-cli
```

Every wizard run (`quickstart`, `setup`, `config`) now also ensures the link, so upgrading through the in-app flow and re-opening the wizard fixes it too. Until then, use `/opt/owlat/scripts/owlat <command>` — it is the same script.
::

### Option C: Manual

For air-gapped environments or if you prefer to drive updates yourself:

```bash
# 1. Pull the pinned compose template for the target version
# 2. Pull the new images
# 3. Deploy the Convex tenant functions (before any app container restarts)
# 4. Recreate the containers on the new release
curl -fsSL https://github.com/wolvesdotink/owlat/releases/download/v1.2.3/docker-compose-1.2.3.yml \
  -o docker-compose.yml &&
docker compose pull &&
docker compose --profile deploy run --rm convex-deploy &&
docker compose up -d
```

::callout{type="warning" title="Deploy the functions before recreating the containers"}
New images do not change the Convex functions; step 3 deploys them. The block runs it before `docker compose up -d`, in the same order the in-app and CLI updates use. The previous release's web, MTA and IMAP containers keep working against the new functions, but a new container can call a function the previous backend does not have yet.

If the release changes the Convex backend image, step 3 also recreates the `convex` container: `docker compose run` first brings the deploy's dependencies in line with the new compose file, so the backend restarts on the new image, and the deploy waits until it is healthy. Every other container keeps running the previous release until step 4.

The steps are chained with `&&`, so the block stops at the first one that fails: if step 3 fails, step 4 does not run. Paste the block as a whole; if you run the steps one by one, check that each succeeded before you run the next. After a failed deploy, do not run `docker compose up` or anything else that runs it (such as `owlat apply`) until step 3 has succeeded. The app containers are still on the previous release and keep serving; fix the cause and run the block again.
::

## Recovering from a failed update

If an update fails mid-flight, your stack may be in a mixed state — some containers on the new version, some on the old. The updater never touches the data volumes, and as of the stage-then-promote flow it only replaces `docker-compose.yml` after images pulled and Convex functions deployed successfully. Still: **take a backup before updating** (`owlat backup`) — a release that ships a breaking schema change may reset or migrate data, and the release notes are the authority on that.

### Diagnose first

```bash
# What's running?
owlat status                       # or: docker compose ps

# What did each container log?
owlat logs web                     # follows the stream (Ctrl-C to exit); for a one-shot snapshot use: docker compose logs --tail=200 web
owlat logs mta
owlat logs convex
owlat logs updater

# Environment health check
owlat doctor                       # checks .env, required env vars, send path, compose override,
                                   # container health, and configured-vs-running version
owlat doctor --json                # the same checks as one JSON report, for scripts

# Everything above in one redacted archive, for a bug report
owlat support-bundle
```

`owlat doctor --json` prints one JSON document and nothing else, with the same exit code as the checklist. Each entry in `checks` has a stable `id` (for example `send_path.credential` or `version.drift`), an optional `subject` (the env key, IP or service it is about), a `component`, a `status` of `pass` or `fail`, and on failures a `remediation` code. The report carries a `schemaVersion` and a `generatedAt` timestamp. Both outputs print a configured URL as scheme, host, port and path only, echo no `.env` value other than `EMAIL_PROVIDER` and `OWLAT_VERSION`, and replace any secret from `.env` that turns up in runtime output with `[redacted]`, whether raw, in another letter case, form-encoded or base64 (also when split by whitespace). If any runtime detail in a finding contains `%` (it could hold a percent-encoded secret), or the finding read as a whole would still spell a secret, all runtime details of that finding are replaced and only its fixed wording prints. The report is safe to attach to a support request.

### If the update is refused with a Docker API error

Before it stages anything, the updater probes the Docker API it has been given. If that probe comes back with `403 Forbidden` (`Request forbidden by administrative rules`), the update stops there with the stack untouched and the reason in `owlat logs updater` and `owlat logs web`.

The cause is the `docker-socket-proxy` allowlist. Instances installed before **0.5.1** run it with `NETWORKS: 0` and `VOLUMES: 0`, which the daemon answers with a 403 for `docker compose up` and `docker compose run` — both of which resolve the project's networks and named volumes before they touch a container. Every in-app update on such an instance died at the `convex-deploy` step. The proxy cannot be reconfigured through itself, so this one is fixed from the host:

```bash
cd /opt/owlat                      # your install directory
docker compose up -d docker-socket-proxy
```

If the install still has the pre-0.5.1 `docker-compose.yml`, take the current release's template first — `owlat upgrade` does that for you, and ends in a full `docker compose up -d`.

Then retry **Update now**.

### If the update is refused for disk space

Every release pulls a full set of new images. Before **0.6.0** nothing removed the previous release's images, so an instance that updated often slowly filled its disk until `docker compose pull` failed with `no space left on device` (shown as "Docker pull failed"). Third-party images piled up the same way until **0.6.1**. Ollama publishes a new, roughly 7 GB `ollama/ollama:latest` every few days, and the stack pulled that floating tag on every update, leaving the previous copy behind untagged. Ollama is now pinned to a version (override it with `OLLAMA_VERSION` in `.env`).

The updater now starts every rollout by removing the images no container uses:

- Owlat's own images, recognised by the Owlat source-repository label.
- Untagged (dangling) images, which is what a moved floating tag such as `convex-backend:latest` leaves behind. These can't be traced back to a repository, so this also removes your own dangling images. Nothing can start a dangling image by name.
- Unused tagged images from the stack's third-party repositories (Ollama, Convex, Redis, Caddy, and the rest of the stack's allowlist).

Your own tagged images and all data volumes are left alone. The updater then checks that at least 4 GB are free before it pulls. If there still isn't enough room, the update stops with the stack untouched and tells you how much space is free. Free space on the host and retry:

```bash
docker system df                   # what is using the space (images, volumes, build cache)
docker image prune -a              # remove every image no container uses
```

The updater that runs an update is the one already installed, so a cleanup only takes effect from the update _after_ the release that introduced it. On an instance whose disk is already full, run the prune once by hand before clicking **Update now**. Rolling back is unaffected: it pulls the old release's images again.

### The snapshot and automatic rollback

After the pull and before the Convex functions are deployed, the updater takes a snapshot of what the rest of the update changes:

- the data of the `convex` and `redis` services: every volume (or bind mount) they mount read-write, found on the containers themselves, so a renamed volume is included;
- `docker-compose.yml`, `docker-compose.override.yml` and `.env` (stored owner-only, since `.env` holds every secret).

The snapshot lives in `.owlat-update-snapshot/` in the install directory. Like `scripts/backup.sh`, the updater stops `convex` and `redis` while it copies their data, so the copy is consistent, and starts them again straight after. Expect a few seconds of backend downtime on a small instance and longer on a large database. The updater checks that the disk can hold the copy plus 512 MB before it stops anything; if it cannot, if `docker-compose.yml` or `.env` cannot be read, if `convex` or `redis` has no container (a removed container can leave its volume behind, which the snapshot would then miss: `docker compose up -d convex redis` brings it back), if one of their bind mounts has a host path with a space or any character other than letters, digits and `_ . / @ -`, or if the copy fails, the update stops with the stack unchanged. The snapshot also records that there was no `docker-compose.override.yml`, when there was none.

If the new release fails before it is confirmed ready, the updater restores the snapshot and starts the previous release again:

- `convex-deploy` failed once its container had started. A failure cannot show that Convex refused the push: the Convex CLI exits with an error both when Convex rejected it and when it lost the answer to a push Convex had already committed, and a deploy that timed out, or whose connection to Docker the updater lost, may have gone on. The new functions might have gone live, so the deploy is stopped before anything is restored;
- the new compose file could not be written, or `docker compose up` failed;
- the new release did not pass the readiness check.

The answer is then `rolled-back`. Everything written to the instance between the snapshot and the rollback is lost. This includes a deploy Convex rejected, for example over an incompatible schema. Only a deploy whose container was never created or never started provably changed nothing; it is not rolled back, the snapshot is discarded, and the stack keeps running as it was.

Once the new release has passed the readiness check, nothing rolls back on its own. The snapshot is kept until the next update replaces it, and you can still restore it from the host:

```bash
owlat rollback          # shows the snapshot, asks for 'yes', then restores it
owlat rollback --yes    # without the prompt
```

The restore goes through the updater, with the same code an automatic rollback runs. It first stops every `convex-deploy` and snapshot copy that an update or rollback of this install may have left running, whether or not that update took a snapshot. They carry an `ink.wolves.owlat.update-install` label naming the install directory, so another Owlat install on the same Docker host is left alone. If Docker cannot tell the updater which install directory it is mounted from, the restore is refused with nothing changed (try again once Docker answers), and so is an update. It then stops `convex`, `redis` and any other container that mounts their data, replaces their data and the three files with the snapshot's copies (removing a `docker-compose.override.yml` the snapshot did not have, for example one a feature change added since), recreates the containers on the previous release, and waits for the readiness check. Everything written since the snapshot is lost, so use it right after an update that went wrong, not days later; for anything older, use a backup.

If a rollback fails partway (a full disk, a Docker error), the updater says so, and no update, feature change or secret rotation can start until a rollback has finished, whatever `OWLAT_UPDATE_SNAPSHOT` says: run `owlat rollback` again. If the data and files were already restored and only starting the previous release failed, `owlat rollback` starts it again without copying the data back a second time. A rollback the updater was stopped in the middle of is reported the same way when it starts again.

To update without a snapshot, for example on a host without room for a second copy of the database, set `OWLAT_UPDATE_SNAPSHOT=off` in `.env`. Updates then behave as before: a release that fails its readiness check stays in place and is reported as `started`, and a failed `docker compose up` is restarted forward (`partially-applied`).

### If the update reports the release started but not ready

`docker compose up -d` returns as soon as the containers are started, before any of them is known to work. After it, the updater waits for every service it started to pass a readiness check: a service with a healthcheck (Convex, Redis, ClamAV) must report `healthy`, every other service must be `running` and not restarting, a one-shot service must have exited with code 0, all of this must still hold a few seconds later, and the web app must answer `http://web:3000/api/instance-info`. The update counts as a success only when that check passes.

The wait is three minutes, longer for a service whose healthcheck declares a long `start_period` or `interval`: Docker only re-checks a container once per interval and ignores failures during the start period, so such a service gets until the check after its start period, up to twelve minutes. ClamAV (`start_period: 600s`, `interval: 60s`) can hold the update for about eleven minutes. A service still inside its start period when the wait ends is reported as warming up. A service that was already unhealthy or crash-looping before the update does not make the rollout fail; it is listed as a warning.

While one rollout runs, the updater answers `409` to a second update, a feature apply or a secret rotation. Try again once it has finished. It keeps answering `/health` throughout.

If the updater is stopped during an update (`docker compose restart updater`, `docker compose down`, a host reboot), what happens depends on how far the update got. Before `convex-deploy` starts (preflight, pull, snapshot), it stops the command in flight, starts `convex` and `redis` again if the snapshot had paused them, removes the staged file and the snapshot, and reports `interrupted`: the running stack is unchanged, and you can run the update again. Once `convex-deploy` has started, the new Convex functions may already be live while the other containers still run the previous release, so it removes the staged file but keeps the snapshot, and reports `interrupted` saying so: run the update again to finish it, or `owlat rollback` to go back. The deploy may keep running after the updater stops; the next update or `owlat rollback` stops it before doing anything else (with or without `OWLAT_UPDATE_SNAPSHOT=off`), and stops with the stack unchanged if it cannot. Once the new compose file is in place, it finishes `docker compose up` before it exits, skips the rest of the readiness wait, and reports `started`; the snapshot is kept, and `owlat rollback` restores it. The updater's `stop_grace_period` is 120 seconds so that `up` has time to finish. If the updater is killed anyway, it reports the update as `interrupted` the next time it starts, and says whether the release had been put in place.

The updater's answer says how far the release got in its `rollout` field, and each step (including `readiness`) is in the update history:

| `rollout`           | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `healthy`           | The release is applied and every service passed the readiness check.                                                                                                                                                                                                                                                                                                                                                                                                           |
| `rolled-back`       | The release failed before it was confirmed ready, and the updater restored the snapshot: the previous release is serving again on its data and configuration. The error says what failed.                                                                                                                                                                                                                                                                                      |
| `failed`            | The update failed before it changed anything, or a rollback did not bring the previous release back. The error says which, and what to run on the host.                                                                                                                                                                                                                                                                                                                        |
| `started`           | The release is applied and its containers were started, but the readiness check did not pass in time, and there was no snapshot to roll back to (`OWLAT_UPDATE_SNAPSHOT=off`) or the updater was being stopped. The error names each service that was not ready and why (failing its healthcheck, restarting after a crash, not started, still starting, warming up). The dashboard shows this as a warning, not as a failed update: running the update again changes nothing. |
| `partially-applied` | `docker compose up` itself failed with snapshots turned off. The updater started the same services again on the new release and ran the same readiness check on them.                                                                                                                                                                                                                                                                                                          |
| `interrupted`       | The updater was stopped before the update reached a verdict. The summary says whether the running stack was left unchanged or the new release had already been put in place. Either way, running the update again completes it, except after an interrupted rollback: run `owlat rollback` first.                                                                                                                                                                              |

The web container that asked for the update is recreated during it, so the dashboard reads the verdict from the updater's `/health` (`lastRollout`), which the updater also keeps in `.owlat-last-rollout.json` in the install directory.

For `rolled-back`, the instance is back where it was; fix what the error names and run the update again. For `started`, look at the services the error names with `docker compose ps` and `owlat logs <service>`. If ClamAV is the only service listed as still starting or warming up, wait and check `docker compose ps` again. For `partially-applied`, re-run the update once the cause is fixed, or run `docker compose up -d` in the install directory.

### Rollback to the previous version

Right after an update, `owlat rollback` restores the snapshot the updater took before it, data included (see [The snapshot and automatic rollback](#the-snapshot-and-automatic-rollback)). It discards everything written since the update, so once the new release has been in use, roll back the release without its data instead.

Every tagged release attaches its `docker-compose-<version>.yml` to the GitHub Release page. To roll back the release only:

**Via CLI:**

```bash
# Replace with the last-known-good version
owlat upgrade --version 1.2.2
```

**Manually:**

```bash
# Download the previous release's compose file, pull the pinned images,
# recreate the containers, then re-deploy the functions at the old version
curl -fsSL https://github.com/wolvesdotink/owlat/releases/download/v1.2.2/docker-compose-1.2.2.yml \
  -o docker-compose.yml &&
docker compose pull &&
docker compose up -d &&
docker compose --profile deploy run --rm convex-deploy
```

This manual rollback recreates the containers before it deploys, the reverse of the update order. That way the older containers briefly run against the newer functions, the direction a release is built to tolerate, never the other way round. As in the update, the commands are chained with `&&`: if `docker compose up -d` fails, some containers may still run the newer release, so the block stops before it deploys the older functions. If the deploy is refused because the newer release has already written data the old schema rejects, restore the backup you took before the update.

Docker will pull images for the pinned tags (e.g. `ghcr.io/wolvesdotink/web:1.2.2`) and swap containers in-place.

### If Convex won't start

Convex holds the primary database; Redis and ClamAV also persist data, plus optional services (code-worker, ollama, IMAP/acme certs) when their feature profiles are enabled. If it's failing to start, check disk space on the `convex-data` volume first:

```bash
docker system df -v | grep convex-data
```

If disk is full, free space or resize the underlying volume. Never delete the `convex-data` volume — that's your database.

The shipped Compose files rotate each container's `json-file` log at 10 MiB and retain five files. On an older installation, check whether unrotated logs already consume space before recreating the stack with the current Compose file:

```bash
docker system df -v
sudo du -sh /var/lib/docker/containers/* 2>/dev/null | sort -h | tail
```

### Nuclear option: restore from backup

If the stack is in an unrecoverable state, restore the most recent backup archive. The `owlat` CLI wraps `scripts/restore.sh`:

```bash
owlat restore backups/owlat-YYYYMMDD-HHMMSS.tar.gz
# equivalently: bash scripts/restore.sh backups/owlat-YYYYMMDD-HHMMSS.tar.gz
```

The script first checks the archive's SHA256 sidecar and reads every volume payload inside it end to end; a corrupt, truncated or missing payload stops the restore while the stack is still running on its current data. It then stops the stack and aborts if a container of the project is still running or any container still holds a volume. A failing `docker compose down` alone does not stop the restore when nothing is running, which is the normal case on a fresh host. On a fresh host with no `.env` yet, Compose gets the archive's `.env` until the restored one is in place. Before overwriting a volume it copies the current contents to `<volume>-pre-restore-<timestamp>`, so the host needs as much free disk as the volumes being replaced. It then repopulates the volumes from the archive (Convex, Redis, and optionally ClamAV), restores `.env`, the compose override, the Caddyfile and `.owlat-flags.json` (the current ones are kept as `<file>.before-restore-<timestamp>`), and brings everything back up.

The volumes go into the Compose project that the restored configuration starts. The archived `.env` (your current one with `--keep-env`) and the archived compose override decide it, the same way they decide it for `docker compose up` afterwards, including a `COMPOSE_PROJECT_NAME` set in your shell and volumes with an explicit `name:`. When that project differs from the one running now, the script says so, stops the current stack and leaves the current project's volumes as they are. It stops before changing anything when `COMPOSE_FILE` is set, when a `compose.yaml` sits next to `docker-compose.yml`, when `docker compose config` cannot read the configuration being restored, or when two payloads would go into the same volume. Without Compose's answer the volumes `docker compose up` mounts would be a guess. The usual cause is an archived `.env` from an older release that lacks a variable the compose file now requires. Write the archive's copy to `.env` (`tar -xzOf <archive> ./env > .env && chmod 600 .env`), add the variable the error names, and run the restore again with `--keep-env`. Before it starts the stack, it checks that the config files now in place mount exactly the restored volumes.

`scripts/backup.sh` records the compose key and volume name of every payload in the archive's `VOLUMES.txt`, so a volume with an explicit `name:` goes back into the volume the restored configuration mounts for that key. Archives made before `VOLUMES.txt` carry only the payload names. The script matches those against the compose keys and volume names of the restored configuration, and stops before changing anything when a payload fits several volumes, or fits none while a mounted volume would get no data.

`.owlat-flags.json` is the CLI's copy of the feature flags; `owlat doctor`, `owlat feature` and `owlat pack` read it. It is restored together with the database and the override, also with `--keep-env`, which keeps only `.env`. Archives made before backups included it have no copy. The script then moves the current file aside as `.owlat-flags.json.before-restore-<timestamp>`, because it describes the install being replaced, and warns that the CLI assumes the default feature flags until the file is written again. Once the stack is up and Convex is healthy (15–30 seconds after it starts), run:

```bash
owlat feature --sync
```

It reads the restored database's feature flags, plugin flags included, through the running `web` container and writes them to `.owlat-flags.json`, the same file the Features page's Apply & restart writes. It changes nothing else: the compose override, `COMPOSE_PROFILES` and the running containers stay as they are. The warning about the missing copy names this step, and so does the summary after "Restore complete.". If the restore stops before it starts the stack, fix what it names and run `docker compose up -d` first. Run it before you toggle anything with `owlat feature` or `owlat pack`, because until then those commands start from the defaults and can turn off services the restored install uses. If it fails, the stack is not up yet; check `owlat status` and run it again.

If a volume cannot be replaced, or you interrupt the restore (Ctrl-C) while it replaces volumes, the script copies the old data back into every volume it had already touched, leaves the config files alone and restarts the previous stack. A fresh-host restore has no previous stack, so the stack stays down. If a config file cannot be restored after the volumes are in, the script says so and leaves the stack stopped; fix the named file, then run `docker compose up -d`. It prints "Restore complete." only after `docker compose up -d` has succeeded. The pre-restore copies are never deleted automatically. Once you have checked the restored instance, remove them with `docker volume rm <volume>-pre-restore-<timestamp>`; the script prints the exact names. See [Backups](/developer/self-hosting-production#backups) for how to produce these archives and set up automated backups. To schedule recurring backups without hand-rolling cron, run `owlat backup-schedule enable` — it installs a daily systemd timer (cron fallback) that runs `scripts/backup.sh`; `owlat backup-schedule disable` removes it.

### Automating Updates

There is deliberately **no unattended-update cron in the box**. Two reasons:

1. Ordering matters: functions must deploy **before** app containers restart
   (the in-app updater and `owlat upgrade` do this for you). A naive
   `pull && up && deploy` cron — which earlier versions of this page
   suggested — restarts containers against an old schema first.
2. Pre-1.0, a release may ship a breaking schema change. Read the release
   notes before applying an update; don't let cron apply them blind.

If you accept those trade-offs, automate `owlat upgrade` (which wraps the
safe ordering) and pair it with a pre-update backup:

```bash
# /etc/cron.d/owlat-update — automated upgrades, at your own risk
0 4 * * 0 root cd /opt/owlat && bash scripts/backup.sh && owlat upgrade
```

::callout{type="warning" title="Update safety"}
Always have a fresh backup before an update. Owlat is pre-1.0: a release
may include breaking schema changes that reset specific tables — the
release notes state when that is the case.
::

## Redis Maintenance

Redis is configured with AOF (Append Only File) persistence by default. This ensures the MTA job queue survives container restarts.

- **Compaction** — Redis automatically rewrites the AOF file to keep it compact.
- **Memory** — monitor Redis memory usage with `docker compose exec redis redis-cli info memory`.
- **Flushing the queue** — if you need to clear the queue (e.g., after a misconfiguration), delete the queue's own keys and nothing else:

  ```bash
  docker compose exec -T redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning \
    --scan --pattern 'groupmq:owlat-mta:*' | \
    xargs -r docker compose exec -T redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning DEL
  ```

  This discards every queued and in-flight email job, and leaves everything else
  in Redis alone.

::callout{type="warning" title="FLUSHALL destroys your DKIM private keys"}
Do not reach for `redis-cli FLUSHALL`. This Redis is not only the job queue — it
is the instance's secret store. It holds each sending domain's DKIM **private
key** (`mta:dkim:{domain}`), generated inside the MTA, which exists nowhere else:
Convex only ever receives the public half, and backups of Convex do not contain
it. `FLUSHALL` also removes per-organization API credentials (`mta:cred:`), IP
warmup progress, and the FCrDNS / DNSBL caches.

After a `FLUSHALL`, the MTA generates a fresh keypair on the next send and signs
with it, while DNS still publishes the old public key at `._domainkey` — so every
message fails DKIM, and every recipient domain on a DMARC `p=reject` policy
rejects it outright. Warmup restarts at phase 0. Recovery means republishing the
new public key for every sending domain and waiting out DNS propagation.
::

::callout{type="info" title="Password-protected Redis"}
Redis always requires a `REDIS_PASSWORD` (see [Redis Authentication](/developer/self-hosting-production#redis-authentication)), so prefix every `redis-cli` command with `-a "$REDIS_PASSWORD" --no-auth-warning`, e.g. `docker compose exec redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning info memory`.
::

## Troubleshooting

### Convex won't start

```bash
docker compose logs convex
```

Common causes:

- **`INSTANCE_SECRET` not set** — check your `.env` file has a valid hex string
- **Disk full** — the `convex-data` volume needs free space for the database
- **Port conflict** — another service is using port 3210 or 3211

### MTA can't send emails

```bash
docker compose logs mta
```

Common causes:

- **`MTA_API_URL` not set in the Convex runtime** — the most common cause after a manual install. `MTA_API_URL` (and `MTA_API_KEY`) must be pushed into the Convex deployment, not just the compose `.env`; without it sending hard-throws `No system email transport configured` (`apps/api/convex/systemMail.ts`) before the MTA is ever reached. Check with `npx convex env list` (or the dashboard) and set it to `http://mta:3100`. The `owlat quickstart` wizard does this for you.
- **EHLO hostname doesn't match PTR record** — receiving servers reject the connection. Verify with `dig -x YOUR_IP +short`
- **DKIM_KEYS JSON is invalid** — validate the JSON: `echo $DKIM_KEYS | jq .`
- **Port 25 blocked** — many cloud providers (AWS, GCP, Azure) block outbound SMTP by default. Request port 25 access or use an email relay
- **MTA_API_KEY mismatch** — the key in Docker `.env` must match the one set in Convex env vars

### ClamAV is slow to start

This is normal. ClamAV loads virus definitions into memory on startup, and on first boot it also downloads the full (~300 MB) signature database — this can take several minutes on a small VPS. The Docker healthcheck has a `start_period: 600s` to account for this.

The MTA waits for ClamAV to be healthy before starting (configured via `depends_on` in Docker Compose).

### Web UI shows connection error

The browser needs to reach the Convex backend directly. If `NUXT_PUBLIC_CONVEX_URL` uses a Docker-internal hostname (like `http://convex:3210`), the browser can't connect.

Fix: set `NUXT_PUBLIC_CONVEX_URL` to a URL reachable from the browser:

- Local dev: `http://localhost:3210`
- Production: `https://api.example.com` (via reverse proxy)

### Function deployment fails

```bash
docker compose --profile deploy run --rm convex-deploy 2>&1
```

Common causes:

- **CONVEX_ADMIN_KEY is wrong or missing** — regenerate: `docker compose exec convex ./generate_admin_key.sh`
- **Convex container not healthy** — check with `docker compose ps`
- **Schema conflict** — if you modified Convex schema files, check for validation errors in the deploy output

### The web app feels slow

The web app times its own boot, opening a message, going back to the list and the Core Web Vitals. With PostHog configured and `analytics.posthog` on, those samples go to PostHog. Without PostHog you can still collect them in one browser, locally:

1. Open the browser console on your Owlat instance and run `localStorage.setItem('owlat:perf-trace', 'on')`, then reload. A number instead of `on` sets how many samples are kept (10 to 5000, default 500).
2. Use the app the way that feels slow.
3. Run `owlatPerfTrace.download()` to save the trace as a JSON file, `owlatPerfTrace.export()` to print it, or `owlatPerfTrace.clear()` to start over.
4. Turn it off with `localStorage.removeItem('owlat:perf-trace')` and a reload.

The trace stays in that tab's memory until you export it; nothing is sent anywhere. It holds the timings with the route name they were taken on (such as `dashboard-postbox-folder`), a summary per route, long main-thread tasks per route, the number of open and lingering live queries, and the version and build of your instance. It never holds message content, addresses, subjects, record ids, URLs or credentials, so you can attach it to a bug report. The sample limit only bounds memory; it is not a performance target.

## Migrating to Production

To move from a local development setup to a production deployment:

1. **Update URLs** in `.env`:

   ```bash
   NUXT_PUBLIC_CONVEX_URL=https://api.example.com
   NUXT_PUBLIC_CONVEX_SITE_URL=https://rest.api.example.com
   NUXT_PUBLIC_SITE_URL=https://owlat.example.com
   ```

2. **Set up DNS** — configure A records, PTR, SPF, DKIM, and DMARC. See [DNS & Email Setup](/developer/self-hosting-dns-email).

3. **Add a reverse proxy** — Caddy or Nginx with TLS. See [Production Deployment](/developer/self-hosting-production).

4. **Check Redis auth** — `REDIS_PASSWORD` is mandatory and the installer generates it, but an `.env` written before that must gain the key or no `docker compose` command runs at all. See [Production Deployment](/developer/self-hosting-production#redis-authentication).

5. **Update Convex env vars** to match the new URLs:

   ```bash
   npx convex env set SITE_URL "https://owlat.example.com" --url http://localhost:3210 --admin-key <key>
   # CONVEX_SITE_URL is a Convex BUILT-IN — do not set it via `convex env set`
   # (the CLI rejects it). It derives from CONVEX_SITE_ORIGIN on the convex
   # container, which docker-compose interpolates from NUXT_PUBLIC_CONVEX_SITE_URL.
   npx convex env set ALLOWED_ORIGINS "https://owlat.example.com" --url http://localhost:3210 --admin-key <key>
   ```

6. **Restart** the stack: `docker compose up -d`

7. **Verify** — send a test email and check delivery with [mail-tester.com](https://www.mail-tester.com).
