Postbox is Owlat's personal-mail feature: per-user mailboxes with a webmail UI and native IMAP4rev1 / SMTP submission support. This page covers the implementation. For the user-facing guide see [Postbox in the product guide](/guide/postbox).

::callout{type="info" title="Feature flag"}
Hosted Postbox is gated by the `postbox` flag (off by default). Enabling it activates the `personal-mail` Docker Compose profile, which starts the `apps/imap` service. The separate `mail.external` flag (covered below) is independent of `postbox` — it lets a user connect an existing external mailbox without registering a sending domain.
::

## Schema

The mail tables are defined in `apps/api/convex/schema/mail.ts` (re-exported into `schema.ts` as `mailTables` and spread into `defineSchema()`). Key relationships:

```
mailboxes (1)──(*) mailFolders (*)──(*) mailMessages (*)──(1) mailThreads
         ├────(*) mailAliases
         ├────(*) mailAppPasswords
         ├────(*) mailFilters
         ├────(*) mailLabels
         ├────(*) mailDrafts
         ├────(*) mailSignatures
         ├────(*) mailForwarding
         ├────(*) mailVacationResponders / mailVacationLog
         ├────(*) mailContacts
         └────(*) mailAuditLog / mailAuthFailures

externalMailAccounts (1)──(1) mailboxes (kind='external')
                     └────(*) externalMailFolderSync
pendingMailboxes        — reserved-mailbox intent attached to an invitation
```

There is **no** `mailOutbound` table — outbound state lives in the embedded `mailMessages.outbound` object (a denormalized aggregate plus a per-recipient array). There is **no** `mailIdentities` table — sending identities are a module (`mail/identities.ts`) layered over `mailSignatures` and the mailbox's allowed-from set. There is **no** `mailSnooze` table — snooze is the `snoozedUntil` / `snoozedFromFolderId` fields on `mailMessages`, swept by a 1-minute cron via the `by_snoozed_until` index.

Index notes:

- `mailMessages` inbox sorting uses `by_mailbox_and_received` on `[mailboxId, receivedAt]`. IMAP UID ranges use `by_folder_and_uid` on `[folderId, uid]`; CONDSTORE fast-resync uses `by_folder_and_modseq`. Thread reads use `by_thread`; the snooze cron uses `by_snoozed_until`. There is also a `search_messages` full-text search index on `snippet`. (There is no `internalDate` index.)
- `mailAppPasswords` stores PBKDF2-SHA256 hashes (100k iterations, encoded `<salt-hex>:<hash-hex>`) — the cleartext is shown to the user exactly once on creation. A separate `passwordPrefix` (first 4 chars) narrows the candidate set via `by_prefix` before the deliberately slow hash compare.
- `mailAliases` stores the canonical lowercase address in the `alias` field and is indexed by `by_alias` on `[alias]` (plus `by_target`). `organizationId` is stored on the row but is **not** part of the lookup index — the inbound router resolves a recipient by the `alias` field alone.

## App-password auth flow

Native IMAP/SMTP clients can't use the dashboard session. They authenticate with **app passwords** — single-mailbox, revocable tokens stored as PBKDF2-SHA256 hashes in `mailAppPasswords`. Both verification paths terminate in the same internal Convex action, `internal.mail.appPasswords.verify`, but they reach it differently.

**IMAP (`apps/imap`)** — the IMAP server holds `CONVEX_ADMIN_KEY` and calls the action over the Convex client directly:

```
1.  user opens /dashboard/preferences/app-passwords
2.  mail/appPasswords.generate creates a row with PBKDF2(password); returns plaintext once
3.  user pastes plaintext into Apple Mail; client connects to apps/imap (port 993)
4.  commands/login calls the Convex action `mail/appPasswords:verify`
        ({ address, password }) over the admin-key client
5.  appPasswords.verify narrows candidates by passwordPrefix, runs PBKDF2(password),
        and returns { ok: true, mailboxId, appPasswordId, ... } on success
6.  apps/imap binds the IMAP session to that mailboxId
        — every subsequent IMAP command runs against Convex as that mailbox
```

**SMTP submission (via `apps/mta`)** — the MTA does not hold the admin key, so it posts to the HMAC-signed HTTP endpoint instead:

```
1.  desktop client submits over SMTP to apps/mta's submission port
2.  apps/mta POSTs /webhooks/mta-verify-credential
        body:    { address, password, scope: 'imap' | 'smtp' }
        headers: x-mta-signature: HMAC-SHA256(`${timestamp}.${body}`, MTA_WEBHOOK_SECRET)
                 x-mta-timestamp: <unix-seconds>
3.  mail/authHttp.ts verifies the HMAC + freshness, then delegates to
        internal.mail.appPasswords.verify, returning { ok, mailboxId, appPasswordId, ... }
```

The HMAC pattern means the MTA never needs the Convex admin key for credential checks — only the shared `MTA_WEBHOOK_SECRET`. The IMAP server, which runs the full command loop against Convex, does hold `CONVEX_ADMIN_KEY`.

## IMAP server (`apps/imap`)

Configuration is read from env on startup:

| Env var | Default | Purpose |
| --- | --- | --- |
| `IMAP_PORT` | `993` | TCP listen port |
| `IMAP_LISTEN` | `0.0.0.0` | Bind address |
| `IMAP_GREETING_HOST` | `hostname()` | Hostname in `* OK` greeting |
| `IMAP_TLS_CERT` / `IMAP_TLS_CERT_FILE` | — | TLS cert (inline or path) |
| `IMAP_TLS_KEY` / `IMAP_TLS_KEY_FILE` | — | TLS private key |
| `TLS_CERT_DIR` | `/opt/owlat/certs` | Shared cert dir as fallback |
| `CONVEX_URL` | — required | Convex backend URL |
| `CONVEX_ADMIN_KEY` | — required | Admin key for the IMAP→Convex client |
| `REDIS_URL` | — | Optional rate-limit backend |

A certificate read from files (`IMAP_TLS_*_FILE` or `TLS_CERT_DIR`) is re-read every five minutes; a renewed pair is used for new connections without a restart. A pair that fails to load is logged as a warning and the current certificate stays in service.

Source layout:

```
apps/imap/src/
├── index.ts        # process entry, signal handling
├── server.ts       # net.createServer + TLS upgrade
├── connection.ts   # IMAP pump: socket lifecycle, line/literal buffering
├── parser.ts       # IMAP command parser
├── mime.ts         # RFC 5322 / 2045 parser
├── convex.ts       # Convex client wrapper used by command modules
├── rateLimit.ts    # per-IP and per-credential throttling
├── config.ts       # env loading
├── logger.ts
└── commands/       # one module per IMAP verb (ADR-0016)
    ├── walker.ts   # typed dispatch registry + CAPABILITY-line assembly
    ├── types.ts    # ImapVerb, CommandModule, session/deps types
    ├── helpers/    # shared session helpers
    └── <verb>/index.ts   # login, select, fetch, store, copy, move, idle, …
```

`connection.ts` is the **pump** — it owns the socket, line buffering, and literal absorption, and knows nothing about IMAP verbs. Command handling was extracted into per-verb modules under `commands/<verb>/index.ts`, dispatched through `commands/walker.ts` (see ADR-0016 and the header comment in `connection.ts`). Multi-verb modules (LIST + LSUB, SELECT + EXAMINE, UNSELECT + CLOSE) register themselves under each verb they declare; the walker also assembles the `CAPABILITY` line from each module's declared atoms.

::callout{type="info" title="Octet-accurate literal framing"}
`connection.ts` leaves the socket in its default binary mode (no `setEncoding`) and buffers raw octets in a `Buffer`, so literal absorption (RFC 3501 §4.3) counts **bytes, not decoded characters**. 8-bit/binary MIME bodies and `{N}` octet declarations frame correctly; command text is decoded as UTF-8 only once a full CRLF-terminated line has been sliced off.
::

Each connection lifecycle: `* OK greeting` → `LOGIN`/`AUTHENTICATE` (→ `mail/authHttp`) → `SELECT inbox` → command loop (`FETCH`, `STORE`, `COPY`, `MOVE`, `IDLE`, …).

## Outbound: composing → SMTP

Sending mail from Postbox goes through the existing MTA, not the IMAP server. The flow is:

1. User clicks Send. The web app moves the draft into `pending_send` (undo-send window) and schedules `internal.mail.outbound.dispatchDraft` (`apps/api/convex/mail/outbound.ts`).
2. `dispatchDraft` (a Node action) validates the draft state and undo token, scans each attachment through the MTA's ClamAV endpoint (fail-open on outage), renders the final HTML + plain-text bodies through `@owlat/email-renderer`, builds an RFC 5322 multipart message, and stores the raw `.eml` in `ctx.storage`. It then hands off to `internal.mail.draftLifecycle.transition({ to: 'sent' })`, which atomically inserts the Sent-folder `mailMessages` row with `outbound.state='queued'` and deletes the draft. See ADR-0028.
3. For a **hosted** mailbox it POSTs one MTA `/send` per recipient, prefixing the MTA message id with `pb-<mailMessageId>-<idx>` so the bounce/sent webhook can look the row back up. A synchronous `5xx` transitions that recipient to `bounced`; a network error transitions it to `failed` — both via `internal.mail.postboxOutboundLifecycle.transition`. (For an **external** mailbox it takes the single-POST `dispatchViaExternalWorker` path described below.)
4. Asynchronous MTA delivery events arrive at `POST /webhooks/mta`. The webhook ceremony (rate limit, signature check, audit, parse, dispatch) lives in `webhooks/pipeline.ts` + `webhooks/adapters/mta.ts`; the route itself is served by the shared `providerFeedbackWebhook('mta')` handler, which does nothing but resolve that adapter out of the registry and delegate to `runInboundPipeline`. For events whose provider message id has the `pb-` prefix, the dispatcher (`webhooks/dispatcher.ts`) calls `internal.mail.postboxOutboundLifecycle.transitionByMtaMessageId`, which parses the id and applies the per-recipient transition.

`postboxOutboundLifecycle.ts` is the **sole writer** of every `mailMessages.outbound.recipients[].state` and the only producer of the derived `mailMessages.outbound.state` aggregate (see ADR-0012). The per-recipient states are `queued | sent | bounced | failed`; `bounced` and `failed` are terminal. The aggregate column adds one extra literal, `partial`, when the recipients are in a mix of states. (Personal mail discards the hard/soft bounce classification — that is a campaign-side concern.)

Native SMTP submission from a desktop client takes the same path: the MTA accepts SMTP on its submission port, calls `mail/authHttp` to verify the credential against `mailAppPasswords`, then enqueues the message normally.

## Inbound: MX → mailbox

```
inbound SMTP ──► apps/mta ──► mailboxResolver (apps/mta/src/inbound)
                                  │
                                  │ POST /webhooks/mta-mailbox
                                  ▼
                         mail/webhookHttp.ts ──► mail/delivery.ts
                                              │
                                              ├── resolve alias → mailbox
                                              ├── apply mailFilters
                                              ├── insert mailMessages row
                                              ├── run mail/deliveryHooks
                                              └── notify subscribers (Convex realtime)
```

The MTA routes personal-mailbox deliveries to the dedicated `POST /webhooks/mta-mailbox` route (`apps/api/convex/http.ts`, handled by `handleMailWebhook` from `mail/webhookHttp.ts`); the routing decision is in `apps/mta/src/webhooks/convexNotifier.ts` (`inbound.mailbox.received` → `/webhooks/mta-mailbox`, everything else → `/webhooks/mta`).

`mailAliases` is the lookup table — every accepted recipient address must match an `alias` row before delivery. Spam and ClamAV checks (when enabled) run before insert.

## External mailboxes (`mail.external`)

Separate from hosted Postbox, the `mail.external` flag (label **"Connect external mailbox"**) lets each user connect their own existing Gmail / Fastmail / company mailbox over IMAP+SMTP — personal mail without registering a sending domain. It is **independent of the hosted `postbox` flag** (intentionally not `requires: ['postbox']`), activates the `external-mail` Docker Compose profile, and runs the `apps/mail-sync` worker.

::callout{type="info" title="Configuration"}
The mail-sync worker is reached via `MAIL_SYNC_API_URL` + `MAIL_SYNC_API_KEY`. Credentials for the connected account are stored encrypted at rest (AES-256-GCM) on `externalMailAccounts`; read queries never return the ciphertext. The Convex backend holds `INSTANCE_SECRET` and decrypts (in the internal `getCredentialsForWorker` action), then hands the plaintext credentials to the mail-sync worker over the admin-key channel.
::

How it differs from a hosted mailbox:

- A connected account creates a `mailboxes` row with `kind='external'` linked 1:1 to an `externalMailAccounts` row (host/port/TLS, auth method, encrypted credential envelope, connection status).
- The worker is the **client** of the remote IMAP server. `externalMailFolderSync` tracks per-(account, folder) incremental fetch cursors (`remoteUidValidity`, `lastSeenUid`, optional CONDSTORE `lastSeenModseq`), distinct from `mailFolders`' own UID state (which tracks Owlat-as-IMAP-server).
- Inbound messages fetched from the remote server are ingested via `mail/external/delivery.ts` (`ingestExternalRaw` / `ingestExternalMessage`).
- New INBOX mail arrives through IMAP IDLE, which only runs while the connection is otherwise idle. The worker also polls the INBOX on its own every minute (`MAIL_SYNC_INBOX_POLL_MS`), so a connection kept busy by cycles, reconcile or a backfill still picks new mail up within that interval. Provider views onto mail filed elsewhere (Gmail's All Mail, Starred and Important) are never mirrored as folders; a view is recognised from its LIST attributes, because imapflow reports `\Important` only there.
- Every ingest carries an **`origin`**: `'sync'` for the forward IDLE/poll loop, `'backfill'` for a historical import (`apps/mail-sync/src/connection.ts` sets it at both call sites). **Forward sync only** enters the AI pipeline: an inbox delivery tagged `'sync'` enqueues the Reply Queue + smart-inbox category classification (`enqueueNeedsReplyCheck` / `enqueueCategoryCheck`), exactly as the hosted webhook path does; a `'backfill'` — and a missing `origin`, which an older worker sends — enqueues nothing, so importing a multi-year mailbox never fans out background LLM work. `ingestExternalRaw` also parses the anti-loop headers (`Precedence:`) out of the raw message and passes them down, since they are not persisted on the message row.
- A worker restart after downtime fetches `lastSeenUid+1:*`, which can be hundreds of messages — all legitimately tagged `'sync'` and all classified. This is the same burst a hosted mailbox absorbs after an outage, on the cheap classifier tier.
- Changes made in Owlat are **written back** to the provider. Every local move (including archive, trash, spam, filter runs and deleting a folder), every read / star / answered flag change and every "Delete forever" in an external mailbox records an `externalMailRemoteOps` row in the same transaction (`mail/external/remoteOps.ts`) and nudges the worker's `/remote-ops` endpoint; the worker replays the queue over IMAP (`apps/mail-sync/src/remoteOps.ts`), draining it again on every poll tick and after each reconnect. The same applies to MOVE, STORE and EXPUNGE from clients connected to Owlat's own IMAP server. Messages are found by `SEARCH HEADER Message-ID` in the folder the op names (each hit confirmed against its envelope), falling back to the other synced folders for moves and flag changes, never for deletes. A user folder is created on the provider the first time a message is moved into it. Gmail's All Mail is copied out of rather than moved from, and never deleted from. A failing op backs off (1, 2, 4 … minutes) and is dropped after eight attempts. Only a folder the server confirms does not exist counts as "not there"; a refused SELECT, STATUS or SEARCH (temporarily unavailable, throttled, no permission) fails the op so it is retried, and a lost connection leaves it untouched. Ops for one message run in the order they were recorded (`mail/external/remoteOpOrder.ts`): an op waits until every older op for its message has settled, except a flag change on different flags. A newer flag change replaces the same flags in the older ops queued for that copy of the message, so a failed older retry never undoes it. A backed-off message holds back only its own ops. A folder rename or delete waits until no queued message op names the folder (or a folder below it) by its remote name.
- Changes made **on the provider** are mirrored too (`mail/external/remoteState.ts`, `apps/mail-sync/src/remoteState.ts`). The worker keeps an in-memory view of every synced folder (UID → Message-ID + flags), refreshed each cycle with `UID SEARCH ALL`, a header fetch for new UIDs only, and `CHANGEDSINCE` for flags (the newest 500 messages are re-read on servers without CONDSTORE). Message-IDs that arrived, left or changed flags are looked up locally and reported as observations; `applyRemoteObservations` moves, re-flags or removes the local rows with `writeBack: false`, so nothing echoes back. A message that left its folder and is in no synced folder is gone: out of Trash or Spam it is purged locally, from anywhere else it moves to Trash. Sent and Drafts are never called gone (Owlat writes mail there the provider may not have). Gmail's All Mail is not kept as a view: vanished mail is searched for there before anything is reported, and its flag changes come from `CHANGEDSINCE`. A message with a write-back still queued is skipped, and drains and reconciles run one at a time per account, so a reconcile never works from a view read before a write-back landed. A full reconcile (every local message, paginated) runs after a worker restart, after a UIDVALIDITY reset, every six hours, and while the account is unaligned.
- The views live in memory, so a restarted worker has not seen anything leave a folder. What survives is each message's `mailMessages.remoteSighting`: the remote folder, UIDVALIDITY and UID the provider was last seen holding it under. Ingest records it, and the reconcile rewrites it only when it no longer matches, so a settled mailbox costs no writes (the first full reconcile after the upgrade writes one per message). When the sighted folder's rebuilt view has the same UIDVALIDITY, has looked past that UID (its highest UID, or the UIDNEXT at its census) and lacks it, the message has left that folder and is handled as if a view had seen it go. The first reconcile after a restart therefore catches what happened while the worker was down: moves, flag changes and deletions, including a Trash or Spam folder emptied at the provider. It does not catch a deletion of mail without a sighting (mail Owlat never saw at the provider, which is the safeguard, and anything deleted before the first full reconcile after the upgrade), a deletion in a folder whose UIDVALIDITY changed between runs (the sightings are void then), or mail that went with a folder the provider deleted while the worker was down. Only a complete look counts as evidence of absence: a census whose SEARCH the server refused or failed concludes nothing, a UID the census listed but FETCH did not return counts as present, and nothing is reported gone while any synced folder's view is incomplete or the All Mail look-up failed. Such a deletion waits for a later pass, because a missed deletion is mirrored later and a wrong one cannot be undone. A merge forgets the sightings of mail it finds in no synced folder, since a merge deletes nothing and they would otherwise delete it once the account is aligned. Mail moved to Trash as gone drops its sighting, so it is not purged from there later.
- With two-way sync every other selectable provider folder is mirrored as a local user folder (`mail/external/mirroredFolders.ts`): `recordFolderMapping` takes a `folderPath`, creates the local tree (a name taken elsewhere gets a numbered variant), and ingest finds the folder by its mapping row. Folders are rediscovered on every full cycle, so a new provider folder is picked up without a reconnect. Renaming or deleting a mirrored folder in Owlat queues a `renameFolder` / `deleteFolder` op (`recordRemoteFolderChange`): a rename changes only the leaf name, and the worker follows its own renames for ops still naming the old path; a delete first moves whatever the provider still holds in the folder to its inbox (what deleting a folder does locally), and system folders are never renamed or deleted. In the other direction, a view whose folder the provider no longer lists is dropped with its messages marked vanished, so they follow a renamed folder or are reported gone; after the completed cycle `forgetRemoteFolders` drops the stale mappings and deletes a local user folder left with no mail, no subfolders and no other mapping.
- `externalMailAccounts.syncMode` switches this per account: `'full'` (absent, the default) or `'incoming'` — new mail only, no write-back, nothing mirrored; switching to `'incoming'` discards the queue (`mail/external/syncMode.ts`, `setSyncMode` / `setSharedSyncMode`). `fullSyncAlignedAt` is cleared whenever two-way sync is (re)enabled, and stays unset on accounts from before this release: until the first full reconcile completes, diverging messages are merged rather than pulled — inbox mail follows the provider, mail filed in Owlat is pushed, flags are OR-ed, and nothing is deleted.
- Outbound for an external mailbox skips the per-recipient MTA path: `dispatchDraft` checks `internal.mail.outboundTransport.resolveOutboundTransport`, and for `kind='external'` calls `dispatchViaExternalWorker` — a single POST to the worker's `/send`, which sends through the user's own SMTP and APPENDs the sent copy to the remote Sent folder. SMTP is synchronous, so the worker's per-recipient result maps straight onto `postboxOutboundLifecycle` with no webhook.

The connect/test/credential modules are `external/accounts.ts` (queries + internal mutations), `external/accountsActions.ts` (`connect` / `testConnection` / credential handling), `external/accountShared.ts` (the row shape + `connectFieldsValidator` both connect paths write through), and `external/delivery.ts` (ingest).

### External-account OAuth (Google)

`externalMailAccounts.authMethod` is `'password'` (an app password) or `'oauth2'` (`oauthProvider: 'google'`). OAuth is **additive**, and the password path is the one that is always there: the connect form renders the email + app-password fields for Gmail whether or not a client is configured, and the Google block is an extra rendered beneath them. Configuring `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` is per-instance operator work, so the UI never depends on it.

The flow is an authorization-code grant with PKCE, and it has **no HTTP route** — the redirect target `${SITE_URL}/oauth/google/callback` is a page in `apps/web` under the dashboard layout, so the user's session is present for the whole handshake and the existing session-bound `_connectInternal` / `_connectSharedInternal` / `_connectSeedInternal` / rotation mutations are reused unchanged:

1. `api.mail.external.googleOAuth.isConfigured` tells the connect form whether to render the extra Google block (a boolean derived from env presence — never the credentials). `false` simply leaves it out; nothing else about the form changes. The block leads instead of trailing in exactly one case — `mode="update"` on an `authMethod: 'oauth2'` account, where "Reconnect with Google" is the action the user came for — and even there the password form follows it, so rotating such an account back onto an app password stays possible.
2. `api.mail.external.googleOAuthActions.start` takes the **intent** (`connect` / `update` / `connectShared` / `updateShared` / `connectSeed`) and a same-site `returnTo`, mints a `state` nonce plus a PKCE verifier, stores them on `externalMailOAuthStates` (15-minute TTL, one live row per user, deleted on use), and returns the authorization URL. Scopes: `https://mail.google.com/ openid email`, with `access_type=offline` + `prompt=consent` so Google returns a refresh token.
3. The callback page hands `code` + `state` to `api.mail.external.googleOAuthActions.complete`. It consumes the state row (single-use; another user's row or an expired one reads as absent), exchanges the code at `https://oauth2.googleapis.com/token`, reads the signed-in address from the `id_token` (`aud` / `iss` / `email_verified` are checked; the signature is not, because the token arrived as the body of our own server-to-server TLS request), and dispatches the recorded intent. Pinning the intent at `start` is what stops a tampered callback turning "reconnect my mailbox" into "connect a team inbox"; a re-authorization additionally must sign in as the same address.
4. The refresh token is stored **inside the existing encrypted envelope** (`{ oauthRefreshToken }` in place of `{ imapPassword, smtpPassword }`), so there is still exactly one encrypt site and one decrypt site for the credential itself. `getCredentialsForWorker` hands the worker a short-lived access token and reuses it while >60s remain: first from the warm Node isolate, then from `externalMailAccessTokens`, one row per account that holds the token sealed in the same AES-256-GCM box. Both tiers are keyed by account **and** by the refresh-token envelope's IV, so a reconnect is never served the previous grant's token, and the row is deleted on disconnect, purge, member erasure and `invalid_grant`. Only a miss in both asks Google for a new token and returns `{ kind: 'credentials', credentials }` with `imapAccessToken` + `smtpAccessToken` and both password fields empty. When it cannot, it answers `{ kind: 'unavailable', reason }`: `auth_revoked` (an `invalid_grant` — the account is marked `auth_error` with "Google authorization was revoked. Reconnect with Google."), `refresh_failed` (a transient refusal from Google), or `missing` (no row, or an envelope that will not decrypt).
5. The mail-sync worker picks the mechanism in `src/auth.ts`: a non-empty access token means `AUTHENTICATE XOAUTH2` (ImapFlow) and SASL XOAUTH2 (`@owlat/smtp-client`); otherwise the password. `isAuthError` (`src/loginFailure.ts`) also counts the XOAUTH2 failure strings as a credential rejection. A rejection only parks the account `auth_error` once logins have been refused for 15 minutes straight; until then it is retried on the ordinary backoff with status `error`, and a refusal the server itself calls temporary (`[UNAVAILABLE]`, `[INUSE]`, `[LIMIT]`, `[OVERQUOTA]`, Gmail's "Too many simultaneous connections") never counts. `auth_revoked` is terminal at once and is handled separately from the retryable reasons: the connect loop stops and writes **no** status, leaving the backend's "Reconnect with Google" message intact, while `missing` / `refresh_failed` keep the ordinary error-and-backoff path. The `/send` route reports the revoked case in those words, and the seed-probe sweep skips the account (a probe it could not look for is never recorded as missing).

`testConnection` stays password-only — an OAuth connection is validated by the worker's first status write-back.

## Integration points

| Other feature | How it interacts with Postbox |
| --- | --- |
| MTA (`apps/mta`) | Submits inbound mail via `/webhooks/mta-mailbox`; verifies SMTP-submission credentials via `mail/authHttp` (`/webhooks/mta-verify-credential`); receives outbound sends; posts delivery events to `/webhooks/mta` |
| mail-sync worker (`apps/mail-sync`) | For `mail.external`: connects to remote IMAP servers, ingests inbound, and sends outbound via the user's own SMTP |
| Content scanner (`scan.content`) | Runs on inbound mail before insert |
| ClamAV (`scan.files`) | Scans attachments during inbound delivery and on outbound dispatch |
| Notification provider | `mail/deliveryHooks` calls the notification provider for new-mail alerts |
| AI agent (`ai.agent`) | Listens to inbound events on the *shared* support inbox feature, not Postbox — Postbox is intentionally personal-only |

## Where to start when extending

- New folder type / system folder → `mail/folders.ts` + dashboard sidebar in `apps/web/app/components/postbox/`
- New filter action → `mail/filters.ts` rule executor + UI in `/dashboard/preferences/filters`
- New IMAP command → add a `apps/imap/src/commands/<verb>/index.ts` module and register it in `commands/walker.ts` (see ADR-0016)
- New outbound state transition → extend `mail/postboxOutboundLifecycle.ts` (the single writer of outbound state)
- Server-side enforcement of the feature flag → check `isFlagEnabled(stored, 'postbox')` (or `'mail.external'`) early in every mutation
