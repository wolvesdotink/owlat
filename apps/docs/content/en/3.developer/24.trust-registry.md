# Trust registry (OSTR)

Sender reputation today lives in private silos. Google Postmaster, Microsoft SNDS, Validity SenderScore and a few dozen blocklists each keep their own list with their own undisclosed criteria. A self-hosted sender cannot carry standing from one to the next, cannot see the evidence behind a listing, and in most cases cannot contest one. The Open Sender Trust Registry is the alternative Owlat is building: signed evidence in an append-only Merkle log, plus a published scoring function that anyone can re-run to get the same number and the same explanation.

Five roles make that work. Observers are receiving mail systems that publish signed counts about mail they actually received: traffic and authentication totals, spam-report batches, trap hits, DKIM key observations. Subjects are sending domains, which self-attest their DNS posture, vouch for others, and appeal evidence they dispute. Logs sequence those attestations into RFC 9162-style Merkle trees and publish signed tree heads on a fixed cadence. Aggregators run the scoring policy over the log and answer queries over DNS, HTTPS and signed snapshots. Monitors watch the logs for equivocation and adjudicate challenge samples. Two rules hold the whole thing together: a spam report only counts when it arrives with cryptographic proof that the accused domain really sent the message, and no individual user's report ever reaches the public record.

Owlat ships every piece of this as workspace packages, and all of it is off in a default install. Consuming the registry, contributing to it as an observer, and operating a registry node are three separate opt-ins with three separate configurations, and you can take any one without the others. Phases 0 and 1 are implemented: the specification, the core library, a single-node log and aggregator, the MTA-side lookup client, the Convex-side observer, and the tier chip in the reader. Phase 2 — pooled submission for instances too small to observe safely — is not, and [what v1 leaves out](#what-v1-leaves-out) says what else an observer deliberately does not publish. OSTR is a working title. The public name is chosen at launch and will not contain "Owlat", because a registry named after one of its operators cannot claim neutrality.

## What a lookup answers

An aggregator answers with a tier, a score from 0 to 100, the policy version that produced them, and a machine-readable explanation naming the log entries behind each contribution. There are five tiers.

| Tier | Meaning |
| --- | --- |
| `unknown` | No evidence, or not enough of it. The default for every sender nobody has attested about. |
| `establishing` | Some corroborated history, not yet enough to stand on. |
| `trusted` | Sustained clean traffic across multiple independent observers. |
| `warned` | Evidence of a problem that has not yet crossed the flagging threshold. |
| `flagged` | Corroborated abuse evidence. |

Treat the tier as a signal rather than a verdict. Owlat records it on every delivered message whatever it says, and the only tier that changes where mail lands is `flagged`, which files the message as spam alongside the existing spam and DMARC signals. No tier rejects a message at SMTP time. `unknown` is the honest answer for most of the internet and is not a synonym for suspicious.

## Consuming the registry

Two things have to be on. The `ostr` feature flag (declared in `packages/shared/src/featureFlags.ts`, see [Feature flags](/developer/feature-flags)) gates the routing decision and the tier chip: with it on, a `flagged` sender's mail is filed as spam and every message's tier renders on the sender badge. It does not gate the lookup or the record — the tier is stored on every delivered message whether the flag is on or off — which is what makes turning it on a reversible step over data that is already there rather than a leap. The flag also declares `requires: ['postbox']`: routing inbound personal mail is a Postbox surface, so without that plane the flag cannot resolve true. The environment variables below point the instance at an aggregator you trust.

The chip half has a second dependency the flag does not declare. It is rendered inside the sender-authenticity badge (`PostboxAuthBadge`), so it appears only where that badge does — with `senderAuthBadges` off, `ostr` still files a `flagged` sender's mail as spam and still records every tier, but no chip is drawn. `senderAuthBadges` is deliberately absent from `requires` because listing it would switch the working routing half off as well; if you want the tier visible in the reader, turn both flags on.

The aggregator's public key matters as much as its URL. Snapshots and diffs are signed, and a client that fetches them without verifying a signature has an unauthenticated feed, so set both or set neither.

| Variable | Read by | Purpose |
| --- | --- | --- |
| `OSTR_AGGREGATOR_URL` | Convex functions | Base URL of the aggregator serving snapshots and the diff feed. Set with `convex env set`. |
| `OSTR_AGGREGATOR_PUBLIC_KEY` | Convex functions | The aggregator's ed25519 public key, raw 32 bytes in base64. Every snapshot is checked against it. |
| `OSTR_ENABLED` | MTA | Turns the inbound tier lookup on. Default `false`. |
| `OSTR_ZONE` | MTA | The aggregator's DNS zone apex, for example `ostr.example`. The query adds its own `q.` label. |
| `OSTR_LOOKUP_TIMEOUT_MS` | MTA | How long the lookup may take before the message continues without it. Default `2000`. |

The MTA reads its own copies of `OSTR_AGGREGATOR_URL` and `OSTR_AGGREGATOR_PUBLIC_KEY` from the compose `.env` file, because it verifies snapshots on the inbound path itself. The values are the same on both sides, and the compose file passes all five variables through to the container, plus `OSTR_OBSERVER_ENABLED` for the observer mode below.

The lookup is a single DNS TXT query per inbound message, so the only thing that leaves your instance is the query name. The client keeps "no evidence about this sender" and "the lookup failed" apart, and a failed lookup never becomes a verdict: on timeout the message is handled exactly as it would be with no registry configured. The resolved tier rides the webhook payload to Convex and is stored on the delivered message as `ostrTier`, which is the one field the reader's chip reads. An absent tier and `unknown` both render nothing, so a sender nobody has attested about looks exactly as it did before.

## Observer mode

Observer mode is the publishing half. Your instance aggregates what it received into windowed counts, signs them with its own key, and submits them to the logs. It is gated by environment variables rather than by a feature flag on purpose, because turning it on is a privacy decision about your users' mail and it should not be one toggle away in an admin UI.

| Variable | Purpose |
| --- | --- |
| `OSTR_OBSERVER_ENABLED` | Master switch. Default `false`. |
| `OSTR_OBSERVER_DOMAIN` | The domain this observer signs as, for example `mx.example.com`. Its public key is published at `_ostr.<domain>`. |
| `OSTR_OBSERVER_PRIVATE_KEY` | The observer's ed25519 signing key, raw 32 bytes in base64. |
| `OSTR_LOG_URLS` | Comma-separated log endpoints. Attestations cross-submit to at least two, so no single log operator can quietly drop yours. |
| `OSTR_MIN_MAILBOXES` | Raises the mailbox floor below which the observer refuses to publish. It can only raise it. |

All five are Convex function variables, set with `convex env set` after deploying functions.

`OSTR_OBSERVER_ENABLED` is the exception that has to be set twice. Observer mode has two halves in two processes: the MTA captures the DKIM evidence an attestation rests on, and Convex retains it, closes the window, signs and submits. The MTA half reads the compose `.env` file, the Convex half reads `convex env set`, and one without the other publishes nothing — either evidence captured that is never signed, or an observer with nothing to attest about.

::callout{type="warning"}
**Observer mode is a bad idea on a small instance.** For a single-mailbox observer, which describes a lot of self-hosters, the observer identity is the user identity. `mx.example.com` attesting "received mail from X, one report" tells X exactly which person reported them. Widening the window does not help, and sender-side timing correlation is the same attack in slow motion: send unique content to one address, then watch that observer's next published window. This is why observer mode ships off by default and why the packaged floor of 5 mailboxes is a refusal rather than a warning. The intended fix for small instances is pooled submission through an aggregation relay that signs as its own accountable observer, which is Phase 2 work. Until it exists, small instances consume without contributing, and the incentive model tolerates that on purpose. See [spec 04 §4.5](https://github.com/wolvesdotink/owlat/blob/main/docs/ostr/spec/04-evidence-and-reporting.md).
::

### The k-anonymity hold-back

An observer may only publish a window that covers enough distinct traffic, and enough distinct reporters, that the published counts cannot describe one person's mail or one person's complaint. A window that falls short is not published in a weakened form and is not dropped. It is held, and the next publication folds it into a wider window running from the earliest held start to the latest end, repeating until the thresholds are met. The narrower window is never published later, because publishing both would let anyone subtract one from the other.

These are the shipped floors.

| Threshold | Default | What it protects |
| --- | --- | --- |
| `minMessages` | 20 | A subject's counts describe traffic, not one delivery. |
| `minRecipients` | 5 | Those messages reached more than one mailbox. |
| `minReports` | 3 | A spam-report batch is not one complaint. |
| `minReporters` | 3 | Three reports from one mailbox are still one person, so distinct reporters are counted separately. |
| `minTrapHits` | 3 | A single hit names one trap address as surely as it names one message. |

Configuration may raise any of these and only raise them. An override below the default is clamped back up rather than honoured: a deployment that lowers a k-floor is not a stricter deployment with different taste, it is a deployment publishing its own users.

Holding is not free and not forever. A held subject occupies memory and holds salted recipient tokens, so it falls under the same retention cutoff that deletes evidence bundles, and a bounded cap drops the smallest held subjects first. A subject whose traffic never reaches the floor eventually ages out unpublished, which is the correct outcome.

### What v1 leaves out

An observer in this release publishes traffic summaries, spam-report batches and DKIM key observations. That is the whole list, and three things the specification allows are deliberately not on it.

**No trap hits.** Publishing a trap-hit count means operating never-subscribed trap addresses, and this deployment operates none. A batch counting nothing is a claim with no evidence under it, so the path is wired when trap addresses exist and not before.

**No IP subjects.** The connecting address is on the MTA's connection record, not on the delivered message the observer aggregates. A Convex-side observer therefore attests about sending domains and says nothing about IPs, which is the honest reading of what it actually witnessed rather than a gap filled with a guess.

**No challenge endpoint.** A monitor sampling a published batch has nowhere to send the request yet. What is here is the retention that makes answering one possible later: every batch's commitment and its ordered list of bundle hashes are kept, because a Merkle root cannot be re-derived from an unordered set and the order is unrecoverable after the fact.

On the consuming side there is one more absence worth naming. The chip shows the tier and nothing behind it. An aggregator's answer carries a machine-readable explanation naming the log entries that produced the score, but the reader does not link through to it, so a tier you want to dispute is investigated at the aggregator rather than from the message.

Nothing here watches your own sending domains either. Owlat asks the registry about senders it receives mail from, never about itself, so your instance's own standing does not reach the deliverability dashboards and raises no alert when it moves. The lookup would work today, since an aggregator answers for any subject you name. What is missing is the outbound side asking, and asking is only worth wiring once a federation exists to answer: your own tier, computed from a log you are the only contributor to, tells you what you already knew.

## Running your own registry node

`apps/ostr-registry` is the server half: the transparency log, the reference aggregator, DNS zone generation, and the HTTPS query API in one process, with SQLite underneath. It is standalone by design. It never reads the Owlat database and does not depend on any other service in the stack.

Most people never need to run one. Consuming and observing both talk to somebody else's node. Run your own for a private federation, a staging log, or a second public node in the federation.

```sh
docker compose --profile ostr up -d ostr-registry
```

That command starts the node, but it leaves `ostr` out of `COMPOSE_PROFILES` in `.env` — and the in-app updater upgrades the stack by running `docker compose pull` and `docker compose up -d` against exactly that list. A node started with `--profile` alone is skipped by every upgrade from then on. It does not stop; it keeps running its original image while the compose file is replaced underneath it, so the failure mode is an indefinitely stale binary holding your log and aggregator signing keys, with nothing visibly wrong. Add the profile to the file to bring the node into the normal upgrade path:

```ini
# .env — alongside whatever profiles are already there
COMPOSE_PROFILES=mta,ostr
```

That line has a sharp edge. Toggling any feature flag in the admin UI rewrites `COMPOSE_PROFILES` from the flag registry, and no flag claims the `ostr` profile — a registry node is not a feature of the instance it happens to sit beside — so the entry is dropped and has to be put back. Check the line after any flag change, or skip it and update the node by hand:

```sh
docker compose --profile ostr pull && docker compose --profile ostr up -d
```

The `tls` profile is in the same position, so this is worth a habit rather than a one-off note.

Configuration lives in the compose `.env` file and is documented there in full. Four points are worth repeating.

The node needs two signing keys, `OSTR_LOG_PRIVATE_KEY` and `OSTR_AGGREGATOR_PRIVATE_KEY`, and they must be different. One key commits to "this log contains these leaves" and the other to "this aggregator computed these scores". Sharing one key makes the two claims indistinguishable to a monitor. `apps/ostr-registry/README.md` has the one-liner that generates them.

`OSTR_ZONE_ORIGIN` is the apex the node publishes its query zone under. Left unset it is `ostr.invalid`, reserved by RFC 2606, so a node nobody has configured publishes an obvious placeholder instead of quietly claiming a real name.

`OSTR_STH_INTERVAL_SECONDS` may not exceed `OSTR_MMD_SECONDS`. Every inclusion promise the node issues states the maximum merge delay, and a node that publishes tree heads less often than that delay cannot keep a single promise it makes. The node refuses to start on that combination rather than running in permanent violation.

The `ostr-data` volume holds the log. That data is append-only evidence, and a node that loses it cannot reproduce the heads it has already signed, which it will refuse to start without. Back it up like a database.

The service publishes no host port. It answers on `ostr-registry:3300` inside the stack, and `/healthz` is a liveness probe that stays up while a refresh is running. Put the query API behind the `tls` profile's reverse proxy rather than binding it raw. `Caddyfile.example` ships commented blocks for the other optional public services; a registry node wants one of the same shape:

```caddyfile
ostr.example.com {
	reverse_proxy ostr-registry:3300

	header {
		Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
		X-Content-Type-Options "nosniff"
		-Server
	}
}
```

## Specification and decisions

The protocol is specified independently of this implementation, and the specification is normative where the two disagree.

- [Specification overview](https://github.com/wolvesdotink/owlat/blob/main/docs/ostr/README.md), with numbered sections under [`docs/ostr/spec/`](https://github.com/wolvesdotink/owlat/tree/main/docs/ostr/spec)
- [ADR-0058: Open Sender Trust Registry](https://github.com/wolvesdotink/owlat/blob/main/docs/adr/0058-open-sender-trust-registry.md), the decision record
- [Privacy rules](https://github.com/wolvesdotink/owlat/blob/main/docs/ostr/spec/09-privacy.md) and the [threat model](https://github.com/wolvesdotink/owlat/blob/main/docs/ostr/spec/10-threat-model.md)

Every tunable of the scoring function is a `POLICY_V1` constant exported from `@owlat/ostr-core`. Those constants are normative and the specification deliberately carries no numbers, so a change to the policy is a change to one file with golden-file tests over it.
