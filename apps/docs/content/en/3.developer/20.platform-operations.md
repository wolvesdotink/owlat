This page documents the operational surface that sits *behind* the product: the abuse-status lifecycle that gates sending, the platform-admin role and its queries, the content review queue, the organization deletion job, system health and in-app self-update, and the dev-mode endpoints, crons, and migrations that keep a deployment maintainable. It is written for operators and contributors working on a self-hosted Owlat instance.

::callout{type="info" title="One organization per deployment"}
Owlat is single-org-per-deployment. The data plane belongs to exactly one organization, and the abuse-status, settings, and stats described here all live on the singleton `instanceSettings` row. There is no multi-tenant org switcher.
::

::callout{type="info" title="What the platform-admin surface covers here"}
This OSS repository ships three platform-admin-gated pages: **System & Updates** (`/dashboard/admin/system`), **Backups** (`/dashboard/admin/backups`), and the **Operator console** (`/dashboard/admin/operator`, which is where the roster, held content, and sending status live). The richer *multi-tenant* control-plane UI that consumed the cross-org queries below was extracted into a separate private repo — anything shaped around many organizations is a **backend/API surface** here, not an in-product dashboard.
::

## Abuse status lifecycle and the sending gate

Every deployment carries a single abuse status on `instanceSettings.abuseStatus`. It drives whether the instance is allowed to send. The four statuses, defined in `apps/api/convex/workspaces/abuseStatus.ts`, form a severity ladder:

| Status | Severity | Sending | Meaning |
| --- | --- | --- | --- |
| `clean` | 0 | Allowed | Normal operation (also the default when no status was ever written) |
| `warned` | 1 | Allowed | Advisory warning issued — still fully operational |
| `suspended` | 2 | **Blocked** | All sending blocked; the account stays accessible |
| `banned` | 3 | **Blocked** | Account fully disabled; terminal for internal writers |

The read and write halves are deliberately split into sibling modules (ADR-0011, `docs/adr/0011-abuse-status-modules.md`):

- **Abuse gate** (`apps/api/convex/workspaces/abuseGate.ts`) is the home of the sending predicate. It exports two surfaces: `isSendingAllowed(status)`, the pure predicate that the live send paths call (the transactional dispatch path in `transactional/dispatch.ts`), and `requireSendingAllowed(ctx)`, a mutation-context helper that fetches `instanceSettings` and throws on `suspended`/`banned`. The campaign send path enforces the same predicate inline through its pre-flight query (`campaigns/preflight.ts`, which checks `abuseStatus` against `suspended`/`banned` directly) rather than calling the helper. Either way the gate always runs — it is not behind a feature flag.
- **Abuse status** (`apps/api/convex/workspaces/abuseStatus.ts`) is the *only* writer of `abuseStatus` and its companion fields (`abuseStatusReason`, `abuseStatusChangedAt`, `abuseStatusChangedBy`).

### Transition rules

There are two write entry points. The internal-writer path enforces severity rules; the admin path bypasses them.

| Entry point | Used by | Rules |
| --- | --- | --- |
| `transition` (internal mutation) | MTA circuit breaker, reputation auto-enforcement | `banned` is terminal; downgrades are refused *except* down to `clean` (the auto-recover path); a same-state attempt is recorded but not patched |
| `adminOverride` (internal mutation) | The platform-admin `setOrganizationStatus` mutation | Bypasses all severity rules — an admin can demote a `banned` org back to `clean` to resolve an appeal |

Both paths write an `abuse_status_changed` audit-log row on **every** call, including same-state no-ops (so "circuit breaker tripped again while already warned" is observable). A missing `instanceSettings` row returns `{ ok: false, reason: 'no_settings_row' }` rather than throwing — an early-deployment edge case.

### What flips the status automatically

| Trigger | Source | Target status |
| --- | --- | --- |
| Reputation reaches `critical` risk | `analytics/sendingReputation.ts` → `evaluateAutoEnforce` (hourly cron) → `autoEnforceReputation` | `suspended` |
| Reputation reaches `high` risk | `analytics/sendingReputation.ts` → `evaluateAutoEnforce` (hourly cron) → `autoEnforceReputation` | `warned` |
| MTA circuit breaker trips | `webhooks/dispatcher.ts` (`internal.circuit_breaker_tripped`) | `warned` |

Reputation is derived on read (a rolling 30-day window — see [Deliverability Infrastructure](/developer/deliverability-infrastructure)), but auto-enforcement is deliberately kept off the read hot path: an hourly `evaluate reputation auto-enforce` cron (`apps/api/convex/crons.ts`) calls `evaluateAutoEnforce`, which summarizes the org window and schedules `autoEnforceReputation` when risk is high/critical. A separate hourly `cleanup sending reputation` cron (`recalculateAll`) ages out >60-day buckets. Because severity downgrades are refused, a `critical → warned` transition never silently relaxes an existing suspension.

## Platform admin role, roster, and operational queries

Platform admins are rows in the `platformAdmins` table, keyed by BetterAuth user id. Two roles exist: `admin` and `superadmin`.

This is the tier **above** the organization roles. Owner/admin/editor govern the product — members, campaigns, mailboxes, settings. Platform admin governs the **deployment**: applying an in-app update, restoring a backup, the operator console. An org owner is therefore not automatically a platform admin; the grant is its own row.

### How the roster is bootstrapped

Owlat is single-org-per-deployment, so the person who runs setup owns both the workspace and the box it runs on. Three ways in, in the order you will meet them:

| Path | Who | When |
| --- | --- | --- |
| `/seed/admin` grants the setup user `superadmin` | The account the setup wizard (or `owlat setup`, or `bun run dev:seed`) creates | Automatic, on every fresh install |
| `claimInitialPlatformAdmin` | The org **owner**, from **Administration** (`/dashboard/admin`) | One click, offered only while the roster is empty — for instances seeded before the automatic grant shipped |
| `addPlatformAdmin` | An existing `superadmin`, from **Operator → Admins** | Any time afterwards |

Both bootstrap paths are one-shot: they refuse as soon as *any* platform admin exists. That empty-table precondition — not the caller's org role — is what keeps them from being an escalation route, and it is why the second path is owner-only rather than admin-only.

Break-glass: if the roster is emptied and no in-app caller can satisfy either path (the last superadmin was removed, or the owner account is gone), an operator with shell access runs `convex run migrations/0036_seed_platform_admin:run '{"authUserId":"…","email":"…"}'`. It, too, only succeeds while the table is empty. All three grant paths write the same `platform_admin.bootstrap_granted` audit row, with `via` set to `setup`, `owner_claim` or `break_glass`.

Grants are revoked in two places besides `removePlatformAdmin`: account deletion / member erasure drops the departing member's row, and `POST /dev/reset` wipes the roster with the rest of the instance.

Gating lives in `apps/api/convex/lib/platformAdminAccess.ts` (the checks), `apps/api/convex/lib/authedFunctions.ts` (the builders) and `apps/api/convex/platformAdmin/` (the probes and the bootstrap):

| Function | Kind | Purpose |
| --- | --- | --- |
| `platformAdminQuery` / `platformAdminMutation` | Builders | Org-member floor, then `requirePlatformAdmin`; the handler receives `{ authUserId, email, role }` as its third argument |
| `platformSuperadminMutation` | Builder | Same, but through `requireSuperadmin`; used by `addPlatformAdmin` / `removePlatformAdmin` |
| `requirePlatformAdmin(ctx)` / `requireSuperadmin(ctx)` | Helpers | Throw `FORBIDDEN` unless the caller is in `platformAdmins` (with the `superadmin` role, for the second); return `{ authUserId, email, role }` |
| `isPlatformAdmin` | Public query | Boolean nav helper, safe for anonymous callers |
| `isPlatformAdminByUserId` | Internal query | Admin check by user id, for HTTP/action contexts that lack a `QueryCtx` |
| `bootstrap.seedInitialPlatformAdmin` | Internal mutation | Grants the setup user the first `superadmin` row; called by `/seed/admin`, no-ops once the roster is non-empty |
| `bootstrap.claimInitialPlatformAdmin` | `ownerMutation` | Lets the org owner claim an empty roster from the admin hub |
| `bootstrap.getBootstrapStatus` | `authedQuery` | `{ rosterEmpty, canClaim }` — drives the admin-hub card; readable by any org member, discloses no identities |
| `migrations/0036_seed_platform_admin:run` | Hand-run internal mutation | Break-glass bootstrap of the first `superadmin` |

The web app gates the deployment-level pages — **System & Updates**, **Backups**, and the **Operator console** — with the `platform-admin` route middleware (`apps/web/app/middleware/platform-admin.ts`), which calls `isPlatformAdmin` and redirects non-admins to `/dashboard`. Every other admin page uses the org-role `admin` middleware instead.

### Operational queries

All of these live in `apps/api/convex/platformAdmin/queries.ts` and are `platformAdminQuery`s. They read the singleton `instanceSettings` row plus derived reputation/stats:

| Query | Returns |
| --- | --- |
| `getPlatformStats` | Contact count, abuse status, 30-day send/delivery/bounce/complaint aggregates, signups-by-day |
| `getOrganizationDetail` | Settings, reputation summary, blocked-email counts (`bounced`/`complained`/`manual`), recent content scans and campaigns |
| `listFlaggedOrganizations` | The instance entry, but only when `warned`/`suspended`/`banned` or reputation risk is `high`/`critical` |
| `listAllOrganizations` | The instance entry with optional `search`/`statusFilter` |
| `listAllUsers` | User profiles with optional `search` |
| `listRecentAbuse` | Flagged content scans (`suspicious`/`blocked`) plus `pending_review` campaigns |
| `listPlatformAdmins` | The full admin roster |

### Roster + status mutations

These live in `apps/api/convex/platformAdmin/mutations.ts`:

| Mutation | Effect |
| --- | --- |
| `setOrganizationStatus` | Sets abuse status via `adminOverride` (bypassing severity rules); writes both `abuse_status_changed` and the legacy `platform_admin.org_status_changed` audit rows |
| `addPlatformAdmin` | Adds an admin (`superadmin`-only; rejects duplicates) |
| `removePlatformAdmin` | Removes an admin (`superadmin`-only; cannot remove yourself) |

## Content review queue (approve/reject pending content)

Campaigns and transactional emails can land in a `pending_review` status (for example when content scanning flags them — see [Email Security](/developer/email-security)). The review surface is platform-admin only.

`getContentReviewQueue` (in `platformAdmin/queries.ts`) returns the pending items joined with their latest content-scan result, plus the recently-reviewed log:

```ts
{
  pending: [{ type: 'campaign' | 'transactional', id, name, subject, scan: { score, level } | null, ... }],
  pendingCount: number,
  recentlyReviewed: [{ action, details, userId, createdAt }],
}
```

The three review mutations (in `platformAdmin/mutations.ts`) all require `pending_review` as the current status and write a `platform_admin.content_approved` or `platform_admin.content_rejected` audit row:

| Mutation | Effect on the resource |
| --- | --- |
| `approveCampaign` | Campaign → `draft` (the owner can then send it) |
| `approveTransactional` | Transactional email → `published` (sets `publishedAt`) |
| `rejectContent` | Campaign → `draft`, or transactional email → `draft`; reason is recorded |

Both approval paths and the rejection path move the resource out of the queue; there is no separate "blocked" terminal state for reviewed content — rejection reverts to `draft` with the reason captured in the audit log.

## Send completions that failed

When a send worker finishes, the workpool hands its result to `delivery/sendCompletion:completeSend`, which moves the Send to `sent` or `failed`. If that step throws, the workpool keeps nothing, and the result is the only place a direct provider's message id exists (SES, Resend, Mandrill, Emailit, SMTP). So `completeSend` catches the error. It writes the provider message id onto the Send, which stays `queued`, and records a compact form of the worker's outcome (never the recipient or the message) and a fixed error code (`CONVEX_VALIDATION`, `MTA_IDENTITY_CONFLICT`, `UNKNOWN` and so on, never the message text) in `sendCompletionFailures`. Provider feedback for that message id finds the Send from then on.

The `replay failed send completions` cron re-runs each record with a growing delay (10 minutes, doubling, at most 6 hours apart) up to 10 times. After a fix is deployed, the backlog drains on its own. A provider event for a Send that has a record replays the record first, whether it comes from a provider webhook or from Owlat's own bounce server. If the replay still fails, a bounce, complaint, delivery or failure event is kept on the record and applied right after the completion when a replay succeeds, in the provider's time order, so the provider does not have to send it again. The record keeps one event of each kind: the latest soft bounce and failure, the earliest hard bounce, complaint and delivery. An event the lifecycle refuses at that point (a bounce stamped after a complaint, for example) is listed on the resolved record. A replay never counts a Send twice: if the Send has already left `queued`, the record only applies the events kept on it. If the completion threw while re-entering a deferred Send, the record re-enters it at once and resolves as `retried`. After 10 failed replays, a record is `exhausted` and waits for an operator. So does a record whose stored outcome would exceed 32 KiB (`PAYLOAD_TOO_LARGE`) or one whose replay would need the envelope it does not keep (`ENVELOPE_NOT_STORED`). Close those by hand: `sent` when the record kept the provider message id of an acceptance, otherwise `failed`, which ends the Send with `SEND_COMPLETION_UNRECOVERABLE`. A close applies the provider events kept on the record right after, as a replay would: after `sent` a kept bounce still lands and suppresses the address, after `failed` the events are listed on the record as refused. A provider message id longer than 512 characters is never kept, so such a record can only be closed as `failed`. Run these from `apps/api` with the deployment configured:

```sh
# How many records are open or exhausted, the oldest, and a sample with the last error
npx convex run delivery/sendCompletionFailureAdmin:status

# Replay one record now
npx convex run delivery/sendCompletionFailures:replayCompletionFailure '{"failureId": "<id>"}'

# After fixing the cause: give exhausted records back to the cron with a fresh budget
npx convex run delivery/sendCompletionFailureAdmin:reopenExhaustedCompletionFailures

# See the full error of one record: runs it without catching, writes nothing when it fails
npx convex run delivery/sendCompletionFailures:applyRecordedCompletion '{"failureId": "<id>"}'

# Close a record the replay cannot finish ("sent" or "failed")
npx convex run delivery/sendCompletionFailureAdmin:closeCompletionFailure '{"failureId": "<id>", "outcome": "failed"}'
```

Each record is also logged once, as `[SendCompletion] Completion failed; outcome recorded`, with the Send's id but not the error text. Resolved records lose their stored outcome right away. The daily `purge send completion failures` cron deletes resolved records 30 days and exhausted records 90 days after their last failure. Erasing a contact deletes its records in a step of its own, and a Send that is already erased gets no new record.

## Sends no completion reached

A Send can stay `queued` with no provider message id when no completion ever reached it: the workpool lost the work, or the completion threw before `sendCompletionFailures` existed (#1184). Provider feedback cannot find such a Send, since it has no id, so its campaign stays `sending`.

Every delivery attempt passes `delivery/routingReentry:issueSnapshot`, which records on the Send when its first attempt started (`firstAttemptAt`, written once; retries and re-entries carry the same start). The four-day delivery deadline runs from that moment, and dispatch refuses any attempt after it. A Send that is still `queued` a day after its deadline therefore has nothing left that could deliver it. The hourly `sweep lost sends` cron fails such Sends with `SEND_COMPLETION_LOST`, and the campaign completes on the next reconcile. Send-time optimization, scheduling, warm-up ramps, rate limits and deferrals all happen before the first attempt or inside the four days, so they never shorten a Send's window.

The cron leaves three kinds of Send alone:

- a Send with a provider message id. MTA custody and stamped acceptances belong to provider feedback.
- a Send with an open or exhausted completion-failure record. Its outcome is known; close it through the commands in the previous section.
- a Send without `firstAttemptAt`. That is every row written before this field shipped, and any Send not attempted yet. Its deadline is unknown, so only you can fail it, and only once it is at least 8 days old (the longest send-time optimization delay of 72 hours, plus the 4-day window, plus the day of grace).

```sh
# Per send table: Sends the next cron tick fails, queued Sends with no first attempt
# (and how many of them are past the 8-day minimum), with samples
npx convex run delivery/stuckSendSweepAdmin:status

# Fail the queued Sends with no provider id and no first attempt created before a time
# (milliseconds; must be at least 8 days ago). Runs in the background.
npx convex run delivery/stuckSendSweepAdmin:failUnanchoredLostSends '{"createdBefore": 1780000000000}'
```

Most rows `status` reports as having no first attempt are simply waiting for it, a scheduled campaign for example. Check `pastMinimumAge` and the sample before you pick a cutoff. Both passes read one index range (`by_status_provider_first_attempt`) a page of 25 at a time and fail each Send in its own nested transaction, so a Send that throws does not hold up the others and is tried again on the next pass. Each failed Send is logged as `[LostSendSweep] Failed a send no completion reached`, with its id.

## Organization deletion job

Deleting the organization is a hard, irreversible wipe of the entire data plane. It runs as one durable job under `apps/api/convex/workspaces/deletion/`: `job.ts` owns the lifecycle, `walker.ts` holds the functions that drive it, `quiesce.ts` cancels pending scheduled work, and `steps/` holds the ordered cascade. The design is ADR-0025 (`docs/adr/0025-organization-deletion-module-family.md`) with its amendment "Durable lifecycle and write fence".

::callout{type="danger" title="Irreversible"}
The job deletes every per-organization table, including storage blobs, audit logs, and finally the singleton `instanceSettings` row that owns the org's existence. There is no soft-delete and no recovery short of a database restore.
::

Accounts are not part of the sweep. The organization, its member rows and the users' accounts live in the BetterAuth component, outside the application schema, and `userProfiles` is classified as non-tenant data. After the job completes, every member can still sign in and finds the same organization with an empty workspace. The danger-zone confirmation in the web app says exactly this, so keep it in step if the sweep ever starts removing identities. See the "Accounts" paragraph of ADR-0025.

Stored credentials go with the workspace: the AI provider configuration (`aiProviderConfig`) with its encrypted language, embedding and decision keys, API keys, webhook secrets and external mailbox credentials. After completion, AI features fall back to the deployment's `LLM_*` environment variables, if set. An action instance that already holds the previous configuration in its cache keeps using it until its next recheck, at most about 30 seconds. The Sealed Mail key vault (`keyVault`) stays: the instance minted those keypairs, and other instances have pinned their fingerprints. See the #1101 amendment of ADR-0025.

### Starting a deletion

Two requests start a deletion. Both open the job inside their own transaction through `beginWorkspaceDeletion` (`job.ts`), so the write fence is up by the time the request commits:

- `workspaces.settings.remove` (`apps/api/convex/workspaces/settings.ts`), the owner's "Delete workspace". Only the owner may call it. It returns the job's `generation` and `isJoined`.
- An owner's account deletion. The daily `processPendingDeletions` cron (`auth/accountDeletion.ts`) picks up a request once its 30-day grace period has passed, and `deleteAccountForRequest` (`auth/accountManagement.ts`) opens the job before it removes the BetterAuth organization.

At most one job is active. A second request joins the running job instead of starting another generation, and joining a job that has `failed` re-arms it. The job row lives in `workspaceDeletionJobs` and is the fence: it changes only when a generation opens and when it ends. The checkpoint lives in `workspaceDeletionProgress` (both in `apps/api/convex/schema/workspaceDeletion.ts`). The sweep never touches either table, so finished rows stay as the history of earlier generations.

`walker.start` and `walker.runStep` remain only for calls the previous release scheduled before an upgrade. They adopt such a walk into a job with `source: 'previous_release'` and are due to be removed after the next release.

### Phases

After the opening transaction, the progress row moves through three phases. Each transaction does one bounded piece of work and saves the checkpoint in the same commit.

| Phase | One transaction | Next |
| --- | --- | --- |
| `quiesce` | Cancels one page of pending scheduled functions, except the survivors listed in `SURVIVING_SCHEDULED_FUNCTIONS` (`quiesce.ts`) | `sweep`, once every pending function has been inspected |
| `sweep` | Deletes one batch from the table named in `step` | The next table in `STEPS` once this one is empty; `verify` after the last table |
| `verify` | Re-scans the scheduler, then checks every registered table for a row | Completes the job on an empty pass; otherwise back to `sweep`, starting at the first table that still has rows |

The deployment holds exactly one workspace, so every pending scheduled function belongs to the workspace being deleted. The quiesce phase cancels them so that a send-later, a snooze wake-up or an automation wait queued before the deletion cannot fire after the fence comes down and write into the emptied workspace. The survivors are the deletion's own chain, the provider-side release of a removed sending domain, member erasure, the account-deletion mail, Sealed Mail key material and the inbound TLS policy push.

Only an empty verify pass completes the job, and that transaction is what lifts the fence. Rows found during verify mean something wrote behind the sweep. After `MAX_VERIFY_PASSES` (5) passes that still find rows, the job fails instead of looping with the fence up. Its checkpoint already points at the table that refilled, so a re-armed job sweeps that table first.

### The write fence

While a job is active, `lib/writeFence.ts` refuses every insert, patch and replace on a table the deletion sweeps. The refusal is an `invalid_state` error with `reason: 'workspace_deletion_in_progress'`, and the user sees "This workspace is being deleted. Changes are not accepted until the deletion has finished." Deletes pass, because removing a row can only help the sweep. Tables outside the deletion registry stay writable: auth identity, instance infrastructure and the two job tables. Sign-in, updates and backups keep working during a deletion. Reads are never fenced.

The check sits in the database handle the mutation builders give their handlers. The public builders in `lib/authedFunctions.ts` use it, and every internal mutation imports the fenced `internalMutation` from `lib/writeFence.ts`. Crons, scheduled chains, HTTP routes and actions all write through these builders, so an action that was already running when the deletion began has its write refused at the mutation it calls. `walker.ts` is the one module built on the raw builder; `apps/api/scripts/check-write-fence.ts` (part of the api lint) fails any other module that does the same.

A few callers handle the refusal on purpose. The recovery crons for integration imports, contact property deletions, outbound webhook deliveries and campaign send walks check for an active job and skip their run. The MTA mail routes answer a refusal with a final `200` and `ignored: 'workspace_deletion_in_progress'`, so the MTA does not retry the delivery or park it in its dead-letter queue. API-key REST routes return the refusal as a `422`.

### Checkpoints, retries and resume

`walker.tick` is one transaction of the job. `walker.drive` is an action that chains up to 20 ticks and then reschedules itself. Every step deletes from the front of its table, so the table name in `step` is the whole sweep cursor. A tick that is interrupted rolls back and leaves the previous checkpoint in place.

When a tick throws, `recordFailure` counts the attempt, keeps the error on the progress row and schedules a retry after 30 seconds, 2 minutes, 10 minutes and 30 minutes. The fifth failed attempt marks the job `failed`.

The `recover workspace deletion` cron runs `walker.recover` every 10 minutes. It restarts an active job whose progress row has been quiet for longer than the longest backoff plus 15 minutes, which covers a lost schedule, a crashed action or a redeploy. It re-arms a `failed` job after an hour. Either way the job continues from the saved checkpoint. Running two chains on one job is harmless, because each tick is a serializable transaction and each step is idempotent.

### When a job stalls

Start with the job's status:

```sh
npx convex run workspaces/deletion/walker:status
```

It returns the active job, or the most recent one, with its `status`, `phase`, `step`, `rowsDeleted`, `verifyPasses`, `attempts`, `rearms`, and the last error together with the step it happened in.

- `retrying` or `failed`: a transaction keeps failing at `lastErrorStep`, and `lastError` says why. The cron re-arms a failed job after an hour. A new removal request re-arms it at once.
- `verify` that keeps going back to `sweep`: something still writes into the table in `step`. After five passes the job fails with "Rows kept reappearing in" that table.
- `running` with an old `updatedAt`: the chain is gone. The recovery cron restarts it once the job has been quiet for 45 minutes.

When a job cannot finish, for example because a table keeps refilling from a writer nobody can stop, `walker.abort` ends it without completing it and lifts the fence:

```sh
npx convex run workspaces/deletion/walker:abort '{"operator":"ops@example.com","reason":"contacts keep refilling"}'
```

An abort writes a `settings.workspace_deletion_aborted` audit row and undoes nothing. Deleted rows stay deleted. Scheduled work the quiesce phase cancelled stays cancelled, so send-laters, snooze wake-ups and automation waits have to be rescheduled by hand. Whatever the sweep had not reached stays in place, and the workspace accepts writes again.

### The cascade

- **Ordered cascade.** `STEPS` (`steps/cascadeOrder.ts`) is the ordered list of every per-organization table, about 190 of them. Children are deleted before parents. Storage-bearing tables (for example `mediaAssets`, `semanticFiles`, `mailMessages`) purge their blobs before the row delete. `auditLogs` comes after every other data table, because delegated lifecycle calls keep writing to it during the wipe. `featureFlagSettings`, `instanceCounters` and finally `instanceSettings` close the list.
- **One step per table.** `ORGANIZATION_DELETION_STEPS` (`steps/registry.ts`) maps each table to a step implementing the `deleteBatch(ctx)` contract from `steps/_common.ts` (default batch size 100). Most tables use the generic sweep from `steps/sweep.ts`. Tables with per-row side effects have their own module under `deletion/steps/`: the storage purges, and the delegating `contacts` and `domains` steps. The `contacts` step deletes each contact through `permanentlyDeleteContactWithRelations`, the same cascade the soft-delete cleanup uses, and the five contact child tables are swept again after it for rows whose contact was already gone.
- **Exhaustive by type.** `OrganizationDeletionTable` in `_common.ts` is the literal union of every swept table. A compile-time guard in `registry.ts` fails the build when a table in the union has no position in `STEPS`, and the same union defines the tables the write fence closes.

Any new per-organization table added to the schema must also add a literal to `OrganizationDeletionTable`, a position in `STEPS` and a registry entry. Otherwise the deletion leaves it orphaned and the write fence does not protect it.

## Bounces and complaints that match no send

A bounce or complaint webhook names the Send by its provider message id. When that id matches no Send at all, because the id was never stored or the mail was not sent by this deployment, the event is kept in `unresolvedFeedback` instead of being dropped, and the function log gets one `unresolved_bounce` line with the event kind and message id. Rows are scoped to ids that match no Send; an event for a Send that exists but cannot take it yet is not stored here.

- **Complaints that name the complainer.** SES (when it lists exactly one complained recipient), Resend (when the message had one recipient), Mandrill and the MTA pass the address along. When the id matches no Send, the address goes on the blocklist as `complained` only if the event proves this deployment sent the mail. Today the only proof is the MTA's `deliveryDomain: production` tag, which it writes only on a report whose signed VERP token decoded. A provider's webhook signature proves the provider sent the report, not which deployment sent the mail: a provider account, webhook or SNS topic shared by several deployments delivers every tenant's feedback to each of them. SES, Resend and Mandrill echo back no marker Owlat stamps per deployment, so their unresolved complaints never block an address. The complaint is stored either way, and its `suppression` column says what happened: `suppressed`, `unattributed`, `no_recipient`, or `not_applicable` for bounces.
- **Bounces** are stored but never suppressed: a bounce event names no address, and a soft bounce says nothing about it. A hard bounce for an id whose stored bounce is soft replaces it, so a later replay applies the hard bounce; a soft bounce never downgrades a hard one.
- **Replay.** The `replay unresolved feedback` cron retries each row 10 minutes, 1 hour, 6 hours and 24 hours after it first arrived (every deadline counted from arrival), which catches a webhook that raced the send storing its id. A replay runs the same transition the webhook would have, so a Send is never moved twice, and the row is closed as soon as its id resolves.
- **What is stored, and erasure.** A row holds no personal data: the message id, the kind, the provider type, the bounce type, the SMTP status code read out of the diagnostic (`5.1.1` or `550`), the delivery-domain tag, the `suppression` outcome, timestamps, counters and replay state. Neither the recipient's address nor the remote server's diagnostic text is kept, since the diagnostic often quotes the address. A replay resolves by message id and the Send carries its own recipient, and an attributed complaint blocks its address when it arrives, from the event in memory. Because the table names no one, erasing a contact does not touch it. Rows are deleted 90 days after they were first seen, the same horizon as raw webhook payloads, and deleting the workspace deletes all of them.

The Delivery page shows the 30-day count. Run these from `apps/api` with the deployment configured:

```sh
# 30-day counts, the open backlog and a sample of open rows (no addresses)
npx convex run webhooks/unresolvedFeedback:status

# After a repair wrote missing provider ids back: replay every open row
npx convex run webhooks/unresolvedFeedback:replayOpen

# Replay one row now
npx convex run webhooks/unresolvedFeedback:replay '{"feedbackId": "<id>"}'
```

## System health and in-app self-update (updater sidecar)

The **System & Updates** page (`/dashboard/admin/system`, platform-admin only) surfaces the current version, container health, the GitHub release check, the update flow, and update history.

### Update check

`apps/api/convex/systemUpdates.ts` polls the GitHub Releases API (`https://api.github.com/repos/wolvesdotink/owlat/releases/latest`), caches the result in a singleton `systemUpdates` row (`kind: 'latestCheck'`) with a 1-hour TTL, and computes `updateAvailable` by comparing the cached latest version to the running `OWLAT_VERSION`.

That `OWLAT_VERSION` is the Convex deployment's own environment variable, not the one in `.env`. Setup writes it, and the `convex-deploy` container sets it to its image's release after every successful function deploy (`docker/convex-deploy.sh`), so the in-app update, `owlat upgrade` and a manual `docker compose --profile deploy run --rm convex-deploy` all move it. A failed deploy leaves it unchanged.

| Function | Kind | Notes |
| --- | --- | --- |
| `checkForUpdates` | Action | Admin-gated; honours the 1-hour cache unless `force: true`; returns cache on GitHub 403/429 rate-limit |
| `getLatestRelease` | Query | Reads the cached latest-check row |
| `listUpdateHistory` | Query | Lists `kind: 'updateRun'` rows (most recent first; capped at 200) |

A local build reporting `OWLAT_VERSION=dev` (or a non-semver value) is always treated as "no update available", because Owlat cannot tell whether a dev build is ahead of or behind the release tag.

### Applying an update

Clicking **Update now** posts to the Nitro route `apps/web/server/api/system/update.post.ts`, which:

::steps

### Verify the caller

The route re-checks platform-admin status via the session cookie, and requires `INSTANCE_SECRET` to be configured.

### Download and verify the pinned compose file

It fetches `docker-compose-<version>.yml` and its `.sha256` manifest from the GitHub Release, verifies the SHA-256 hash, and confirms the body references `ghcr.io/wolvesdotink/web:<version>`. A hash mismatch aborts the update.

### Record the attempt

It records an `updateRun` row via `recordUpdateStart`, capturing `versionFrom`/`versionTo`. The actor is stamped from the admin's session inside Convex, not passed in. Recording is best-effort: if the write fails, the update still goes ahead — an operator reaching for **Update now** is often reaching for it because something is unwell, and the audit row must not be what stops the fix.

### Dispatch to the updater sidecar

It POSTs the verified compose template to `http://updater:3200/update` with the `X-Instance-Secret` header.

### Record the outcome

It records `recordUpdateFinish` with `success`/`failed` and the step output. Both record mutations also emit a structured JSON log line for external log sinks.

::

### The updater sidecar

The updater (`apps/updater/src/index.ts`, image `ghcr.io/wolvesdotink/updater`, listening on port 3200, exposed only on an internal docker network (no host port mapping) so only the web container can reach it via `http://updater:3200`) is the only component that touches Docker. It authenticates every request with a timing-safe `X-Instance-Secret` compare and reaches Docker through a least-privilege socket proxy (it can pull/recreate/list containers but not exec, build, or touch volumes).

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/update` | POST | Validate the compose template against an image allowlist + dangerous-mount/privileged-mode rules, write it, `docker compose pull`, run a one-shot `convex-deploy` (function deploy *before* restart — a bad schema aborts here and the old containers keep serving), move `.env`'s `OWLAT_VERSION` pin to the version the template names (so the recreated containers report the release they are actually running), then `docker compose up -d`, then wait (bounded, following each service's declared healthcheck cadence) for every started service to pass the readiness check; a service already failing before the update is reported under `warnings`. The answer's `rollout` field is `healthy`, `started` (running but not ready in time) or `partially-applied` (`up` failed and the stack was started forward again); `success: true` only for `healthy`. `/update`, `/apply-profiles` and `/rotate-env` share one lock: while one runs, the others answer `409` |
| `/health` | GET | Per-service container state, image tag, and health, plus the configured `OWLAT_VERSION` read from `.env` (`configuredVersion`) and a derived `versionDrift` verdict — `version` alone is the *running* value, so both are needed to tell that `.env` moved on and the containers did not; `lastRollout` carries the last update's phase and verdict, `rolloutInProgress` the rollout running now (auth-required to prevent enumeration) |
| `/apply-profiles` | POST | Derive the compose profiles from a posted feature-flag snapshot (flags in, profiles never), converge `.env`'s `COMPOSE_PROFILES` + the compose override + the CLI flag mirror, then `docker compose up -d` |
| `/profile-state` | GET | Read-only: the applied `COMPOSE_PROFILES`, the delivery provider from `.env`, and per-service `compose ps` state — the durable source for the "services out of sync" banner |
| `/configure-ip` | POST | Attach/detach a floating IPv4 to `eth0` and the campaign IP pool, then restart the MTA |
| `/rotate-env` | POST | Rewrite rotated secrets in `.env` and force-recreate containers (requires all secret fields; tightest rate limit) |

The System & Updates page reads `/health` (proxied by `apps/web/server/api/internal/updater-health.get.ts`) to render the container-health table. The `convex-deploy`-before-restart ordering is the safety property: an incompatible schema fails the deploy step and the running Web/MTA containers are never restarted against a half-deployed backend.

::callout{type="warning" title="Operator-provided distribution"}
The in-app updater applies images and compose templates from the GitHub Release pipeline; it is the supported self-update path. The *desktop* app's auto-update key is an empty placeholder, so desktop auto-update is not production-ready and desktop distribution is operator-provided — see [Desktop App](/guide/desktop-app).
::

For the operator-facing update playbook (rollback, recovery, automation), see [Maintenance & Updates](/developer/self-hosting-maintenance).

## Dev-mode endpoints, crons, and migrations

### Dev-mode endpoints

A small set of destructive shortcuts exist for local development. They are **fail-closed**: the guard in `apps/api/convex/devShortcuts/_guard.ts` treats the deployment as production unless the operator explicitly sets `OWLAT_DEV_MODE=true` in the Convex backend runtime env (`npx convex env set OWLAT_DEV_MODE true`). The CLI-side `CONVEX_DEPLOYMENT` env var is *not* propagated into the function runtime, so it cannot be used as a security boundary.

| Endpoint | Guard | Purpose |
| --- | --- | --- |
| `POST /dev/reset` | `OWLAT_DEV_MODE` + `X-Instance-Secret` | Wipe the instance back to a blank slate (tenant tables, BetterAuth tables, and local auth tables) so the signup flow can be re-exercised without `docker compose down -v`; idempotent |
| `POST /seed/demo` | `OWLAT_DEV_MODE` + `X-Instance-Secret` | Seed realistic demo content (idempotent) |
| `forceVerifyDomain` | `OWLAT_DEV_MODE` + `organization:manage` | Force a domain to `verified` with synthesised DNS results, bypassing live DNS lookups |

::callout{type="danger" title="Never enable OWLAT_DEV_MODE in production"}
`/dev/reset` deletes everything tenant-side — not just seed-tagged rows. Leave `OWLAT_DEV_MODE` unset on any deployment that holds real data.
::

Wanting demo content is not a reason to enable it. `POST /sample-data/{install,remove,status}` (`apps/api/convex/sampleData/`) seeds the same dataset minus the dummy sign-ins and mailboxes, is authenticated with `X-Instance-Secret` alone, and removes exactly what it inserted (`seedTag`-scoped, re-checked inside the delete transaction). Drive it with `owlat sample-data <install|remove|status>`.

### Crons

Scheduled jobs are registered in `apps/api/convex/crons.ts`. Operationally relevant ones include:

| Cron | Interval | Job |
| --- | --- | --- |
| process scheduled campaigns | 1 min | Backup dispatch for campaigns whose `scheduledAt` has passed |
| reconcile sending campaigns | 1 min | Advance `sending → sent` when no queued sends remain |
| replay failed send completions | 10 min | Replay recorded send completions that threw (see [Send completions that failed](#send-completions-that-failed)) |
| purge send completion failures | 24 h | Delete resolved completion records after 30 days and exhausted ones after 90 |
| sweep lost sends | 1 h | Fail queued Sends with no provider id a day past their delivery deadline (see [Sends no completion reached](#sends-no-completion-reached)) |
| process account deletions | 24 h | Process accounts past their 30-day grace period |
| recover workspace deletion | 10 min | Restart a workspace deletion job whose chain went quiet, or re-arm a failed one after an hour |
| cleanup webhook logs | weekly | Remove delivery logs older than 30 days |
| replay unresolved feedback | 10 min | Retry bounces and complaints that matched no send (see [Bounces and complaints that match no send](#bounces-and-complaints-that-match-no-send)) |
| retention: unresolved feedback | 24 h | Delete those rows 90 days after they were first seen |
| cleanup sending reputation | 1 h | Age out reputation buckets older than 60 days (both scopes) |
| cleanup soft-deleted contacts | 24 h | Permanently delete contacts past their 30-day retention |
| knowledge graph maintenance | 24 h | Confidence decay + expiry cleanup |
| knowledge backfill stale sweep | 24 h | Mark knowledge backfill jobs still `running` but untouched for over an hour as `failed` |
| channel health checks | 5 min | Probe channel connectivity |
| agent metrics rollup | 5 min | Compute queue depth/latency/error rates and evaluate circuit breakers |
| report analytics | 15 min | Report instance analytics to the control plane |

Counter-reconciliation crons (`reconcile contact counts`, `reconcile topic member counts`, `refresh segment counts`, `reconcile transactional send counts`) keep denormalized counters honest against any drift from partial failures.

### Migrations

Schema and data migrations are numbered internal functions under `apps/api/convex/migrations/` (`NNNN_name.ts`), each exporting `run`. Most are internal actions that page through a table and call one bounded internal mutation per page; each is **idempotent**, so re-running it after an interruption, or after it has finished, is safe.

Nothing runs them automatically, with one exception: a cron starts and resumes `0054_backfill_folder_membership` by itself, because until it completes, the IMAP server reads every folder it has not reached in full, on every command that names messages. The updater deploys the new functions and recreates the containers, and that is all. When a release needs a migration, its release notes say so, and the operator runs it by name through the Convex CLI:

```sh
npx convex run migrations/0038_rebuild_file_search_text:run
```

[Maintenance & Updates](/developer/self-hosting-maintenance) shows how such a note reads (the chat attachment privacy migration).

### Release data compatibility

A self-hosted deployment updates in place, over the data the previous release wrote. The updater runs `convex-deploy` against the live backend first and recreates the web, MTA and worker containers after it (`apps/updater/src/update.ts`). Between those two steps, and for as long as an old browser tab or desktop client stays open, the previous release's clients and workers call the new functions. The full contract lives in `apps/api/convex/CONVENTIONS.md` ("Release data compatibility"). In short:

- **Upgrade window.** Release N upgrades a deployment on N-1 with no step beyond its migration manifest. Skipping releases works across additive releases. A release whose migration a later cleanup depends on is a stepping stone, and the later release's notes name it. Going back to N-1 by redeploying its functions works only until N writes data N-1's schema rejects; after that, restore the pre-update backup.
- **Expand, migrate, contract.** An incompatible data change ships over at least two releases: add the new shape next to the old one, migrate the rows, and remove the old shape only in a later release, once the migration has completed.
- **Old clients against new functions.** New function arguments are optional, and no argument or result field that the previous release uses is removed or changes meaning in the same release.
- **Migration manifest, progress and recovery.** A release that needs data work lists each migration, whether it must finish before users return, and what depends on it. Migrations page through tables in bounded, resumable steps, record their progress and completion in the database, fail loudly on rows they cannot map, and can be re-run safely. Take a backup before every update.

Migrations from `0053_project_open_commitments` on record their cursor, counts and completion in the `migrationRuns` ledger (`apps/api/convex/schema/migrationRuns.ts`, written through `lib/migrationLedger.ts`). A contract step or a stepping-stone check reads `status` and `completedAt` there instead of trusting a log line. Older migrations predate the ledger and leave no row in it. One part is not built yet. The updater does not run migrations, so the release notes are the manifest.

`apps/api/convex/__tests__/schemaCompat/compat.test.ts` enforces the schema half. It builds rows from the previous release's table validators and fails any change that the stored rows would not survive: an optional field made required, a type changed, a union narrowed, a field or table dropped. The snapshot is refreshed at each release (`bun run --cwd apps/api schema-compat:refresh`). The guard does not upgrade a real previous-release dataset. The release E2E does not do that either: its `seeded` leg carries Redis and ClamAV volumes over from the previous release, not Convex data.

::callout{type="warning" title="Open decision: when reset-based development ends"}
Owlat is pre-1.0, and a release may still reset specific tables if its release notes say so. The release from which a reset stops being an acceptable upgrade path has not been decided. Until it is, treat released data as data that must survive: follow the contract above, and reset only where a release's notes say so. `/dev/reset` and reseeding remain for development deployments (`OWLAT_DEV_MODE`), never for released data.
::
