# UI localization — adding a language

Owlat has two independent translation systems. Do not confuse them:

| System | What it translates | Where it lives |
| --- | --- | --- |
| **Email content translations** | The campaigns, templates and blocks *you send* | Per-workspace, stored in Convex — see [Translations in the product guide](/guide/translations) |
| **UI localization** (this page) | The Owlat interface *your team and your recipients read* | `apps/web/i18n/locales/*.json`, shipped with the app |

The UI layer is [`@nuxtjs/i18n`](https://i18n.nuxtjs.org). `en` is the default locale and the fallback for every other one, so an untranslated key renders its English text rather than a raw key path.

## Where things live

```
apps/web/
├── nuxt.config.ts          # the `i18n` block: locale list, strategy
└── i18n/
    ├── i18n.config.ts      # vue-i18n runtime options (fallbackLocale, warnings)
    └── locales/
        ├── en.json         # source of truth
        └── de.json         # a translation
```

Locale files are **lazy-loaded**: a visitor downloads only the catalog for the locale they are actually shown.

Routes are **not** prefixed (`strategy: 'no_prefix'`). Every Owlat URL is either a dashboard route or a token link that was already printed inside a sent email (`/unsubscribe?token=…`), so a `/de/` segment would break live links.

## Adding a locale

1. **Copy the source catalog.**

   ```sh
   cp apps/web/i18n/locales/en.json apps/web/i18n/locales/fr.json
   ```

2. **Register it** in `apps/web/nuxt.config.ts`:

   ```ts
   locales: [
     { code: 'en', language: 'en-US', name: 'English', file: 'en.json' },
     { code: 'de', language: 'de-DE', name: 'Deutsch', file: 'de.json' },
     { code: 'fr', language: 'fr-FR', name: 'Français', file: 'fr.json' },
   ],
   ```

   `code` is the identifier the app switches on, `language` is the BCP 47 tag written into `lang`/`hreflang`, and `name` is what a language picker shows.

3. **Translate the values, never the keys.** Keep the object shape identical to `en.json` — the catalog guard test compares the two key sets and fails on a missing or invented key.

4. **Run the guards.**

   ```sh
   cd apps/web && npx vitest run app/__tests__/localeCatalogs.test.ts
   ```

   This checks, for every locale: full key coverage against `en`, identical placeholder names per message, no markup, and no unescaped `@`.

5. **Check the long strings in the UI.** German and French run 20–35% longer than English; buttons, switch rows and card headers are where that shows first.

### Pick a register and hold it

Each locale should read as one voice. The shipped `de` catalog uses formal *Sie* throughout, because the most-read surfaces (unsubscribe, preference centre, double opt-in) are read by strangers who never chose Owlat. Follow the existing catalog rather than the habits of one file.

## Writing translatable strings

**Every visible string goes through `t()`.** Import it once per component:

```vue
<script setup lang="ts">
const { t } = useI18n();
</script>

<template>
  <p>{{ t('recipient.preferences.noTopics') }}</p>
</template>
```

Script-side strings — validation messages, error copy, `useBackendOperation` labels, `useHead`/`useSeoMeta` titles — go through the same `t()`.

**Anything captured once at setup takes a getter, not a value.** A bare `t('…')` in an options object is evaluated while the component is being set up and then frozen there, so it keeps the locale that happened to be active at mount. `useHead`/`useSeoMeta` and `useBackendOperation`'s `label` all accept `() => t('…')` and read it when they actually use it:

```ts
useHead({ title: () => t('auth.login.pageTitle') });

const { run } = useBackendOperation(api.auth.userProfiles.create, {
  label: () => t('auth.register.createProfileOperation'),
});
```

**Interpolate values, never concatenate sentences.** Word order differs per language, so a string split into a prefix and a suffix around a value is untranslatable:

```json
{ "intro": "Update your email preferences for {organization}." }
```

**When part of a sentence carries markup, use `<I18nT>` with a named slot** — not `v-html`, which would render an unescaped contact name or organization name straight into the page:

```vue
<I18nT keypath="recipient.preferences.intro" tag="span" scope="global">
  <template #organization><strong>{{ contactInfo.teamName }}</strong></template>
</I18nT>
```

**Escape a literal `@`.** The message compiler reads `@` as a linked-message marker, so an email placeholder is written `you{'@'}example.com`.

**No HTML in message values.** `compilation.strictMessage` rejects it at build time, so a smuggled `<strong>` is a failed build rather than a broken string.

**Format dates and numbers against the active locale**, not a pinned one:

```ts
const { t, locale } = useI18n();
new Intl.DateTimeFormat(locale.value, { dateStyle: 'long' }).format(sentAt);
```

## What is extracted so far

Extraction is landing surface by surface. A surface is either fully extracted or untouched — a half-extracted page produces a sentence in two languages.

| Surface | Files | State |
| --- | --- | --- |
| Auth | `auth/login.vue`, `auth/register.vue`, `auth/forgot-password.vue`, `auth/reset-password.vue` | Extracted |
| Welcome / onboarding | `welcome.vue`, `components/onboarding/FreshStart.vue`, `components/postbox/PostboxMailboxGuard.vue` | Extracted |
| Recipient-facing pages | `archive.vue`, `share.vue`, `unsubscribe.vue`, `confirm.vue`, `preferences.vue` | Catalog only — the `recipient.*` messages, and the `common.poweredBy` footer they share, ship here; the pages are switched over by the responsive recipient work later in the same stack |

The mailbox guard is listed under onboarding because the fresh-start screen embeds it: it is a whole-screen empty state of its own, so extracting it keeps that screen from being half-translated even though the Postbox pages around it are not extracted yet.

Everything else — the dashboard, settings, Postbox, the admin surfaces — is still hardcoded English.

Because of that, **browser-language detection is deliberately off** (`detectBrowserLanguage: false` in `nuxt.config.ts`). Auto-switching a German visitor today would hand them a page that is German at the top and English below it. Turn it on in the same commit that finishes dashboard extraction:

```ts
detectBrowserLanguage: { useCookie: true, cookieKey: 'owlat-locale' },
```

The same milestone is when the app needs a language picker and a `<html lang>` that follows the active locale — today `app.head.htmlAttrs.lang` is pinned to `en`.
