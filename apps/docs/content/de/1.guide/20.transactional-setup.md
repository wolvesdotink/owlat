Transaktionale E-Mails werden durch eine Benutzeraktion ausgelöst — ein Passwort-Reset, eine Bestellbestätigung, eine Willkommensnachricht nach der Registrierung. Anders als Marketing-Kampagnen gehen sie an einen einzelnen Empfänger zu einem bestimmten Zeitpunkt, und die Empfänger erwarten sie sofort. Diese Anleitung führt durch das Erstellen einer transaktionalen E-Mail, das Erzeugen eines API-Keys und den Versand aus deiner Anwendung.

Für den konzeptionellen Überblick (transaktional vs. Marketing, Slugs, Anhänge, Monitoring) siehe [Transaktionale E-Mails](/guide/transactional). Diese Seite konzentriert sich auf die Integrationsschritte.

Häufige Beispiele:

- Links zum Zurücksetzen des Passworts
- Willkommens-E-Mails nach der Registrierung
- Bestellbestätigungen und Belege
- Versandbenachrichtigungen
- E-Mails zur Kontoverifizierung

## Eine transaktionale E-Mail erstellen

Transaktionale E-Mails sind eine eigenständige Entität, getrennt von Marketing-Vorlagen — jede hat einen eindeutigen **Slug**, den deine Anwendung beim Versand referenziert.

::steps

### Mail > Transaktional öffnen

Geh in deinem Dashboard zu **Mail > Transaktional**. Die Listenseite (Titel „Transaktionale E-Mails“) zeigt alles, was du angelegt hast.

### Die E-Mail anlegen

Klicke auf **Neue transaktionale E-Mail**. Gib im Dialog einen **Namen** (z. B. „Bestellbestätigung“) und einen eindeutigen **Slug** (z. B. `order-confirmation`) ein. Der Slug besteht aus Kleinbuchstaben, Ziffern und Bindestrichen und ist die Kennung, über die dein Code bestimmt, welche E-Mail versendet wird — wähle ihn sorgfältig und ändere ihn nicht mehr, sobald er im Einsatz ist.

### Den Inhalt gestalten

Du gelangst in den E-Mail-Editor. Baue das Layout genauso auf wie bei jeder anderen [E-Mail](/guide/email-editor). Überall dort, wo du dynamische Inhalte benötigst, fügst du mit dem **Befehl `/var`** eine Datenvariable ein — zum Beispiel eine Variable `customerName`, `orderNumber` oder `total`. Die Werte für diese Variablen lieferst du beim Versand.

### Veröffentlichen

Eine transaktionale E-Mail muss **veröffentlicht** sein, bevor sie versendet werden kann. Klicke im Editor auf **Veröffentlichen**. Bis dahin werden Sendeanfragen abgelehnt (siehe [Fehlerbehandlung](#fehlerbehandlung)). Wenn der Content-Scanner die E-Mail markiert, wechselt sie in den Zustand **Prüfung ausstehend**, statt sofort live zu gehen.

::

::callout{type="tip"}
Verwende sprechende Variablennamen wie `orderNumber` statt generischer wie `var1`. Das macht deine API-Aufrufe selbsterklärend und leichter zu debuggen. Im gerenderten HTML werden daraus `{{orderNumber}}`-Platzhalter, aber du tippst die geschweiften Klammern nie selbst — der Befehl `/var` fügt sie für dich ein.
::

::callout{type="info"}
Jede transaktionale E-Mail geht vom **Standardabsender** raus, den du unter **Einstellungen > Allgemein** festlegst (Route `/dashboard/admin/instance/general`), und diese Adresse muss auf einer verifizierten Versanddomain liegen. Fehlt sie, wird jede Sendeanfrage mit `422` abgelehnt. Oben auf **Mail > Transaktional** siehst du, ob Transaktionsmails gerade raus können und was du sonst beheben musst.
::

## Einen API-Key erzeugen

Für transaktionale Sendevorgänge benötigst du einen API-Key zur Authentifizierung.

::steps

### Einstellungen > API öffnen

Geh in deinem Dashboard zu **Einstellungen > API** (Route `/dashboard/admin/team/api`). Die Verwaltung von API-Keys steht Eigentümern und Administratoren der Organisation zur Verfügung.

### Den Key erstellen

Klicke auf **API-Key erstellen** und vergib einen sprechenden Namen (z. B. „Production“) sowie **mindestens einen Scope**. Keys folgen dem Prinzip der minimalen Rechte — für transaktionale Sendevorgänge wählst du `transactional:send`. (Weitere verfügbare Scopes: `contacts:read`, `contacts:write`, `events:write`, `topics:write`.)

### Den Key kopieren

Kopiere den erzeugten Key. Er beginnt mit `lm_live_` und wird nur ein einziges Mal angezeigt.

::

::callout{type="warning" title="Halte deinen Key geheim"}
Ein Owlat-API-Key trägt nur die Scopes, die du ihm gewährst — ein transaktionaler Versand benötigt `transactional:send`. Behandle ihn wie ein Passwort: Speichere ihn in einer Umgebungsvariablen oder einem Secrets-Manager, committe ihn nie in die Versionskontrolle und gib ihn niemals in clientseitigem Code preis. Der Key wird ausschließlich bei der Erstellung angezeigt.
::

## Versand über das TypeScript-SDK

Installiere das Owlat-SDK und versende deine erste transaktionale E-Mail:

```typescript
import { Owlat } from '@owlat/sdk-js'

const owlat = new Owlat({
  apiKey: 'lm_live_...',
  // Your deployment's API URL, the same host as in the cURL example below
  baseUrl: 'https://your-deployment.convex.site',
})

const result = await owlat.transactional.send(
  {
    email: 'user@example.com',
    slug: 'order-confirmation',
    dataVariables: {
      orderNumber: '#12345',
      customerName: 'Jane',
      total: '$49.99',
    },
  },
  // Makes the call safe to retry: one key, at most one email
  { idempotencyKey: 'order-12345-confirmation' }
)

// result.transactionalEmailId — the send id; webhooks carry it as sendId
```

Das SDK übernimmt Authentifizierung, Serialisierung und Fehlerbehandlung für dich. Übergib im Objekt `dataVariables` alle Datenvariablen, die deine E-Mail erwartet. Du kannst eine E-Mail über `slug` oder über `transactionalId` adressieren. Setze `baseUrl` auf dein eigenes Deployment: Ohne die Angabe ruft das SDK die gehostete Owlat-API auf, bei der dein Key nicht gültig ist.

## Versand über das Java-SDK

```java
Owlat owlat = new Owlat(OwlatConfig.builder("lm_live_...")
    // Your deployment's API URL, the same host as in the cURL example below
    .baseUrl("https://your-deployment.convex.site")
    .build());

owlat.transactional().send(
    SendTransactionalParams.builder("user@example.com")
        .slug("order-confirmation")
        .dataVariables(Map.of(
            "orderNumber", "#12345",
            "customerName", "Jane",
            "total", "$49.99"
        ))
        .build(),
    // Makes the call safe to retry: one key, at most one email
    RequestOptions.idempotencyKey("order-12345-confirmation")
);
```

Der Builder nimmt die Empfängeradresse als einziges Positionsargument entgegen; den Slug setzt du mit `.slug(...)` und alle Variablen übergibst du auf einmal mit `.dataVariables(Map)`.

## Versand über cURL

Wenn du die API lieber direkt aufrufst:

```bash
curl -X POST https://your-deployment.convex.site/api/v1/transactional \
  -H "Authorization: Bearer lm_live_..." \
  -H "Content-Type: application/json" \
  -d '{
    "slug": "order-confirmation",
    "email": "user@example.com",
    "dataVariables": {
      "orderNumber": "#12345",
      "customerName": "Jane",
      "total": "$49.99"
    }
  }'
```

Eine erfolgreiche Anfrage liefert den Status **`202 Accepted`** — die E-Mail wird zur Zustellung eingereiht, nicht synchron versendet. Der Response-Body enthält:

| Feld | Beschreibung |
|---|---|
| `status` | Bei Erfolg immer `"queued"` |
| `transactionalEmailId` | Die ID der Sendung. Jeder `email.*`-[Webhook](/api/webhooks) dafür trägt diese ID als `sendId`, und `GET /api/v1/transactional/{sendId}` liest ihren Status |
| `email` | Die Empfängeradresse |
| `slug` | Der Slug der E-Mail, auch wenn du sie per `transactionalId` adressiert hast |
| `contactId` | Der zugehörige Kontakt (gefunden oder angelegt) |
| `contactCreated` | `true`, wenn für diesen Empfänger ein neuer Kontakt angelegt wurde |
| `language` | Die für den Versand verwendete Sprache |

## API-Code im Dashboard ansehen

Du musst den Aufruf nicht von Hand schreiben. In der Liste **Transaktional** hat jede E-Mail die Aktion **API-Code anzeigen** (das Symbol `< >`, ebenfalls im Menü der Zeile), die einen fertigen Sende-Codeausschnitt in cURL, JavaScript und Python öffnet — bereits mit dem Slug der E-Mail vorbelegt. Kopieren, deinen API-Key einsetzen, und schon versendest du.

## Fehlerbehandlung

Schlägt ein transaktionaler Versand fehl, gibt die API einen der unten aufgeführten kategorisierten Status zurück. Richte deine Retry-Logik am Statuscode aus, nicht am Meldungstext.

| Status | Bedeutung | Häufige Ursachen |
|---|---|---|
| `400` | Ungültige Eingabe | Fehlerhaftes Payload, fehlendes `email`/`slug`, eine Datenvariable, deren Wert nicht dem an der E-Mail deklarierten Typ entspricht, oder eine Variable, die die E-Mail ohne Fallback-Wert verwendet und die in der Anfrage fehlt oder `null` ist |
| `401` | Nicht authentifiziert | Fehlender oder ungültiger API-Key |
| `403` | Verboten | Das Konto wurde gesperrt, oder dem API-Key fehlt der erforderliche Scope (`transactional:send`) |
| `404` | Nicht gefunden | Keine transaktionale E-Mail passt zum angegebenen Slug oder zur angegebenen ID |
| `422` | Ungültiger Zustand | Die E-Mail ist nicht veröffentlicht, hat keinen Inhalt, die Versanddomain ist nicht verifiziert, oder der Empfänger ist blockiert (früherer Bounce/frühere Beschwerde) |
| `429` | Ratenbegrenzt | Mehr als 10 Anfragen/Sekunde auf diesem Key, mehr als 5 Sends einer E-Mail an eine Adresse pro Stunde oder das Tageslimit des Keys — `Retry-After` abwarten und erneut versuchen ([Limits](/api#rate-limits)) |
| `500` | Serverfehler | Nach kurzer Wartezeit erneut versuchen |

::callout{type="warning"}
Eine fehlende oder falsch typisierte Datenvariable ergibt einen **`400`**, keinen `422` — `422` ist Zustandsproblemen wie einer unveröffentlichten E-Mail oder einer unverifizierten Domain vorbehalten. Verschlucke Sendefehler nicht stillschweigend: Protokolliere Fehlschläge und alarmiere dein Team. Eine fehlgeschlagene Passwort-Reset-E-Mail bedeutet einen ausgesperrten Benutzer.
::

Bei den Fehlern `429` und `500` und bei einer Anfrage, die in einen Timeout gelaufen ist, wiederholst du mit exponentiellem Backoff. Sende bei jedem Versand, den du womöglich wiederholst, einen `Idempotency-Key`-Header (die Option `idempotencyKey` der SDKs): Ein `500` oder ein Timeout kann kommen, nachdem die E-Mail schon eingereiht wurde, und ohne den Schlüssel reiht die Wiederholung eine zweite ein. Mit dem Schlüssel liefert eine Wiederholung innerhalb von 24 Stunden die erste Antwort und sendet nichts. Siehe [Idempotente Wiederholungen](/api/transactional#idempotente-wiederholungen).

Ein `202` heißt, dass die E-Mail eingereiht wurde, nicht, dass sie zugestellt ist. Um von einer E-Mail zu erfahren, die später fehlschlägt (der Dienst lehnt sie ab oder die Zustellung bleibt über ihre viertägige Frist hinaus pausiert), abonniere mit einem [Webhook](/api/webhooks) `email.failed` und ordne ihn über `sendId` zu, oder lies die Sendung mit `GET /api/v1/transactional/{sendId}`.
