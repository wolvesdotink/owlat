Transaktionale E-Mails sind Eins-zu-eins-Nachrichten, die von deiner Anwendung ausgelöst werden — etwa Passwort-Resets, Bestellbestätigungen, Willkommens-E-Mails oder Kontobenachrichtigungen. Anders als Marketing-Kampagnen, die an ein Thema oder Segment gehen, werden transaktionale E-Mails an einen bestimmten Kontakt als Reaktion auf eine von ihm ausgeführte Aktion versendet.

::callout{type="info" title="Erfordert einen Zustellanbieter"}
Transaktionale E-Mails werden über einen Zustellanbieter versendet (den eingebauten MTA, Resend oder SES) und benötigen eine verifizierte Sendedomain. In einem reinen IMAP-Deployment ist das **nicht** verfügbar — ein verbundenes externes Postfach versendet persönliche 1:1-Antworten, keine transaktionale API-Mail. Siehe [Betriebsmodi](/guide/operating-modes).
::

## Transaktionale vs. Marketing-E-Mails

|                     | Transaktional                                          | Marketing                          |
| ------------------- | ------------------------------------------------------ | ---------------------------------- |
| **Ausgelöst durch** | Ein Ereignis in deiner Anwendung                       | Du selbst, über eine Kampagne      |
| **Gesendet an**     | Einen einzelnen Kontakt                                | Ein Thema oder Segment             |
| **Inhalt**          | Mit dynamischen Daten personalisiert                   | Gleicher Inhalt für alle Empfänger |
| **Abmeldung**       | Nicht erforderlich (der Empfänger erwartet die E-Mail) | Muss einen Abmeldelink enthalten   |
| **Beispiele**       | Passwort-Reset, Bestellbestätigung, Willkommens-E-Mail | Newsletter, Produkt-Launch, Aktion |

## Transaktionale Vorlagen anlegen

1. Öffne **Versand > Transaktional**.
2. Klicke auf **Neue transaktionale E-Mail**.
3. Gib im Dialog **Transaktionale E-Mail erstellen** einen **Namen** und einen **Slug** ein — der Slug ist eine kurze, eindeutige Kennung, die du beim Versand referenzierst (z. B. „welcome-email“ oder „password-reset“).
4. Klicke auf **Erstellen & bearbeiten**, um die Vorlage im [E-Mail-Editor](/guide/email-editor) zu öffnen.
5. Trag über dem Inhalt den **Betreff** ein und bei Bedarf die Zeile **Vorschau**: den Text, den ein Posteingang neben dem Betreff zeigt. Beide können deine Datenvariablen verwenden, etwa `{{orderNumber}}`. Der Vorschautext bleibt in der E-Mail selbst unsichtbar und fehlt in der Nur-Text-Version.
6. Baue deinen E-Mail-Inhalt und speichere deine Arbeit.
7. **Veröffentliche die Vorlage.** Neue Vorlagen starten als _Entwurf_, und die Sende-API versendet einen Entwurf **nicht**. Nutze die Aktion **Veröffentlichen** im Editor, um sie versandfähig zu machen — eine nicht veröffentlichte oder leere Vorlage wird beim Versand abgewiesen (siehe [Veröffentlichung](#veröffentlichung-und-prüfung)).

### Slugs

Der Slug ist der Weg, über den deine Anwendung erkennt, welche Vorlage versendet werden soll. Wähle etwas Beschreibendes und Stabiles:

- „welcome-email“ — für die Registrierung neuer Nutzer
- „password-reset“ — für die Passwortwiederherstellung
- „order-confirmation“ — für Kaufbelege

::callout{type="tip"}
Behandle Slugs wie API-Kennungen — wähle sie sorgfältig und ändere sie nicht mehr, sobald sie im Einsatz sind, da dein Anwendungscode sie direkt referenziert.
::

## Veröffentlichung und Prüfung

Eine transaktionale Vorlage durchläuft drei Zustände:

| Status                 | Was er bedeutet                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Entwurf**            | Die Voreinstellung für eine neue oder bearbeitete Vorlage. Nicht versandfähig.                                                                        |
| **Prüfung ausstehend** | Der Inhaltsscanner hat die Vorlage beim Veröffentlichen markiert. Zurückgehalten, bis eine Administration sie freigibt; weiterhin nicht versandfähig. |
| **Veröffentlicht**     | Live und über die API versandfähig.                                                                                                                   |

Eine Vorlage **muss veröffentlicht sein**, bevor die API sie versendet. Rufst du den Sende-Endpunkt mit einer nicht veröffentlichten Vorlage auf, wird die Anfrage abgewiesen (`template_not_published`); eine veröffentlichte Vorlage ohne gerendertes HTML wird ebenfalls abgewiesen (`template_no_content`). Einen Entwurf zu veröffentlichen ist die mit Abstand häufigste Lösung, wenn ein transaktionaler Versand nicht rausgeht.

Wenn du im Editor auf **Veröffentlichen** klickst, prüft der Inhaltsscanner Betreff, Vorschautext und HTML. Stuft er den Inhalt als verdächtig ein, landet die Vorlage in **Prüfung ausstehend**, statt live zu gehen — sie bleibt unversendbar, bis eine Administration sie freigibt. Schwer beanstandete Inhalte werden vollständig blockiert und lassen sich gar nicht veröffentlichen. Mit **Veröffentlichung zurücknehmen** setzt du eine Live-Vorlage für Bearbeitungen zurück in den Entwurf.

Die Liste der transaktionalen Vorlagen und ihr Statusfilter bezeichnen genau diesen Zustand als **Prüfung ausstehend**, während der Editor ihn **Wartet auf Prüfung** nennt — beides meint denselben zurückgehaltenen Status.

::callout{type="warning" title="„Wartet auf Prüfung“ ist eine Admin-Schranke"}
Es gibt keine Aktion auf Autorenseite, um eine Vorlage aus **Wartet auf Prüfung** herauszubewegen — nur eine Administration kann sie freigeben (oder ablehnen). Bis dahin behandelt die Sende-API sie genauso wie einen Entwurf.
::

## Variablen

Transaktionale Vorlagen können dynamische Variablen enthalten, die mit Daten befüllt werden, die du beim Versand mitgibst. So bringst du Bestelldetails, Kontoinformationen oder beliebige für das auslösende Ereignis spezifische Daten unter.

Häufige Einsatzzwecke für Variablen:

- Kontaktfelder (Vorname, E-Mail)
- Eigene Daten, die beim Versand übergeben werden (Bestellsumme, Sendungsverfolgungslink, Reset-URL)
- Blöcke, die nur erscheinen, wenn eine Variable gesetzt ist oder einen bestimmten Wert hat
- Ein Block, der für jeden Eintrag einer Liste wiederholt wird, etwa Bestellpositionen

Füge Variablen im Editor ein, indem du `{{` oder `@` tippst, um die Variablenauswahl zu öffnen — genau wie in Marketing-Vorlagen.

### Einen Block nur manchmal zeigen

Die Einstellung **Bedingung** eines Blocks entscheidet bei jedem Versand anhand der `dataVariables` dieser Anfrage, ob der Block mitgeht. **Existiert** zeigt den Block, wenn die Anfrage die Variable mit einem Wert schickt, **Existiert nicht**, wenn nicht. **Gleich**, **Ungleich** und **Enthält** vergleichen den Wert als Text, also ist `5` gleich `"5"`.

Ein leerer String, `null` und eine Variable, die die Anfrage weglässt, existieren nicht. `false`, `0` und eine leere Liste existieren: Sie sind Werte. Prüfe sie mit **Gleich**. Die Textversion der E-Mail folgt denselben Bedingungen.

Eine Variable, die nur ein ausgeblendeter Block nutzt, ist für diesen Versand nicht erforderlich.

### Einen Block für eine Liste wiederholen

Leg in der E-Mail eine Variable vom Typ **Liste** an und setze unter **Wiederholen** des Blocks diese Variable. Der Block geht dann einmal pro Eintrag raus. Darin ist `{{item.name}}` das Feld `name` des Eintrags und `{{$index}}` seine Position, gezählt ab 0. Passt `item` nicht, änderst du den Namen unter **Wiederholen**.

```json
{
	"slug": "order-confirmation",
	"email": "customer@example.com",
	"dataVariables": {
		"items": [
			{ "name": "Zelt", "quantity": 1 },
			{ "name": "Kocher", "quantity": 2 }
		]
	}
}
```

Jeder Eintrag ist ein Objekt aus Strings, Zahlen, Booleans oder `null`, oder ein einzelner solcher Wert. Eine Liste hat höchstens 500 Einträge, und die E-Mail, die sie ergeben, darf höchstens 1.000.000 Zeichen lang sein. Mit einer leeren Liste geht die E-Mail ohne den Block raus. Eine Liste, die die E-Mail wiederholt, ist erforderlich, außer du markierst sie als optional.

Um beide Fassungen im Editor zu sehen, öffne die Vorschau und gib unter **Variablen** Beispielwerte ein. Der Beispielwert einer Liste ist ihr JSON, etwa `[{"name":"Zelt"}]`.

## Von welcher Adresse sie kommt

Transaktionsmails verwenden die erste dieser Adressen, die festgelegt ist:

1. Den eigenen Absender der Mail, festgelegt in ihrem Editor unter **Absender**.
2. Den **Transaktionsabsender**, festgelegt auf **Versand > Transaktional** mit **Ändern** neben **Sendet von**.
3. Den **Standardabsender** des Workspaces unter **Einstellungen > Allgemein**.

Gib Transaktionsmails einen eigenen Absender auf einer Subdomain wie `mail.example.com`. Postfachanbieter bewerten jeden Domainnamen für sich, deshalb bremsen Beschwerden über Newsletter von `news.example.com` keine Passwort-Resets von `mail.example.com` aus. Wenn unter deinen verifizierten Domains so eine Subdomain ist, schlägt Owlat sie als Transaktionsabsender vor.

Eine Änderung gilt ab der nächsten Sendung. Eine Sendung, die schon in der Warteschlange ist, behält die Adresse, die sie bekommen hat.

## Transaktionale E-Mails versenden

Transaktionale E-Mails werden über die API versendet. Deine Anwendung führt einen API-Aufruf aus und gibt dabei an:

- Den zu verwendenden **Vorlagen-Slug** (oder dessen `transactionalId`)
- Die **E-Mail-Adresse des Empfängers**
- Etwaige Vorlagenvariablen, übergeben als Objekt `dataVariables`

Details zum Endpunkt, das Anfrageformat und Codebeispiele findest du in der [API-Dokumentation](/api/transactional).

::callout{type="info"}
Transaktionale E-Mails umgehen die Marketing-Abonnementeinstellungen. Ein Kontakt, der sich von Marketing-E-Mails abgemeldet hat, erhält weiterhin transaktionale E-Mails, da es sich um erwartete, durch eine Aktion ausgelöste Nachrichten handelt.
::

## Sendungen überwachen

Verfolge die Zustellung deiner transaktionalen E-Mails im Dashboard:

- Sendestatus einzelner transaktionaler E-Mails einsehen
- Zustell- und Bounce-Raten überwachen
- Vorlagen erkennen, die Darstellungs- oder Zustellprobleme haben könnten

Ein Send behält die Datenvariablen, mit denen er verschickt wurde, noch einen Tag
nach dem Versand, damit du prüfen kannst, was ein frischer Send bekommen hat. Die
Werte sehen nur Inhaber und Admins; danach bleiben nur die Variablennamen.
Reset-Links und Anmeldetokens bleiben so nicht dauerhaft im Dashboard lesbar.

## Anhänge

Transaktionale E-Mails können Dateianhänge enthalten — nützlich für Rechnungen, Belege, Tickets oder jedes Dokument, das der Empfänger braucht.

### Anhänge im Dashboard hinzufügen

Nutze beim Konfigurieren einer transaktionalen Vorlage die Anhangsauswahl, um Dateien aus deiner [Medienbibliothek](/guide/media-library) zu wählen. Das ist praktisch für statische Anhänge, die sich nicht je Empfänger unterscheiden.

### Anhänge über die API hinzufügen

Für dynamische Anhänge übergibst du in deiner API-Anfrage ein Array `attachments`:

```json
{
	"slug": "order-confirmation",
	"email": "customer@example.com",
	"attachments": [
		{
			"filename": "invoice.pdf",
			"url": "https://example.com/invoices/12345.pdf",
			"contentType": "application/pdf"
		}
	]
}
```

Jeder Anhang kann den Dateiinhalt als Base64-String (`content`) oder als abzurufende URL (`url`) bereitstellen. Die vollständige Feldreferenz findest du in der Dokumentation zur [Transaktions-API](/api/transactional).

**Limits:** maximal 10 Anhänge, 10 MB Gesamtgröße.

## Bewährte Praktiken

- **Transaktionale E-Mails fokussiert halten** — nimm nur die Informationen auf, die der Empfänger braucht. Eine E-Mail zum Passwort-Reset sollte den Reset-Link enthalten, keine Werbespalte.
- **Mit echten Daten testen** — versende Test-E-Mails mit realistischen Variablenwerten, um sicherzugehen, dass deine Vorlage mit unterschiedlichen Daten korrekt umgeht (lange Namen, fehlende Felder usw.).
- **Fehlerbehandlung einrichten** — deine Anwendung sollte API-Fehler sauber abfangen. Schlägt der Versand einer transaktionalen E-Mail fehl, protokolliere den Fehler und erwäge eine Wiederholungsstrategie.
- **Klare Absendernamen verwenden** — transaktionale E-Mails sollten von einem wiedererkennbaren Absender kommen, damit Empfänger ihnen vertrauen und sie öffnen.
