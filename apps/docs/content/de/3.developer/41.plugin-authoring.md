Dies ist der Weg des Plugin-Autors vom leeren Verzeichnis bis zur Contribution, die in einem Deployment läuft. Ein Checkout des Owlat-Workspace wird vorausgesetzt; die Betreiberseite findest du unter [Installation & Betrieb](/developer/plugin-operations).

## 1. Das Paket scaffolden

```sh
bun run plugins:prepare     # build the plugin-kit contracts once
bun run owlat-plugins create hello-owlat --name @acme/owlat-plugin-hello-owlat
```

Ersetze `@acme` durch einen npm-Scope, in dem du veröffentlichen darfst. Schritt 6 veröffentlicht das Paket, und der Standardname `@owlat/plugin-<id>` liegt im Scope des Owlat-Projekts.

`owlat-plugins` ist die Plugin-CLI. Nach `bun install` gibt es sie in jedem Owlat-Checkout, und `bun run owlat-plugins` startet sie aus jedem Verzeichnis des Checkouts.

`create` schreibt ausschließlich Dateien — es installiert, importiert oder führt niemals etwas aus, ist bei erneutem Lauf idempotent, verweigert das Überschreiben einer Datei mit abweichendem Inhalt und rollt jede angelegte Datei und jedes angelegte Verzeichnis zurück, wenn ein Schreibvorgang fehlschlägt.

Standardwerte: Paketname `@owlat/plugin-<id>`, Verzeichnis `examples/plugins/<id>`. Überschreibe sie mit `--name` und `--dir`; eine Vorschau erhältst du mit `--dry-run`.

Willst du das Plugin in einem eigenen Repository führen, gib ein `--dir` außerhalb des Checkouts an, zum Beispiel `--dir ../hello-owlat`. Das Paket ist dann eigenständig: Es hängt von `@owlat/plugin-kit` aus npm in der Kit-Version des Checkouts ab (`^<version>`), seine `tsconfig.json` und `vitest.config.ts` zeigen nirgendwo anders hin, und sein `lint`-Skript startet `oxlint` aus den eigenen Dependencies. Führe vor Schritt 5 darin `bun install` aus. Schritt 6 beginnt für so ein Paket mit `bun publish` in seinem Ordner, und seine README listet die Befehle. Der Baum unten zeigt den Standard innerhalb des Checkouts.

```text
examples/plugins/hello-owlat/
├── package.json          # private, depends on @owlat/plugin-kit (workspace:*)
├── tsconfig.json         # extends the workspace base config
├── vitest.config.ts      # aliases @owlat/plugin-kit to its sources
├── README.md
└── src/
    ├── manifest.ts       # the definePlugin declaration
    ├── index.ts          # re-exports the manifest
    └── __tests__/manifest.test.ts
```

## 2. Das Manifest deklarieren

Das Manifest ist der gesamte Vertrag. Der Host leitet Berechtigungen, Feature-Flags, das Einstellungsformular und die generierte Komposition aus diesen Daten ab, **ohne Plugin-Code auszuführen** — halte es deshalb als statische, rein datenbasierte Deklaration.

```ts
import { definePlugin } from '@owlat/plugin-kit';

export const helloOwlatPlugin = definePlugin({
	id: 'hello-owlat',
	version: '0.1.0',
	capabilities: ['plugin-storage:read', 'plugin-storage:write'],
	// Storage capabilities REQUIRE a flag: access must be revocable at runtime.
	flag: { default: false },
});

export default helloOwlatPlugin;
```

`definePlugin` erhält die literale TypeScript-Inferenz und validiert zur Laufzeit; im Fehlerfall wird ein `PluginManifestError` mit einer Liste von `{ code, path, message }`-Issues geworfen. Für Tooling existieren zwei Geschwisterformen: `validatePluginManifest(value)` liefert `{ ok, manifest | issues }` und wirft nie, `parsePluginManifest(value)` wirft.

Die Validierung weist unbekannte Felder, Accessor-Properties, fehlerhafte Bezeichner, doppelte Capabilities oder Umgebungsvariablen, ungültige Budgets, unsichere Export-Pfade und unbekannte Contribution-Buckets zurück. Referenzen werden als **Daten** inspiziert und nie aufgerufen.

### Regeln, die der Validator durchsetzt

- Ein Contribution-Bucket erfordert sowohl seine Capability *als auch* ein explizites `flag`. Du kannst keine Contribution ausliefern, die ein Betreiber nicht abschalten kann.
- `plugin-storage:read` / `plugin-storage:write` erfordern aus demselben Grund ein explizites `flag`.
- `llm:invoke` erfordert ein explizites `flag` **und** ein gültiges `llmBudget.dailyUsd` (> 0, ≤ 1.000.000, höchstens sechs Nachkommastellen).
- Die `signature.secretEnvVar` eines Feedback-Webhooks muss zusätzlich in `flag.requiredEnvVars` aufgeführt sein. Die Route, die sie speist, kann ohne das Secret nichts verifizieren — deshalb muss ihr Fehlen bei der Aktivierung auffallen und nicht bei jeder einzelnen Zustellung.
- Obergrenzen: 64 Capabilities, 64 erforderliche Umgebungsvariablen, 256 Einträge pro Contribution-Bucket, 64 Einstellungsfelder.

## 3. Contributions hinzufügen

Jede Contribution ist ein Daten-Deskriptor, dessen ausführbare Hälfte an genau einem **bedingungsunabhängigen Paket-Export** liegt, zum Beispiel `./gate`. Die Codegen prüft, dass der Export existiert, ohne ihn auszuführen, und erzeugt den statischen Import. Führe jeden davon in `exports` der `package.json` des Pakets als einen String auf, zum Beispiel `"./gate": "./src/gate.ts"`, und gib dem Modul einen Default-Export: Die generierte Komposition importiert es per Default-Import.

Das Manifest unten ist ein eigenes Beispiel-Plugin, `preflight`. Ergänze in deinem Scaffold die Teile, die du brauchst, in `src/manifest.ts` und behalte dessen Default-Export. Der Import des Beispiels holt `definePlugin` zusammen mit den Capability-Konstanten, die das Manifest aufführt.

```ts
import {
	definePlugin,
	PLUGIN_AUTONOMY_GATE_CAPABILITY,
	PLUGIN_CRON_CAPABILITY,
	PLUGIN_NAV_ITEM_CAPABILITY,
	PLUGIN_SETTINGS_PANEL_CAPABILITY,
	PLUGIN_WORKER_CAPABILITY,
} from '@owlat/plugin-kit';

export const preflightPlugin = definePlugin({
	id: 'preflight',
	version: '1.0.0',
	capabilities: [
		PLUGIN_AUTONOMY_GATE_CAPABILITY,
		PLUGIN_CRON_CAPABILITY,
		PLUGIN_NAV_ITEM_CAPABILITY,
		PLUGIN_SETTINGS_PANEL_CAPABILITY,
		PLUGIN_WORKER_CAPABILITY,
		'llm:invoke',
	],
	// Contributions REQUIRE an explicit flag: an operator must be able to turn
	// the plugin off without a redeploy.
	flag: { default: false, requiredEnvVars: ['PREFLIGHT_API_KEY'] },
	// `llm:invoke` additionally requires a hard daily budget in USD.
	llmBudget: { dailyUsd: 1.5 },
	contributes: {
		sendGates: [
			{
				id: 'preflight',
				label: 'Pre-send preflight',
				module: { exportPath: './gate' },
				timeoutMs: 15_000,
			},
		],
		crons: [
			{
				id: 'refresh-rules',
				label: 'Refresh preflight rules',
				module: { exportPath: './cron' },
				schedule: { intervalMinutes: 360 },
				timeoutMs: 60_000,
			},
		],
		navItems: [
			{
				id: 'dashboard',
				section: 'administration',
				name: 'Preflight',
				href: '/dashboard/admin/instance/plugins/preflight',
				icon: 'coolicons:radar',
			},
		],
		settingsPanels: [
			{
				id: 'settings',
				name: 'Preflight',
				href: '/dashboard/admin/instance/plugins/preflight',
				icon: 'coolicons:radar',
			},
		],
	},
	settingsSchema: [
		{
			kind: 'boolean',
			key: 'holdOnFail',
			label: 'Hold sends that fail preflight',
			default: true,
		},
		{
			kind: 'secret',
			key: 'vendorApiKey',
			envVar: 'PLUGIN_VENDOR_API_KEY',
			label: 'Vendor API key',
			required: false,
		},
	],
});
```

Die `section` eines `navItems`-Eintrags muss einer der **Kern-Sidebar-Section-Keys** sein — `inbox`, `postbox`, `chat`, `assistant`, `send`, `audience`, `knowledge`, `administration`, `preferences`. Ein Plugin kann keine Section anlegen, und der Host verwirft einen Eintrag mit unbekannter Section fail-closed — ein falscher Key wird also stillschweigend nie gerendert. Bestehende Plugins, die noch den früheren Key `settings` verwenden, werden während des Kompatibilitätsfensters an `administration` gehängt.

Das `icon` eines `navItems`- oder `settingsPanels`-Eintrags ist ein coolicons-Token, `coolicons:<name>`, mit einem Namen von [coolicons.cool](https://coolicons.cool). `bun run plugins:codegen` kompiliert die genannten Icons in den Web-Build. Ein Name, den coolicons nicht kennt, lässt den Build scheitern, und jedes andere Präfix (etwa `lucide:`) scheitert an der Manifest-Prüfung.

Jeder Bucket und seine Semantik sind in der [Contribution-Referenz](/developer/plugin-contributions) aufgeführt.

## 4. Die Module schreiben

Ein Modul implementiert eine kleine Schnittstelle und erhält **ausschließlich host-vermittelte Services** — niemals einen Convex-Context, ein Datenbank-Handle, eine Tenant-ID, eine Scheduler-Referenz oder eine Umgebungsvariable, die es nicht deklariert hat.

```ts
import type {
	PluginAutonomyGateInput,
	PluginAutonomyGateModule,
	PluginAutonomyGateResult,
	PluginAutonomyGateServices,
} from '@owlat/plugin-kit';

/** A gate may object or stand aside. There is deliberately no "approve" result. */
export const gate: PluginAutonomyGateModule = {
	async evaluate(
		input: PluginAutonomyGateInput,
		services: PluginAutonomyGateServices
	): Promise<PluginAutonomyGateResult> {
		if (services.signal.aborted) return { outcome: 'objection', reason: 'preflight cancelled' };
		if (input.draftBody.includes('http://')) {
			return { outcome: 'objection', reason: 'draft contains a plaintext HTTP link' };
		}
		return { outcome: 'no-objection' };
	},
};

export default gate;
```

Hintergrundarbeit erhält ein Abort-Signal, einen Logger und — sofern `llm:invoke` deklariert, gewährt und im Budget ist — den attribuierten LLM-Dispatch des Hosts:

```ts
import type { PluginCronModule, PluginCronServices } from '@owlat/plugin-kit';

export const cron: PluginCronModule = {
	async run(services: PluginCronServices): Promise<void> {
		// Cancellation is cooperative: the host aborts `signal` at the declared
		// timeout and stops waiting either way.
		if (services.signal.aborted) return;
		const summary = await services.llm.generate({
			tier: 'fast',
			prompt: 'Summarise this week of deliverability tips in one sentence.',
		});
		services.logger.info('refreshed preflight rules', { length: summary.text.length });
	},
};

export default cron;
```

### Was jedes Modul erhält

Ein Modul bekommt die Argumente, die seine Schnittstelle in `@owlat/plugin-kit` nennt, und sonst nichts:

| Bucket | Der Host ruft auf | Neben der Eingabe bekommt das Modul |
| --- | --- | --- |
| `sendTransports` | `parseExtras(input)`, `send(params, extras, config)`, `buildDispatchExtras(context)`, wenn du es definierst, und `buildSystemMailExtras(context)`, das ein Transport mit `deduplicatesOnIdempotencyKey: true` definieren muss | Nur `send` bekommt `config`: die Werte der Umgebungsvariablen, die dieser Transport deklariert hat, für die Instanz, an die der Versand adressiert ist |
| `sendTransports`, Feedback-Webhook | `parseEvents(rawBody)` | nichts |
| `sendTransports`, Domain-Identität | `registerDomain(domain, config)`, `checkDomain(domain, config)` | `config` in derselben Form wie bei `send`, immer für die Standardinstanz des Transports |
| `agentSteps` | `execute(input)` | nichts |
| `draftStrategies` | `generate(input, services)` | `services.llm` |
| `sendGates` | `evaluate(input, services)` | `services.signal` |
| `automationSteps` | `execute(input, config)` | die Konfiguration des Schritts, geparst von deinem `parseConfig` |
| `crons` | `run(services)` | `services.signal`, `services.logger`, `services.llm` |
| `navItems`, `settingsPanels` | nichts: sie sind Daten | — |

`services.llm` dispatcht nur, solange das Manifest `llm:invoke` deklariert, der Operator es gewährt hat und das Tagesbudget des Plugins noch reicht. Die Buckets, die der Host annimmt, aber noch nicht aufruft, stehen in der [Contribution-Referenz](/developer/plugin-contributions#deklariert-und-katalogisiert-aber-noch-nicht-aufgerufen).

Plugin-Storage, ein Scheduler und ein gemeinsamer `PluginContext` sind nicht ausgeliefert. Das Kit exportiert ihre Typen, aber kein Host übergibt sie einem Modul. Ein Plugin kann heute also keinen Zustand zwischen zwei Läufen behalten und keine Folgearbeit einplanen. Was geplant ist, steht unter [Capabilities, Grants & Vertrauen](/developer/plugin-capabilities#geplant-storage-scheduling-und-ein-plugin-kontext).

::callout{type="warning" title="Für die Verweigerung entwerfen"}
Jeder gehostete Aufruf kann im letzten Moment verweigert werden — das Flag kann umgelegt worden sein, die Grant kann widerrufen sein, eine Umgebungsvariable kann fehlen. Schreib Module so, dass ein `PluginHostError` oder ein Timeout keinen halb angewendeten Zustand hinterlässt; der Host wendet in jedem Fall den deklarierten sicheren Fallback der Contribution an.
::

## 5. Das Plugin testen

Contribution-Module sind gewöhnliches TypeScript und lassen sich daher als Units mit vitest testen. Prüfe immer auch das Manifest selbst: `parsePluginManifest` ist derselbe Validator, den die Codegen ausführt — ein Manifest-Test lässt den Build also scheitern, bevor ein defektes Paket komponiert werden kann.

```sh
bun run --cwd examples/plugins/hello-owlat test
bun run --cwd examples/plugins/hello-owlat typecheck
```

Die Referenz-Plugins sind die ausgearbeiteten Beispiele, eines je Tier: `examples/plugins/escalation-guard` (Tier 1 — Agent-Step, Draft-Strategie, Automation-Trigger/-Step/-Condition, Webhook-Event, Navigations- und Einstellungseinträge), `examples/plugins/slack-approvals` (Tier 2 — eine Connected App mit einem ausschließlich einschränkenden Hold-Gate) und `examples/plugins/deliverability-lab` (Tier 3 — ein gesandboxter Seed-List-Job plus ein Tier-1-Gate, Cron und UI).

`examples/conformance` spielt anschließend alle drei durch den echten Host, die Codegen und das CLI — saubere Installation, add, remove, disable, upgrade sowie ein vollständiger Pipeline-Replay —, sodass eine Vertragsänderung die Galerie im selben Commit bricht.

::callout{type="danger" title="Niemals vitests Globals über bun test verwenden"}
Führe Tests mit `vitest` aus, nicht mit `bun test`. Erst das vitest-Setup des Workspace macht die Suites aussagekräftig.
::

## 6. Bündeln

Die Codegen bündelt ein Plugin nur, wenn es im Workspace-Root aus einer Package-Registry installiert und in `bun.lock` mit seinem Integritäts-Hash festgehalten ist. Das ist eine Supply-Chain-Regel: Der Build enthält genau das veröffentlichte Artefakt, nie einen Ordner, der sich darunter ändern kann. Das Paket, das `create` geschrieben hat, ist ein Ordner in diesem Workspace, also musst du es vor dem Bündeln veröffentlichen. Rufst du `add` direkt darauf auf, lehnt `add` ab und gibt die folgenden Schritte mit den Namen deines Pakets aus.

Im Root des Checkouts:

```sh
cd examples/plugins/hello-owlat
npm pkg delete private      # a registry refuses a private package
bun publish --access public # writes real versions for workspace:* and catalog:
cd -
mv examples/plugins/hello-owlat ../hello-owlat
bun add --exact @acme/owlat-plugin-hello-owlat@0.0.0
bun run owlat-plugins add @acme/owlat-plugin-hello-owlat
bun run plugins:codegen
```

- `bun publish` veröffentlicht auf npm, solange du keine andere Registry konfigurierst. Die Codegen akzeptiert jede Registry, also reicht eine Registry auf deinem eigenen Rechner, um ein Plugin vor dem Release auszuprobieren: siehe [Ein Plugin vor dem Release ausprobieren](#ein-plugin-vor-dem-release-ausprobieren).
- Der Ordner muss den Checkout vor `bun add` verlassen: Bun verlinkt einen Workspace-Ordner anstelle des veröffentlichten Pakets mit demselben Namen, und die Codegen lehnt ein verlinktes Paket ab. Entwickle das Plugin an seinem neuen Ort oder in einem zweiten Checkout weiter. Seine `tsconfig.json`, `vitest.config.ts` und sein `lint`-Skript zeigen weiterhin über relative Pfade in einen Owlat-Checkout.
- `0.0.0` ist die Version, die `create` geschrieben hat. Für ein späteres Release führst du vor `bun publish` `npm pkg set version=<version>` aus und installierst danach genau diese Version mit `bun add --exact`.

`add` bearbeitet die eingecheckte `plugins.config.ts` und gibt das Capability-Diff aus, das die Änderung einführt. `codegen` prüft Paketidentität, Lockfile-Integrität und Realpath-Containment, importiert ausschließlich den Manifest-Entry und schreibt die generierten Kompositionsdateien neu. Committe `package.json`, `bun.lock`, die Konfiguration **und** die generierten Dateien gemeinsam, baue dann neu und deploye. Der Build installiert das Plugin aus dem Lockfile, also lässt sich ein Commit ohne die ersten beiden nicht bauen.

Das Plugin existiert nun im Deployment, tut aber nichts: Sein Feature-Flag steht auf dem deklarierten Standardwert und seine Capabilities sind ungewährt, bis ein Betreiber handelt.

## Ein Plugin vor dem Release ausprobieren

Die Codegen hat keinen Weg an einer Registry vorbei, aber die Registry muss nicht öffentlich sein. Verdaccio in einem Container ist der kürzeste Aufbau:

```sh
docker run -d --name verdaccio -p 4873:4873 verdaccio/verdaccio:6
npm adduser --registry http://localhost:4873/ --scope=@acme --auth-type=legacy
```

`npm adduser` fragt nach Benutzername, Passwort und E-Mail. Jeder Wert funktioniert: Das Konto gibt es nur in dieser Registry. Außerdem schreibt es `@acme:registry=http://localhost:4873/` in `~/.npmrc`, sodass Bun ab dann jedes `@acme`-Paket über Verdaccio veröffentlicht und installiert. Führe Schritt 6 wie beschrieben aus. Alle anderen Pakete reicht Verdaccio von npm durch.

- Committe `package.json`, `bun.lock` und die generierten Dateien aus dieser Installation nicht. Der Lock zeigt auf `localhost:4873`, und den erreicht kein Deployment-Build.
- Verdaccio nimmt jede Version nur einmal an. Bevor du eine Änderung veröffentlichst, führe im Ordner des Plugins `npm pkg set version=<next>` aus und installiere diese Version.

So gehst du für `@acme` zurück zur öffentlichen Registry:

```sh
npm config delete @acme:registry
docker rm -f verdaccio
```

## Checkliste vor der Veröffentlichung

- Der Standard-Export-Pfad des Manifests ist ein bedingungsunabhängiger Root-Export, damit Bun, Convex, Nuxt SSR und der Browser-Build alle dasselbe Manifest auflösen.
- Kein `postinstall` und keine Seiteneffekte zur Importzeit — die Codegen importiert den Manifest-Entry.
- Der `module.exportPath` jeder Contribution ist ein echter, exakter Paket-Export.
- `flag.requiredEnvVars` führt nur Variablen auf, die ein ausgeliefertes Modul tatsächlich benötigt; eine fehlende erforderliche Variable blockiert die Aktivierung.
- Versionssprünge folgen semver; die `@owlat/plugin-kit`-Major-Version, gegen die du baust, ist deine Kompatibilitätslinie.
