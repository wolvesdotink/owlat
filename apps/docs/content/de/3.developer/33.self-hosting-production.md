Diese Anleitung behandelt das Härten deiner selbst gehosteten Owlat-Instanz für den
produktiven Einsatz. Für die Ersteinrichtung siehe [Self-Hosting](/developer/self-hosting).
Bevor du den eingebauten MTA nach außen freigibst, arbeite den Preflight zu
Provider, ausgehenden Ports, Reverse DNS und Warm-up in [Versand von einem VPS](/guide/sending-from-a-vps) durch.

## Reverse Proxy

Setze in der Produktion einen Reverse Proxy vor den Docker-Stack, der die TLS-Terminierung übernimmt und den Traffic routet.

### Caddy (empfohlen)

Owlat liefert einen fertigen Caddy-Reverse-Proxy als Service `caddy` innerhalb von `docker-compose.yml` mit, abgesichert über das Compose-Profil `tls`. Er beschafft und erneuert TLS-Zertifikate automatisch über Let's Encrypt und proxyt die übrigen Container über ihre Docker-Servicenamen — ein separater Proxy-Host ist nicht nötig.

::steps

### Beispielkonfiguration kopieren

```bash
cp Caddyfile.example Caddyfile
```

### Deine Domains eintragen

Bearbeite die `Caddyfile`, ersetze jedes `example.com` durch deine echte Domain und setze die `email` im globalen Optionsblock (wird für die Registrierung bei Let's Encrypt verwendet). Die mitgelieferte Datei proxyt drei Subdomains auf die netzinternen Servicenamen:

```caddyfile
owlat.example.com {
    reverse_proxy web:3000
}

api.example.com {
    reverse_proxy convex:3210
}

rest.api.example.com {
    reverse_proxy convex:3211
}
```

`convex` (3210, WebSocket/HTTP zum Browser) und `convex-site` (3211, HTTP-Actions wie BetterAuth und Webhooks) werden vom **selben** `convex`-Container bedient — es sind zwei Ports eines Service, nicht zwei Services.

### DNS setzen und Ports öffnen

Lege für jede Subdomain einen A-Record an, der auf diesen Server zeigt, und stell sicher, dass die Ports `80` und `443` offen sind. Caddy benötigt sie, um die ACME-HTTP-Challenge abzuschließen.

### Stack starten

```bash
docker compose --profile tls up -d
```

Der `caddy`-Service bindet `80`/`443` und bezieht die Zertifikate beim ersten Start.

::

Sobald der Proxy läuft, passe deine `.env` auf die HTTPS-URLs an:

```bash
NUXT_PUBLIC_CONVEX_URL=https://api.example.com
NUXT_PUBLIC_CONVEX_SITE_URL=https://rest.api.example.com
NUXT_PUBLIC_SITE_URL=https://owlat.example.com
```

Aktualisiere anschließend die zugehörigen Convex-Umgebungsvariablen:

```bash
npx convex env set SITE_URL "https://owlat.example.com" --url http://localhost:3210 --admin-key <key>
# CONVEX_SITE_URL is a Convex BUILT-IN — do not set it via `convex env set`
   # (the CLI rejects it). It derives from CONVEX_SITE_ORIGIN on the convex
   # container, which docker-compose interpolates from NUXT_PUBLIC_CONVEX_SITE_URL.
```

::callout{type="tip" title="Staging-Zertifikate"}
Um den Proxy zu testen, ohne die Rate Limits von Let's Encrypt aufzubrauchen, entferne im globalen Optionsblock der `Caddyfile` das Kommentarzeichen vor der Zeile `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory`, starte den Stack und wechsle zurück zur Produktion, sobald DNS und Routing stimmen.
::

### Externer Reverse Proxy (Alternative)

Wenn du den Proxy lieber außerhalb von Docker auf dem Host betreibst — oder dem Stack ein bestehendes Nginx/Caddy voranstellst —, verwende das mitgelieferte `tls`-Profil **nicht**. Proxye stattdessen auf die am Host veröffentlichten Container-Ports. Standardmäßig veröffentlicht `docker-compose.yml` web (`3000`) auf allen Interfaces, während convex (`3210`) und convex-site (`3211`) nur an `127.0.0.1` gebunden sind — ein hostlokaler Proxy auf `localhost:*` funktioniert also genau wie beschrieben. Läuft der Proxy auf einem anderen Host, setze `CONVEX_BIND`, um 3210/3211 über das Loopback hinaus verfügbar zu machen (und sichere sie per Firewall ab). Da der Proxy hier außerhalb des Docker-Netzwerks läuft, muss er `localhost:*` ansprechen, nicht die Servicenamen.

```nginx
server {
    listen 80;
    server_name owlat.example.com;
    return 301 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name owlat.example.com;

    ssl_certificate /etc/letsencrypt/live/owlat.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/owlat.example.com/privkey.pem;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# Repeat similar blocks for api.example.com (localhost:3210)
# and rest.api.example.com (localhost:3211).
```

Installiere die Zertifikate mit Certbot:

```bash
sudo certbot --nginx -d owlat.example.com -d api.example.com -d rest.api.example.com
```

### Client-IP für das Rate Limiting

Zwei Limiter ordnen Anfragen nach Client-IP zu: der Limiter für öffentliche Endpunkte (Formulare, Tracking, Abmeldelinks, Webhooks) und der Limiter für Anmeldung und Passwort-Zurücksetzung. Beide lesen `RATE_LIMIT_TRUSTED_PROXY`, um zu entscheiden, welchem Forwarded-Header sie glauben, falls überhaupt einem. Der Convex-Site-Origin ist auch ohne Umweg über deinen Proxy erreichbar, deshalb ist ein Forwarded-Header nur so vertrauenswürdig, wie die Regel des jeweiligen Modus unten es zulässt. Wird keinem Header vertraut, teilen sich alle Aufrufer einen Bucket: Die Limits sind gröber, greifen aber weiterhin.

| `RATE_LIMIT_TRUSTED_PROXY` | Öffentliche Endpunkte | Anmeldung und Passwort-Zurücksetzung |
| --- | --- | --- |
| nicht gesetzt oder ein unbekannter Wert | Keinem Header wird vertraut; ein gemeinsamer Bucket | Keinem Header wird vertraut; ein gemeinsamer Bucket |
| `xforwarded` / `xforwarded:<hops>` | `X-Forwarded-For`, der Eintrag `<hops>` Stellen von rechts (Standard 1) | `X-Forwarded-For` von rechts nach links gelesen, wobei die Adressen aus `RATE_LIMIT_TRUSTED_PROXIES` übersprungen werden; `<hops>` wird ignoriert. Ohne diese Liste wird nur ein Header mit genau einem Wert vertraut, eine längere Kette nutzt den gemeinsamen Bucket. Die Anmeldung im Browser über die Web-App teilt sich weiterhin einen Bucket (siehe unten) |
| `cloudflare` | `CF-Connecting-IP`, nur wenn `X-Owlat-Proxy-Secret` mit `RATE_LIMIT_PROXY_SECRET` übereinstimmt; sonst der gemeinsame Bucket | Wie bei öffentlichen Endpunkten |
| `xrealip` | `X-Real-IP`, nur wenn `X-Owlat-Proxy-Secret` mit `RATE_LIMIT_PROXY_SECRET` übereinstimmt; sonst der gemeinsame Bucket | Wie bei öffentlichen Endpunkten |

`xforwarded` braucht kein Geheimnis und passt zu einem einzelnen Proxy, der die verbindende Adresse anhängt, etwa dem mitgelieferten Caddy. Hinter mehr als einem Proxy setzt du `xforwarded:<hops>` für den Limiter der öffentlichen Endpunkte und trägst die Proxy-Adressen in `RATE_LIMIT_TRUSTED_PROXIES` für den Anmelde-Limiter ein; die beiden Einstellungen ersetzen einander nicht.

Im Modus `xforwarded` teilen sich Anmeldung und Passwort-Zurücksetzung im Browser weiterhin einen Bucket. Der Handler `/api/auth/*` der Web-App ersetzt `X-Forwarded-For` durch die Adresse der Verbindung, die er empfangen hat, also deines Proxys, bevor er die Anfrage an die Convex-Site weiterreicht. Der Anmelde-Limiter sieht deshalb für jeden Browser dieselbe Adresse. Eigene Buckets pro Client erhalten nur Anfragen, die `/api/auth` direkt auf der Convex-Site aufrufen. Für Anmelde-Limits pro Client im Browser-Verkehr verwendest du `cloudflare` oder `xrealip` mit dem Proxy-Geheimnis.

`cloudflare` und `xrealip` lesen einen Header, den jeder Client setzen kann, und brauchen daher `RATE_LIMIT_PROXY_SECRET`. Konfiguriere deinen Proxy so, dass er `X-Owlat-Proxy-Secret` mit diesem Wert zusammen mit dem IP-Header auf jedem Origin sendet, über den `/api/auth` erreichbar ist: dem Convex-Site-Origin (oben `rest.api.example.com`) und dem Origin der Web-App (`owlat.example.com`). Anmeldung und Passwort-Zurücksetzung im Browser rufen `/api/auth/*` auf der Web-App auf, die die Anfrage samt Headern an die Convex-Site weiterreicht; ein Geheimnis, das nur im vhost der Convex-Site gesetzt ist, erreicht den Anmelde-Limiter daher nie. Der Proxy muss außerdem jede vom Client mitgeschickte Kopie des Headers verwerfen. Ohne das Geheimnis, oder bei einer Anfrage ohne diesen Header, nutzen beide Limiter den gemeinsamen Bucket.

Das Geheimnis bürgt für den IP-Header daneben; deshalb muss es derselbe Hop hinzufügen, der den IP-Header setzt. Bei `cloudflare` fügst du `X-Owlat-Proxy-Secret` entweder bei Cloudflare hinzu (etwa mit einer Transform Rule für Request-Header), oder, falls dein Origin-Proxy es hinzufügt, nimmt dieser Origin nur Verbindungen aus den veröffentlichten IP-Bereichen von Cloudflare an. Ein Origin, der das Geheimnis auch an Anfragen hängt, die ihn direkt erreicht haben, bürgt sonst für einen `CF-Connecting-IP`-Wert, den der Client gewählt hat. Für `xrealip` gilt dasselbe: Der Proxy, der `X-Real-IP` aus der verbindenden Adresse setzt, fügt das Geheimnis hinzu.

## Firewall

Verwende UFW (oder die Firewall deiner Distribution), um den Zugriff auf die notwendigen Ports zu beschränken.

```bash
# Allow SSH
sudo ufw allow 22/tcp

# Allow HTTP/HTTPS (reverse proxy)
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Allow SMTP (bounce processing)
sudo ufw allow 25/tcp

# Allow IMAPS — NUR wenn du die Funktion personal-mail nutzt, für Mail-Clients
# (sonst weglassen; ohne sie lauscht nichts auf 993)
sudo ufw allow 993/tcp

# Enable the firewall
sudo ufw enable
```

::callout{type="warning" title="Interne Ports nicht freigeben"}
Die Ports `3210`, `3211`, `3000`, `3100`, `6379` und `3310` sollten aus dem Internet **nicht** erreichbar sein. Der Reverse Proxy nimmt externen Traffic auf den Ports `80`/`443` entgegen und leitet ihn an die internen Services weiter.

Beachte, dass web (`3000`) standardmäßig auf allen Interfaces veröffentlicht wird (damit die SPA für den lokalen Quickstart-Weg erreichbar ist), während convex (`3210`/`3211`) an das Loopback gebunden ist. Wenn nur der Reverse Proxy die Web-Oberfläche erreichen soll, setze `WEB_PORT` mit vorangestellter Host-IP (z. B. `127.0.0.1:3000`) oder sichere den Port per Firewall ab.

Zwei weitere verdienen Beachtung:

- **`3200`** — der Updater-Sidecar. Er ist konzeptbedingt rein intern (kein veröffentlichter Port in `docker-compose.yml`, erreichbar nur als `http://updater:3200` über das Docker-Netzwerk). Lass das so.
- **`6791`** — das Convex-Dashboard. Es ist an das Loopback gebunden (`127.0.0.1:6791`) und profilgesteuert, also standardmäßig aus und nur über einen SSH-Tunnel erreichbar, nachdem du es mit `--profile dashboard` gestartet hast. Siehe [Dashboard absichern](#secure-the-dashboard) weiter unten.
::

## Ausgehende Ports

Deine eigene Firewall ist nur die halbe Frage. Hoster sperren ausgehende Ports
routinemäßig — Mail-Ports vor allem —, und ein gesperrter Port meldet sich
nicht: Das Verbinden eines bestehenden Postfachs läuft einfach in einen Timeout,
und die Direktzustellung bleibt mit voller Warteschlange stehen. Bitte
deinen Hoster, diese Ports für die Maschine zu öffnen — am besten in derselben
Anfrage wie die Reverse-DNS-Änderung.

| Port | Wofür | Nötig, wenn |
| --- | --- | --- |
| 443/tcp | Image-Downloads, Update-Prüfungen, alle Provider- und KI-APIs | Immer |
| 53/udp+tcp | MX-Abfragen, Domain-Prüfung, Blocklist-Checks | Immer |
| 25/tcp | Direkte Zustellung an die Mailserver der Empfänger | Der eingebaute MTA ist dein Versandweg |
| 587/tcp | Übergabe an ein externes SMTP-Relay | Dein Versandweg ist ein generisches SMTP-Relay |
| 465/tcp | Versand aus einem verbundenen Postfach über implizites TLS | `mail.external` — verbundene Postfächer |
| 993/tcp | Lesen eines verbundenen Postfachs über IMAP | `mail.external` — verbundene Postfächer |

Zwei Punkte sind hervorzuheben, weil Hoster sie gemeinsam falsch machen:

- **Die Mail-Ports sind häufig gesperrt, und nicht als Block.** Hetzner Cloud
  sperrt 25 und 465, DigitalOcean 25, 465 und 587, OVHcloud 25.
  [Versand von einem VPS](/guide/sending-from-a-vps) führt Politik und
  Freischaltweg je Anbieter auf. Ein offenes 587 sagt nichts über 25 aus, und
  eine Freischaltung für einen Port gilt nicht für die anderen — nenne im
  Ticket jeden Port, den du brauchst.
- **53 zu anderen Resolvern als dem des Hosters** ist häufiger gesperrt als
  erwartet. Spamhaus weist Anfragen von gemeinsam genutzten Hoster-Resolvern
  mit einer Policy-Antwort ab, deshalb schickt die MTA ihre Sperrlistenabfragen
  über einen eigenen Resolver (den Dienst `dns-resolver`), der das Internet
  über 53 erreichen muss. Bekommt keiner eine Antwort, kann Owlat nicht messen,
  ob deine IP gelistet ist, und versendet bewusst gar nicht, statt blind zu
  senden. Die Lösung, die aus jedem Netz funktioniert, steht unter
  [Spamhaus erreichen](/developer/dnsbl-delisting#spamhaus-erreichen).

::callout{type="info" title="Von der Instanz aus prüfen"}
**Administration → System & Updates → Netzwerk-Ports** prüft diese Ports vom
Server aus und zeigt pro Port, was gefunden wurde und welche Funktion daran
hängt. Die Prüfungen laufen nur auf Knopfdruck: Jede öffnet eine Verbindung zu
einem bekannten Host und schließt sie sofort wieder, ohne etwas zu senden.

Zwei Grenzen sind wichtig: Die eingehenden Zeilen werden aus dem Docker-Netz
heraus geprüft und belegen daher, dass ein Dienst **lauscht** — ob das Internet
ihn erreicht, hängt an der davorliegenden Firewall, die von der Maschine aus
niemand testen kann. Und die DNS-Zeile fragt nur, ob dein Resolver überhaupt
antwortet; die oben beschriebene Policy-Abweisung, bei der er alles außer
Blocklist-Anfragen beantwortet, erkennt sie nicht. Das leistet die Karte
**Sperrlistenabfragen** unter **Zustellung → Anbieter**: Sie zeigt, ob Spamhaus
die letzte Prüfung beantwortet hat und warum nicht.
::

## Dashboard absichern

Das Convex-Dashboard auf Port `6791` bietet vollen Lese-/Schreibzugriff auf deine Datenbank und hat **keine eingebaute Authentifizierung**. Die `docker-compose.yml` im Projektstamm bindet es bereits ausschließlich an das Loopback-Interface (`127.0.0.1:${DASHBOARD_PORT:-6791}:6791`) und sichert es über das Compose-Profil `dashboard` ab; in einem frischen Stack ist es also weder öffentlich veröffentlicht noch überhaupt gestartet. Belass es vor dem Produktivgang dabei.

**Option 1: Den ausgelieferten Standard nutzen** (empfohlen)

Es ist kein Override nötig — das Dashboard ist bereits an das Loopback gebunden und startet nur unter `--profile dashboard`. Starte es bei Bedarf und prüfe die Bindung:

```bash
docker compose --profile dashboard up -d convex-dashboard
docker compose --profile dashboard port convex-dashboard 6791
# Should show: 127.0.0.1:6791
```

**Option 2: SSH-Tunnel** (für Fernzugriff nach der Bindung an localhost)

```bash
ssh -L 6791:localhost:6791 user@your-server
# Then open http://localhost:6791 in your browser
```

**Option 3: Per Firewall absichern** — wenn du die Bindung nicht ändern kannst, blockiere Port `6791` in der Host-Firewall (er fehlt in den UFW-Regeln oben bewusst), sodass nur das Loopback oder ein VPN ihn erreicht.

::callout{type="danger" title="Das Dashboard niemals offen proxyen"}
Wenn du das Dashboard über den mitgelieferten Caddy-Proxy freigibst, sichere es hinter Basic Auth oder einer IP-Allowlist ab — es wird ohne Login ausgeliefert. Der auskommentierte Block `convex-dashboard.example.com` in `Caddyfile.example` zeigt ein Beispiel für eine IP-Allowlist.
::

## Redis-Authentifizierung

Die Redis-Authentifizierung ist ab Werk aktiv und verpflichtend. `docker-compose.yml` interpoliert `${REDIS_PASSWORD:?…}` im Redis-Kommando, in dessen Healthcheck und in der `REDIS_URL` der MTA — es gibt kein Override zu schreiben und keinen unauthentifizierten Fallback. Der Setup-Assistent und `owlat quickstart` erzeugen das Passwort, wenn sie die `.env` schreiben.

::callout{type="warning" title="Upgrade einer älteren .env"}
Eine `.env`, die vor der verpflichtenden Redis-Authentifizierung entstand, enthält kein `REDIS_PASSWORD`. Compose interpoliert die gesamte Datei, bevor es Services auswählt — deshalb scheitert **jeder** Unterbefehl, auch die zur Fehlersuche: `docker compose down`, `logs` und `ps`.
::

Den fehlenden Schlüssel erzeugen und den Stack starten:

```bash
echo "REDIS_PASSWORD=$(openssl rand -base64 32)" >> .env
docker compose up -d
```

## Backups

Verwende das mitgelieferte Skript — es ist der einzige Erzeuger von Archiven,
die `scripts/restore.sh` akzeptiert, und es übernimmt die Konsistenzarbeit für dich
(kurzes Pausieren von convex + redis rund um den Kopiervorgang, Ermitteln sämtlicher
Projekt-Volumes, Sichern von `.env`, des Compose-Overrides und der Caddyfile sowie
Schreiben einer SHA256-Sidecar-Datei):

```bash
bash scripts/backup.sh                 # → ./backups/owlat-<timestamp>.tar.gz
owlat backup                           # same, via the CLI wrapper
```

Das Volume `convex-data` ist das kritische — es enthält sämtliche Anwendungsdaten
(Kontakte, Kampagnen, Vorlagen, hochgeladene Dateien, Einstellungen). Das
Convex-Backend speichert seinen Zustand in **SQLite**, rohe Hot-Kopien des Volumes
sind daher nicht crash-konsistent; das Skript pausiert den Container für die
Sekunden, die das Kopieren dauert. Dasselbe gilt für die mehrteilige AOF von
Redis 7 (`appendonlydir/`).

**Volume-Snapshots des Anbieters** (Hetzner, AWS, …) sind eine gute Ergänzung, mit
demselben Vorbehalt: Erstelle den Snapshot bei gestopptem Stack, oder nimm
in Kauf, dass ein mitten im Schreibvorgang erstellter Snapshot beim
Wiederherstellen eine AOF-/SQLite-Wiederherstellung erfordern kann.

ClamAV-Signaturen und Ollama-Modelle benötigen kein Backup — beide laden sich neu herunter.

### Disaster Recovery (neuer VPS / defekte Festplatte)

1. Stell einen frischen VPS bereit und installiere Docker + Compose v2.
2. Klone das Owlat-Repository per `git clone` (dieselbe Version wie das Backup — das
   MANIFEST hält fest, wann es erstellt wurde) und wechsle mit `cd` hinein.
   Verwende denselben Verzeichnisnamen wie auf dem alten Server (`owlat` bei
   einem einfachen Klon): Compose benennt die Volumes danach. Weichen die Namen ab,
   warnt die Wiederherstellung und stellt in die Volumes wieder her, die
   `docker compose up` in diesem Checkout verwendet.
3. Kopiere dein `owlat-<timestamp>.tar.gz` **und dessen `.sha256`-Sidecar-Datei** herüber.
4. `bash scripts/restore.sh owlat-<timestamp>.tar.gz` — das überprüft die
   Prüfsumme und jedes Volume-Archiv, stellt jedes Volume sowie
   `.env`/Override/Caddyfile wieder her und startet den Stack mit deinen
   Feature-Profilen. Eine `.env` musst du vorher nicht anlegen: Bis die
   wiederhergestellte vorliegt, übergibt das Skript Compose die `.env` aus dem
   Archiv. Beim ersten Fehler bricht es ab und meldet nur dann Erfolg,
   wenn der Stack gestartet ist (siehe
   [Wiederherstellung aus dem Backup](/developer/self-hosting-maintenance#letztes-mittel-aus-dem-backup-wiederherstellen)).
5. Richte DNS auf den neuen Server um; TLS-Zertifikate werden automatisch neu
   ausgestellt, sobald DNS auflöst.

Bewahre mindestens ein Backup **außerhalb des VPS** auf (Object Storage, dein Laptop) —
ein Backup auf der defekten Festplatte ist kein Backup.

## Monitoring

### Healthchecks

Für die kritischen Services (Convex, Redis, ClamAV) sind Docker-Healthchecks bereits konfiguriert. Ihren Status prüfst du so:

```bash
docker compose ps
```

Für externes Monitoring erstellst du ein Healthcheck-Skript:

```bash
#!/bin/bash
# health-check.sh

CONVEX_OK=$(curl -sf http://localhost:3210/version && echo "ok" || echo "fail")
WEB_OK=$(curl -sf http://localhost:3000 && echo "ok" || echo "fail")
MTA_OK=$(curl -sf http://localhost:3100/health && echo "ok" || echo "fail")

echo "Convex: $CONVEX_OK | Web: $WEB_OK | MTA: $MTA_OK"

if [[ "$CONVEX_OK" != "ok" || "$WEB_OK" != "ok" || "$MTA_OK" != "ok" ]]; then
  exit 1  # Unhealthy — trigger your alerting system
fi
```

### MTA-Metriken

Der MTA stellt Prometheus-kompatible Metriken bereit:

```bash
curl http://localhost:3100/metrics
```

Verbinde diese mit Prometheus + Grafana, um Dashboards für Versandraten, Bounce-Raten und Queue-Tiefe zu erhalten.

## Ressourcenanforderungen

Dies sind informelle Größenklassen, keine Tarife — der OSS-Self-Host-Build kennt weder Stufen noch Abrechnung.

| Größe | vCPU | RAM | Festplatte | Geeignet für |
| --- | --- | --- | --- | --- |
| Klein | 2 | 4 GB | 40 GB | Bis zu 10.000 Kontakte, geringes Versandvolumen |
| Mittel | 4 | 8 GB | 80 GB | Bis zu 100.000 Kontakte, regelmäßige Kampagnen |
| Groß | 8 | 16 GB | 160 GB | 100.000+ Kontakte, hohes Versandvolumen |

ClamAV belegt für die Virendefinitionen etwa 1 GB RAM. Wenn der Arbeitsspeicher knapp ist, kannst du ClamAV deaktivieren, indem du es aus der Docker-Compose-Datei entfernst und die Konfiguration von `CLAMAV_HOST`/`CLAMAV_PORT` weglässt.
