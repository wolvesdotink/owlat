title: "Self-Hosting"
description: "Owlat mit Docker Compose auf deiner eigenen Infrastruktur betreiben. Vollständige Anleitung vom ersten Start bis zur Produktion."
---

Owlat läuft vollständig auf deiner eigenen Infrastruktur über eine einzige Docker-Compose-Datei. Cloud-Dienste sind nicht erforderlich — der Stack bringt eine eigene Datenbank und Echtzeit-Engine mit und kann seinen eigenen Mailserver (MTA) sowie einen Virenscanner (ClamAV) betreiben. Mailserver und Virenscanner sind über Docker-Compose-Profile (`mta` und `clamav`) abgesichert; welche davon laufen, hängt also von deinem `COMPOSE_PROFILES` ab — siehe [Stack-Überblick](#stack-überblick).

## Warum Self-Hosting

- **Datensouveränität** — deine E-Mails, Kontakte und Analysedaten verlassen niemals deine Server
- **Compliance** — Anforderungen der DSGVO, von HIPAA oder branchenspezifische Vorgaben zur Datenlokalisierung erfüllen
- **Air-Gapped-Umgebungen** — Betrieb ganz ohne externe Netzwerkabhängigkeiten
- **Volle Kontrolle** — jede Komponente anpassen, auditieren und erweitern

## Voraussetzungen

| Anforderung | Minimum |
| --- | --- |
| CPU-Architektur | x86_64 (amd64) oder aarch64 (arm64) — z. B. Hetzner CAX, Oracle Ampere, AWS Graviton |
| Docker | 20.10+ |
| Docker Compose | v2 (das `docker compose`-Plugin) |
| RAM | 4 GB (8 GB empfohlen) |
| Festplatte | 20 GB frei |
| openssl | Beliebige Version (zum Erzeugen von Secrets) |
| Domain + DNS-Kontrolle | Für den produktiven E-Mail-Versand erforderlich |
| Reverse-DNS-(PTR-)Kontrolle für die Versand-IP | Für die eingebaute MTA erforderlich — den PTR in der Konsole deines Hosters auf deinen EHLO-Hostnamen setzen. Ohne ihn schließt das Setup nicht ab. |

## Unterstützte Plattformen

Owlat läuft auf unterschiedlichen Betriebssystemen — je nachdem, welchen Teil du meinst: den Desktop-Client, den selbst gehosteten Server oder ein Checkout zum Mitentwickeln.

| Rolle | macOS | Linux | Windows |
| --- | --- | --- | --- |
| **Desktop-App** | Unterstützt (universal) | Unterstützt | Unterstützt |
| **Selbst gehosteter Server** | Nicht unterstützt (nur zur Evaluierung via Docker Desktop) | Unterstützt | Nicht unterstützt (nur zur Evaluierung via Docker Desktop) |
| **Contributor-/Dev-Checkout** | Unterstützt | Unterstützt | Unterstützt über WSL2 oder Git Bash |

### Desktop-App

Die Desktop-App wird für macOS (Universal Binary), Linux und Windows ausgeliefert. Unter Linux benötigen Endanwender einige System-Laufzeitbibliotheken, damit die WebKit-basierte Shell startet:

- **Debian / Ubuntu**: `libwebkit2gtk-4.1-0`, `librsvg2-2`
- **Fedora**: `webkit2gtk4.1`, `librsvg2`

macOS und Windows bringen alles Nötige mit, dort sind keine zusätzlichen Pakete erforderlich.

### Selbst gehosteter Server

Der selbst gehostete Server läuft konzeptbedingt **ausschließlich unter Linux**. Er setzt auf systemd und Docker Engine und belegt die üblichen Mail- und Web-Ports (25, 143, 443, 993). Der [empfohlene Installationsweg](#der-schnellste-weg) führt über einen frischen Linux-VPS.

macOS und Windows werden als Server-Host **nicht** unterstützt. Für eine lokale Evaluierung auf diesen Systemen verwendest du [Docker Desktop](https://docs.docker.com/desktop/) mit dem manuellen [`docker compose`-Ablauf](#option-b-manuelles-setup) — damit laufen dieselben Container, ohne dass ein Linux-Host nötig ist.

### Contributor-/Dev-Checkout

Das Mitentwickeln funktioniert nativ unter macOS und Linux. Unter Windows betreibst du das Repository in **WSL2** oder **Git Bash**, da die Lint- und Verifikations-Gates Bash-Skripte sind. Das vollständige Entwicklungs-Setup findest du unter [CONTRIBUTING](https://github.com/wolvesdotink/owlat/blob/main/CONTRIBUTING.md).

## Der schnellste Weg

Auf einem frischen Linux-VPS mit installiertem Docker + Docker Compose v2:

```sh
curl -fsSL https://get.owlat.app | bash
```

Der Einzeiler klont das Repository, führt Preflight-Checks aus, installiert das `owlat`-CLI nach `/usr/local/bin` und übergibt an den containerisierten `owlat quickstart`-Assistenten. Dieser eine Ablauf erzeugt Secrets, schreibt deine `.env`, startet den Docker-Stack, erstellt den Convex-Admin-Key, deployt die Functions, setzt die Convex-Laufzeit-Umgebungsvariablen und legt dein Admin-Konto an — ohne Bun oder Node auf dem Host. Nicht-interaktive Nutzung:

```sh
# Skip prompts, accept all defaults
curl -fsSL https://get.owlat.app | OWLAT_ASSUME_YES=1 bash

# Read answers from a config file (for CI / Ansible)
curl -fsSL https://get.owlat.app | OWLAT_CONFIG_FILE=/path/to/answers.json bash

# Pin a specific release tag for a reproducible install
curl -fsSL https://get.owlat.app | OWLAT_REF=v0.1.0 bash
```

::callout{type="info" title="Version für reproduzierbare / auditierbare Installationen pinnen"}
Standardmäßig löst der Installer auf das zuletzt veröffentlichte **Release-Tag** auf (nicht auf einen wandernden Branch) — `curl | bash` bittet einmalig um dein Vertrauen, und dieses Vertrauen sollte nicht stillschweigend auf jeden künftigen Commit ausgeweitet werden. Setze `OWLAT_REF` auf ein Tag (z. B. `v0.1.0`), damit Wiederholungsläufe und CI byteweise denselben Code installieren, den du geprüft hast; `OWLAT_REF=main` nur dann, wenn du ausdrücklich den allerneuesten Stand willst.
::

::callout{type="info" title="Lieber eine grafische Oberfläche?"}
Die [Desktop-App kann einen frischen Server für dich über SSH installieren](/developer/self-hosting-desktop) — ganz ohne Terminal — mit einer Live-Zeitleiste des Provisionierungsfortschritts. Sie steuert denselben Installer aus der Ferne.
::

::callout{type="info" title="Nicht im Self-Hosting enthalten"}
Stripe-Abrechnung, Hetzner-VPS-Provisionierung und Tarifverwaltung gehören zur Control Plane der Managed Cloud (eine separate, private Codebasis) und sind nicht Teil der quelloffenen Self-Hosting-Distribution. Self-Hoster betreiben den Owlat-Stack direkt mit `docker compose up -d`.
::

## Schnellstart

### Option A: `owlat quickstart` (empfohlen)

Der empfohlene Ablauf beim ersten Start ist der containerisierte `quickstart`-Assistent. Er führt das Setup-CLI (gebaut aus `apps/setup-cli/`) im Docker-Image `wolvesdotink/setup` aus, sodass auf dem Host nur Docker und Docker Compose v2 vorausgesetzt werden. Ein Befehl erledigt das komplette Deployment: Konfigurationsassistent → `docker compose up -d` → Erstellen des Admin-Keys → Function-Deployment → Convex-Umgebungsvariablen → Admin-Bootstrap.

```bash
git clone https://github.com/wolvesdotink/owlat.git
cd owlat
scripts/owlat quickstart
```

Wenn du den Einzeiler oben ausgeführt hast, liegt das `owlat`-CLI bereits in deinem `PATH`, du kannst also einfach `owlat quickstart` aufrufen. Der komplette Ablauf dauert vom leeren VPS bis zur funktionierenden Installation rund 10 Minuten und erledigt alles aus Option B weiter unten automatisch — einschließlich des Übertragens der Convex-Laufzeit-Umgebungsvariablen (`BETTER_AUTH_SECRET`, `SITE_URL`, `UNSUBSCRIBE_SECRET`, `EMAIL_PROVIDER`, `MTA_API_URL` sowie der Absenderidentität) in das Deployment, damit Auth-Einladungen und der erste Versand ohne weitere Schritte funktionieren. Sperrt dein VPS-Anbieter ausgehenden Port 25, sagt dir das die Zusammenfassung am Ende und nennt die Auswege; siehe [Versand von einem VPS](/guide/sending-from-a-vps). Der Terminal-Assistent lässt `SITE_URL` auf `http://localhost:3000`, die Links in Bestätigungs-, Passwort-Reset- und Einladungsmails gehen also nur auf dem Server auf, bis du Owlat hinter einen [Reverse Proxy](/developer/self-hosting-production#reverse-proxy) stellst und die öffentliche URL setzt; die Zusammenfassung und `owlat doctor` erinnern dich daran, und [die Setup-CLI-Seite](/developer/setup-cli#setup-assistent-web-vs-terminal) nennt die Befehle.

::callout{type="info" title="Alter Bash-Assistent"}
Der ältere, reine Bash-Assistent wird weiterhin ausgeliefert und funktioniert: `bash scripts/setup.sh` (wähle bei der Abfrage „Self-Hosted (Docker Compose)“). Er ist der Legacy-Pfad und über das CLI mit `owlat quickstart --legacy` oder über den Einzeiler mit `curl -fsSL https://get.owlat.app | OWLAT_LEGACY_WIZARD=1 bash` erreichbar. Für neue Installationen ist `owlat quickstart` vorzuziehen.
::

### Option B: Manuelles Setup

Der manuelle Weg führt dieselben Schritte wie `owlat quickstart` einzeln aus. Für den Schritt, der die Convex-Laufzeitvariablen überträgt, nutzt er trotzdem das `owlat`-CLI, denn dieser Schritt leitet mehrere davon aus der `.env` ab, und eine von Hand gepflegte Liste veraltet.

**1. Klonen und konfigurieren**

```bash
git clone --branch v1.2.3 https://github.com/wolvesdotink/owlat.git
cd owlat
cp .env.selfhost.example .env
```

Ersetze `v1.2.3` durch das [neueste Release](https://github.com/wolvesdotink/owlat/releases) und trage dieselbe Version ohne `v` in die `.env` ein, damit Compose die dafür veröffentlichten Images zieht:

```bash
OWLAT_VERSION=1.2.3
```

Statt die Datei zu kopieren, kannst du auch `scripts/owlat setup` ausführen. In einem Checkout ohne `.env` schreibt es eine, in der die Secrets und der Deduplizierungsmodus unten schon eingetragen sind, und fragt nach EHLO-Hostname, Bounce-Domain und Absenderadresse. Prüfe die übrigen Werte aus Schritt 2 und mach dann bei Schritt 3 weiter.

**2. Die `.env` ausfüllen**

`docker compose up` startet nicht, solange einer der Werte leer ist, die es verlangt. Erzeuge für jede Variable ein eigenes Secret:

```bash
openssl rand -hex 32
```

Trage in jeden dieser Schlüssel einen eigenen Wert ein:

| Schlüssel | Gelesen von |
| --- | --- |
| `INSTANCE_SECRET` | Convex-Backend (muss hex sein) |
| `REDIS_PASSWORD` | Redis und die MTA |
| `MTA_SECRET` | MTA, versiegelt die DKIM-Schlüssel (bleibt dauerhaft gleich) |
| `MTA_API_KEY` | MTA und Convex-Functions |
| `MTA_WEBHOOK_SECRET` | MTA und Convex-Functions |
| `BOUNCE_VERP_KEY` | MTA, signiert die Bounce-Adressen (Convex bekommt ihn in Schritt 7 als `MTA_BOUNCE_VERP_KEY`) |
| `BETTER_AUTH_SECRET` | Convex-Functions, Signatur der Sitzungen |
| `UNSUBSCRIBE_SECRET` | Convex-Functions, Abmeldelinks |

Setze bei einer frischen Installation außerdem den Modus für die Deduplizierung von Beschwerden:

```bash
FBL_DEDUP_PROTOCOL=owned-v2
FBL_DEDUP_CUTOVER_ACK=fresh-install
```

Setze dann die Absenderidentität; alle diese Werte kommen mit Beispielwerten:

- `EHLO_HOSTNAME`: der Hostname, auf den der PTR-Eintrag deiner Versand-IP zeigt.
- `IP_POOLS_TRANSACTIONAL` und `IP_POOLS_CAMPAIGN`: deine öffentliche IPv4-Versandadresse (mit dem ausgelieferten `127.0.0.1` lässt sich keine Mail zustellen).
- `RETURN_PATH_DOMAIN`: die Bounce-Domain, zum Beispiel `bounces.example.com`.
- `DEFAULT_FROM_EMAIL`, `DEFAULT_FROM_NAME` und `DEFAULT_FROM_DOMAIN`: der Absender der Systemmails (Einladungen, Passwort-Resets) auf einer Domain, die dir gehört.
- `SITE_URL` und die drei `NUXT_PUBLIC_*`-URLs, wenn die Instanz von einem anderen Rechner aus erreichbar sein soll.

Welche Einträge diese Namen brauchen, steht unter [DNS- & E-Mail-Setup](/developer/self-hosting-dns-email).

**3. Stack starten**

```bash
docker compose up -d
```

**4. Warten, bis Convex bereit ist**

```bash
# Watch logs until you see "ready" or "listening"
docker compose logs -f convex
# Press Ctrl+C once ready
```

**5. Admin-Key erzeugen**

```bash
docker compose exec convex ./generate_admin_key.sh
```

Kopiere den ausgegebenen Key und füge ihn deiner `.env` hinzu:

```bash
# In .env, set:
CONVEX_ADMIN_KEY=<paste-key-here>
```

Ein Neustart ist nicht nötig — die dauerhaft laufenden Services lesen `CONVEX_ADMIN_KEY` nicht. Nur der einmalig laufende Container `convex-deploy` (nächster Schritt) und die optionalen Sidecars verwenden ihn, und diese lesen die `.env` bei jedem Lauf neu ein.

**6. Functions deployen**

```bash
# Deploy the main Convex functions
docker compose --profile deploy run --rm convex-deploy
```

**7. Die Convex-Laufzeitvariablen übertragen**

Convex-Functions lesen ihre Konfiguration aus dem Deployment, nicht aus der `.env`. Übertrage sie:

```bash
scripts/owlat apply
```

`apply` überträgt jeden Laufzeitschlüssel, der in der `.env` einen Wert hat (Auth-Secrets, `SITE_URL`, `EMAIL_PROVIDER`, `MTA_API_URL`, `MTA_API_KEY`, `MTA_WEBHOOK_SECRET`, `EHLO_HOSTNAME`, die Absenderidentität und die übrigen), und leitet `MTA_IP_POOLS`, `MTA_RETURN_PATH_DOMAIN` und `MTA_BOUNCE_VERP_KEY` aus `IP_POOLS_*`, `RETURN_PATH_DOMAIN` und `BOUNCE_VERP_KEY` ab. Führe es nach jeder späteren Änderung an der `.env` erneut aus. Was es genau tut, beschreibt [Setup-CLI](/developer/setup-cli#owlat-apply).

**8. Das Admin-Konto anlegen**

Das legt das Setup-CLI an. Auf einem Linux-Host führst du es aus dem Setup-Image deiner Version aus:

```bash
docker run --rm --network host -v "$PWD:/opt/owlat" ghcr.io/wolvesdotink/setup:1.2.3 \
  bootstrap-org --owlat-dir /opt/owlat \
  --email admin@example.com --name "Admin" --password "a-strong-password"
```

**9. Die App öffnen**

Öffne `http://localhost:3000` (oder deine `SITE_URL`) und melde dich an. `scripts/owlat doctor` prüft die Installation, einschließlich Reverse DNS und ausgehendem Port 25.

## Stack-Überblick

| Service | Port(s) | Rolle |
| --- | --- | --- |
| **Convex** | 3210, 3211 | Datenbank, Echtzeit-Subscriptions, Serverless-Functions, Dateispeicher |
| **Web** | 3000 | Nuxt-Anwendung — Dashboard, E-Mail-Builder, Einstellungen |
| **MTA** | 3100, 25 | Mail Transfer Agent — SMTP-Zustellung, Bounce-Verarbeitung, IP-Warming. **Profilgesteuert** (`mta`); die Standarddatei `.env.selfhost.example` liefert `COMPOSE_PROFILES=mta` aus, der Dienst läuft also bei einem Standard-Self-Host, wird aber übersprungen, wenn du auf einen Drittanbieter (Resend/SES) umstellst |
| **Redis** | nur intern (6379) | Job-Queue und Rate-Limiting-Zustand für den MTA |
| **ClamAV** | nur intern (3310) | Virenprüfung für E-Mail-Anhänge. **Profilgesteuert** (`clamav`) und **nicht** in den Standard-`COMPOSE_PROFILES` enthalten — siehe Hinweis unten |
| **Updater** | nur intern (3200) | Sidecar für Selbst-Updates aus der App heraus — führt stellvertretend für die Web-App `docker compose pull && up -d` aus. Bindet ausschließlich `OWLAT_INSTALL_DIR` ein; der Docker-Socket wird nicht mehr eingebunden, stattdessen wird Docker über den Least-Privilege-`docker-socket-proxy` gesteuert (`DOCKER_HOST=tcp://docker-socket-proxy:2375`), den einzigen Container, der `/var/run/docker.sock` einbindet (schreibgeschützt). Erreichbar über das Docker-Netzwerk unter `http://updater:3200` |
| **Caddy** | 80, 443 | Optionaler Reverse Proxy mit automatischem HTTPS, aktivierbar über `--profile tls` (siehe Caddyfile.example) |

::callout{type="warning" title="`docker compose up -d` startet nur die Profile in COMPOSE_PROFILES"}
`docker compose up -d` berücksichtigt `COMPOSE_PROFILES` aus deiner `.env`: Es startet die dauerhaft laufenden Basis-Services plus die dort aufgeführten Profile und **überspringt jeden profilgesteuerten Service, der nicht aufgeführt ist**. Die Standarddatei `.env.selfhost.example` liefert `COMPOSE_PROFILES=mta` aus — damit startet der MTA, aber **nicht** ClamAV. Auch wenn das Feature-Flag `scan.files` standardmäßig aktiv ist und die Anhangsprüfung **fail-open** arbeitet (Mail wird auch zugestellt, wenn der Scanner nicht erreichbar ist), startet ClamAV bei einer Standardinstallation nie — **Anhänge werden also ungeprüft zugestellt**. Damit Dateien tatsächlich geprüft werden, ergänze `clamav` in `COMPOSE_PROFILES` (z. B. `COMPOSE_PROFILES=mta,clamav`) und führe `docker compose up -d` erneut aus, oder aktiviere das Paket `scan.files` über den Assistenten, der das Profil `clamav` für dich einbindet.
::

Einige weitere Services laufen nur bei Bedarf und nicht als Teil des dauerhaft laufenden Stacks:

- **`convex-deploy`** (`--profile deploy`) — einmalig laufender Container, der die Functions, das Schema und die HTTP-Routen aus `apps/api` an das Backend überträgt und die Convex-Laufzeit-Umgebungsvariablen setzt. Führe ihn nach dem ersten Start und nach jedem Image-Pull aus: `docker compose --profile deploy run --rm convex-deploy`.
- **`code-worker`** (`--profile inbox-codetasks`, ebenfalls über `--profile dev` verfügbar) — der optionale Sidecar für den KI-Coding-Agenten; standardmäßig aus.
- **`convex-dashboard`** (`--profile dashboard`) — Admin-Oberfläche zum Inspizieren von Daten und Debuggen von Functions. Starte sie mit `docker compose --profile dashboard up -d convex-dashboard`. Sie bindet nur an `127.0.0.1`; öffne auf einem entfernten VPS daher einen SSH-Tunnel (`ssh -L 6791:127.0.0.1:6791 host`), bevor du `http://localhost:6791` aufrufst.

Einen tieferen Einblick in die Architektur findest du unter [Self-Hosting-Architektur](/vision/self-hosting).
