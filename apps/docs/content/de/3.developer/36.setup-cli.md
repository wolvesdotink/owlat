Owlat liefert eine einzige Self-Hosting-Toolchain: einen Einzeiler-Installer (`install.sh`), der einen Host aufsetzt, und das `owlat-setup`-CLI (gebaut aus `apps/setup-cli/`), das alles von der Konfiguration bis zur vollständig deployten, mit Daten befüllten Instanz erledigt. Diese Seite ist die Kommandoreferenz für beides. Für die erzählende Deploy-Anleitung beginnst du bei [Self-Hosting](/developer/self-hosting); diese Seite dokumentiert die einzelnen Kommandos, die jene Anleitungen aufrufen.

## Der Einzeiler-Installer

`install.sh` wird unter `https://get.owlat.app` ausgeliefert. Auf einem frischen Linux-VPS mit installiertem Docker und Docker Compose v2:

```sh
curl -fsSL https://get.owlat.app | bash
```

Das Skript (`install.sh`) erledigt vier Dinge und übergibt dann an das CLI:

::steps

### Preflight

Prüft `curl`, `git`, `docker`, ob der Docker-Daemon erreichbar ist (`docker info`) und ob `docker compose version` funktioniert (Compose v2 ist erforderlich).

### Klonen oder erkennen

Wenn du dich bereits in einem Klon befindest (es wird nach `scripts/setup.sh` + `docker-compose.yml` gesucht), wird dieser verwendet. Andernfalls wird `github.com/wolvesdotink/owlat` flach nach `/opt/owlat` geklont (der Standardwert von `OWLAT_INSTALL_DIR`). Ist das übergeordnete Verzeichnis des Installationsverzeichnisses nicht beschreibbar, wird es mit `sudo` angelegt und dir per chown übertragen. Ein vorhandener Klon wird gefetcht und (detached) auf die Ziel-Ref ausgecheckt.

### Das `owlat`-CLI installieren

Führt `scripts/owlat install-cli` aus, was den Wrapper per Symlink nach `/usr/local/bin/owlat` verlinkt (bei Bedarf mit `sudo`), sodass du anschließend `owlat <command>` von überall ausführen kannst.

Der Link wird vom Wrapper selbst angelegt und nicht von `install.sh`, denn `install.sh` ist nicht der einzige Weg, auf dem ein Server provisioniert wird: Der [Desktop-Setup-Assistent](/developer/self-hosting-desktop) und der manuelle `git clone`-Ablauf rufen beide direkt `scripts/owlat quickstart` auf. Auch diese Pfade installieren das CLI — `quickstart`, `setup` und `config` stellen den Link jeweils sicher, bevor sie an den Assistenten übergeben. Eine Installation, die vor dieser Änderung entstanden ist, repariert sich damit beim nächsten Öffnen des Assistenten selbst.

Falls `owlat` weiterhin nicht in deinem `PATH` liegt (etwa weil `/usr/local/bin` zur Installationszeit nicht beschreibbar war), kannst du den Link jederzeit selbst anlegen:

```bash
sudo /opt/owlat/scripts/owlat install-cli
```

Mit `OWLAT_CLI_LINK` verlinkst du an einen anderen Ort als `/usr/local/bin/owlat`, mit `OWLAT_SKIP_CLI_LINK=1` schaltest du das Verlinken ganz ab. Eine bereits vorhandene Datei, die **kein** Symlink ist, wird nie überschrieben.

### Den Assistenten starten

Führt den containerisierten Quickstart aus: `scripts/owlat quickstart --terminal`. Das Flag `--terminal` wird erzwungen, weil der browserbasierte Web-Assistent nicht innerhalb des containerisierten Installers laufen kann.

::

Da der Assistent im Docker-Image `wolvesdotink/setup` läuft, benötigt der Host nur Docker und Compose — **kein Bun und kein Node**.

::callout{type="warning" title="Bestehende MTA-Installationen erfordern eine explizite FBL-Umstellung"}
Ein frisches Setup schreibt das Owned-v2-Beschwerdeprotokoll mit einer
`fresh-install`-Bestätigung. Ein erneuter Setup-Lauf gegen eine bestehende Umgebung
erfindet diesen Zustand niemals. Bevor du eine ältere MTA aktualisierst, folge
der koordinierten Ruhigstellungs- und Drain-Prozedur unter [FBL-Deduplizierungs-Upgrade](/developer/mta-system#fbl-deduplication-upgrade)
und setze anschließend `FBL_DEDUP_PROTOCOL=owned-v2` und
`FBL_DEDUP_CUTOVER_ACK=quiesced-v1-intake` explizit.
::

### Umgebungsvariablen des Installers

| Variable              | Wirkung                                                                                                                                                                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `OWLAT_REPO`          | Zu klonende Git-URL (Standard `https://github.com/wolvesdotink/owlat.git`)                                                                                                                                                                                                                 |
| `OWLAT_REF`           | Zu installierende Tag/Branch/Ref (Standard: neuestes Release-Tag; fällt nur dann auf `main` zurück, wenn das Repository kein veröffentlichtes Release hat — HTTP 404. Ein harter API-Fehler oder ein Rate-Limit bricht die Installation ab, statt stillschweigend `main` zu installieren.) |
| `OWLAT_BRANCH`        | Wird nur als Fallback berücksichtigt, wenn `OWLAT_REF` nicht gesetzt ist; es fällt nicht auf `main` zurück                                                                                                                                                                                 |
| `OWLAT_INSTALL_DIR`   | Wohin geklont wird (Standard `/opt/owlat`; wird mit sudo angelegt und dir per chown übertragen, wenn das übergeordnete Verzeichnis nicht beschreibbar ist)                                                                                                                                 |
| `OWLAT_ASSUME_YES`    | `1` übergibt `--assume-yes` an den Assistenten (CI / Ansible)                                                                                                                                                                                                                              |
| `OWLAT_CONFIG_FILE`   | Pfad zu einer Antwortdatei, wird als `--config <path>` übergeben                                                                                                                                                                                                                           |
| `OWLAT_LEGACY_WIZARD` | `1` startet stattdessen den alten Bash-Assistenten (`scripts/setup.sh`)                                                                                                                                                                                                                    |

Nicht-interaktive Beispiele:

```sh
# Accept all defaults
OWLAT_ASSUME_YES=1 curl -fsSL https://get.owlat.app | bash

# Drive from a config file (CI / Ansible)
OWLAT_CONFIG_FILE=/path/to/answers.env curl -fsSL https://get.owlat.app | bash
```

## `owlat quickstart` — Deploy von Anfang bis Ende

`quickstart` (`apps/setup-cli/src/commands/quickstart.ts`) bringt einen frischen Klon bis hin zu einer laufenden, mit Admin-Konto versehenen und optional befüllten Instanz. Jeder Schritt ist idempotent, ein erneuter Lauf ist also unbedenklich.

```sh
owlat quickstart
```

Der Ablauf:

1. **Plausibilitätsprüfungen** — bestätigt, dass du dich im Monorepo befindest (unter `--owlat-dir` existiert eine `turbo.json`) und dass der Docker-Daemon erreichbar ist.
2. **Konfiguration** — fehlt `.env` oder `docker-compose.override.yml`, wird zunächst der [Setup-Assistent](#setup-wizard-web-vs-terminal) ausgeführt; andernfalls wird die vorhandene Konfiguration weiterverwendet.
3. **Modus-Abfrage** — `populated` (Admin + Demodaten, der Standard), `blank` (kein Admin, keine Daten — um den echten Registrierungsablauf `/auth/register` zu testen) oder `custom` (Entscheidung pro Schritt).
4. **Reverse-DNS-Vorabprüfung** (nur mit MTA-Profil) — setzt die Versand-Pools standardmäßig auf die primäre IPv4 des Servers, löst dann den PTR jeder Versand-IP auf und vergleicht ihn mit `EHLO_HOSTNAME`. Bei einer Abweichung wird der exakt anzulegende Eintrag ausgegeben — samt Ort (Konsole deines Hosters, nicht deine DNS-Zone) — und im Terminal eine erneute Prüfung angeboten. Nur ein Hinweis: Du darfst fortfahren, Schritt 6 nicht.
5. **`docker compose up -d`** — startet den Self-Hosting-Stack.
6. **Identitätsprüfung für den Versand** (nur mit MTA-Profil) — fragt `/health` der MTA, ob jede konfigurierte IP FCrDNS besteht. Diese Prüfung ist bindend: Die Installation bricht ab, statt eine Instanz abzuschließen, die nicht versenden kann. PTR korrigieren und `owlat quickstart` erneut ausführen — die Provisionierung setzt am Checkpoint fort.
7. **Auf Convex warten** — pollt `/version` auf dem Convex-Cloud-Port (3210). Die HTTP-Routen der Anwendung existieren erst nach dem Deploy der Functions, deshalb wird hier der Cloud-Port abgefragt.
8. **Backend deployen** — siehe [Convex-Runtime-Umgebungsvariablen pushen](#pushing-convex-runtime-env-vars-convex-deploy). Dieser Schritt erzeugt den Admin-Key, deployt die Functions und pusht die Runtime-Umgebungsvariablen.
9. **Auf HTTP-Routen warten** — pollt `/api/v1/health` auf dem Convex-Site-Proxy (3211), wo die frisch deployten `http.route`-Handler (`/seed/*`, `/dev/*`, Tracking, Webhooks) leben.
10. **Admin-Bootstrap** (außer bei `blank`) — siehe [Admin-Bootstrap](#admin-bootstrap).
11. **Beispieldaten** (außer bei `blank` oder `--no-seed`) — `POST /sample-data/install`. Ein lokales `dev`-Deployment, bei dem `OWLAT_DEV_MODE=true` bereits gesetzt ist, erhält stattdessen den umfangreicheren Datensatz `/seed/demo` (Dummy-Anmeldungen von Teamkolleginnen und -kollegen + Postbox-Postfächer); kein Installationsablauf schaltet dieses Flag jemals ein.
12. **Zusammenfassung** — gibt die URL der Web-App (`http://localhost:3000`), die Convex-URL und die Admin-E-Mail-Adresse aus.

::callout{type="info" title="Warum ein frisches Backend den Deploy-Schritt braucht"}
Ein frisch gestartetes selbst gehostetes Convex-Backend ist **leer**: Es bedient das Sync-Protokoll und `/version` auf dem Cloud-Port, hat aber keinerlei Anwendungs-Functions, kein Schema und keine Umgebungsvariablen für die Function-Runtime. Schritt 8 verwandelt dieses leere Backend in ein funktionierendes Deployment — es ist genau der Schritt, den frühere Installer komplett ausgelassen haben.
::

### Quickstart-Flags

| Flag                 | Zweck                                                                            |
| -------------------- | -------------------------------------------------------------------------------- |
| `--mode <m>`         | `populated` \| `blank` \| `custom` (überspringt die Modus-Abfrage)               |
| `--email <e>`        | Admin-E-Mail-Adresse für den Bootstrap                                           |
| `--name <n>`         | Anzeigename des Admins                                                           |
| `--password <p>`     | Admin-Passwort (mindestens 12 Zeichen)                                           |
| `--no-seed`          | Befüllung mit Demodaten überspringen                                             |
| `--assume-yes`, `-y` | Standardwerte übernehmen (impliziert Modus `populated`, Admin `dev@example.com`) |
| `--owlat-dir <dir>`  | Installationsverzeichnis (Standard: aufwärts bis zur Monorepo-Wurzel suchen)     |

```sh
# Fully scripted populated install
owlat quickstart -y --email admin@example.com --name "Admin" --password "a-strong-password"
```

## Kommandoreferenz

Führe jedes Kommando als `owlat <command>` aus (nach dem Symlink des Installers) oder als `bunx owlat-setup <command>` aus einem Klon heraus. Mit `--help` erhältst du das vollständige Usage-Banner. Optionen mit Wert kannst du als `--option wert` oder `--option=wert` angeben, vor oder nach den Argumenten des Kommandos, zum Beispiel `bunx owlat-setup env SITE_URL https://mail.example.com --owlat-dir /opt/owlat`.

| Kommando                                | Was es tut                                                                                                                                                             |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quickstart`                            | Deploy von Anfang bis Ende (Konfiguration → `up` → Deploy → Bootstrap → Seed).                                                                                         |
| `setup`                                 | Konfigurationsassistent für den Erststart — schreibt ausschließlich `.env` + `docker-compose.override.yml`.                                                            |
| `config`                                | Öffnet den Assistenten für eine bestehende Installation erneut (überspringt bereits gesetzte Felder).                                                                  |
| `bootstrap-org`                         | Legt den ersten Admin-Benutzer + die Singleton-Organisation an.                                                                                                        |
| `sample-data <install\|remove\|status>` | Optionale Demo-Inhalte für eine echte Installation und deren exakte Entfernung. Kein Dev-Modus erforderlich.                                                           |
| `seed [--reset]`                        | Vollständiger Demo-Seed nur für die Entwicklung (`OWLAT_DEV_MODE`), inklusive der Dummy-Anmeldungen von Teammitgliedern.                                               |
| `reset`                                 | Setzt die Instanz komplett auf leer zurück (um den Registrierungsablauf erneut zu testen).                                                                             |
| `feature <key> <on\|off>`               | Schaltet ein einzelnes Feature-Flag um und erzeugt das Compose-Override neu.                                                                                           |
| `pack <key> <on\|off>`                  | Schaltet alle Flags eines Feature-Pakets um.                                                                                                                           |
| `env <KEY> <VALUE>`                     | Setzt eine einzelne Umgebungsvariable in `.env`.                                                                                                                       |
| `env --show`                            | Listet die Umgebungsvariablen auf, die der aktuelle Feature-Flag-Zustand erfordert, ob sie jeweils gesetzt sind (Geheimnisse maskiert) und welches Flag sie erfordert. |
| `unset-env <KEY> [KEY...]`              | Entfernt Convex-Function-Runtime-Schlüssel aus dem Deployment und aus `.env`.                                                                                          |
| `doctor`                                | Diagnostiziert eine defekte Installation (`.env`, erforderliche Variablen, Override, Container-Zustand).                                                               |

### bootstrap-org

Legt den ersten Admin-Benutzer und die Singleton-Organisation an, indem `/seed/admin` per POST aufgerufen wird (siehe [Admin-Bootstrap](#admin-bootstrap)). Das Passwort wird clientseitig im scrypt-Format von BetterAuth gehasht, sodass das Backend eine Zugangsinformation speichert, die zu einer normalen Anmeldung passt. Das Kommando ist idempotent: Ein `409` (Admin existiert bereits) beendet es mit `0`.

```sh
owlat bootstrap-org --email admin@example.com --name "Admin" --password "a-strong-password"
```

### sample-data

Der Demo-Datensatz, den eine echte Installation tatsächlich verwenden kann. `install` sendet ein POST an `/sample-data/install`, `remove` an `/sample-data/remove`, `status` an `/sample-data/status` — alle drei authentifiziert über den Header `X-Instance-Secret` (das On-Box-Betreibergeheimnis aus `.env`, dasselbe, das auch `/seed/admin` verwendet) und **nicht** durch `OWLAT_DEV_MODE` gesteuert. Diese Unterscheidung ist Absicht: Den Dev-Modus einzuschalten, um `/seed/demo` zu erreichen, würde auch den Komplettlösch-Endpunkt `/dev/reset` freischalten und das Rate-Limiting von BetterAuth auf einer Produktivinstanz aushebeln. Wie bei `/seed/admin` wird jeder Aufruf einem Budget pro Client-IP angerechnet, bevor das Geheimnis verglichen wird (`apps/api/convex/lib/instanceSecret.ts`); wer es ausschöpft, erhält `429` mit `Retry-After`.

```sh
owlat sample-data install   # idempotent — re-running inserts nothing new
owlat sample-data status    # how many sample rows are left
owlat sample-data remove    # deletes exactly those rows (prompts unless --assume-yes)
```

Was geschrieben wird: 15 Kontakte über 3 Themen hinweg, E-Mail-Vorlagen und gespeicherte Blöcke, eine versendete Kampagne mit Statistiken je Empfänger, eine Automatisierung, ein Webhook, transaktionale E-Mail-Historie sowie eine verifizierte Versanddomain `demo.localhost`. Was **nicht** geschrieben wird: Benutzerkonten oder Postfächer. Das nur für die Entwicklung gedachte `/seed/demo` legt Dummy-Anmeldungen von Teammitgliedern an, deren Passwort-Hashes in den Fixtures des Repositorys veröffentlicht sind — die haben auf einer Instanz, die auch andere erreichen können, nichts verloren, deshalb lässt die Sample-Data-Auswahl die Loader `accounts` und `mailboxes` aus (`apps/api/convex/seedDemo/pipeline.ts` → `SAMPLE_DATA_MODULES`). Ebenfalls ausgelassen werden die Volumen-Rollups für Gmail-Massenversender, die sich auf einer echten Installation wie eine reale Domain lesen würden, die in der Compliance-Ansicht knapp unter dem Schwellwert liegt.

Der Datensatz ist **konstruktionsbedingt inert**. `/seed/demo` schreibt seine Automatisierung als `active` und seinen Webhook als aktiviert; der Sample-Data-Pfad führt dieselben Loader mit `{ inert: true }` aus, was die Automatisierung als `paused` (ohne `activatedAt`) und den Webhook als deaktiviert schreibt. Das ist wichtig, weil keines der beiden Abonnements zum Auslösezeitpunkt weiß, dass es aus einem Seed stammt: Die Automatisierung wird durch `contact_created` ausgelöst, und der Webhook-Pool greift jedes aktive Abonnement auf — eine aktive Beispielzeile würde also deiner nächsten echten Anmeldung eine Demo-Werbemail schicken und die Daten dieser Person an eine Fixture-URL posten. Schalte beides selbst ein, wenn du zusehen möchtest, wie sie laufen.

Die Entfernung ist exakt und kein Tabellen-Wipe: Jede Zeile, die ein Loader einfügt, trägt `seedTag: 'demo'`, die Entfernung löscht nur getaggte Zeilen und prüft das Tag innerhalb der Löschtransaktion erneut. Ein Beispielkontakt, den du bearbeitet hast, ist weiterhin getaggt und verschwindet ebenfalls; ein Kontakt, den du angelegt hast, ist nicht getaggt und bleibt. Das Löschen eines Beispielkontakts oder -themas löst dieselbe Kaskade aus wie ein dauerhaftes Löschen eines Kontakts, sodass eigene Zeilen, die daran hängen (eine Aktivität, ein Automatisierungslauf, eine Mitgliedschaft), mitgehen statt verwaist zurückzubleiben. Da das Tag keinen Index hat, scannt die Entfernung seitenweise aus einer Action heraus statt in einer einzigen Mutation, damit sie auf einer Instanz, die inzwischen echte Daten angesammelt hat, innerhalb des Leselimits pro Transaktion bleibt; ist eine Tabelle so groß, dass der Scan sein Seitenlimit erreicht, enthält die Antwort `truncated: true` und das CLI weist darauf hin — führe es erneut aus, um fortzufahren.

`quickstart` führt denselben Installationsschritt aus, wenn du „mit Beispieldaten erkunden“ wählst, sodass eine frische Installation nie `OWLAT_DEV_MODE` benötigt, um befüllt auszusehen.

### seed und reset

`seed` sendet ein POST an `/seed/demo`; `reset` an `/dev/reset`. Beide Endpunkte sind hinter `OWLAT_DEV_MODE` **fail-closed** abgesichert (siehe [den Hinweis zum Dev-Modus](#dev-only-endpoints)) und benötigen den Header `X-Instance-Secret`. `seed --reset` löscht seed-getaggte Zeilen, bevor neu eingefügt wird. `reset` löscht **alle** Benutzer, die Organisation und jede geseedete Zeile, sodass der nächste Besuch von `http://localhost:3000` auf `/auth/register` umleitet — verwende es nur auf Wegwerf-Instanzen.

```sh
owlat seed            # idempotent insert
owlat seed --reset    # wipe seed rows, then re-seed
owlat reset           # full wipe (prompts unless --assume-yes)
```

### feature und pack

`feature` schaltet ein Flag aus dem Katalog der [Feature-Flags](/developer/feature-flags) um und erzeugt `docker-compose.override.yml` neu; Abhängigkeitskaskaden werden angewendet und gemeldet. `pack` schaltet eine ganze Gruppe auf einmal um. Die drei Pakete sind:

| Paket         | Flags, die es steuert                                                                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `emailClient` | `inbox`, `chat`, `postbox`                                                                                                                                             |
| `marketing`   | `campaigns`, `automations`, `transactional`                                                                                                                            |
| `ai`          | `ai`, `ai.agent`, `ai.autonomy`, `ai.knowledge`, `ai.knowledge.autoLink`, `ai.knowledge.graphRetrieval`, `ai.knowledge.analytics`, `ai.assistant`, `ai.visualizations` |

```sh
owlat feature ai on        # enable a single flag
owlat pack marketing on    # enable campaigns + automations + transactional
```

Beide geben die neuen aktiven Compose-Profile aus und erinnern dich daran, `owlat apply` auszuführen, damit die Änderung wirksam wird. Beide schreiben die neue Profilliste außerdem nach `COMPOSE_PROFILES` in `.env`, sodass `.env` und das Override übereinstimmen.

Beide gehen von `.owlat-flags.json` aus, der CLI-Kopie der Instanz-Flags. `owlat feature --sync` aus dem Wrapper schreibt diese Kopie aus den Flags neu, die das laufende Backend hält, Plugin-Flags eingeschlossen, und ändert sonst nichts. Führe es aus, wenn die Kopie fehlt oder veraltet ist, zum Beispiel nach dem [Wiederherstellen eines Archivs](/developer/self-hosting-maintenance#letztes-mittel-aus-dem-backup-wiederherstellen), das erstellt wurde, bevor Backups sie enthielten. Der Stack muss dafür laufen und Convex bereit sein.

### env

Setzt eine einzelne Variable in `.env`. Der Schlüssel muss ein großgeschriebener, shell-sicherer Bezeichner sein; Werte für `*_KEY`, `*_SECRET` und `*_PASSWORD` werden in der Ausgabe maskiert.

```sh
owlat env LLM_API_KEY sk-...
owlat apply
```

`env` schreibt nur `.env`. Führe danach `owlat apply` aus, egal welcher Schlüssel es ist: Es erzeugt jeden Container neu, dessen Konfiguration sich geändert hat, und pusht die Convex-Function-Runtime-Schlüssel ins Deployment (siehe `apply` im Wrapper weiter unten).

`env --show` listet stattdessen die Variablen auf, die dein **aktueller Feature-Flag-Zustand** erfordert — dieselbe Menge erforderlicher Variablen, die `doctor` prüft, abzüglich der Docker-/Container-Prüfungen. Jede Zeile zeigt, ob die Variable gesetzt ist (Werte von `*_KEY` / `*_SECRET` / `*_PASSWORD` maskiert) und welches Flag (oder der providerabhängige Versandpfad) sie erfordert, sodass du auf einen Blick siehst, was vor dem Deployment noch fehlt.

```sh
owlat env --show
```

```
  KEY                           SET / VALUE      REQUIRED BY
────────────────────────────────────────────────────────────
✗ GOOGLE_SAFE_BROWSING_API_KEY  (unset)          scan.urls
✓ LLM_PROVIDER                  openrouter       ai
✓ MTA_API_KEY                   ********…        send path (EMAIL_PROVIDER=mta)
```

Es ist schreibgeschützt und beendet sich immer mit `0` — verwende `doctor`, wenn du ein Pass/Fail-Gate benötigst.

::callout{type="warning" title="env aktualisiert nur .env"}
`env` schreibt die Compose-Datei `.env` und sonst nichts: Noch sieht weder ein Container noch eine Convex-Function den neuen Wert. Führe [`owlat apply`](#owlat-apply) aus, damit er wirksam wird. `apply` erzeugt jeden Container neu, dessen Konfiguration sich geändert hat, und pusht die Convex-Function-Runtime-Schlüssel ins Deployment; ein Runtime-Schlüssel braucht also kein eigenes `convex env set`. Einen Runtime-Schlüssel löscht `apply` allerdings nie: Um einen zu entfernen, verwendest du [`owlat unset-env`](#unset-env), statt ihn mit `env` zu leeren.
::

### unset-env

`owlat apply` löscht nie einen Runtime-Schlüssel. Es pusht die Schlüssel, die in `.env` einen Wert haben, und lässt alles andere im Env-Speicher des Deployments unangetastet. Leerst du einen Wert mit `owlat env LLM_BASE_URL ""` oder löschst du seine Zeile aus `.env`, bleibt der alte Wert also aktiv. Um einen Schlüssel zu entfernen, nennst du ihn:

```sh
owlat unset-env LLM_BASE_URL
owlat unset-env LOCAL_EMBEDDING_BASE_URL AI_SPEND_DAILY_BUDGET_USD
```

`unset-env` führt für jeden Schlüssel `convex env remove` im `convex-deploy`-Container aus. Wie `push-env` braucht es dafür den Docker-Socket und den Convex-Admin-Schlüssel in `.env`. Danach löscht es die Zeile des Schlüssels aus `.env`, damit das nächste `apply` den Wert nicht wieder pusht. Einen Schlüssel, den das Deployment hat, `.env` aber nicht, etwa einen von Hand mit `convex env set` gesetzten, entfernt es nur aus dem Deployment.

Jeder Schlüssel wird geprüft, bevor sich etwas ändert, und eine fehlgeschlagene Prüfung stoppt den ganzen Lauf:

- Angenommen werden nur Schlüssel aus `CONVEX_RUNTIME_ENV_KEYS`, der Liste, die `apply` pusht. Eine reine Compose-Variable steht nur in `.env`, dort bearbeitest du die Datei. Variablen benannter Transport-Instanzen wie `SMTP_RELAY_HOST__BACKUP` und Plugin-Variablen (`PLUGIN_*`) stehen nicht auf der Liste. Sie werden direkt im Convex-Env-Speicher gesetzt, und du entfernst sie dort mit `convex env remove`.
- `BETTER_AUTH_SECRET`, `INSTANCE_SECRET` und `SITE_URL` braucht jede Installation, sie lassen sich nicht entfernen. Ersetze sie mit `owlat env` und `owlat apply`.
- `MTA_IP_POOLS`, `MTA_RETURN_PATH_DOMAIN` und `MTA_BOUNCE_VERP_KEY` werden abgelehnt, solange `.env` noch die Einstellung enthält, aus der sie abgeleitet werden (`IP_POOLS_TRANSACTIONAL` oder `IP_POOLS_CAMPAIGN`, `RETURN_PATH_DOMAIN`, `BOUNCE_VERP_KEY`), weil `apply` sie sonst wieder pusht. Ändere stattdessen die Quelleinstellung.
- Ohne Convex-Admin-Schlüssel in `.env` ändert sich nichts.

Zuerst wird das Deployment aktualisiert, danach `.env`. Schlägt das Backend fehl, bleibt jeder Schlüssel, den es nicht entfernt hat, an beiden Stellen stehen. Das Kommando listet diese Schlüssel auf und endet mit einem Fehlercode. Ein erneuter Aufruf ist sicher, denn das Entfernen eines schon fehlenden Schlüssels gelingt. Ein Schlüssel, der vor dem Fehler entfernt wurde, verschwindet auch aus `.env`. `unset-env` erzeugt keine Container neu. Führe danach `owlat apply` aus, wenn der Schlüssel auch einen Container konfiguriert. Ist das Setup-Image des Stacks älter als `unset-env`, ändert der Wrapper nichts und sagt dir, dass du zuerst `owlat upgrade` ausführen sollst.

### doctor

Führt eine Checkliste gegen die Installation aus und beendet sich bei jedem Fehlschlag mit einem Wert ungleich null:

1. `.env` existiert und lässt sich parsen.
2. Jede vom aktiven Feature-Set benötigte Umgebungsvariable ist befüllt.
3. **Sendepfad** — wenn ein Sende-Feature aktiv ist, ist ein Zustellanbieter konfiguriert, und (für die eingebaute MTA) werden dessen ausgehende Identität, die TCP/25-Erreichbarkeit und das DNSBL-Audit gemeldet.
4. `docker-compose.override.yml` existiert.
5. Mindestens ein Compose-Service läuft (`docker compose ps`).
6. **Container** — kein Container befindet sich in einer Neustartschleife oder fällt durch seinen Healthcheck. Von `docker compose ps` aufgeführt zu werden bedeutet nicht, dass ein Container läuft: Ein Container in einer Neustartschleife wird weiterhin aufgeführt.
7. **Version** — jeder Owlat-Container läuft tatsächlich mit der konfigurierten `OWLAT_VERSION`.

```sh
owlat doctor
```

::callout{type="warning" title="Konfigurierte Version vs. laufende Version"}
`docker-compose.yml` pinnt jedes Owlat-Image auf `${OWLAT_VERSION:-dev}`. Die Version in `.env` ist daher die Version, mit der der Stack laufen _soll_ — nicht zwingend die, mit der er _läuft_. Wird `.env` (oder der Git-Checkout) weitergezogen, ohne die Container neu zu erzeugen, driften beide auseinander, und jede Versionsanzeige im Produkt meldet den konfigurierten Wert. Prüfung 7 vergleicht beide und schlägt fehl, wenn sie nicht übereinstimmen; `owlat start` (`docker compose up -d`) wendet die konfigurierte Version an.
::

### Lifecycle-Kommandos des Wrappers

Der installierte Wrapper `/usr/local/bin/owlat` (`scripts/owlat`) stellt zusätzlich Day-2-Ops-Kommandos bereit, die reine `docker compose`-Zeremonie sind — diese gibt es nur im Wrapper und ohne `owlat-setup`-Entsprechung:

| Kommando             | Was es tut                                                                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `start`              | `docker compose up -d` (aktiviert die Profile für eingeschaltete Features).                                                                                                                                        |
| `stop`               | `docker compose down`.                                                                                                                                                                                             |
| `apply [service...]` | Bringt den laufenden Stack auf den Stand von `.env` und den aktiven Features — siehe unten. Nach `owlat env`, `owlat feature` oder einer Handänderung an `.env` ausführen.                                         |
| `restart [service]`  | `docker compose restart [service]`. Ein reiner Prozessneustart: Jeder Container behält die Umgebung, mit der er erzeugt wurde, eine `.env`-Änderung wird dadurch also **nicht** übernommen. Dafür gibt es `apply`. |
| `status`             | `docker compose ps`.                                                                                                                                                                                               |
| `logs [service]`     | `docker compose logs -f [service]`.                                                                                                                                                                                |
| `shell <service>`    | `docker compose exec <service> sh` (standardmäßig der `web`-Service).                                                                                                                                              |
| `version`            | Gibt die laufende Stack-Version aus (aus dem `web`-Container gelesen, mit Rückfall auf die lokale `.env` / `package.json`).                                                                                        |
| `install-cli`        | Verlinkt den Wrapper (erneut) nach `/usr/local/bin/owlat` und eskaliert bei Bedarf mit `sudo`. Idempotent; damit reparierst du eine Installation, deren CLI nicht im `PATH` liegt.                                 |
| `feature --sync`     | Schreibt `.owlat-flags.json` aus den Feature-Flags des laufenden Backends neu (siehe [feature und pack](#feature-und-pack)). Liest sie über den `web`-Container und funktioniert deshalb mit jeder Stack-Version.  |

Der Wrapper stellt außerdem `backup`, `restore`, `backup-schedule`, `enable-backups` und `upgrade` (Alias `update`) für Backups und In-App-Updates bereit.

#### owlat apply

Ein Wert aus `.env` erreicht Owlat auf einem von drei Wegen, und `owlat apply` deckt alle drei ab:

1. **Container-Umgebung.** Einstellungen, die die Compose-Datei in einen Container interpoliert (`EHLO_HOSTNAMES`, `IP_POOLS_TRANSACTIONAL`, `IP_POOLS_CAMPAIGN`, `WORKER_CONCURRENCY` und die übrigen MTA-Einstellungen), liest der Container einmal beim Start. `apply` führt `docker compose up -d` aus. Das erzeugt jeden Container neu, dessen aufgelöste Konfiguration sich geändert hat, und lässt die anderen weiterlaufen.
2. **Compose-Profile.** Es verwendet die Profile aus `COMPOSE_PROFILES` in `.env` zusammen mit der Liste `x-owlat-profiles` in `docker-compose.override.yml`, also dieselbe Menge wie `owlat start`. Ein Dienst, dessen Profil gerade eingeschaltet wurde, wird gestartet. Ein laufender Dienst, der zu einem Feature-Flag gehört (die Profile `mta`, `clamav`, `personal-mail`, `external-mail`, `inbox-codetasks` und `ai`), wird gestoppt und entfernt, sobald sein Profil nicht mehr aktiv ist. Dienste unter anderen Profilen laufen weiter: Ein `convex-dashboard`, das du mit `docker compose --profile dashboard up -d` gestartet hast, übersteht ein `apply`. Solche Dienste stoppst du mit `docker compose stop`.
3. **Convex-Function-Runtime-Schlüssel.** Provider-Zugangsdaten, `EMAIL_PROVIDER`, `LLM_*`, `POSTHOG_*` und die anderen Schlüssel, die Convex-Funktionen lesen, kommen aus dem Env-Speicher des Deployments, nicht aus einem Container. `apply` pusht sie mit `owlat-setup push-env` (derselbe `convex env set`-Schritt, mit dem `owlat quickstart` endet) im Setup-Image mit eingebundenem Docker-Socket. Der Push braucht den Convex-Admin-Schlüssel in `.env`. Fehlt er, meldet `apply`, warum nichts gepusht wurde, und endet mit einem Fehlercode, nachdem die Container bereits aktualisiert sind.

`owlat apply mta` (oder eine beliebige Liste von Diensten) beschränkt den Lauf auf `docker compose up -d` für diese Dienste: keine Profilbereinigung und kein Push der Runtime-Schlüssel.

`apply` pusht nur Schlüssel, die in `.env` einen Wert haben. Ein aus `.env` gelöschter Schlüssel bleibt im Deployment gesetzt. Entfernen kannst du ihn mit [`owlat unset-env`](#unset-env).

`push-env` liest `.env` nach den Regeln von docker compose, damit Convex denselben Wert bekommt wie die Container: Ein vorangestelltes `export ` wird ignoriert, ` #` (ein Leerzeichen, dann `#`) beginnt in einem Wert ohne Anführungszeichen einen Kommentar, einfache Anführungszeichen sind wörtlich, und doppelte Anführungszeichen werten `\n`, `\"`, `\\` und `\$` aus. Außerhalb einfacher Anführungszeichen steht `$$` wie in compose für ein wörtliches `$`. Ein Variablenverweis wie `${OTHER}` wird unverändert gepusht, weil compose ihn gegen die Shell auflöst, in der es läuft. Convex bekommt also den Text `${OTHER}`, nicht den aufgelösten Wert. `owlat env` und die Setup-Werkzeuge schreiben eine Zeile, die sie nicht geändert haben, genau so zurück, wie sie war, damit compose den Verweis weiter auflöst. Einen Wert, den sie selbst setzen, schreiben sie mit maskiertem `$`. Für ein wörtliches `$` schreibst du `$$`, setzt den Wert in einfache Anführungszeichen oder setzt ihn mit `owlat env`.

Ist das gepinnte Setup-Image des Stacks älter als `owlat apply` selbst (ein neues `owlat` auf dem Host vor einem älteren Stack), erzeugt `apply` die Container neu und bricht dann mit dem Hinweis ab, zuerst `owlat upgrade` auszuführen, statt ein `push-env` aufzurufen, das das Image nicht kennt.

## Convex-Runtime-Umgebungsvariablen pushen (convex-deploy)

Convex-**Functions** lesen ihre Konfiguration aus dem Deployment, nicht aus der Compose-`.env`. Die Compose-`.env` konfiguriert nur die Container-Prozesse; sie erreicht die Convex-Function-Sandbox nicht. Ein Deploy besteht daher aus drei hostseitigen Schritten (`apps/setup-cli/src/lib/convexDeploy.ts`), die allesamt reine `docker compose`-Aufrufe sind:

::steps

### Den Admin-Key erzeugen

`generateConvexAdminKey()` führt `docker compose exec convex ./generate_admin_key.sh` aus. Der Schlüssel wird **vom laufenden Backend ausgestellt** und kann nicht clientseitig fabriziert werden — eine Zufallszeichenkette wird abgelehnt. Der erzeugte Schlüssel wird als `CONVEX_ADMIN_KEY` in `.env` geschrieben, damit sich die nächsten beiden Schritte per Compose-Interpolation authentifizieren können.

### Functions deployen

`deployConvexFunctions()` führt das einmalige Deploy-Profil aus und pusht die Functions, das Schema und die `http.route`-Handler aus `apps/api`:

```sh
docker compose --profile deploy run --rm convex-deploy
```

### Runtime-Umgebungsvariablen pushen

`setConvexEnvVars()` führt `convex env set` für jede befüllte Runtime-Variable aus, wiederum über den `convex-deploy`-Container (der das CLI bereits pinnt und `CONVEX_SELF_HOSTED_URL` + `CONVEX_SELF_HOSTED_ADMIN_KEY` erhält). Die Werte gehen base64-kodiert, einer pro Zeile, über stdin in den Container. Für jeden schreibt der Container eine temporäre Datei, die nur ihr Besitzer lesen kann, führt `convex env set --from-file <Datei> -- <KEY>` aus und löscht die Datei wieder. Kein Wert steht in einer Befehlszeile, weder in der Prozessliste des Hosts noch in `Config.Cmd` des Containers noch im `convex`-Prozess darin, und keine Shell wertet einen aus.

::

Die Liste der Schlüssel, die gepusht werden, ist `CONVEX_RUNTIME_ENV_KEYS`, definiert in `packages/shared/src/convexRuntimeEnv.ts` und re-exportiert aus `apps/setup-cli/src/lib/convexDeploy.ts`, synchron gehalten mit der `EnvKey`-Union in `apps/api/convex/lib/env.ts`. Sie umfasst Auth- und Instanzgeheimnisse, Site-URLs, E-Mail-/MTA-Standardwerte, Provider-Schlüssel (Resend, SES), die LLM-Konfiguration, den Vector Store, Analytics sowie die Webhook-Geheimnisse der eingehenden Kanäle. Reine Compose-Variablen (Ports, Image-Versionen, `NUXT_PUBLIC_*`, `REDIS_*`) sind bewusst ausgeschlossen — sie gehören nie ins Deployment.

::callout{type="info" title="Der Cloud-Port vs. der Site-Proxy"}
Convex bedient das Sync-Protokoll und das eingebaute `/version` auf dem **Cloud**-Port (`3210`), aber die `http.route`-Handler der Anwendung — `/seed/admin`, `/seed/demo`, `/dev/reset`, Tracking, Webhooks, Abmeldung — leben auf dem **Site-Proxy** (`3211`) und existieren erst nach dem Deploy der Functions. Das CLI fragt `3210` ab, während es auf den Start des Backends wartet, und danach `3211`, sobald die Functions deployt sind. Ein POST auf `/seed/*` an `3210` liefert stillschweigend 404.
::

## Setup-Assistent: Web vs. Terminal

`owlat setup` (`apps/setup-cli/src/commands/setup.ts`) ist der Konfigurationsassistent für den Erststart. Er schreibt **ausschließlich** `.env` und das Compose-Override — er deployt nichts und legt dein Admin-Konto nicht an. (`config` ist derselbe Assistent, erneut geöffnet für eine bestehende Installation.)

Es gibt zwei Wege:

- **Web-Assistent** (Standard, wenn ein Browser verfügbar ist) — bereitet `.env` für den Setup-Modus vor und verweist dich auf `http://localhost:3000/setup`. Er erzeugt außerdem ein einmaliges **Setup-Token**, schreibt es in die root-eigene `.env` (`OWLAT_SETUP_TOKEN`) und gibt es auf der Konsole aus — kopiere es in den letzten Schritt des Assistenten. Die `/api/setup/*`-Endpunkte laufen unauthentifiziert (es gibt noch kein Admin-Konto), verlangen dieses Token daher in einem `X-Setup-Token`-Header, der mit einem laufzeitkonstanten Vergleich geprüft wird; ein fehlendes oder falsches Token ergibt `401`. Ohne dieses Token könnte der erste Aufrufer, der den Assistenten erreicht, das Plattform-Admin-Konto anlegen und `.env` umschreiben. Für SSH-Installationen ohne lokalen Browser verwendest du stattdessen den Terminal-Assistenten (siehe unten). Im letzten Schritt „Launch“ legt sein Endpunkt `/api/setup/apply` den Admin an (`POST /seed/admin`) **und** pusht die Umgebungsvariablen der Function-Runtime (`EMAIL_PROVIDER`, `RESEND_API_KEY` / `AWS_SES_*` / `SMTP_RELAY_*` und den Rest von [`CONVEX_RUNTIME_ENV_KEYS`](#pushing-convex-runtime-env-vars-convex-deploy)) über die Admin-API in das Convex-Deployment — das HTTP-Äquivalent zu `convex env set`, da der schreibgeschützte Web-Container den `convex-deploy`-Schritt nicht ausführen kann. So erreicht die Wahl des E-Mail-Providers tatsächlich den Versandcode und nicht nur `.env`. Der Provider-Schritt ist eine ehrliche Entscheidung auf Instanzebene — eine eigene MTA betreiben, Amazon SES oder ein SMTP-Relay (mit Presets für Mailgun/Postmark/SendGrid/Brevo oder einem eigenen Server), dazu Resend — und er validiert die Zugangsdaten, bevor es weitergeht (eine Live-API-Prüfung für Resend, ein echter SMTP-Handshake + AUTH für ein Relay).
- **Terminal-Assistent** (`--terminal`) — ein vollständiges TUI, das dieselben Fragen abdeckt: Deployment-Modus, [Feature-Auswahl](/developer/feature-flags), Versandprovider (eigene MTA / Amazon SES / SMTP-Relay / Resend), KI-Provider (OpenRouter / OpenAI / eigener OpenAI-kompatibler Dienst), optionale Integrationen (Google Safe Browsing, PostHog), das Admin-Konto und — für die selbst gehostete MTA — deine EHLO- und Bounce-Domains.

Der Assistent erzeugt alle benötigten Geheimnisse automatisch (siehe unten), spiegelt den aufgelösten Flag-Zustand nach `.owlat-flags.json` (damit `doctor`, `feature` und `pack` dieselbe Basis teilen) und schließt mit dem Hinweis ab, `owlat quickstart` auszuführen, um den Stack tatsächlich hochzufahren.

::callout{type="info" title="Web-Assistent innerhalb des Installers"}
Der Einzeiler erzwingt `--terminal`, weil der browserbasierte Assistent nicht innerhalb des containerisierten Installers laufen kann. Wähle den Web-Assistenten nur, wenn du `owlat setup` direkt auf einem Host mit Browser ausführst.
::

### Erzeugte Geheimnisse

`ensureSecrets()` (`packages/shared/src/setupSecrets.ts`) füllt jedes fehlende Geheimnis auf und bewahrt dabei Änderungen des Betreibers:

| Variable             | Format                                             |
| -------------------- | -------------------------------------------------- |
| `BETTER_AUTH_SECRET` | 48 Zeichen langes URL-sicheres Token               |
| `INSTANCE_SECRET`    | **64 Hex-Zeichen** (32 Byte) — siehe Hinweis unten |
| `UNSUBSCRIBE_SECRET` | 48 Zeichen langes URL-sicheres Token               |
| `MTA_API_KEY`        | `mta_` + 40 Zeichen langes Token                   |
| `MTA_WEBHOOK_SECRET` | `whsec_` + 40 Zeichen langes Token                 |
| `REDIS_PASSWORD`     | 32 Zeichen langes Token                            |

`CONVEX_ADMIN_KEY` wird hier bewusst **nicht** erzeugt — er muss während des Deploy-Schritts vom laufenden Backend ausgestellt werden.

::callout{type="warning" title="INSTANCE_SECRET muss hexadezimal sein"}
Das selbst gehostete Convex-Backend dekodiert `INSTANCE_SECRET` beim Start als Hex und stürzt ab (`Couldn't hexdecode key`), wenn es kein gültiges Hex ist. Der Assistent erzeugt 64 Hex-Zeichen; wenn du den Wert von Hand setzt, orientiere dich am `openssl rand -hex 32` des alten Installers.
::

### Berechtigungen von .env

Jedes Werkzeug, das `.env` schreibt (`setup`, `config`, `quickstart`, `env`, `feature` und `pack`, der Web-Assistent, der Editor für Versandanbieter und der Updater), schreibt die Datei mit Modus `600`, also nur für den Besitzer lesbar. Eine bestehende Datei wird auf Modus `600` gesetzt, bevor etwas hineingeschrieben wird. Die Datei wird an Ort und Stelle neu geschrieben, behält also ihren Besitzer, und eine einzeln per Bind-Mount eingebundene `.env` funktioniert weiter. Lässt sich der Modus nicht setzen (die Datei gehört einem anderen Konto) oder hält er nicht (ein Dateisystem ohne Unix-Berechtigungen), wird der Schreibvorgang mit einer Fehlermeldung abgelehnt, die die Datei nennt, und nichts wird geändert. Für eine bestehende Installation siehe [.env mit Modus 600](/developer/self-hosting-maintenance#env-mit-modus-600).

Im Web-Assistenten erscheint so ein Fehler im Schritt Prüfen. Das Administratorkonto und die Laufzeiteinstellungen gibt es zu diesem Zeitpunkt schon. Behebe also das Problem mit der Datei auf dem Host und starte erneut. Der zweite Versuch behält das Administratorkonto aus dem ersten Versuch und schreibt die Dateien noch einmal.

`.owlat-flags.json` enthält keine Geheimnisse, wird aber von jedem Werkzeug, das die Datei schreibt (die CLI, der Web-Assistent und der Updater), ebenfalls mit Modus `600` angelegt. Ihr Modus hängt also nicht mehr davon ab, welches Werkzeug sie zuerst geschrieben hat.

## Admin-Bootstrap

`bootstrap-org` (und `quickstart`) legen den ersten Admin an, indem sie `POST /seed/admin` aufrufen (`apps/api/convex/seedAdminHttp.ts`).

```http
POST /seed/admin
X-Instance-Secret: <INSTANCE_SECRET>
Content-Type: application/json

{ "email": "admin@example.com", "name": "Admin", "passwordHash": "<scrypt-hash>" }
```

Der Handler:

- Verlangt einen passenden `X-Instance-Secret`-Header (laufzeitsicherer Vergleich mit dem `INSTANCE_SECRET` des Deployments); eine Abweichung ergibt `401`.
- Ist **einmalig**: Existiert bereits irgendein Benutzer, liefert er `409`.
- Legt bei Erfolg (`201`) den BetterAuth-Benutzer, das Credential-Konto (mit gespeichertem scrypt-Passwort-Hash), die Singleton-Organisation (Slug aus dem lokalen Teil der E-Mail-Adresse abgeleitet), eine `owner`-Mitgliedschaft, das Benutzerprofil und die Instanzeinstellungen an.

| Status | Bedeutung                                                        |
| ------ | ---------------------------------------------------------------- |
| `201`  | Admin + Organisation angelegt                                    |
| `400`  | Ungültiges JSON oder fehlendes `email` / `name` / `passwordHash` |
| `401`  | Fehlendes oder falsches `X-Instance-Secret`                      |
| `409`  | Es existiert bereits ein Benutzer (der Endpunkt ist einmalig)    |

Das CLI hasht das Passwort vor dem Senden: `bootstrap-org` leitet einen BetterAuth-kompatiblen scrypt-Hash ab (`apps/setup-cli/src/lib/passwordHash.ts`), damit die geseedete Zugangsinformation zu einer normalen Anmeldung passt. Du sendest das Klartextpasswort nie an das Backend.

### Endpunkte nur für die Entwicklung

`/seed/demo` und `/dev/reset` sind durch `OWLAT_DEV_MODE` geschützt (`apps/api/convex/devShortcuts/_guard.ts`) und **fail-closed**: Sofern `OWLAT_DEV_MODE` in der Convex-Function-Runtime nicht wahr ist, liefern sie `403`. Lokale `dev`-Installationen haben es standardmäßig an; ein produktives Self-Hosting lässt es aus, und **nichts im Installationsablauf schaltet es ein** — Demo-Inhalte für eine echte Installation laufen über [`sample-data`](#sample-data), das per Instanzgeheimnis authentifiziert und nicht dev-gesteuert ist. `/seed/admin` selbst ist **nicht** dev-gesteuert — es ist der produktive Pfad für den Admin-Bootstrap, geschützt durch das Instanzgeheimnis und die Einmaligkeitsprüfung.
