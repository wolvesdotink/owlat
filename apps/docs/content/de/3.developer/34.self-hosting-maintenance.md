Diese Anleitung behandelt die tägliche Wartung deiner selbst gehosteten Owlat-Instanz. Für die Ersteinrichtung siehe [Self-Hosting](/developer/self-hosting).

## Aktualisieren

Owlat unterstützt drei Wege zum Aktualisieren: **in der App**, per **CLI** oder **manuell**. Alle drei tun unter der Haube dasselbe — das gepinnte Compose-Template eines getaggten Release ziehen, es anwenden und die Convex-Functions erneut deployen.

### .env mit Modus 600

`.env` enthält alle Geheimnisse des Deployments. `owlat setup`, `owlat env`, der Web-Einrichtungsassistent, der Editor für Versandanbieter und der Updater setzen die Datei bei jedem Schreiben auf Modus `600`, sodass nur der Besitzer sie lesen und schreiben kann. Wenn das nicht geht, schreiben sie nicht: wenn die Datei einem anderen Konto gehört oder das Installationsverzeichnis auf einem Dateisystem liegt, das keine Unix-Berechtigungen speichert. Die Fehlermeldung nennt die Datei, und die Datei bleibt unverändert.

Eine bestehende Installation behält ihren aktuellen Modus, bis eines dieser Werkzeuge `.env` das nächste Mal schreibt. Um sie sofort abzusichern, führe im Installationsverzeichnis als Besitzer von `.env` aus:

```bash
chmod 600 .env
ls -l .env .env.backup.* 2>/dev/null
```

`.env.backup.<timestamp>`-Dateien sind Kopien einer früheren `.env`, die der alte Bash-Assistent (`owlat setup --legacy`) angelegt hat, und sie enthalten dieselben Geheimnisse. Führe auch für sie `chmod 600` aus oder lösche die, die du nicht mehr brauchst.

Wenn ein Schreibvorgang mit `could not make it owner-only` fehlschlägt, gehört `.env` nicht dem schreibenden Konto. Bei einer Standardinstallation legt der Setup-Container `.env` als root an, und der Updater kann den Modus nur bei einer Datei ändern, die root gehört. Gib die Datei deshalb an root zurück: `sudo chown root: .env && sudo chmod 600 .env`.

### Migration für private Chat-Anhänge

Wenn die Instanz bereits Chat genutzt hat, beschränke den Benutzerzugriff während des Sicherheitsupdates und der folgenden Migration. Führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0044_private_chat_media:run
```

Warte auf den Abschluss, bevor du den Zugriff wieder freigibst. Die Migration arbeitet seitenweise und kann nach einer Unterbrechung erneut ausgeführt werden. Sie markiert alle in Chat-Nachrichten referenzierten Dateien wieder als privat, auch wenn deren Kennzeichnung entfernt wurde, und erfasst alle Medieneinträge für denselben gespeicherten Inhalt. Auch private Uploads ohne zugehörige Nachricht werden berücksichtigt. Bei einem zweiten Durchlauf ist der zurückgegebene Wert `updated` null.

Bisher gemeinsam genutzte Marketingdateien, die in einem Chat verwendet wurden, werden vorsorglich ebenfalls privat. Prüfe diese Dateien und lade bei Bedarf eine separate Kopie in die gemeinsame Medienbibliothek hoch. Update und Migration verhindern weitere Offenlegungen durch die Bibliothek; bereits heruntergeladene Kopien oder offengelegte Speicher-URLs lassen sich damit nicht zurückholen.

### Performance-Migrationen (0046 bis 0049)

Das Release nach 0.6.4 legt häufig geschriebene Zähler, Listenzahlen und Nachrichtentexte in eigene Tabellen. Die App wartet nicht auf diese Migrationen: Bis sie gelaufen sind, liest sie die neuen Zeilen und greift ersatzweise auf die alten Felder zurück. Sobald das Release stabil läuft, führe sie im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0046_split_hot_rows:run
npx convex run migrations/0047_denormalize_thread_rows:run
npx convex run migrations/0048_backfill_counters:run
npx convex run migrations/0049_move_message_bodies:run
```

- `0046_split_hot_rows` kopiert die Feature-Flags, die Instanzzähler und den belegten Speicher jedes Postfachs in eigene Zeilen.
- `0047_denormalize_thread_rows` kopiert das Zurückstellen der neuesten Nachricht sowie Absender und Betreff des Auslösers der Antwortliste in jede Unterhaltung.
- `0048_backfill_counters` beginnt mit dem Zählen der Label-, Abschnitts- und Neue-Mail-Zahlen, der Statusfilter für Kampagnen, Vorlagen und Automationen sowie des Abonnentenwachstums. Das Zählen läuft im Hintergrund weiter, nachdem der Befehl zurückgekehrt ist. `npx convex run migrations/0048_backfill_counters:status` zeigt den Fortschritt. Bis eine Zahl fertig ist, zählt die App sie auf die alte, langsamere Weise.
- `0049_move_message_bodies` verschiebt Text und HTML bestehender Nachrichten in eine eigene Tabelle, versiegelt wie zuvor.

Alle vier sind idempotent und können nach einer Unterbrechung erneut ausgeführt werden. Nachdem `0049` gelaufen ist, zeigt ein auf 0.6.4 oder älter zurückgesetztes Backend die verschobenen Nachrichten ohne ihren Text an. Führe sie deshalb erst aus, wenn du beim neuen Release bleibst.

### Bereinigung der Tiefensuche (0051)

Wenn die Tiefensuche in Nachrichtentexten (Einstellungen → Allgemein → Mailsuche) jemals aktiviert war und jetzt deaktiviert ist, führe nach dem Update einmal Folgendes aus, aus `apps/api` und mit dem richtigen Deployment konfiguriert:

```bash
npx convex run migrations/0051_clear_residual_search_bodies:run
```

Die Migration startet im Hintergrund denselben Durchlauf, der beim Deaktivieren der Einstellung startet, und löscht die gespeicherten Textauszüge. Solange die Tiefensuche aktiv ist, tut sie nichts. Läuft bereits ein Durchlauf, schließt sie sich ihm an, und sie kann gefahrlos erneut ausgeführt werden. Den Fortschritt (`status`, `scannedCount`, `clearedCount`) zeigt die Zeile in `mailBodySearchPurges` im Convex-Dashboard.

### Frühere Kontolöschungen abschließen (0052)

Die Kontolöschung läuft jetzt als nachverfolgter Auftrag, der auch den Login selbst entfernt (Passwort, Sitzungen, Passkeys, Zwei-Faktor-Geheimnis), dazu private Assistenten-Unterhaltungen und hochgeladene Mail-Archive, und eine Anfrage erst dann als abgeschlossen markiert, wenn geprüft ist, dass die Daten weg sind. Anfragen, die ein früheres Release als abgeschlossen markiert hat, können davon noch etwas übrig gelassen haben. Sobald das Release stabil läuft, führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0052_reerase_legacy_account_deletions:run
```

Sie öffnet eine abgeschlossene Anfrage nur dann erneut, wenn genau ein Login mit der Adresse der Anfrage existiert, dieser Login älter als die Anfrage ist und weder ein Profil noch eine Organisationsmitgliedschaft hat. Anfragen, die sich so nicht zuordnen lassen, zählt sie und lässt sie unverändert. Die Löschung läuft danach im Hintergrund weiter; `npx convex run auth/erasure/lifecycle:status '{"requestId": "…"}'` zeigt den Fortschritt und einen etwaigen Fehler. Die Migration ist idempotent.

### IMAP-Ordnerinhalt (0054)

Der IMAP-Server hat bisher bei jedem Befehl, der Nachrichten benennt, alle Nachrichten eines Ordners gelesen, um die Nachrichtennummern zu bestimmen. Ein Befehl für eine einzige Nachricht in einem Ordner mit 100.000 Nachrichten las also 100.000 Nachrichten. Das Backend führt jetzt pro Ordner eine kompakte Liste der Nachrichten-UIDs, und der IMAP-Server verwendet sie wieder, bis sich der Ordner ändert. Ordner, die nach dem Update angelegt werden, sind von Anfang an erfasst. Bestehende Ordner erfasst die Migration 0054, die das Backend selbst startet: Alle 10 Minuten prüft es die Migration, startet sie, falls sie noch nie gelaufen ist, und setzt sie fort, wenn sie sich eine Stunde lang nicht bewegt hat. Willst du sie früher starten, führ im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0054_backfill_folder_membership:run
```

Die Liste jedes Ordners wird im Hintergrund aufgebaut, nachdem der Befehl zurückkehrt; `npx convex run migrations/0054_backfill_folder_membership:status` zeigt, wie viele Ordner fertig sind, und meldet `completed`, sobald alle fertig sind. Bis ein Ordner fertig ist, liest der IMAP-Server ihn auf dem alten, langsameren Weg, es muss also nichts darauf warten. Die Migration ist idempotent: Nach einer Unterbrechung führst du sie erneut aus, und sie macht dort weiter, wo jeder Ordner stehen geblieben ist. `'{"rebuild": true}'` baut alle Listen aus den Nachrichten neu auf; solange das läuft, liest der IMAP-Server jeden Ordner wieder auf dem alten Weg, bis dessen Liste neu aufgebaut ist. Wird ein Neuaufbau unterbrochen, führ den Befehl ohne Argumente erneut aus: Er setzt den Neuaufbau fort, statt in einen gewöhnlichen Durchlauf zu wechseln (`status` zeigt bei einem Neuaufbau `isRebuild: true`). `'{"restart": true}'` wird abgelehnt, solange ein Neuaufbau nicht fertig ist.

Aktualisiere das Backend vor dem IMAP-Container, wie es das Update in der App und über die CLI tun: Der neue IMAP-Server ruft Funktionen auf, die das vorherige Backend nicht hat.

### Versionen von Backend und IMAP-Server

Der IMAP-Container ruft das Backend direkt auf, deshalb müssen beide dieselbe Version dieser Schnittstelle sprechen. Der unterstützte Versionsabstand:

- Aktualisiere zuerst das Backend, dann den IMAP-Container. Das Update in der App und `owlat upgrade` machen beides in dieser Reihenfolge.
- Der IMAP-Server darf höchstens ein Release hinter dem Backend liegen.
- Er ist nie neuer als das Backend. Ein neuerer IMAP-Server wartet, schreibt `Update the backend first` ins Log, versucht es erneut und nimmt den Betrieb auf, sobald das Backend deployt ist. Der manuelle Weg unten deployt das Backend in Schritt 3, bevor Schritt 4 den IMAP-Container neu erstellt.
- Ein IMAP-Server, der älter ist, als das Backend unterstützt, wird abgewiesen. Einer, der seine Version meldet (jedes Release nach 0.6.7), startet nicht: Er schreibt beide Versionen und `Update the IMAP container` ins Log und beendet sich. Ein laufender hält bei seiner nächsten erfolgreichen Meldung an, meist innerhalb von 5 Minuten nach dem Backend-Update. Eine fehlgeschlagene Meldung wird nur ins Log geschrieben, und der Server arbeitet weiter, bis eine spätere durchkommt. IMAP-Server bis 0.6.7 melden sich nicht und laufen deshalb weiter, aber das Backend lehnt ihre Anmeldungen ab, sobald es sie nicht mehr unterstützt.

Jeder IMAP-Server aus einem Release nach 0.6.7 meldet dem Backend sein Release beim Start und alle 5 Minuten. Welche IMAP-Server in den letzten 7 Tagen liefen, siehst du unter **Einstellungen → System & Updates** (Karte **IMAP-Server**), oder du führst im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run mail/imap/serverRegistry:status '{"days": 7}'
```

Die Ausgabe listet jeden Server mit Release, Protokollversion, letzter Meldung und ob das Backend ihn noch unterstützt. IMAP-Server bis 0.6.7 melden sich nicht; ihre Anmeldungen erscheinen als `legacyImapSeenAt`. Bevor du auf ein Release aktualisierst, dessen Release Notes sagen, dass es einen älteren IMAP-Server nicht mehr unterstützt, prüf den Status, bring jeden älteren IMAP-Container auf das Release, das dein Backend gerade hat (auch einen, der noch auf 0.6.7 oder älter läuft), und aktualisiere erst danach. Ein älterer IMAP-Server, der weiterläuft, wird nicht sofort angehalten. Seine neuen Anmeldungen werden abgelehnt, ebenso seine Aufrufe, die von der Änderung betroffen sind, bevor sie etwas verändern. Sitzungen, die er schon offen hatte, können die Aufrufe, die die Änderung nicht berührt, weiter nutzen, auch schreibende: `STORE`, `COPY`, `MOVE`, `APPEND` und `FETCH`, das eine Nachricht als `\Seen` markiert.

### Doppelte Block-IDs in gespeicherten E-Mails (0055)

Vor 0.6.7 bekam beim Duplizieren eines Container-, Hero-, Spalten- oder Akkordeon-Blocks im E-Mail-Editor nur die Kopie selbst eine neue ID; die Blöcke und Akkordeon-Abschnitte darin behielten die IDs des Originals. In der versendeten E-Mail öffnet oder schließt ein Klick auf eine Abschnittsüberschrift in der zweiten Kopie eines Akkordeons dann den Abschnitt in der ersten, und eine Übersetzung gilt für beide Kopien eines Blocks. Um Vorlagen und Transaktions-E-Mails zu reparieren, die vor der Korrektur gespeichert wurden, führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0055_repair_repeated_block_ids:run
```

Sie gibt jeder wiederholten ID nach der ersten eine neue und kopiert die Übersetzungen dieses Blocks auf die neue ID. So behalten beide Kopien den Text, den sie heute zeigen, und lassen sich ab dann getrennt übersetzen. E-Mails ohne wiederholte ID bleiben unverändert. Das HTML einer reparierten E-Mail wird im Hintergrund neu gerendert, so wie nach dem Bearbeiten eines gespeicherten Blocks; bis dahin wird sie mit ihrem bisherigen HTML versendet, und das Veröffentlichen wartet auf das Rendern. Ein Editor-Tab, der noch mit einer reparierten E-Mail offen ist, muss neu geladen werden, bevor er speichern kann. Den Fortschritt (`status`, `scannedCount`, `changedCount`) zeigt die Zeile `0055_repair_repeated_block_ids` in `migrationRuns` im Convex-Dashboard. Die Migration kann jederzeit laufen, setzt nach einer Unterbrechung fort und kann gefahrlos erneut ausgeführt werden.

### Bestätigungslinks nach einer Abmeldung zurückziehen (0057)

Eine globale Abmeldung zieht jetzt den offenen Double-Opt-in-Bestätigungslink des Kontakts zurück. Kontakte, die sich vor dieser Änderung abgemeldet haben, können den Link von damals noch haben. Sobald das Release stabil läuft, führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0057_withdraw_opted_out_confirmation_tokens:run
```

Sie zieht das Bestätigungstoken jedes abgemeldeten Kontakts zurück, dessen Token vor oder bei der Abmeldung ausgestellt wurde, und lässt ein danach ausgestelltes Token stehen (eine spätere Anmeldung, die auf ihre Bestätigung wartet). Der Durchlauf läuft im Hintergrund weiter; den Fortschritt (`status`, `scannedCount`, `changedCount`) zeigt die `migrationRuns`-Zeile `0057_withdraw_opted_out_confirmation_tokens` im Convex-Dashboard. Ein erneuter Aufruf setzt einen unfertigen Durchlauf fort und tut nichts mehr, sobald er abgeschlossen ist.

### Gespeicherte Antworten zuordnen (0060)

Textbausteine galten je Postfach; gespeicherte Antworten gehören einer Person oder dem Team. Jeder Lesezugriff leitet den neuen Geltungsbereich eines Textbausteins aus seinem Postfach ab, deshalb wartet nichts auf diese Migration. Sie schreibt diesen Bereich aber in jede Zeile, damit die Zeilen über ihre Besitzerin und ihr Team gefunden werden. Sobald das Release ausgerollt ist, führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0060_saved_reply_scopes:run
```

Ein Textbaustein in einem persönlichen Postfach wird zur persönlichen Antwort seiner Besitzerin; ein Textbaustein in einem Team-Postfach wird zu einer geteilten Antwort, beschränkt auf dieses Postfach. Beide behalten ihr Postfach, sodass Browser-Tabs, die vor dem Update geöffnet wurden, sie weiter finden. Ein Textbaustein, dessen Postfach nicht mehr existiert, bleibt unverändert, und seine ID wird protokolliert. Den Fortschritt (`status`, `scannedCount`, `changedCount`) zeigt die `migrationRuns`-Zeile `0060_saved_reply_scopes` im Convex-Dashboard. Ein erneuter Aufruf setzt einen unfertigen Durchlauf fort und tut nichts mehr, sobald er abgeschlossen ist.

### Sendezeit-Profile aus früheren Kampagnen (0064)

Die Planung „Pro Kontakt optimiert“ lernt die übliche Lesestunde jedes Kontakts aus neuen Öffnungen und Klicks, sobald sie eintreffen. Damit Kontakte, die schon vor dem Update reagiert haben, sofort ein Profil bekommen, führe aus `apps/api` mit der richtigen Deployment-Konfiguration aus:

```bash
npx convex run migrations/0064_backfill_send_time_profiles:run
```

Sie baut das Profil jedes Kontakts aus seinen letzten 60 Kampagnen-Sends neu auf und aus denselben Ereignissen das Stunden-Histogramm der Organisation. Es zählen nur Kampagnen, die automatisierte Öffnungen und Klicks bereits aus ihrer Statistik herausgehalten haben, sodass Abrufe durch Apple Mail Privacy Protection und Scanner-Klicks aus älteren Kampagnen nicht gelernt werden. Der Durchlauf läuft im Hintergrund weiter; den Fortschritt (`status`, `scannedCount`, `changedCount`) zeigt die `migrationRuns`-Zeile `0064_backfill_send_time_profiles` im Convex-Dashboard. Sie kann jederzeit laufen: Bis sie fertig ist, bekommen Kontakte ohne Profil die übliche Stunde der Organisation oder die Startzeit. Ein erneuter Aufruf setzt einen unfertigen Durchlauf fort; `'{"restart": true}'` baut alles neu auf.

### Antwortverlauf im Team-Postfach (0065)

Die Antwortzeiten im Team-Postfach lesen die Zeit bis zur ersten Antwort und bis zum Erledigen jeder Konversation, die Konversationen von vor 0.6.8 nicht haben. Die Auswertungsseite startet diese Nachberechnung, wenn eine Inhaberin, ein Inhaber oder ein Admin sie zum ersten Mal öffnet; um sie selbst zu starten, führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0065_backfill_thread_response_metrics:run
```

Sie setzt die Zeit der ersten Antwort jeder Konversation aus ihrer frühesten gesendeten Antwort oder Nachfass-Nachricht und danach die Erledigt-Zeit jeder erledigten oder geschlossenen Konversation aus dem Audit-Protokoll. Sie läuft im Hintergrund, nichts wartet auf sie; den Fortschritt (`status`, `scannedCount`, `changedCount`) zeigt die `migrationRuns`-Zeile `0065_backfill_thread_response_metrics` im Convex-Dashboard. Ein erneuter Aufruf setzt einen unfertigen Durchlauf fort und tut nichts mehr, sobald er abgeschlossen ist (`'{"restart":true}'` beginnt von vorn).

### Herkunft von Rückfragen (0066)

Rückfragen in der Antwort-Warteschlange und im Antwortmodus haben ihre Herkunft früher als einen englischen Satz gespeichert. Jetzt speichern sie die Domain des Absenders, und die Web-App schreibt die Zeile „Aus einer E-Mail von …“ in der Sprache der Leserin oder des Lesers. Ältere Rückfragen tragen nur den Satz; die Web-App liest die Domain daraus, deshalb wartet nichts auf diese Migration. Sie wandelt diese Rückfragen um, damit ein späteres Release das alte Feld entfernen kann. Sobald das Release ausgerollt ist, führe im Verzeichnis `apps/api` mit dem konfigurierten Ziel-Deployment aus:

```bash
npx convex run migrations/0066_backfill_clarification_origin:run
```

Sie geht alle Mail-Threads und danach alle Sitzungen des Antwortmodus durch und ersetzt jeden alten Satz durch die Domain, die er nennt. Die Herkunftszeile sieht davor und danach gleich aus. Sie läuft im Hintergrund; den Fortschritt (`status`, `scannedCount`, `changedCount`) zeigt die `migrationRuns`-Zeile `0066_backfill_clarification_origin` im Convex-Dashboard. Ein erneuter Aufruf setzt einen unfertigen Durchlauf fort und tut nichts mehr, sobald er abgeschlossen ist (`'{"restart":true}'` beginnt von vorn). Das Release, das das alte Feld entfernt, nennt diese Migration als Schritt, der vorher abgeschlossen sein muss.

### Option A: Update in der App (empfohlen)

Plattform-Admins sehen unter **Einstellungen → System & Updates** eine Benachrichtigung „Update verfügbar“, sobald eine neue Version veröffentlicht wurde. Klicke auf **Jetzt aktualisieren**, bestätige, und die Web-App wird:

1. Die gepinnte `docker-compose-<version>.yml` von den GitHub Releases herunterladen
2. Sie an den Updater-Sidecar übergeben
3. Neue Images ziehen, Convex-Functions erneut deployen, danach Container neu erstellen
4. Überprüfen, dass die neue Version aktiv ist

Die Seite fragt die Container-Gesundheit ab und lädt sich nach Abschluss des Updates automatisch neu. Gesamtdauer: typischerweise 2–5 Minuten.

Zwei Container bleiben in Schritt 3 bewusst außen vor, weil das Update _durch_ sie hindurch läuft: der **Updater** selbst und der **docker-socket-proxy**, der seine Docker-API-Aufrufe transportiert. Wird einer von beiden neu erstellt, stoppt das mitten in der Service-Liste genau den Befehl, der das Update ausführt. Der Updater übergibt seinen eigenen Austausch deshalb an einen kurzlebigen Hilfs-Container, der startet, sobald das Update gemeldet ist; der Socket-Proxy — ein Fremd-Image, dessen Konfiguration sich nur ändert, wenn ein Owlat-Release sie ändert — bleibt dem Host überlassen. Wenn die Release Notes eine Änderung an seiner Stanza nennen, führe danach im Installationsverzeichnis `docker compose up -d docker-socket-proxy` aus (oder einfach `owlat upgrade`, das ohnehin ein vollständiges `docker compose up -d` macht).

### Option B: CLI `owlat upgrade`

Wird von jedem Provisionierungspfad nach `/usr/local/bin/owlat` installiert — vom Einzeiler-Installer, vom Desktop-Setup-Assistenten und von einem manuellen `scripts/owlat quickstart`:

```bash
owlat upgrade                     # to latest
owlat upgrade --version 1.2.3     # to a specific version (useful for rollback)
```

Das CLI steuert denselben Updater-Sidecar, den auch der Ablauf in der App nutzt.

::callout{type="info" title="`owlat: command not found`?"}
Ältere Installationen, die über den Desktop-Assistenten oder ein manuelles `git clone` entstanden sind, haben den Symlink `/usr/local/bin/owlat` nie erhalten — nur der Einzeiler-Installer hat ihn angelegt. So stellst du ihn wieder her:

```bash
sudo /opt/owlat/scripts/owlat install-cli
```

Jeder Assistenten-Lauf (`quickstart`, `setup`, `config`) stellt den Link inzwischen ebenfalls sicher — ein erneutes Öffnen des Assistenten behebt das also auch. Bis dahin verwendest du `/opt/owlat/scripts/owlat <command>`; es ist dasselbe Skript.
::

### Option C: Manuell

Für Air-Gapped-Umgebungen oder wenn du Updates lieber selbst steuerst:

```bash
# 1. Pull the pinned compose template for the target version
# 2. Pull the new images
# 3. Deploy the Convex tenant functions (before any app container restarts)
# 4. Recreate the containers on the new release
curl -fsSL https://github.com/wolvesdotink/owlat/releases/download/v1.2.3/docker-compose-1.2.3.yml \
  -o docker-compose.yml &&
docker compose pull &&
docker compose --profile deploy run --rm convex-deploy &&
docker compose up -d
```

::callout{type="warning" title="Functions deployen, bevor du die Container neu erstellst"}
Neue Images ändern die Convex-Functions nicht; die deployt Schritt 3. Der Block führt ihn vor `docker compose up -d` aus, in derselben Reihenfolge wie das Update in der App und über das CLI. Die Web-, MTA- und IMAP-Container des vorigen Releases funktionieren mit den neuen Functions weiter, ein neuer Container kann aber eine Function aufrufen, die das vorige Backend noch nicht hat.

Ändert das Release das Image des Convex-Backends, erstellt Schritt 3 auch den Container `convex` neu: `docker compose run` bringt zuerst die Abhängigkeiten des Deploys auf den Stand der neuen Compose-Datei, das Backend startet also mit dem neuen Image neu, und der Deploy wartet, bis es healthy ist. Alle anderen Container laufen bis Schritt 4 mit dem vorigen Release weiter.

Die Schritte sind mit `&&` verkettet, der Block hält also beim ersten Schritt an, der fehlschlägt: Schlägt Schritt 3 fehl, läuft Schritt 4 nicht. Füg den Block als Ganzes ein; führst du die Schritte einzeln aus, prüf nach jedem, ob er geklappt hat, bevor du den nächsten ausführst. Nach einem fehlgeschlagenen Deploy führ weder `docker compose up` noch etwas anderes aus, das es ausführt (etwa `owlat apply`), bis Schritt 3 geklappt hat. Die App-Container laufen noch mit dem vorigen Release und bedienen weiter; behebe die Ursache und führ den Block erneut aus.
::

## Wiederherstellung nach einem fehlgeschlagenen Update

Schlägt ein Update mittendrin fehl, kann dein Stack in einem gemischten Zustand sein — einige Container auf der neuen Version, andere auf der alten. Der Updater fasst die Daten-Volumes nie an, und seit dem Stage-then-Promote-Ablauf ersetzt er `docker-compose.yml` erst, nachdem Images gezogen und Convex-Functions erfolgreich deployt wurden. Dennoch gilt: **Erstelle vor dem Update ein Backup** (`owlat backup`) — ein Release mit einer brechenden Schemaänderung kann Daten zurücksetzen oder migrieren, und maßgeblich dafür sind die Release Notes.

### Zuerst diagnostizieren

```bash
# What's running?
owlat status                       # or: docker compose ps

# What did each container log?
owlat logs web                     # follows the stream (Ctrl-C to exit); for a one-shot snapshot use: docker compose logs --tail=200 web
owlat logs mta
owlat logs convex
owlat logs updater

# Environment health check
owlat doctor                       # checks .env, required env vars, send path, compose override,
                                   # container health, and configured-vs-running version
```

### Wenn das Update mit einem Docker-API-Fehler abgelehnt wird

Bevor der Updater irgendetwas staged, prüft er die Docker-API, die ihm gegeben wurde. Antwortet diese Prüfung mit `403 Forbidden` (`Request forbidden by administrative rules`), bricht das Update an dieser Stelle ab — der Stack bleibt unangetastet, der Grund steht in `owlat logs updater` und `owlat logs web`.

Ursache ist die Allowlist des `docker-socket-proxy`. Instanzen, die vor **0.5.1** installiert wurden, betreiben ihn mit `NETWORKS: 0` und `VOLUMES: 0`; der Daemon beantwortet damit `docker compose up` und `docker compose run` mit einem 403 — beide lösen die Netzwerke und benannten Volumes des Projekts auf, bevor sie einen Container anfassen. Auf solchen Instanzen starb jedes In-App-Update im Schritt `convex-deploy`. Der Proxy lässt sich nicht durch sich selbst umkonfigurieren, dieser Schritt läuft daher auf dem Host:

```bash
cd /opt/owlat                      # Dein Installationsverzeichnis
docker compose up -d docker-socket-proxy
```

Liegt dort noch die `docker-compose.yml` von vor 0.5.1, hol zuerst das Template des aktuellen Releases — `owlat upgrade` erledigt das und endet in einem vollständigen `docker compose up -d`.

Danach **Jetzt aktualisieren** erneut ausführen.

### Wenn das Update wegen Speicherplatz abgelehnt wird

Jedes Release lädt einen vollständigen Satz neuer Images. Vor **0.6.0** hat nichts die Images des vorherigen Releases entfernt, sodass sich die Festplatte einer häufig aktualisierten Instanz langsam füllte, bis `docker compose pull` mit `no space left on device` fehlschlug (angezeigt als „Docker pull failed“). Bis **0.6.1** sammelten sich Images von Drittanbietern auf dieselbe Weise an. Ollama veröffentlicht alle paar Tage ein neues, rund 7 GB großes `ollama/ollama:latest`, und der Stack zog dieses bewegliche Tag bei jedem Update, wobei die vorherige Kopie ohne Tag liegen blieb. Ollama ist jetzt auf eine Version festgelegt (überschreibbar mit `OLLAMA_VERSION` in der `.env`).

Der Updater entfernt jetzt zu Beginn jedes Rollouts die Images, die kein Container verwendet:

- Owlats eigene Images, erkannt am Label des Owlat-Quell-Repositorys.
- Images ohne Tag (dangling), die ein verschobenes bewegliches Tag wie `convex-backend:latest` zurücklässt. Sie lassen sich keinem Repository mehr zuordnen, daher entfernt das auch deine eigenen Dangling-Images. Ein Dangling-Image kann niemand per Name starten.
- Ungenutzte Images mit Tag aus den Drittanbieter-Repositorys des Stacks (Ollama, Convex, Redis, Caddy und der Rest der Allowlist des Stacks).

Deine eigenen Images mit Tag und alle Daten-Volumes bleiben unangetastet. Danach prüft der Updater vor dem Pull, dass mindestens 4 GB frei sind. Reicht der Platz trotzdem nicht, bricht das Update ab, lässt den Stack unverändert und nennt den freien Speicher. Schaffe auf dem Host Platz und versuche es erneut:

```bash
docker system df                   # was den Platz belegt (Images, Volumes, Build-Cache)
docker image prune -a              # entfernt jedes Image, das kein Container verwendet
```

Ein Update führt immer der bereits installierte Updater aus. Eine Aufräumfunktion wirkt deshalb erst ab dem Update _nach_ dem Release, das sie eingeführt hat. Ist die Festplatte bereits voll, führe den Prune einmal von Hand aus, bevor du auf **Jetzt aktualisieren** klickst. Ein Rollback ist davon nicht betroffen: Er lädt die Images des alten Releases erneut.

### Wenn das Update meldet, das Release sei gestartet, aber nicht bereit

`docker compose up -d` kehrt zurück, sobald die Container gestartet sind, bevor feststeht, dass einer davon funktioniert. Danach wartet der Updater, bis jeder Dienst, den er gestartet hat, eine Bereitschaftsprüfung besteht: Ein Dienst mit Healthcheck (Convex, Redis, ClamAV) muss `healthy` melden, jeder andere Dienst muss `running` sein und darf nicht neu starten, ein einmaliger Dienst muss mit Code 0 beendet sein, all das muss wenige Sekunden später noch gelten, und die Web-App muss auf `http://web:3000/api/instance-info` antworten. Nur wenn diese Prüfung besteht, gilt das Update als erfolgreich.

Die Wartezeit beträgt drei Minuten, länger für einen Dienst, dessen Healthcheck eine lange `start_period` oder ein langes `interval` angibt: Docker prüft einen Container nur einmal pro Intervall und ignoriert Fehlschläge während der Startphase, daher erhält ein solcher Dienst Zeit bis zur Prüfung nach seiner Startphase, höchstens zwölf Minuten. ClamAV (`start_period: 600s`, `interval: 60s`) kann das Update etwa elf Minuten aufhalten. Ein Dienst, der sich bei Ende der Wartezeit noch in seiner Startphase befindet, wird als „warming up“ gemeldet. Ein Dienst, der schon vor dem Update fehlerhaft war oder ständig neu startete, lässt das Rollout nicht scheitern; er wird als Warnung aufgeführt.

Solange ein Rollout läuft, beantwortet der Updater ein zweites Update, das Anwenden von Features oder eine Secret-Rotation mit `409`. Versuche es erneut, sobald es abgeschlossen ist. `/health` beantwortet er währenddessen weiter.

Wird der Updater während eines Updates gestoppt (`docker compose restart updater`, `docker compose down`, ein Neustart des Hosts), hängt das Ergebnis davon ab, wie weit das Update gekommen ist. Solange die neue Compose-Datei noch nicht übernommen ist (Vorabprüfung, Pull, `convex-deploy`), bricht er den laufenden Befehl ab, entfernt die bereitgelegte Datei und meldet `interrupted`: Der laufende Stack ist unverändert, und du kannst das Update erneut ausführen. Ist die neue Compose-Datei übernommen, führt er `docker compose up` zu Ende, bevor er sich beendet, bricht die restliche Bereitschaftsprüfung ab und meldet `started`. Die `stop_grace_period` des Updaters beträgt 120 Sekunden, damit `up` genug Zeit hat. Wird der Updater trotzdem hart beendet, meldet er das Update beim nächsten Start als `interrupted` und gibt an, ob das Release bereits übernommen war.

Wie weit das Release gekommen ist, steht im Feld `rollout` der Antwort des Updaters; jeder Schritt (auch `readiness`) steht im Update-Verlauf:

| `rollout`           | Bedeutung                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `healthy`           | Das Release ist angewendet und jeder Dienst hat die Bereitschaftsprüfung bestanden.                                                                                                                                                                                                                                                                                                                                                |
| `started`           | Das Release ist angewendet und seine Container wurden gestartet, aber die Bereitschaftsprüfung hat nicht rechtzeitig bestanden. Die Fehlermeldung nennt jeden Dienst, der nicht bereit war, und den Grund (Healthcheck schlägt fehl, startet nach einem Absturz neu, nicht gestartet, startet noch, in der Startphase). Das Dashboard zeigt das als Warnung, nicht als fehlgeschlagenes Update: Ein erneutes Update ändert nichts. |
| `partially-applied` | `docker compose up` selbst ist fehlgeschlagen. Der Updater hat dieselben Dienste auf dem neuen Release erneut gestartet und dieselbe Bereitschaftsprüfung auf sie angewendet. Einen automatischen Rollback gibt es nicht: Die alten Container sind zu diesem Zeitpunkt entfernt, die Wiederherstellung geht also nach vorn.                                                                                                        |
| `interrupted`       | Der Updater wurde gestoppt, bevor das Update ein Ergebnis hatte. Die Zusammenfassung sagt, ob der laufende Stack unverändert blieb oder das neue Release bereits übernommen war. In beiden Fällen schließt ein erneutes Ausführen des Updates es ab.                                                                                                                                                                               |

Der Web-Container, der das Update angestoßen hat, wird dabei neu erstellt. Das Dashboard liest das Ergebnis deshalb aus dem `/health` des Updaters (`lastRollout`), der es auch in `.owlat-last-rollout.json` im Installationsverzeichnis ablegt.

Bei `started` sieh dir die genannten Dienste mit `docker compose ps` und `owlat logs <dienst>` an. Ist ClamAV der einzige Dienst, der noch startet oder sich in der Startphase befindet, warte und prüfe `docker compose ps` erneut. Bei `partially-applied` führe das Update erneut aus, sobald die Ursache behoben ist, oder führe im Installationsverzeichnis `docker compose up -d` aus.

### Rollback auf die vorherige Version

Jedes getaggte Release hängt seine `docker-compose-<version>.yml` an die GitHub-Release-Seite an. So machst du ein Rollback:

**Per CLI:**

```bash
# Replace with the last-known-good version
owlat upgrade --version 1.2.2
```

**Manuell:**

```bash
# Download the previous release's compose file, pull the pinned images,
# recreate the containers, then re-deploy the functions at the old version
curl -fsSL https://github.com/wolvesdotink/owlat/releases/download/v1.2.2/docker-compose-1.2.2.yml \
  -o docker-compose.yml &&
docker compose pull &&
docker compose up -d &&
docker compose --profile deploy run --rm convex-deploy
```

Dieser manuelle Rollback erstellt die Container neu, bevor er deployt, also in umgekehrter Reihenfolge zum Update. So laufen kurz die älteren Container gegen die neueren Functions, die Richtung, die ein Release verträgt, und nie umgekehrt. Wie beim Update sind die Befehle mit `&&` verkettet: Schlägt `docker compose up -d` fehl, laufen womöglich noch Container mit dem neueren Release, deshalb hält der Block an, bevor er die älteren Functions deployt. Scheitert der Deploy, weil das neuere Release schon Daten geschrieben hat, die das alte Schema nicht akzeptiert, spiel das Backup ein, das du vor dem Update erstellt hast.

Docker zieht die Images zu den gepinnten Tags (z. B. `ghcr.io/wolvesdotink/web:1.2.2`) und tauscht die Container an Ort und Stelle aus.

### Wenn der Web-Container nicht startet

```bash
# See why
docker compose logs web

# Rule out a stale image
docker compose pull web
docker compose up -d --force-recreate web
```

### Wenn Convex nicht startet

Convex hält die primäre Datenbank; Redis und ClamAV persistieren ebenfalls Daten, dazu kommen optionale Services (code-worker, ollama, IMAP-/ACME-Zertifikate), sofern deren Feature-Profile aktiviert sind. Wenn der Start scheitert, prüfe zuerst den Speicherplatz auf dem Volume `convex-data`:

```bash
docker system df -v | grep convex-data
```

Ist die Festplatte voll, schaffe Platz oder vergrößere das zugrunde liegende Volume. Lösche das Volume `convex-data` niemals — das ist deine Datenbank.

Die ausgelieferten Compose-Dateien rotieren das `json-file`-Log jedes Containers bei 10 MiB und behalten fünf Dateien. Prüfe auf einer älteren Installation, ob unrotierte Logs bereits Speicher belegen, bevor du den Stack mit der aktuellen Compose-Datei neu erstellst:

```bash
docker system df -v
sudo du -sh /var/lib/docker/containers/* 2>/dev/null | sort -h | tail
```

### Letztes Mittel: aus dem Backup wiederherstellen

Ist der Stack in einem nicht mehr reparablen Zustand, stelle das jüngste Backup-Archiv wieder her. Das `owlat`-CLI kapselt `scripts/restore.sh`:

```bash
owlat restore backups/owlat-YYYYMMDD-HHMMSS.tar.gz
# equivalently: bash scripts/restore.sh backups/owlat-YYYYMMDD-HHMMSS.tar.gz
```

Das Skript prüft zuerst die SHA256-Datei neben dem Archiv und liest jedes Volume-Archiv darin vollständig; ein beschädigtes, abgeschnittenes oder fehlendes Volume-Archiv bricht die Wiederherstellung ab, solange der Stack noch mit den bisherigen Daten läuft. Danach stoppt es den Stack und bricht ab, wenn noch ein Container des Projekts läuft oder ein Container ein Volume belegt. Schlägt nur `docker compose down` fehl und läuft nichts mehr, macht die Wiederherstellung weiter; auf einem frischen Host ist das der Normalfall. Gibt es auf einem frischen Host noch keine `.env`, erhält Compose die `.env` aus dem Archiv, bis die wiederhergestellte vorliegt. Bevor es ein Volume überschreibt, kopiert es den aktuellen Inhalt nach `<volume>-pre-restore-<timestamp>`; auf dem Host muss also so viel Speicher frei sein, wie die ersetzten Volumes belegen. Anschließend befüllt es die Volumes aus dem Archiv (Convex, Redis und optional ClamAV), stellt `.env`, das Compose-Override, das Caddyfile und `.owlat-flags.json` wieder her (die aktuellen bleiben als `<datei>.before-restore-<timestamp>` erhalten) und fährt alles wieder hoch.

Die Volumes landen in dem Compose-Projekt, das die wiederhergestellte Konfiguration startet. Darüber entscheiden die archivierte `.env` (mit `--keep-env` deine aktuelle) und das archivierte Compose-Override, genauso wie danach bei `docker compose up`, einschließlich eines in deiner Shell gesetzten `COMPOSE_PROJECT_NAME` und Volumes mit explizitem `name:`. Weicht dieses Projekt von dem ab, das gerade läuft, meldet das Skript das, stoppt den aktuellen Stack und lässt die Volumes des aktuellen Projekts unverändert. Es bricht ab, bevor es etwas ändert, wenn `COMPOSE_FILE` gesetzt ist, wenn neben `docker-compose.yml` eine `compose.yaml` liegt, wenn `docker compose config` die wiederherzustellende Konfiguration nicht lesen kann oder wenn zwei Volume-Archive im selben Volume landen würden. Ohne die Antwort von Compose wären die Volumes, die `docker compose up` einbindet, geraten. Meist ist die Ursache eine archivierte `.env` aus einem älteren Release, der eine Variable fehlt, die die Compose-Datei inzwischen verlangt. Schreib die Kopie aus dem Archiv nach `.env` (`tar -xzOf <archiv> ./env > .env && chmod 600 .env`), ergänze die Variable aus der Fehlermeldung und starte die Wiederherstellung erneut mit `--keep-env`. Bevor es den Stack startet, prüft es, dass die nun vorhandenen Konfigurationsdateien genau die wiederhergestellten Volumes einbinden.

`scripts/backup.sh` hält in der `VOLUMES.txt` des Archivs für jedes Volume-Archiv den Compose-Schlüssel und den Volume-Namen fest. So kommt ein Volume mit explizitem `name:` in das Volume zurück, das die wiederhergestellte Konfiguration für diesen Schlüssel einbindet. Archive aus der Zeit vor `VOLUMES.txt` enthalten nur die Namen der Volume-Archive. Das Skript gleicht sie mit den Compose-Schlüsseln und Volume-Namen der wiederhergestellten Konfiguration ab und bricht ab, bevor es etwas ändert, wenn ein Volume-Archiv zu mehreren Volumes passt oder zu keinem, während ein eingebundenes Volume keine Daten bekäme.

`.owlat-flags.json` ist die CLI-Kopie der Feature-Flags; `owlat doctor`, `owlat feature` und `owlat pack` lesen sie. Sie wird zusammen mit der Datenbank und dem Override wiederhergestellt, auch mit `--keep-env`, das nur die `.env` behält. Archive aus der Zeit, bevor Backups sie enthielten, haben keine Kopie. Das Skript legt die aktuelle Datei dann als `.owlat-flags.json.before-restore-<timestamp>` beiseite, weil sie die ersetzte Installation beschreibt, und warnt, dass die CLI bis zum nächsten Schreiben der Datei die Standard-Feature-Flags annimmt. Sobald der Stack läuft und Convex bereit ist (15–30 Sekunden nach dem Start), führe aus:

```bash
owlat feature --sync
```

Der Befehl liest die Feature-Flags der wiederhergestellten Datenbank, Plugin-Flags eingeschlossen, über den laufenden `web`-Container und schreibt sie nach `.owlat-flags.json`, dieselbe Datei, die „Anwenden & neu starten“ auf der Features-Seite schreibt. Sonst ändert er nichts: Das Compose-Override, `COMPOSE_PROFILES` und die laufenden Container bleiben, wie sie sind. Die Warnung zur fehlenden Kopie nennt diesen Schritt, ebenso die Zusammenfassung nach „Restore complete.“. Bricht die Wiederherstellung ab, bevor sie den Stack startet, behebe, was sie nennt, und führe zuerst `docker compose up -d` aus. Führe ihn aus, bevor du mit `owlat feature` oder `owlat pack` etwas umschaltest, denn bis dahin gehen diese Befehle von den Standardwerten aus und können Dienste abschalten, die die wiederhergestellte Installation nutzt. Schlägt er fehl, läuft der Stack noch nicht; prüfe `owlat status` und führe ihn erneut aus.

Lässt sich ein Volume nicht ersetzen oder unterbrichst du die Wiederherstellung (Strg+C), während sie Volumes ersetzt, kopiert das Skript die alten Daten in jedes bereits angefasste Volume zurück, lässt die Konfigurationsdateien unverändert und startet den bisherigen Stack neu. Bei einer Wiederherstellung auf einem frischen Host gibt es keinen bisherigen Stack; er bleibt dann gestoppt. Lässt sich nach den Volumes eine Konfigurationsdatei nicht wiederherstellen, meldet das Skript das und lässt den Stack gestoppt; behebe das Problem mit der genannten Datei und führe dann `docker compose up -d` aus. „Restore complete.“ meldet es erst, wenn `docker compose up -d` erfolgreich war. Die Pre-Restore-Kopien werden nie automatisch gelöscht. Sobald du die wiederhergestellte Instanz geprüft hast, entferne sie mit `docker volume rm <volume>-pre-restore-<timestamp>`; die genauen Namen gibt das Skript aus. Wie du solche Archive erzeugst und automatische Backups einrichtest, steht unter [Backups](/developer/self-hosting-production#backups). Um wiederkehrende Backups einzurichten, ohne selbst Cron-Einträge zu basteln, führe `owlat backup-schedule enable` aus — das installiert einen täglichen systemd-Timer (mit Cron als Fallback), der `scripts/backup.sh` ausführt; `owlat backup-schedule disable` entfernt ihn wieder.

### Updates automatisieren

Es gibt bewusst **keinen Cron-Job für unbeaufsichtigte Updates ab Werk**. Zwei Gründe:

1. Die Reihenfolge zählt: Functions müssen deployt werden, **bevor** die App-Container
   neu starten (der Updater in der App und `owlat upgrade` erledigen das für dich). Ein naiver
   `pull && up && deploy`-Cron — wie ihn frühere Fassungen dieser Seite
   vorschlugen — startet die Container zuerst gegen ein altes Schema neu.
2. Vor 1.0 kann ein Release eine brechende Schemaänderung enthalten. Lies die
   Release Notes, bevor du ein Update anwendest; lass sie nicht blind per Cron einspielen.

Wenn du diese Kompromisse akzeptierst, automatisiere `owlat upgrade` (das die
sichere Reihenfolge kapselt) und kombiniere es mit einem Backup vor dem Update:

```bash
# /etc/cron.d/owlat-update — automated upgrades, at your own risk
0 4 * * 0 root cd /opt/owlat && bash scripts/backup.sh && owlat upgrade
```

::callout{type="warning" title="Update-Sicherheit"}
Halte vor einem Update stets ein frisches Backup bereit. Owlat ist vor 1.0: Ein
Release kann brechende Schemaänderungen enthalten, die bestimmte Tabellen
zurücksetzen — die Release Notes weisen darauf hin, wenn das der Fall ist.
::

## Redis-Wartung

Redis ist standardmäßig mit AOF-Persistenz (Append Only File) konfiguriert. Das stellt sicher, dass die MTA-Job-Queue Container-Neustarts übersteht.

- **Kompaktierung** — Redis schreibt die AOF-Datei automatisch neu, um sie kompakt zu halten.
- **Arbeitsspeicher** — überwache den Speicherverbrauch von Redis mit `docker compose exec redis redis-cli info memory`.
- **Queue leeren** — wenn du die Queue leeren musst (z. B. nach einer Fehlkonfiguration), lösche ausschließlich die Schlüssel der Queue:

  ```bash
  docker compose exec -T redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning \
    --scan --pattern 'groupmq:owlat-mta:*' | \
    xargs -r docker compose exec -T redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning DEL
  ```

  Das verwirft alle eingereihten und laufenden E-Mail-Jobs und lässt alles andere
  in Redis unangetastet.

::callout{type="warning" title="FLUSHALL vernichtet deine privaten DKIM-Schlüssel"}
Greif nicht zu `redis-cli FLUSHALL`. Dieses Redis ist nicht nur die
Job-Queue, sondern der Geheimnisspeicher der Instanz. Es hält den **privaten**
DKIM-Schlüssel jeder Versanddomain (`mta:dkim:{domain}`), der im MTA erzeugt wird
und sonst nirgends existiert: Convex erhält immer nur den öffentlichen Teil, und
Convex-Backups enthalten ihn nicht. `FLUSHALL` entfernt außerdem die
API-Zugangsdaten pro Organisation (`mta:cred:`), den Warmup-Fortschritt der IPs
sowie die FCrDNS- und DNSBL-Caches.

Nach einem `FLUSHALL` erzeugt der MTA beim nächsten Versand ein frisches
Schlüsselpaar und signiert damit, während im DNS weiterhin der alte öffentliche
Schlüssel unter `._domainkey` steht — jede Nachricht scheitert also an DKIM, und
jede Empfängerdomain mit DMARC-Policy `p=reject` weist sie rundheraus ab. Das
Warmup beginnt wieder bei Phase 0. Die Wiederherstellung bedeutet, für jede
Versanddomain den neuen öffentlichen Schlüssel zu veröffentlichen und die
DNS-Propagation abzuwarten.
::

::callout{type="info" title="Passwortgeschütztes Redis"}
Redis verlangt immer ein `REDIS_PASSWORD` (siehe [Redis-Authentifizierung](/developer/self-hosting-production#redis-authentifizierung)), stell deshalb jedem `redis-cli`-Befehl `-a "$REDIS_PASSWORD" --no-auth-warning` voran, z. B. `docker compose exec redis redis-cli -a "$REDIS_PASSWORD" --no-auth-warning info memory`.
::

## Fehlerbehebung

### Convex startet nicht

```bash
docker compose logs convex
```

Häufige Ursachen:

- **`INSTANCE_SECRET` ist nicht gesetzt** — prüfe, ob deine `.env`-Datei eine gültige Hex-Zeichenkette enthält
- **Festplatte voll** — das Volume `convex-data` benötigt freien Speicher für die Datenbank
- **Port-Konflikt** — ein anderer Service belegt Port 3210 oder 3211

### Der MTA kann keine E-Mails versenden

```bash
docker compose logs mta
```

Häufige Ursachen:

- **`MTA_API_URL` ist in der Convex-Laufzeit nicht gesetzt** — die häufigste Ursache nach einer manuellen Installation. `MTA_API_URL` (und `MTA_API_KEY`) müssen in das Convex-Deployment übertragen werden, nicht nur in die Compose-`.env`; ohne sie löst der Versand einen harten Fehler `No system email transport configured` aus (`apps/api/convex/systemMail.ts`), bevor der MTA überhaupt erreicht wird. Prüfe das mit `npx convex env list` (oder über das Dashboard) und setze den Wert auf `http://mta:3100`. Der Assistent `owlat quickstart` erledigt das für dich.
- **Der EHLO-Hostname passt nicht zum PTR-Record** — empfangende Server weisen die Verbindung ab. Prüfe mit `dig -x YOUR_IP +short`
- **Das JSON in DKIM_KEYS ist ungültig** — validiere das JSON: `echo $DKIM_KEYS | jq .`
- **Port 25 blockiert** — viele Cloud-Anbieter (AWS, GCP, Azure) blockieren ausgehendes SMTP standardmäßig. Beantrage die Freigabe von Port 25 oder nutze ein E-Mail-Relay
- **MTA_API_KEY stimmt nicht überein** — der Key in der Docker-`.env` muss dem in den Convex-Umgebungsvariablen gesetzten entsprechen

### ClamAV startet langsam

Das ist normal. ClamAV lädt beim Start die Virendefinitionen in den Arbeitsspeicher und beim allerersten Start zusätzlich die vollständige Signaturdatenbank (~300 MB) herunter — auf einem kleinen VPS kann das mehrere Minuten dauern. Der Docker-Healthcheck hat dafür ein `start_period: 600s`.

Der MTA wartet, bis ClamAV healthy ist, bevor er startet (konfiguriert über `depends_on` in Docker Compose).

### Die Web-Oberfläche zeigt einen Verbindungsfehler

Der Browser muss das Convex-Backend direkt erreichen. Wenn `NUXT_PUBLIC_CONVEX_URL` einen Docker-internen Hostnamen verwendet (etwa `http://convex:3210`), kann der Browser keine Verbindung aufbauen.

Abhilfe: Setze `NUXT_PUBLIC_CONVEX_URL` auf eine aus dem Browser erreichbare URL:

- Lokale Entwicklung: `http://localhost:3210`
- Produktion: `https://api.example.com` (über den Reverse Proxy)

### Das Deployment der Functions schlägt fehl

```bash
docker compose --profile deploy run --rm convex-deploy 2>&1
```

Häufige Ursachen:

- **CONVEX_ADMIN_KEY ist falsch oder fehlt** — neu erzeugen: `docker compose exec convex ./generate_admin_key.sh`
- **Der Convex-Container ist nicht healthy** — mit `docker compose ps` prüfen
- **Schemakonflikt** — wenn du Convex-Schemadateien geändert hast, suche in der Deploy-Ausgabe nach Validierungsfehlern

## Umzug in die Produktion

So wechselst du von einem lokalen Entwicklungs-Setup zu einem Produktions-Deployment:

1. **URLs aktualisieren** in `.env`:

   ```bash
   NUXT_PUBLIC_CONVEX_URL=https://api.example.com
   NUXT_PUBLIC_CONVEX_SITE_URL=https://rest.api.example.com
   NUXT_PUBLIC_SITE_URL=https://owlat.example.com
   ```

2. **DNS einrichten** — A-Records, PTR, SPF, DKIM und DMARC konfigurieren. Siehe [DNS- & E-Mail-Setup](/developer/self-hosting-dns-email).

3. **Reverse Proxy ergänzen** — Caddy oder Nginx mit TLS. Siehe [Produktions-Deployment](/developer/self-hosting-production).

4. **Redis-Authentifizierung prüfen** — `REDIS_PASSWORD` ist verpflichtend und wird vom Installer erzeugt; eine ältere `.env` braucht den Schlüssel jedoch nachträglich, sonst läuft kein einziger `docker compose`-Befehl mehr. Siehe [Produktions-Deployment](/developer/self-hosting-production#redis-authentifizierung).

5. **Convex-Umgebungsvariablen aktualisieren**, damit sie zu den neuen URLs passen:

   ```bash
   npx convex env set SITE_URL "https://owlat.example.com" --url http://localhost:3210 --admin-key <key>
   # CONVEX_SITE_URL is a Convex BUILT-IN — do not set it via `convex env set`
   # (the CLI rejects it). It derives from CONVEX_SITE_ORIGIN on the convex
   # container, which docker-compose interpolates from NUXT_PUBLIC_CONVEX_SITE_URL.
   npx convex env set ALLOWED_ORIGINS "https://owlat.example.com" --url http://localhost:3210 --admin-key <key>
   ```

6. **Stack neu starten**: `docker compose up -d`

7. **Überprüfen** — sende eine Test-E-Mail und prüfe die Zustellung mit [mail-tester.com](https://www.mail-tester.com).
