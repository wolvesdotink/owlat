Dies ist der maßgebliche Wire-Contract für die ausgehenden Webhooks, die Owlat an *deine* Endpunkte sendet. Um Abonnements zu konfigurieren, Signaturen zu prüfen und das Retry-Verhalten auf höherer Ebene zu verstehen, beginne mit der [Webhooks](/api/webhooks)-Referenz; diese Seite dokumentiert die exakte JSON-Struktur jedes Ereignisses.

::callout{type="info" title="Payload-Version 1 — eingefroren"}
Jedes nachfolgende Payload ist zum Stand `payloadVersion` 1 eingefroren. Ein Feld umzubenennen, einen Typ zu ändern oder ein Feld zu entfernen, ist für Empfänger ein Breaking Change und erfordert eine Anhebung der Payload-Version. Ein Feld zu den `data` eines Ereignisses oder einen völlig neuen Ereignistyp hinzuzufügen ist **kein** Breaking Change, sofern dein Handler unbekannte Felder und Ereignisse ignoriert.
::

## Envelope

Jede Zustellung ist die JSON-serialisierte Form dieses Envelopes:

```json
{
  "event": "<event-name>",
  "timestamp": "<ISO-8601 UTC>",
  "data": { /* event-specific, see below */ }
}
```

- `event` — das Ereignis-Literal, z. B. `email.delivered`.
- `timestamp` — Zeitpunkt, zu dem der Envelope erzeugt wurde, als ISO-8601-UTC-String.
- `data` — das ereignisspezifische Payload. Der HTTP-Request-Body ist exakt die Zeichenkette `JSON.stringify({ event, timestamp, data })`, und beide HMAC-Signaturen werden über genau diese Zeichenkette berechnet.

### Signatur-Header

Jede Zustellung trägt diese Header:

| Header | Wert |
| --- | --- |
| `X-Owlat-Signature` | `t=<timestamp>,v1=<hex>`, wobei `v1` der HMAC-SHA256 über `` `${t}.${X-Webhook-Delivery-Id}.${body}` `` ist, mit deinem Webhook-Secret als Schlüssel |
| `X-Signature` | **Veraltet**, entfällt nach dem nächsten Release. HMAC-SHA256 nur über den Request-Body, hex-kodiert, mit deinem Webhook-Secret als Schlüssel |
| `X-Timestamp` | Unix-Sekunden zum Zeitpunkt des Zustellversuchs; derselbe Wert wie `t` in `X-Owlat-Signature` |
| `X-Webhook-Id` | Convex-ID des Webhook-Abonnements |
| `X-Webhook-Delivery-Id` | ID dieser Zustellung; bei jedem erneuten Versuch gleich, damit ein Empfänger eine bereits verarbeitete Zustellung ignorieren kann |
| `X-Webhook-Attempt` | Nummer dieses Zustellversuchs, beginnend bei 1 |
| `User-Agent` | `Owlat-Webhooks/1.0` |
| `Content-Type` | `application/json` |

Webhook-Secrets verwenden das Format `whsec_...` und werden beim Anlegen des Webhooks erzeugt. Prüfe `X-Owlat-Signature`, indem du den HMAC über Zeitstempel, Zustell-ID und rohen Body neu berechnest, in konstanter Zeit vergleichst und einen Zeitstempel ablehnst, der mehr als 5 Minuten abweicht — siehe das [Verifizierungsbeispiel in der Webhooks-Referenz](/api/webhooks#signaturprüfung).

::callout{type="warning" title="Über den rohen Body signieren, nicht über ein neu serialisiertes Objekt"}
Die Signatur wird über die wörtlichen Request-Bytes berechnet. Wenn dein Framework das JSON parst und neu serialisiert, bevor du es hashst, können sich Schlüsselreihenfolge oder Leerzeichen ändern und die Signatur stimmt nicht überein. Lies zuerst den rohen Body-String, verifiziere ihn und parse erst danach.
::

### Strukturvorgaben für `data`

In Payload-Version 1 ist `data` eine **flache Map aus Primitiven**: `string`, `number`, `boolean` oder `null`. Es gibt keine verschachtelten Objekte oder Arrays. Alles Strukturierte wird JSON-kodiert in ein String-Feld gelegt — siehe `topic.unsubscribed.listsRemoved` weiter unten. Eine künftige Payload-Version kann diese Vorgabe lockern.

## E-Mail-Ereignisse

Diese werden ausgelöst, während eine Kampagnen- oder transaktionale E-Mail Versand, Zustellung und Interaktion durchläuft.

### Sendungen zuordnen

Jedes `email.*`-Ereignis benennt die zugehörige Sendung mit drei Feldern. Jedes ist immer vorhanden und `null`, wenn es nicht zutrifft.

| Feld | Gesetzt für | Wert |
| --- | --- | --- |
| `sendId` | E-Mails, die über die [transaktionale API](/api/transactional) gesendet wurden | Die `transactionalEmailId`, mit der der Sendeaufruf geantwortet hat |
| `campaignId` | Kampagnen-E-Mails | Die ID der Kampagne |
| `templateId` | E-Mails, die über die transaktionale API gesendet wurden | Die ID der transaktionalen Vorlage |

Speichere die `transactionalEmailId` aus der Sendeantwort und ordne eingehende Ereignisse über `sendId` zu. `GET /api/v1/transactional/{sendId}` liest den Status derselben Sendung. E-Mails aus Automationen und dem Posteingang tragen in allen drei Feldern `null`.

### `email.sent`

Wird ausgelöst, wenn eine Kampagnen- oder transaktionale E-Mail an den Versanddienst übergeben wird. `transactionalEmailId` enthält die ID der **Vorlage**, denselben Wert wie `templateId`; das Feld bleibt für Empfänger erhalten, die es schon lesen. Um das Ereignis einer Sendung zuzuordnen, nutze `sendId`.

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "transactionalEmailId": "<Id<'transactionalEmails'> | null>",
  "timestamp": "<ISO-8601>"
}
```

### `email.delivered`

Wird ausgelöst, wenn der empfangende Mailserver die Zustellung annimmt.

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "timestamp": "<ISO-8601>"
}
```

### `email.opened`

Wird beim ersten Öffnen ausgelöst, erfasst über ein 1×1-Pixel-Beacon. Abrufe des Pixels durch Apple Mail Privacy Protection und Sicherheitsscanner zählen nicht als Öffnung und lösen dieses Ereignis nicht aus.

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "timestamp": "<ISO-8601>"
}
```

### `email.clicked`

Wird bei jedem Linkklick ausgelöst, über die Weiterleitung der getrackten URL. Links, die Sicherheits-Gateways und Linkscanner aufrufen, zählen nicht als Klick und lösen dieses Ereignis nicht aus; der Scanner wird trotzdem weitergeleitet.

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "url": "https://www.example.com/landing",
  "timestamp": "<ISO-8601>"
}
```

::callout{type="info" title="Öffnungen und Klicks nach einem Bounce oder einer Beschwerde"}
`email.opened` und `email.clicked` werden auch für einen Versand ausgelöst, der einen weichen Bounce hatte oder eine Spam-Beschwerde erhalten hat, zum Beispiel wenn ein erneuter Versuch nach einem weichen Bounce durchgekommen ist oder wenn der Empfänger die Mail nach der Meldung aus dem Spam-Ordner öffnet. Der Status des Versands bleibt `bounced` bzw. `complained`, und eine Öffnung oder ein Klick hebt nie eine Sperre auf. Werte diese Ereignisse nicht als Zeichen, dass du den Empfänger wieder anschreiben darfst: Prüfe zuerst `email.bounced`, `email.complained` und deinen eigenen Sperrstatus. Ein Versand mit hartem Bounce löst sie nie aus.
::

### `email.bounced`

Wird bei einem harten oder weichen Bounce ausgelöst, den der Dienst meldet. `message` ist der vom Dienst gelieferte Grund oder ein leerer String `""`, wenn keiner angegeben wurde.

`cause` sagt, ob die Adresse schuld ist. `recipient`: ja (ein harter Bounce heißt, die Adresse ist dauerhaft ungültig, und Owlat sperrt sie). `sender`: nichts zeigt das. Meist hat der Empfangsserver die Versand-IP oder -Domain abgelehnt, zum Beispiel wegen Reputation oder Authentifizierung; `sender` steht auch dann da, wenn der Bericht des Versanddienstes nichts gegen die Adresse sagt (kein Problem beim Empfänger, kein dauerhafter Fehlschlag). Owlat sperrt die Adresse nicht, also sperre sie auch bei dir nicht. Im Deliverability Center siehst du, was Empfangsserver ablehnen.

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "bounceType": "hard | soft",
  "cause": "recipient | sender",
  "message": "<provider reason or ''>",
  "timestamp": "<ISO-8601>"
}
```

### `email.complained`

Wird ausgelöst, wenn der Empfänger die E-Mail als Spam markiert (Feedback-Loop des Dienstes).

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "timestamp": "<ISO-8601>"
}
```

### `email.failed`

Wird einmal ausgelöst, wenn eine E-Mail nicht gesendet wird: Der Dienst hat sie abgelehnt, die Zustellung blieb über die viertägige Zustellfrist hinaus pausiert, oder der Mailserver konnte sie nicht annehmen. Einen Bounce meldet stattdessen `email.bounced`, und eine E-Mail, die nur wartet (eine pausierte Zustellung, ein erneuter Versuch), löst nichts aus, bis sie abgeschlossen ist.

Ein Empfänger, der beim Versand gesperrt, abgemeldet oder gelöscht ist, wird übersprungen. Bei einer Kampagne oder einer Automation löst so ein Überspringen kein `email.failed` aus, die Sendung wird aber trotzdem mit ihrem `errorCode` als fehlgeschlagen gespeichert und im Kampagnenbericht als fehlgeschlagen gezählt. Bei einer E-Mail, die du über die Transaktions-API gesendet hast, wird es ausgelöst, mit `errorCode` `RECIPIENT_SUPPRESSED`, `RECIPIENT_UNSUBSCRIBED` oder `CONTACT_DELETED`, denn deine Anfrage wurde mit `202` beantwortet, und so erfährst du, dass nichts rausging. Bestehende Webhooks erhalten das Ereignis erst, wenn du **E-Mail fehlgeschlagen** in ihrer Event-Liste anhakst.

```json
{
  "email": "recipient@example.com",
  "sendId": "<send id | null>",
  "campaignId": "<Id<'campaigns'> | null>",
  "templateId": "<Id<'transactionalEmails'> | null>",
  "errorCode": "MTA_UNREACHABLE",
  "message": "The mail server could not be reached before the delivery deadline passed",
  "timestamp": "<ISO-8601>"
}
```

Verzweige anhand von `errorCode`; `message` ist für Menschen gedacht und kann sich ändern. Codes, die du sehen wirst, sind unter anderem:

- `DELIVERY_HOLD_EXPIRED`: Die Zustellung war pausiert (ein offener Sicherheits-Circuit für die Zustellung oder ein nicht verfügbares Relay), bis die Frist abgelaufen war.
- `MTA_UNREACHABLE`: Der Mailserver war bis zum Ablauf der Frist nicht erreichbar.
- `DELIVERY_DEADLINE_EXPIRED` und `ROUTING_RETRY_LIMIT_EXHAUSTED`: Jeder Versuch wurde zurückgestellt, bis Zeit oder Versuche aufgebraucht waren.
- `RECIPIENT_SUPPRESSED`: Die Adresse stand auf der Unterdrückungsliste, als die E-Mail rausgehen sollte.
- `WORKPOOL_FAILED`: Der Versand-Worker ist fehlgeschlagen; `message` enthält seinen Fehler.

## Kontaktereignisse

### `contact.created`

Wird ausgelöst, wenn ein neuer Kontakt hinzugefügt wird. `source` hält fest, wie der Kontakt ins System gelangt ist.

```json
{
  "contactId": "<Id<'contacts'>>",
  "email": "person@example.com",
  "source": "api | import | form | transactional | inbound",
  "timestamp": "<ISO-8601>"
}
```

| `source` | Bedeutung |
| --- | --- |
| `api` | Über die [Kontakte-API](/api/contacts) angelegt |
| `import` | Über einen CSV-Import hinzugefügt |
| `form` | Hat ein gehostetes Formular abgesendet |
| `transactional` | Beim Versand einer transaktionalen E-Mail automatisch angelegt |
| `inbound` | Aus einer eingehenden Nachricht erstellt |

## Themen-Ereignisse

### `topic.unsubscribed`

Wird ausgelöst, wenn sich ein Kontakt von einem oder mehreren [Themen](/guide/topics) abmeldet.

```json
{
  "contactId": "<Id<'contacts'>>",
  "email": "person@example.com",
  "unsubscribedAt": 1710505200000,
  "listsRemoved": "[{\"topicId\":\"...\",\"topicName\":\"...\"}]"
}
```

::callout{type="warning" title="listsRemoved ist ein JSON-kodierter String"}
Da Payload-Version 1 nur flache Primitive erlaubt, ist `listsRemoved` ein **String**, der JSON enthält, und kein Array. Du musst ihn mit `JSON.parse` einlesen, um die Einträge zu lesen. Jeder Eintrag hat die Form `{ topicId, topicName }`. Beachte außerdem, dass `unsubscribedAt` Epoch-Millisekunden enthält (eine Zahl), anders als das ISO-8601-`timestamp` der E-Mail-Ereignisse.
::

```typescript
const removed: Array<{ topicId: string; topicName: string }> =
  JSON.parse(data.listsRemoved)
```

## Ereignisse zu Zustellbarkeitsalarmen

Leite Zustellbarkeitsalarme an dein Bereitschafts-Tool oder deinen Team-Chat weiter. Die Alarm-E-Mail läuft über deinen Mailserver. Betrifft ein Alarm genau diesen Server (Port 25 gesperrt, jede Versand-IP auf einer Blocklist), kommt die E-Mail vielleicht nie an; diese Ereignisse hängen nicht von ihm ab. Abonniere sie im Deliverability Center (**Wohin Zustellbarkeitsalarme gehen → Alarm-Webhook hinzufügen**) oder im Webhook-Formular. Bestehende Webhooks bekommen sie erst, wenn du sie zu ihrer Ereignisliste hinzufügst.

### `deliverability.alert_raised`

Wird ausgelöst, wenn eine Prüfung, die schon bestanden hatte, wieder fehlschlägt und Owlat einen Alarm auslöst, im selben Moment wie die Alarm-E-Mail.

```json
{
	"alertId": "<Id<'deliverabilityRegressionAlerts'>>",
	"checkId": "deployment.port25",
	"check": "Outbound SMTP port 25",
	"severity": "blocking | reputation | recommended",
	"scope": "deployment | domain",
	"domain": "mail.example.com",
	"message": "Outbound SMTP port 25 regressed after a confirmed pass: ...",
	"nextAction": "Request outbound TCP/25 access or configure a verified relay fallback.",
	"observedAt": "<ISO-8601>",
	"emailMayNotArrive": true,
	"isTest": false
}
```

| Feld                | Bedeutung                                                                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scope`             | `deployment` für eine Prüfung des Servers selbst, `domain` für das DNS einer Versanddomain. Bei einer Serverprüfung ist `domain` `null`.                               |
| `nextAction`        | Die Behebung, die das Deliverability Center für diese Prüfung zeigt, auf Englisch.                                                                                     |
| `emailMayNotArrive` | `true`, wenn der Alarm den Server betrifft, über den die Alarm-E-Mail rausgeht. Sie kommt dann vielleicht nicht an.                                                    |
| `isTest`            | `true`, wenn **Testalarm senden** ihn geschickt hat. `alertId` und `checkId` sind dann `test`, `nextAction` ist ein fester Satz, und keine Prüfung ist zurückgefallen. |

#### Wenn der Versand ausgesetzt wird

Dasselbe Ereignis wird ausgelöst, wenn der Versand auf der Instanz stoppt: Die stündliche Reputationsprüfung setzt ihn aus, oder ein Plattform-Admin setzt ihn aus oder sperrt die Instanz mit einem Bann. `checkId` ist `deployment.sending_hold`, `message` ist der Grund, der mit dem Status gespeichert ist, und zwei weitere Felder sagen, welche Sperre es ist und wie sie endet:

```json
{
	"alertId": "sending_hold:1795176000000",
	"checkId": "deployment.sending_hold",
	"check": "Sending suspended",
	"severity": "blocking",
	"scope": "deployment",
	"domain": null,
	"message": "Auto-suspended: complaint rate or bounce rate exceeded critical thresholds",
	"nextAction": "It lifts by itself once the bounce rate over the last 30 days is under 5%; it is 12% now. Nothing to do unless you want sending back sooner: a platform admin can lift it in the Operator console.",
	"observedAt": "<ISO-8601>",
	"emailMayNotArrive": true,
	"isTest": false,
	"holdStatus": "suspended",
	"lift": "{\"mode\":\"automatic\",\"condition\":{\"trigger\":\"bounce_rate\",\"domain\":null,\"currentPct\":12,\"limitPct\":5,\"isClear\":false,\"clearsAt\":null}}"
}
```

| Feld                | Bedeutung                                                                                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `holdStatus`        | `suspended` (ausgesetzt) oder `banned` (Bann). Nur bei diesem Alarm.                                                                                                                                            |
| `lift`              | Wie der Versand zurückkommt, als JSON-Text (Ereignisdaten enthalten nur flache Werte). Geparst ist es das Objekt `sendingHold.lift` von [`GET /api/v1/status`](/api/status). Nur bei diesem Alarm.              |
| `nextAction`        | Nichts zu tun, wenn die Sperre von selbst endet; sonst, dass ein Plattform-Admin sie in der **Operator-Konsole** aufhebt.                                                                                        |
| `emailMayNotArrive` | `true`, wenn Systemmails über den eingebauten Mailserver rausgehen, um dessen Mails es bei der Sperre geht. Die Alarm-E-Mail verlässt eine gesperrte Instanz trotzdem: Systemmails werden nicht zurückgehalten. |

Wird aus der Sperre ein Bann oder umgekehrt, bleibt es derselbe Alarm: Erst wenn der Versand wieder anläuft, kommt ein neues Ereignis. Eine Warnung löst nichts aus.

### `deliverability.alert_resolved`

Wird einmal ausgelöst, wenn der Alarm geschlossen wird. `alertId` ist dieselbe wie beim `deliverability.alert_raised`, der ihn geöffnet hat, damit du den Vorfall schließen kannst.

```json
{
	"alertId": "<Id<'deliverabilityRegressionAlerts'>>",
	"checkId": "deployment.port25",
	"check": "Outbound SMTP port 25",
	"scope": "deployment | domain",
	"domain": null,
	"resolvedAt": "<ISO-8601>",
	"resolution": "manual | automatic"
}
```

`manual` heißt, ein Admin hat den Alarm aufgelöst; `automatic` heißt, die Prüfung besteht wieder oder Owlat hat ihn geschlossen. Bei `deployment.sending_hold` kommt es, wenn der Versand wieder anläuft: `automatic`, wenn die Reputationsprüfung die Sperre von selbst aufgehoben hat, `manual`, wenn ein Plattform-Admin sie aufgehoben hat.

Die TypeScript-Typen sind `DeliverabilityAlertRaisedWebhook` und `DeliverabilityAlertResolvedWebhook` in `@owlat/public-contract`.

## `test`

Nicht abonnierbar — wird nur gesendet, wenn du im Webhook-Dashboard den Testauslöser verwendest, um einen Empfänger-Endpunkt zu prüfen. Nutze ihn, um Erreichbarkeit und Signaturprüfung deines Endpunkts zu bestätigen, bevor du dich auf Live-Ereignisse verlässt.

```json
{
  "message": "This is a test webhook from Owlat",
  "webhookId": "<Id<'webhooks'>>",
  "webhookName": "<your label>"
}
```

## Payload-Version und Vorwärtskompatibilität

Der Envelope trägt auf der Leitung kein Versionsfeld, doch jede Zeile im Zustellprotokoll speichert die `payloadVersion`, mit der sie erzeugt wurde. Schreib deinen Empfänger defensiv:

- **Unbekannte Ereignisse ignorieren.** Neue Ereignis-Literale können ohne Versionsanhebung hinzukommen; Handler, die unbekannte `event`-Werte strikt ablehnen, brechen beim Upgrade.
- **Unbekannte Felder ignorieren.** Die `data` eines Ereignisses können ohne Versionsanhebung um Felder ergänzt werden; scheitere nicht an Extras.
- **Nach Typ verzweigen, nicht nach Position.** Denk daran: `timestamp` ist bei E-Mail-/Kontaktereignissen ISO-8601, `unsubscribedAt` bei `topic.unsubscribed` hingegen Epoch-Millisekunden.

Eine künftige Version 2 kann die Beschränkung auf flache Primitive lockern und verschachtelte Arrays/Objekte zulassen (womit die JSON-String-Kodierung von `listsRemoved` entfällt). Wenn es so weit ist, wird die Version angehoben und beide Strukturen werden dokumentiert.

## Retry-Verhalten und Zustellprotokolle

Owlat behandelt jede Nicht-2xx-Antwort — ebenso wie einen Netzwerkfehler, ein Timeout oder eine URL, die auf ein privates/lokales Netzwerk auflöst — als fehlgeschlagene Zustellung und wiederholt sie mit Backoff auf insgesamt bis zu **3 Versuche**:

::steps

### Versuch 1

Wird sofort zugestellt, wenn das Ereignis ausgelöst wird.

### Versuch 2

Wiederholung nach **1 Minute**, falls Versuch 1 fehlgeschlagen ist.

### Versuch 3

Wiederholung nach **5 Minuten**, falls Versuch 2 fehlgeschlagen ist. Nach diesem letzten Versuch wird die Zustellung als fehlgeschlagen markiert und nicht erneut wiederholt.

::

Jede Anfrage hat ein **30-Sekunden-Timeout** und folgt keinen Weiterleitungen. Jeder Versuch wird in einem Zustellprotokoll mit einem dieser Status festgehalten:

| Status | Bedeutung |
| --- | --- |
| `pending` | Protokolliert, eingeplant, noch nicht versucht |
| `retrying` | Ein Versuch ist fehlgeschlagen und ein weiterer ist eingeplant |
| `success` | Der Endpunkt hat eine 2xx-Antwort geliefert |
| `failed` | Alle Versuche aufgebraucht oder der Webhook war deaktiviert/nicht auffindbar |

Protokolle erfassen den HTTP-Statuscode, einen gekürzten Response-Body (die ersten 1000 Zeichen), im Fehlerfall eine Fehlermeldung sowie die Dauer je Versuch. Da Owlat bei jeder Nicht-2xx-Antwort wiederholt, sollte dein Endpunkt **mit einem 2xx quittieren, sobald er das Ereignis dauerhaft entgegengenommen hat**, und asynchron verarbeiten — und er sollte idempotent sein, denn ein langsames oder unzuverlässiges 2xx kann dennoch zu einer doppelten Zustellung führen.
