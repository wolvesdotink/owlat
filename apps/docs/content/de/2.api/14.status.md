Prüfe, ob deine Instanz senden kann, und wenn nicht, warum und was es behebt.
Die Antwort ist derselbe Zustellstatus, den die Web-App in der Seitenleiste und
im Zustellungs-Hub zeigt. Ein Skript, ein Monitoring-Job oder ein KI-Agent kann
ihn also vor einem Start prüfen, statt es erst an einer abgelehnten Sendung zu
merken.

## Endpunkt

| Methode | Pfad             | Zweck                       |
| ------- | ---------------- | --------------------------- |
| `GET`   | `/api/v1/status` | Lesen, ob das Senden klappt |

## Authentifizierung

Die Route braucht einen API-Schlüssel mit dem Scope `status:read`. Ein
Schlüssel, der nur sendet oder nur Kontakte verwaltet, bekommt `403` mit
`data.reason` `missing_scope`, bis du einen mit `status:read` anlegst. Alles,
was die Route liefert, sieht jedes Mitglied deines Workspaces in der Web-App.
DNS-Einträge, Anbieter-Einstellungen und die Prüfungen des Deliverability
Centers gehören nicht dazu.

## Antwort

```json
{
	"data": {
		"level": "error",
		"reasonCode": "sending_suspended",
		"explanation": "Sending is suspended on this instance, so new sends are refused and campaigns hold until a platform admin of this instance reviews the recorded reason and lifts the suspension in the operator console, while transactional mail already queued is still delivered and a campaign held past its delivery deadline stops without mailing the rest.",
		"fix": { "route": "/dashboard/admin/operator", "who": "platform_admin" },
		"domains": [
			{ "domain": "mail.example.com", "status": "verified" },
			{ "domain": "news.example.com", "status": "pending" }
		],
		"rates": {
			"windowDays": 30,
			"sent": 12000,
			"bounce": { "ratePct": 1.25, "limitPct": 2, "isOver": false },
			"complaint": { "ratePct": 0.42, "limitPct": 0.1, "isOver": true }
		},
		"sendingHold": {
			"status": "suspended",
			"since": "2026-11-20T09:00:00.000Z",
			"detail": "Auto-suspended: complaint rate 0.42% over the 0.1% limit"
		}
	}
}
```

- `level` ist `ok`, `warn` (einen Blick wert) oder `error` (ein ernstes Problem,
  das die Zustellung trifft oder gefährdet: Mails werden abgelehnt,
  zurückgehalten oder verzögert, oder eine Bounce-Rate liegt über der Grenze,
  ab der das Senden gesperrt wird). Ob das Senden gerade gesperrt ist,
  sagt `sendingHold`, nicht `level`.
- `reasonCode` nennt das schwerste Problem. Treffen mehrere zu, gewinnt das
  schwerste, und bei gleichem Gewicht steht eine Sperre an erster Stelle.
  Verzweige nach dem Code; `explanation` ist ein englischer Satz für Menschen.
- `fix.route` ist die Seite in der Web-App deiner Instanz, auf der das Problem
  behoben wird, und `fix.who` sagt, wer es dort kann: `workspace_admin`,
  `platform_admin` (ein Admin der ganzen Instanz), `contact_manager` oder
  `deployment_operator` (wer die Umgebung des Deployments setzt). `fix` ist
  `null`, solange das Senden in Ordnung ist.
- `domains` listet jede Absenderdomain mit ihrem Prüfstatus: `registering`,
  `pending`, `verified` oder `failed`. Nur eine verifizierte Domain kann
  senden.
- `rates` enthält die Bounce- und Beschwerderate der letzten 30 Tage in Prozent,
  neben der Grenze, ab der sie gegen dein Senden zählen. `isOver` ist `true`,
  sobald eine Rate ihre Grenze erreicht. `rates` ist `null`, solange der
  Zeitraum keine Sendungen, Zustellungen, Bounces oder Beschwerden enthält.
- `sendingHold` ist gesetzt, solange das Senden gesperrt oder dauerhaft
  deaktiviert ist. Es hat die Felder `status`, `since` und `detail` der `403`,
  die eine transaktionale Sendung bei gesperrtem Senden bekommt, sodass ein
  Client an beiden Stellen dieselbe Form liest. `detail` ist der Grund, der mit
  der Sperre gespeichert wurde. `sendingHold` ist `null`, solange das Senden
  erlaubt ist.

## Grund-Codes

Neue Codes können dazukommen. Behandle einen unbekannten Code nach seinem
`level`.

| Code                             | Level   | Was zu tun ist                                                                                                                                              |
| -------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `healthy`                        | `ok`    | Nichts.                                                                                                                                                     |
| `sending_suspended`              | `error` | Ein Plattform-Admin prüft den Grund in `sendingHold.detail` und hebt die Sperre in der Operator-Konsole auf.                                                |
| `sending_banned`                 | `error` | Das Senden bleibt deaktiviert, bis ein Plattform-Admin die Sperre in der Operator-Konsole aufhebt.                                                          |
| `no_provider`                    | `error` | Ein Admin richtet auf der Seite für den Zustellweg einen Anbieter ein.                                                                                      |
| `no_provider_transactional`      | `error` | Ein Admin ergänzt einen Anbieter für den transaktionalen Weg.                                                                                               |
| `no_provider_campaign`           | `error` | Ein Admin ergänzt einen Anbieter für den Kampagnenweg.                                                                                                      |
| `feedback_missing_campaign`      | `error` | Der Betreiber setzt die Bounce- und Beschwerde-Einstellungen des Kampagnenanbieters in der Umgebung des Deployments. Bis dahin werden Kampagnen abgelehnt.  |
| `feedback_missing_transactional` | `warn`  | Der Betreiber setzt die Bounce- und Beschwerde-Einstellungen des transaktionalen Anbieters. Bis dahin werden schlechte Adressen nicht unterdrückt.          |
| `mta_signing_held`               | `error` | Mails der genannten Domains werden ohne nutzbaren DKIM-Schlüssel zurückgehalten. Ein Admin behebt Schlüssel und Eintrag auf der Seite der Absenderdomains.  |
| `mta_signing_held_unnamed`       | `error` | Dasselbe für eine Domain, die der Mailserver nicht genannt hat.                                                                                             |
| `mta_degraded`                   | `error` | Der eingebaute Mailserver meldet ein Problem. Ein Admin prüft ihn auf der Seite für den Zustellweg.                                                         |
| `mta_unreachable`                | `error` | Owlat erreicht den eingebauten Mailserver nicht. Ein Admin prüft ihn.                                                                                       |
| `mta_stale`                      | `warn`  | Der Mailserver hat seinen Zustand länger nicht gemeldet.                                                                                                    |
| `mta_unchecked`                  | `warn`  | Der Mailserver hat seinen Zustand noch nicht gemeldet.                                                                                                      |
| `ips_all_held`                   | `error` | Alle Sende-IPs eines Pools sind zurückgehalten, etwa wegen einer Blockliste. Ein Admin prüft sie auf der Deliverability-Seite.                              |
| `ips_some_held`                  | `warn`  | Einige Sende-IPs sind zurückgehalten, die übrigen tragen die Mails mit weniger Volumen.                                                                     |
| `domain_failed`                  | `error` | Eine Absenderdomain ist bei Einrichtung oder Prüfung gescheitert. Ein Admin behebt den Fehler auf der Seite der Absenderdomains und prüft sie erneut.       |
| `no_domain`                      | `error` | Ein Admin legt eine Absenderdomain an und verifiziert sie.                                                                                                  |
| `no_verified_domain`             | `error` | Ein Admin veröffentlicht die DNS-Einträge einer Domain und verifiziert sie.                                                                                 |
| `domain_pending`                 | `warn`  | Eine Absenderdomain wartet noch auf die DNS-Prüfung.                                                                                                        |
| `sender_missing`                 | `error` | Ein Admin setzt einen Standardabsender für transaktionale Mails.                                                                                            |
| `sender_unverified`              | `error` | Die Domain des transaktionalen Standardabsenders ist nicht verifiziert. Ein Admin verifiziert sie oder wählt einen Absender auf einer verifizierten Domain. |
| `warmup_halted`                  | `warn`  | Das IP-Warm-up ist angehalten, das Kampagnenvolumen wächst nicht weiter, bis ein Admin es prüft.                                                            |
| `reputation_critical`            | `error` | Eine Rate liegt über der kritischen Grenze, ab der das Senden automatisch gesperrt wird. Schreib keine Adressen mehr an, die bouncen oder nie reagieren.    |
| `reputation_high`                | `warn`  | Eine Rate ist so hoch, dass sie das Senden gefährdet. Räum die Liste auf.                                                                                   |
| `reputation_medium`              | `warn`  | Eine Rate liegt über ihrer Grenze. Räum die Liste vor der nächsten Sendung auf.                                                                             |

## Abfragen aus einem Job oder Agenten

Der Status ändert sich über Minuten, nicht Sekunden: Der eingebaute Mailserver
meldet seinen Zustand alle zwei Minuten, und die Raten bewegen sich mit den
Mails, die du sendest. Alle fünf Minuten reicht für einen Monitoring-Job, öfter
als einmal pro Minute bringt nichts. Die Route zählt wie jeder andere Aufruf
gegen das Rate-Limit des Schlüssels (siehe
[Authentifizierung](/api/authentication)).

Ein Agent, der gefragt wird, warum keine Mails rausgehen, kann `reasonCode` und
`explanation` lesen und der Person sagen, welche Seite sie öffnen soll
(`fix.route`) und wen sie fragen soll (`fix.who`). Willst du von einer
fehlschlagenden Deliverability-Prüfung erfahren, ohne zu fragen, abonniere mit
einem Webhook `deliverability.alert_raised` (siehe
[Webhook-Payloads](/api/webhook-payloads)).

Mit einem SDK:

```ts
const status = await owlat.status.get();
if (status.level === 'error') console.warn(status.reasonCode, status.fix?.route);
```

```java
DeliveryStatus status = owlat.status().get();
```
