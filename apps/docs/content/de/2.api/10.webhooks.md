Owlat unterstützt sowohl ausgehende Kunden-Webhooks als auch eingehende Provider-Webhooks.

## Ausgehende Kunden-Webhooks

Konfiguration unter **Einstellungen → Webhooks**.

Unterstützte ausgehende Events:

- `email.sent`
- `email.delivered`
- `email.opened`
- `email.clicked`
- `email.bounced`
- `email.complained`
- `contact.created`
- `topic.unsubscribed`

### Hinweise zur Zustellung

- Der Endpunkt muss `POST` akzeptieren
- Verwenden Sie öffentlich erreichbare HTTP/HTTPS-URLs
- Hosts in privaten/lokalen Netzwerken werden abgelehnt
- Fehlgeschlagene Zustellungen werden erfasst und können erneut versucht werden

### Signaturprüfung

Webhook-Secrets verwenden das Format `whsec_...` und werden bei der Erstellung des Webhooks generiert.

Jede Zustellung enthält diese Header:

| Header                  | Beschreibung                                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-Owlat-Signature`     | `t=<timestamp>,v1=<signature>`: `v1` ist der HMAC-SHA256-Hex-Digest über `` `${t}.${X-Webhook-Delivery-Id}.${body}` ``, mit Ihrem Secret als Schlüssel |
| `X-Signature`           | **Veraltet.** HMAC-SHA256-Hex-Digest nur über den JSON-Payload-Body                                                                                    |
| `X-Timestamp`           | Unix-Zeitstempel (Sekunden) zum Zeitpunkt des Versands dieses Versuchs; derselbe Wert wie `t` in `X-Owlat-Signature`                                   |
| `X-Webhook-Id`          | Die Webhook-ID                                                                                                                                         |
| `X-Webhook-Delivery-Id` | ID dieser Zustellung; bei jedem erneuten Versuch gleich, damit ein Empfänger eine bereits verarbeitete Zustellung ignorieren kann                      |
| `X-Webhook-Attempt`     | Nummer dieses Zustellversuchs, beginnend bei 1                                                                                                         |
| `Content-Type`          | `application/json`                                                                                                                                     |
| `User-Agent`            | `Owlat-Webhooks/1.0`                                                                                                                                   |

Prüfen Sie `X-Owlat-Signature`. Ihre `v1`-Signatur deckt neben dem Body auch den Zeitstempel und die Zustell-ID ab. Eine gültige Signatur bestätigt also, dass `X-Timestamp` und `X-Webhook-Delivery-Id` die Werte sind, die Owlat gesendet hat. Danach:

1. Lehnen Sie die Anfrage ab, wenn `t` mehr als 5 Minuten von der Uhr Ihres Servers abweicht.
2. Ignorieren Sie eine Zustell-ID, die Sie bereits verarbeitet haben. Ein erneuter Versuch trägt dieselbe `X-Webhook-Delivery-Id` mit neuem Zeitstempel und neuer Signatur und kann nach Ablauf des 5-Minuten-Fensters eintreffen (siehe unten zum Wiederholungsverhalten). Speichern Sie verarbeitete IDs deshalb mindestens 24 Stunden, nicht nur für das Zeitfenster. Speichern Sie eine ID erst, wenn Ihr Handler erfolgreich war. Schlägt die Verarbeitung fehl, antworten Sie mit einem Status außerhalb von `2xx` und speichern die ID nicht, damit der erneute Versuch verarbeitet wird.

::callout{type="warning" title="X-Signature ist veraltet"}
`X-Signature` signiert nur den Body. Die Signatur deckt weder `X-Timestamp` noch `X-Webhook-Delivery-Id` ab, ein Empfänger, der nur sie prüft, erkennt also nicht, ob diese Header verändert wurden. Owlat sendet sie noch ein weiteres Release lang neben `X-Owlat-Signature`, damit bestehende Empfänger weiter funktionieren, und stellt sie danach ein. Stellen Sie Ihren Empfänger jetzt auf `X-Owlat-Signature` um.
::

#### Aufbau des Payloads

```json
{
	"event": "email.delivered",
	"timestamp": "2026-03-15T12:00:00.000Z",
	"data": {/* event-specific data */}
}
```

Der `timestamp` im Payload gibt an, wann das Ereignis erzeugt wurde, und bleibt bei jedem erneuten Versuch gleich. Prüfen Sie die Aktualität anhand von `t`, nicht anhand dieses Felds.

#### Beispiel zur Prüfung (Node.js)

```typescript
import crypto from 'node:crypto';

const TOLERANCE_SECONDS = 300;

function verifyOwlatWebhook(headers: Headers, body: string, secret: string): boolean {
	const timestamp = headers.get('X-Timestamp') ?? '';
	const deliveryId = headers.get('X-Webhook-Delivery-Id') ?? '';
	const fields = new Map(
		(headers.get('X-Owlat-Signature') ?? '').split(',').map((part): [string, string] => {
			const eq = part.indexOf('=');
			return [part.slice(0, eq), part.slice(eq + 1)];
		})
	);
	const v1 = fields.get('v1');
	if (!v1 || !deliveryId || !/^\d+$/.test(timestamp) || fields.get('t') !== timestamp) {
		return false;
	}

	// 1. Die Signatur deckt Zeitstempel, Zustell-ID und rohen Body ab.
	const expected = crypto
		.createHmac('sha256', secret)
		.update(`${timestamp}.${deliveryId}.${body}`)
		.digest();
	const presented = Buffer.from(v1, 'hex');
	if (presented.length !== expected.length || !crypto.timingSafeEqual(presented, expected)) {
		return false;
	}

	// 2. Aktualität: Anfragen ablehnen, die mehr als 5 Minuten von jetzt abweichen.
	return Math.abs(Date.now() / 1000 - Number(timestamp)) <= TOLERANCE_SECONDS;
}

// In Ihrem Webhook-Handler:
const body = await request.text(); // der rohe Body, vor jedem JSON-Parsing
if (!verifyOwlatWebhook(request.headers, body, webhookSecret)) {
	return new Response('Invalid signature', { status: 401 });
}
// Danach das Ereignis überspringen, wenn diese X-Webhook-Delivery-Id schon verarbeitet wurde.
```

### Wiederholungsverhalten

Fehlgeschlagene Zustellungen werden bis zu **3-mal** erneut versucht:

1. Sofort
2. Nach 1 Minute
3. Nach 5 Minuten

Jede Anfrage hat ein **Timeout von 30 Sekunden**. Endpunkte, die auf IPs in privaten/lokalen Netzwerken auflösen, werden abgelehnt.

Geht ein Versuch verloren, bevor er ein Ergebnis festhält (etwa weil das Backend während der Anfrage neu startet), sendet Owlat ihn mit derselben `X-Webhook-Delivery-Id` erneut, höchstens dreimal, und markiert die Zustellung danach als fehlgeschlagen. Zustellungen, die ein Release vor 0.5.6 wartend hinterlassen hat, werden nach dem Update ebenso aufgegriffen, außer sie warten schon länger als 24 Stunden. Diese werden nicht gesendet. Sie erscheinen im Zustellprotokoll als fehlgeschlagen, mit dem Fehler „Abandoned: stuck before the delivery-recovery upgrade“.

## Eingehende Provider-Webhook-Routen

Das sind die Endpunkte, die Owlat selbst bereitstellt, um Zustellstatus und eingehende Mail von seinem Versandprovider entgegenzunehmen. Sie sind von den oben beschriebenen ausgehenden Webhooks zu unterscheiden, die Owlat an _Ihre_ Endpunkte sendet.

Jeder rückmeldefähige Versandweg besitzt eine feste eingehende Route:

| Route                     | Provider                | Wann sie verwendet wird                 |
| ------------------------- | ----------------------- | --------------------------------------- |
| `POST /webhooks/mta`      | Mitgelieferte Owlat-MTA | Standard beim Self-Hosting              |
| `POST /webhooks/ses`      | Amazon SES über SNS     | Wenn SES-Feedback konfiguriert ist      |
| `POST /webhooks/resend`   | Resend                  | Wenn als Versandprovider konfiguriert   |
| `POST /webhooks/mandrill` | Mailchimp Transactional | Wenn Mandrill-Feedback konfiguriert ist |
| `POST /webhooks/emailit`  | Emailit                 | Wenn Emailit-Feedback konfiguriert ist  |

Eine Anfrage ohne die Signatur-Header, die das Verfahren ihres Providers verlangt, wird mit `401` abgelehnt, bevor ihr Body gelesen wird. Außer bei SES prüft jede Route dann die Signatur, bevor sie das Rate-Limit des Providers belastet, sodass unsignierter Verkehr das Limit echter Zustellungen nicht aufbrauchen kann. Diese kostenlose Prüfung gilt für Bodies, die höchstens 256 KiB angeben. Ein größerer oder gechunkter Body (etwa ein großer Mandrill-Batch `mandrill_events`, bis zur Grenze von 5 MiB) wird vor dem Lesen einem eigenen Limit angerechnet, das er mit allen anderen großen unverifizierten Anfragen auf dieser Route teilt. Bei einer Flut großer Junk-Anfragen auf derselben Route kann ein solcher Batch mit `429` beantwortet werden; der Provider wiederholt ihn später, wie bei jeder Antwort außerhalb von 2xx.

### Route der mitgelieferten MTA

```http
POST /webhooks/mta
```

Bei selbst gehosteten Deployments ist die mitgelieferte MTA der Standardversandweg, daher ist dies die primäre eingehende Route. Sie verarbeitet Zustellstatus, eingehende Mail und betriebliche Reputationsereignisse:

| Event                                                                        | Wirkung                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bounced`                                                                    | Erfasst den Bounce (hard/soft, von der MTA vorklassifiziert) und aktualisiert Blockliste + Kontaktaktivität                                                                                                                                                                                                      |
| `complained`                                                                 | Erfasst die Spam-Beschwerde und aktualisiert Blockliste + Kontaktaktivität                                                                                                                                                                                                                                       |
| `sent`                                                                       | Markiert den Versand als abgesetzt                                                                                                                                                                                                                                                                               |
| `inbound.received`                                                           | Nimmt eingehende Mail (z. B. Kampagnenantworten) in das Team-Postfach auf. **Altweg**: Eine aktuelle MTA sendet dieses Ereignis stattdessen an `POST /webhooks/mta-inbound`, wo die Rohnachricht mitkommt; diese Route nimmt es weiterhin für DLQ-Wiederholungen und ältere MTA-Binaries an, dann ohne die Bytes |
| `org.circuit_breaker`                                                        | Löst den Versands-Circuit-Breaker bei hoher Bounce-Rate aus                                                                                                                                                                                                                                                      |
| `ip.blocklisted` / `ip.delisted` / `ip.warming_complete` / `all_ips_blocked` | Macht Änderungen der IP-Reputation sichtbar                                                                                                                                                                                                                                                                      |

Anfragen werden mit HMAC-SHA256 über `${timestamp}.${body}` signiert:

| Header                   | Beschreibung                                                                                                                                                                                                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-MTA-Signature`        | HMAC-SHA256-Hex-Digest                                                                                                                                                                                                                                                           |
| `X-MTA-Timestamp`        | Unix-Zeitstempel (Sekunden); wird abgelehnt, wenn er mehr als 5 Minuten von der Serverzeit abweicht                                                                                                                                                                              |
| `X-MTA-Length-Signature` | HMAC-SHA256-Hex-Digest über `owlat-mta-length-v1.${timestamp}.${byteLength}`. Damit lesen die Rohnachrichten-Routen einen Body über 256 KiB, ohne vorher den Rate-Limit-Schlüssel zu belasten, den sie mit unverifizierten Anfragen teilen. Optional; ältere MTAs lassen ihn weg |

Das gemeinsame Secret stammt aus der Umgebungsvariablen `MTA_WEBHOOK_SECRET`. Ist sie nicht gesetzt, schlägt der Endpunkt sicherheitshalber mit `503` fehl.

### Route des Team-Postfachs

```http
POST /webhooks/mta-inbound
```

Hierhin sendet eine aktuelle MTA `inbound.received`. Gleiches HMAC-Verfahren, gleiches `MTA_WEBHOOK_SECRET`, gleiches Fünf-Minuten-Fenster wie bei der Route darüber — die Prüfung ist eine gemeinsame Implementierung.

Sie existiert getrennt, weil ihr Anfragetext `rawBytesBase64` trägt, also die vollständige empfangene Nachricht. Die gemeinsame Webhook-Pipeline begrenzt den Anfragetext **vor** der Authentifizierung auf 5 MiB und antwortet darüber mit `413`, was die MTA wiederholt und schließlich in die DLQ schiebt; diese Route kennt diese Grenze nicht, eine Nachricht bis zu den 10 MiB, die der eingehende Listener annimmt, kommt also vollständig an. Die Rohnachricht wird verschlüsselt gespeichert, ihre Anhangsteile werden auf Schadsoftware geprüft, und die Anhänge lassen sich aus der Thread-Ansicht herunterladen.

Die Audit-Zeile dieser Route ist ein **Digest** des Anfragetexts plus den Umschlagdaten, keine Kopie der Mail: Ein Convex-Dokument ist auf 1 MiB begrenzt, ein wörtliches Speichern würde also genau bei den Nachrichten mit Anhängen stillschweigend fehlschlagen.

### Resend-Route

```http
POST /webhooks/resend
```

Resend sendet eine größere Menge an Provider-Events, doch Owlat **handelt nur bei zweien davon**:

| Event              | Wirkung                                                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `email.bounced`    | Erfasst den Bounce (anhand der Provider-Nachricht als hard/soft klassifiziert) und aktualisiert Blockliste + Kontaktaktivität |
| `email.complained` | Erfasst die Spam-Beschwerde und aktualisiert Blockliste + Kontaktaktivität                                                    |

Die übrigen Resend-Events — `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.opened`, `email.clicked` — werden empfangen und mit `200 {"success": true, "ignored": true}` quittiert, aber von Owlat nicht verarbeitet. Der Versandstatus wird zum Zeitpunkt des Absetzens festgehalten, und Öffnungs- sowie Klickdaten stammen aus Owlats eigenem Tracking-Pixel und den Link-Weiterleitungen, nicht aus den Zählern von Resend.

::callout{type="warning" title="Keine Delivered-/Open-/Click-Effekte aus dem eingehenden Pfad"}
Bauen Sie keine Integrationen, die erwarten, dass die eingehende Resend-Route Auswertungen zu Zustellungen, Öffnungen oder Klicks speist — nur Bounce- und Beschwerde-Events haben eine Wirkung. Nutzen Sie die oben beschriebenen [ausgehenden Webhooks](#outbound-customer-webhooks), um die Events `email.delivered`, `email.opened` und `email.clicked` zu erhalten.
::

Resend-Anfragen werden mit dem Signaturverfahren von [Svix](https://www.svix.com) geprüft:

| Header           | Beschreibung                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| `svix-id`        | Nachrichten-ID                                                                                      |
| `svix-timestamp` | Unix-Zeitstempel (Sekunden); wird abgelehnt, wenn er mehr als 5 Minuten von der Serverzeit abweicht |
| `svix-signature` | Eine oder mehrere durch Leerzeichen getrennte HMAC-Signaturen der Form `v1,<sig>`                   |

Die Signatur wird gegen die Umgebungsvariable `RESEND_WEBHOOK_SECRET` geprüft (das `whsec_`-Base64-Secret aus Ihrem Resend-Dashboard). Ist sie nicht gesetzt, schlägt der Endpunkt sicherheitshalber mit `503` fehl.

### Emailit-Route

```http
POST /webhooks/emailit
```

Die Emailit-Events `accepted`, `attempted`, `delivered`, `bounced`, `complained`, `failed`, `rejected` und `suppressed` durchlaufen dieselbe normalisierte Lifecycle-Pipeline wie die etablierten Provider. Unterdrückungsgründe werden auf Owlats geschlossenes, empfängersicheres Vokabular abgebildet; Loaded-/Clicked-Events werden ignoriert, weil das eigene Tracking maßgeblich bleibt.

Anfragen erfordern `X-Emailit-Timestamp` und `X-Emailit-Signature`. Owlat berechnet den kleingeschriebenen hexadezimalen HMAC-SHA256 von `<timestamp>.<raw body>` mit dem vollständigen `EMAILIT_WEBHOOK_SECRET` und lehnt Zeitstempel außerhalb von fünf Minuten ab. Ein nicht gesetztes Secret führt sicherheitshalber zu `503`.

### TLS-Report-Route

```http
POST /webhooks/mta-tls-report
```

Eingehende TLS-RPT-Aggregatberichte (RFC 8460). Die MTA registriert die `_smtp._tls`-`rua=`-Adresse des Betreibers als System-Inbound-Route, die hierher zustellt; der Handler dekodiert den gzip-komprimierten Berichtsanhang und speichert den Digest. Gleiches HMAC-Verfahren und gleiches `MTA_WEBHOOK_SECRET` wie bei den Routen oben, mit einem Frischefenster von 60 Sekunden. Ein fehlerhafter oder zu großer Bericht wird mit `2xx` beantwortet, ohne übernommen zu werden, damit die MTA einen dauerhaft defekten Bericht nicht erneut sendet.

### Route für mitgelieferte Plugins

```http
POST /webhooks/plugin/{pluginId}
```

Rückmeldungen eines mitgelieferten Plugin-Transports — eine Route für jedes Plugin, das eigene Ergebnisse meldet. Bewusst nicht authentifiziert und aus dem Internet erreichbar: Der Aufrufer ist ein Drittanbieter ohne Owlat-Sitzung, deshalb schließt jedes Tor der Reihe nach sicherheitshalber — Rate-Limit je Plugin-ID, Registrierung (eine nicht vergebene ID ergibt `404`, bevor der Body gelesen wird), Body-Größe, das im Vertrag des Plugins deklarierte Signaturverfahren, die Freigabe des Betreibers für dieses Plugin und Replay-Schutz über den Zustell-Digest.

### GitHub-Route

```http
POST /webhooks/github
```

Merge-Benachrichtigungen für das Code-Work-Board. Prüft `X-Hub-Signature-256` gegen `GITHUB_WEBHOOK_SECRET` und reagiert nur auf `pull_request`-`closed`-Events, bei denen der PR gemerged wurde; die passende Aufgabe wandert dann auf `merged`. Ein nicht gesetztes Secret führt sicherheitshalber zu `503`; ein Event ohne passende Aufgabe wird mit `200` beantwortet, damit GitHub nicht erneut zustellt.
