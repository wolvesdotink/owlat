---

Lies, schreibe und veröffentliche Transaktions-E-Mails und gespeicherte Blöcke.
Ein Skript kann so die E-Mails eines Produkts importieren, das zu Owlat
umzieht, Vorlagen aus einem Repository von einer Staging-Instanz in die
Produktion bringen oder das Variablenschema einer E-Mail lesen, um es mit dem
Dienst abzugleichen, der sie sendet.

## Authentifizierung

Lesen braucht einen API-Schlüssel mit dem Scope `templates:read`, Schreiben und
Veröffentlichen brauchen `templates:write`. Der Sende-Scope
(`transactional:send`) gewährt keinen von beiden. Ein Schlüssel, den du
angelegt hast, bevor es diese Scopes gab, hat sie nicht: Leg unter
**Einstellungen → API** einen neuen Schlüssel mit den nötigen Scopes an.

Transaktions-E-Mails folgen der Funktion **Transaktions-E-Mails**: Ist sie aus,
antworten diese Routen mit `403` und `data.reason` `feature_disabled`.
Gespeicherte Blöcke hängen nicht davon ab.

## Endpunkte

| Methode | Pfad                                           | Zweck                                        |
| ------- | ---------------------------------------------- | -------------------------------------------- |
| `GET`   | `/api/v1/transactional-emails`                 | Transaktions-E-Mails auflisten               |
| `POST`  | `/api/v1/transactional-emails`                 | Eine Transaktions-E-Mail als Entwurf anlegen |
| `GET`   | `/api/v1/transactional-emails/:slug`           | Eine mit ihrem Inhalt lesen                  |
| `PUT`   | `/api/v1/transactional-emails/:slug`           | Per Slug anlegen oder ersetzen               |
| `POST`  | `/api/v1/transactional-emails/:slug/publish`   | Veröffentlichen                              |
| `POST`  | `/api/v1/transactional-emails/:slug/unpublish` | Zurück in den Entwurf setzen                 |
| `GET`   | `/api/v1/saved-blocks`                         | Gespeicherte Blöcke auflisten                |
| `POST`  | `/api/v1/saved-blocks`                         | Einen gespeicherten Block anlegen            |
| `GET`   | `/api/v1/saved-blocks/:id`                     | Einen mit seinen Blöcken lesen               |
| `PUT`   | `/api/v1/saved-blocks/:id`                     | Ersetzen                                     |

Die Listen kommen älteste zuerst, seitenweise: `limit` (höchstens 100,
Standard 25) und der `pagination.cursor` der vorigen Seite, bis
`pagination.isDone` gilt. Sie enthalten keinen Inhalt; dafür liest du den
einzelnen Eintrag.

## Eine Transaktions-E-Mail

```json
{
	"data": {
		"id": "k57t3mpl4te0000000000000000000",
		"slug": "order-confirmation",
		"name": "Order confirmation",
		"status": "published",
		"subject": "Your order {{orderNumber}}",
		"defaultLanguage": "en",
		"languages": ["en", "de"],
		"revision": 4,
		"publishedAt": "2026-11-02T09:00:00.000Z",
		"createdAt": "2026-10-30T14:00:00.000Z",
		"updatedAt": "2026-11-02T09:00:00.000Z",
		"blocks": [
			{
				"id": "b-heading",
				"type": "text",
				"content": {
					"html": "<h1>Thanks for your order</h1>",
					"blockType": "h1",
					"fontSize": 28,
					"textColor": "#111827"
				}
			}
		],
		"translations": {
			"de": {
				"subject": "Deine Bestellung {{orderNumber}}",
				"blocks": { "b-heading": { "html": "<h1>Danke für deine Bestellung</h1>" } }
			}
		},
		"dataVariablesSchema": { "orderNumber": "string", "total": "number" },
		"showUnsubscribe": false
	}
}
```

- `blocks` sind die Blöcke der E-Mail genau so, wie der Editor sie speichert.
  Der `content` eines Blocks enthält jedes Feld seines Typs; die
  Inhaltsprüfung unten lehnt einen Block ab, dem ein Feld fehlt oder bei dem
  es den falschen Typ hat. Am schnellsten siehst du die Felder eines Blocktyps,
  wenn du im Editor eine E-Mail baust und sie hier liest. Bilder sind URLs: Die
  API lädt keine Medien hoch.
- `translations` enthält die anderen Sprachen: einen Betreff (`null` nimmt den
  Standardbetreff) und den übersetzten Text jedes Blocks nach Block-ID (`html`
  für Text, `buttonText` für einen Button, `alt` für ein Bild). Das Layout
  kommt immer aus `blocks`.
- `dataVariablesSchema` nennt die Variablen, die ein Versand mitgibt, und ihren
  Typ: `string`, `number`, `boolean` oder `date`. Spätere Versionen können
  Typen ergänzen.
- `id` kannst du beim Senden als `transactionalId` angeben; die Routen hier
  nehmen den Slug.

Spätere Versionen können neue Felder ergänzen. Lies die, die du kennst, und
ignoriere den Rest.

## Schreiben

`POST /api/v1/transactional-emails` legt einen Entwurf an; der Body braucht
einen `slug`. `PUT /api/v1/transactional-emails/:slug` legt die E-Mail mit
diesem Slug an, wenn es keine gibt, und ersetzt sonst ihre bearbeitbaren
Felder: `name`, `subject`, `blocks`, `translations`, `dataVariablesSchema`,
`defaultLanguage` und `showUnsubscribe`. Ein Feld, das ein `PUT` weglässt,
bekommt seinen Standard (keine Variablen, keine Übersetzungen, `en`, kein
Abmeldelink). Schick also jedes Mal die ganze E-Mail. Absender, Anhänge und der
selbst geschriebene Text-Teil gehören nicht zur API und behalten ihren Wert.

Ein Schreibzugriff nimmt denselben Weg wie das Speichern im Editor: Das HTML in
Textblöcken wird bereinigt, die E-Mail wird auf dem Server gerendert, eine
Änderung an einer veröffentlichten E-Mail wird gescannt, und das Audit-Log
verzeichnet den Zugriff mit dem API-Schlüssel als Akteur (`api`).

Die Antwort ist die gespeicherte E-Mail und was die Inhaltsprüfung gefunden hat:

```json
{
	"data": {
		"email": { "slug": "order-confirmation", "revision": 5 },
		"issues": [
			{
				"severity": "warning",
				"code": "BUTTON_NO_TEXT",
				"message": "Button block has no text",
				"blockId": "b-button",
				"blockType": "button"
			}
		]
	}
}
```

Warnungen und Hinweise halten einen Schreibzugriff nicht auf. Ein Block mit
einem Fehler schon: Der Zugriff wird mit `400` abgelehnt, mit `data.reason`
`invalid_content`, dem ersten fehlerhaften Block in `data.blockId` und allen
Befunden in `data.issues`, und nichts wird gespeichert. Ein `PUT` einer E-Mail,
die der Editor mit so einem Block gespeichert hat, wird genauso abgelehnt, bis
der Block repariert ist.

### Export und Import

Lesen ist der Export: Ein `PUT` der unveränderten `data` eines `GET` auf
denselben Slug speichert dieselbe E-Mail. Die nur lesbaren Felder darin (`id`,
`status`, `revision`, die Zeitstempel, `languages`) werden ignoriert. Um eine
E-Mail in eine andere Instanz zu kopieren, liest du sie mit `GET` aus der einen
und schreibst sie mit `PUT` in die andere. Ein Block, der mit einem
gespeicherten Block verknüpft ist, nennt dessen ID in `savedBlockRef`, und die
IDs gespeicherter Blöcke unterscheiden sich zwischen Instanzen: Leg die
gespeicherten Blöcke zuerst im Ziel an und setz ihre neuen IDs ein, oder
entferne `savedBlockRef`, um den Inhalt als einfache Blöcke zu importieren. Eine
Verknüpfung zu einem gespeicherten Block, den die Instanz nicht hat, wird mit
`invalid_content` abgelehnt.

### Die Änderung von jemand anderem

Jedes `GET` und jeder Schreibzugriff antwortet mit der `revision` der E-Mail,
auch als `ETag`-Header. Schick sie als `If-Match` zurück, dann wird der Zugriff
mit `409`, `data.reason` `revision_mismatch` und `data.currentRevision`
abgelehnt, wenn sich die E-Mail geändert hat, nachdem du sie gelesen hast, zum
Beispiel im Editor. Lies sie dann neu und wende deine Änderung auf den
aktuellen Stand an.

```bash
curl -X PUT "$OWLAT_API/api/v1/transactional-emails/order-confirmation" \
  -H "Authorization: Bearer $OWLAT_KEY" \
  -H 'Content-Type: application/json' \
  -H 'If-Match: "4"' \
  --data @order-confirmation.json
```

### Eine veröffentlichte E-Mail

Ein `PUT` auf eine veröffentlichte E-Mail wird mit `422` und `email_published`
abgelehnt, außer es sagt `?whilePublished=true`. Dann geht die Änderung sofort
live, nach dem Inhaltsscan: Blockierter Inhalt wird mit `content_blocked`
abgelehnt und nichts ändert sich, verdächtiger Inhalt setzt die E-Mail auf
`pending_review`, bis ein Admin sie freigibt.

## Veröffentlichen

`POST .../publish` rendert die E-Mail und führt den Inhaltsscan aus. Eine
saubere E-Mail ist danach `published`; eine verdächtige kommt als
`pending_review` zurück und geht live, sobald ein Admin sie freigibt; eine
blockierte wird mit `422`, `content_blocked` und dem Scan-Wert in
`data.scanScore` abgelehnt. Eine veröffentlichte E-Mail erneut zu
veröffentlichen ändert nichts. `If-Match` gilt auch hier, damit du genau die
Revision veröffentlichst, die du geprüft hast. `POST .../unpublish` setzt die
E-Mail zurück in den Entwurf; Sendungen, die sie nennen, werden abgelehnt, bis
sie wieder veröffentlicht ist.

## Gespeicherte Blöcke

Ein gespeicherter Block ist ein oder mehrere Blöcke, mit denen E-Mails
verknüpft sind. Sein Body ist `name`, `description` und `blocks`, geprüft wie
bei einer E-Mail. Ein `PUT` ersetzt alle drei. Eine Änderung an den Blöcken
erreicht jede verknüpfte E-Mail, wie eine Änderung im Editor: Die E-Mails werden
im Hintergrund neu gerendert, und das neue HTML einer veröffentlichten E-Mail
wird gescannt, bevor es live geht.

## Grenzen

- Ein Request-Body darf bis zu 1 MB groß sein. Eine gespeicherte E-Mail
  enthält ihre Blöcke, ihre Übersetzungen und das für jede Sprache gerenderte
  HTML; eine E-Mail, die nicht hineinpasst, wird mit `400` und
  `content_too_large` abgelehnt.
- Schreiben und Veröffentlichen teilen sich ein Limit von 60 pro Minute und
  Schlüssel, mit Spitzen bis 30, unabhängig vom Request-Limit und von den
  Sendelimits. Darüber hinaus kommt `429` mit `data.reason`
  `template_write_rate_limited` und `Retry-After`.

## Ablehnungen

| Status | `data.reason`                 | Bedeutung                                                    |
| ------ | ----------------------------- | ------------------------------------------------------------ |
| `400`  | `invalid_content`             | Ein Block hat einen Fehler; `data.issues` listet sie         |
| `400`  | `content_too_large`           | Die E-Mail passt nicht in einen gespeicherten Datensatz      |
| `403`  | `missing_scope`               | Dem Schlüssel fehlt `templates:read` oder `templates:write`  |
| `403`  | `feature_disabled`            | Transaktions-E-Mails sind ausgeschaltet                      |
| `409`  | `slug_taken`                  | Eine andere E-Mail hat den Slug                              |
| `409`  | `revision_mismatch`           | Die E-Mail hat sich seit der Revision in `If-Match` geändert |
| `422`  | `email_published`             | Die E-Mail ist live; schick `whilePublished=true`            |
| `422`  | `default_language_change`     | Mit Übersetzungen ändert sich die Standardsprache nicht      |
| `422`  | `content_blocked`             | Der Inhaltsscan hat den Inhalt abgelehnt                     |
| `422`  | `html_render_pending`         | Ein verwendeter gespeicherter Block wird noch neu gerendert  |
| `429`  | `template_write_rate_limited` | Zu viele Vorlagen-Schreibzugriffe mit diesem Schlüssel       |

Ein fehlerhaftes Feld ist ein `400`, das es in `data.field` nennt, etwa `slug`,
`blocks` oder `dataVariablesSchema.total`.

## Noch nicht in der API

Bilder und Dateien hochladen, Absender und Anhänge einer E-Mail, E-Mails und
gespeicherte Blöcke löschen und Marketing-Vorlagen gibt es nur in der Web-App.
