Owlat stellt authentifizierte API-Endpunkte unter der API-URL deiner Instanz bereit.

## Basis-URL

Jede Owlat-Installation liefert ihre eigene API aus. Die Web-App zeigt die
Adresse als **Deine API-Basis-URL** unter **Einstellungen → API →
API-Schnellstart**. Es ist die `NUXT_PUBLIC_CONVEX_SITE_URL`, die der Betreiber
gesetzt hat, zum Beispiel:

```txt
https://rest.api.example.com
```

Authentifizierte Endpunkte liegen derzeit unter:

```txt
/api/v1/*
```

## Authentifizierung

Sende deinen API-Key im Header `Authorization`:

```txt
Authorization: Bearer lm_live_...
```

API-Keys werden unter **Einstellungen → API** erstellt.

## SDKs

Verwende für serverseitige Integrationen ein offizielles SDK statt roher HTTP-Aufrufe:

- [TypeScript-SDK](/api/sdk) -- `@owlat/sdk-js` für Node.js, Bun und Deno
- [Java-SDK](/api/sdk-java) -- `com.owlat:owlat-sdk` für JVM-Anwendungen (Java 11+)

## OpenAPI-Dokument

Jede Instanz liefert das OpenAPI-3.1-Dokument ihrer eigenen API, ohne
API-Schlüssel:

```txt
GET <deine API-Basis-URL>/api/v1/openapi.json
```

Sein Eintrag `servers` ist die API-Basis-URL deiner Instanz. Ein
API-Client-Generator, ein HTTP-Werkzeug oder ein KI-Agent, den du auf diese
eine URL richtest, erfährt so jeden Pfad, jeden Scope, jedes Schema und jedes
Beispiel und wohin die Anfragen gehen. Jede Operation nennt den Scope, den ihr
Schlüssel braucht.

Die Anfrage- und Antwortformen jeder `/api/v1`-Operation sind einmal im Paket
`@owlat/public-contract` festgelegt. Der API-Server validiert Anfragen damit,
das TypeScript-SDK übernimmt seine Typen daraus, und die Tests des Java-SDK
prüfen das SDK gegen das daraus erzeugte Dokument. Das Repository enthält eine
Kopie mit einem Platzhalter als Server:
[`packages/public-contract/openapi.json`](https://github.com/wolvesdotink/owlat/blob/main/packages/public-contract/openapi.json).

Wenn du den Vertrag änderst, erzeuge das Dokument neu und committe es zusammen
mit der Änderung:

```bash
bun run --cwd packages/public-contract openapi
```

CI schlägt fehl, wenn das committete Dokument veraltet ist
(`bun run --cwd packages/public-contract openapi:check`).

## Antwortformat

Die meisten Endpunkte liefern JSON in dieser Form zurück:

```json
{
	"data": {}
}
```

Fehler verwenden das festgeschriebene Operation-Error-Envelope — eine für
Menschen lesbare `message`, eine geschlossene `category` und ein optionales
Objekt `data` mit den Details:

```json
{
	"error": {
		"category": "invalid_input",
		"message": "Human readable message",
		"data": { "field": "email" }
	}
}
```

`category` ist einer der folgenden Werte: `unauthenticated` (401), `limit_reached` (402),
`forbidden` (403), `not_found` (404), `invalid_input` (400), `already_exists`
(409), `conflict` (409), `invalid_state` (422), `rate_limited` (429),
`internal` (500).

Ein `400` zu einer Eingabe nennt sie in `data.field`. Ein Feld des Bodys steht
so da, wie der Body es adressiert: `email`, `dataVariables.name`,
`attachments.0.filename`. Ein Pfadsegment, ein Query-Parameter oder ein Header
steht unter seinem Namen aus dieser Referenz: `id`, `topicId`, `cursor`,
`limit`, `Idempotency-Key`. Ein Fehler zum Body als Ganzes (einem, der weder
`transactionalId` noch `slug` nennt) trägt kein `data.field`.

Eine Route, die schreibt, antwortet mit `422` `invalid_state` und
`data.reason: "workspace_deletion_in_progress"`, solange der Workspace gelöscht
wird. Es wird nichts geschrieben; versuche es erneut, wenn die Löschung fertig
ist oder abgebrochen wurde.

Eine Methode, die ein Pfad nicht unterstützt, etwa `PATCH /api/v1/contacts`,
erreicht die API gar nicht: Sie antwortet mit `404` und einem Body aus reinem
Text, nicht mit diesem Envelope.

## CORS

Private API-Endpunkte (`/api/v1/*`) werden über die Umgebungsvariable `ALLOWED_ORIGINS` eingeschränkt. Setze sie im Convex-Dashboard auf eine kommaseparierte Liste erlaubter Origins:

```bash
npx convex env set ALLOWED_ORIGINS "https://app.example.com,http://localhost:3000"
```

Öffentliche Endpunkte (Formulare, Abmeldung, Präferenzzentrum) erlauben alle Origins.

## Rate Limits

Authentifizierte API-Anfragen sind auf **10 Anfragen pro Sekunde** je API-Key begrenzt.

Header:

```txt
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
```

Bei Überschreitung antworten die Endpunkte mit `429` und dem Header `Retry-After`.
Regle nach `Retry-After` zurück: `X-RateLimit-Remaining` und `X-RateLimit-Reset`
sind feste Werte und geben das Limit nicht wieder
([Authentifizierung](/api/authentication#rate-limit-überschritten-429) sagt, was
jeder enthält).

Für transaktionale Sends (`POST /api/v1/transactional`) gelten zwei weitere
Limits. Der Instanz-Admin kann jedes davon unter **Einstellungen > API**
(`/dashboard/admin/team/api`) erhöhen, senken oder abschalten; eine Änderung
gilt ab der nächsten Anfrage. Die Standardwerte:

- **5 Sends pro Stunde aus einer Vorlage an eine Adresse.** Mehr Passwort-Resets
  oder Anmeldelinks braucht dieselbe Person nicht, und eine Schleife gegen eine
  Adresse endet hier. `data.reason` im Fehler ist `recipient_rate_limited`.
  Eine Vorlage, die immer nur an eine feste Adresse geht (eine
  Bestellbenachrichtigung an deinen eigenen Shop), kann sich in ihrem Editor
  von diesem Limit ausnehmen.
- **50.000 Sends pro API-Key und UTC-Tag.** Es begrenzt, was ein geleakter Key
  senden kann. `data.reason` im Fehler ist `daily_send_limit`, und
  `Retry-After` zeigt auf die nächste Mitternacht (UTC). Keine Vorlage kann sich
  davon ausnehmen.

Beide antworten mit `429` und `Retry-After` in Sekunden. Eine Anfrage, die einen
bereits angenommenen `Idempotency-Key` wiederholt, bekommt die erste Antwort und
zählt gegen keins der beiden Limits.

`GET /api/v1/limits` liest beide Limits so, wie sie gerade eingestellt sind, mit
jedem Key. Für das Tageslimit liefert es auch den Zählerstand des anfragenden
Keys: `used`, `remaining` und `resetsAt`, die nächste Mitternacht (UTC), gelesen
aus demselben Zähler, den die Senderoute prüft. Ein Send, der zwischen deinem
Lesen und deinem nächsten Send eingeht, zählt mit, nimm `remaining` also als den
Rest zum Zeitpunkt des Lesens. Solange das Tageslimit abgeschaltet ist, wird
nichts gezählt, und die drei Felder sind `null`.

Was vom Limit pro Vorlage und Adresse übrig ist, hängt von Vorlage und Adresse
ab, also nenne beide, um es zu lesen:
`GET /api/v1/limits?email=ada@example.com&slug=password-reset` (oder
`transactionalId=` statt `slug`, wie beim Senden). `recipientSends.usage` enthält
dann `used`, `remaining` und `resetsAt`, wann der Zähler wieder bei null ist.
Das Kontingent füllt sich laufend auf, ein Send wird also schon vorher frei. Es
zählen die Sends jedes Keys mit dieser Vorlage an diese Adresse, darum braucht
dieses Lesen den Scope `transactional:send`, wie die Liste der Sendungen. Das
Lesen ändert den Zähler nicht. Eine Adresse ohne Vorlage oder eine Vorlage ohne
Adresse wird mit `400` abgelehnt, das den fehlenden Parameter nennt, eine
unbekannte Vorlage beantwortet die Route mit `404`. Für eine ausgenommene
Vorlage oder solange das Limit abgeschaltet ist, sagen das `isExempt` oder
`isEnabled`, und die drei Felder sind `null`.

```json
{
	"data": {
		"dailySends": {
			"isEnabled": true,
			"limit": 50000,
			"used": 1204,
			"remaining": 48796,
			"resetsAt": "2026-11-24T00:00:00.000Z"
		},
		"recipientSends": {
			"isEnabled": true,
			"limit": 5,
			"windowSeconds": 3600,
			"usage": {
				"email": "ada@example.com",
				"templateId": "k57t3mpl4te0000000000000000000",
				"slug": "password-reset",
				"isExempt": false,
				"used": 2,
				"remaining": 3,
				"resetsAt": "2026-11-23T15:54:00.000Z"
			}
		}
	}
}
```

`usage` gibt es nur, wenn die Anfrage eine Vorlage und eine Adresse nennt.
