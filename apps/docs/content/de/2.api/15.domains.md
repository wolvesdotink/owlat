title: 'Domains-API'
description: 'Liste die Absenderdomains und die DNS-Einträge, die jede noch braucht, und fordere eine neue Prüfung an.'
---

Liste deine Absenderdomains mit ihrem Prüfstatus und jedem DNS-Eintrag, den
jede braucht: wo er hingehört, sein Wert und was die letzte Prüfung dort
gefunden hat. Ein Skript oder ein KI-Agent, der die Absender-Einrichtung
abschließt, liest so, was noch fehlt, ohne die Web-App zu öffnen.

## Endpunkt

| Methode | Pfad                              | Zweck                                           |
| ------- | --------------------------------- | ----------------------------------------------- |
| `GET`   | `/api/v1/domains`                 | Absenderdomains und ihre DNS-Einträge auflisten |
| `POST`  | `/api/v1/domains/{domain}/verify` | Eine neue DNS-Prüfung einer Domain anfordern    |

## Authentifizierung

Die Liste braucht einen API-Schlüssel mit dem Scope `status:read`, demselben
wie die [Status-API](/api/status), die den Prüfstatus jeder Domain nennt. Ein
Schlüssel ohne ihn bekommt `403` mit `data.reason` `missing_scope`. Jedes
Mitglied deines Workspaces sieht dieselben Einträge auf der Seite der
Absenderdomains; Anbieter-Tokens und gespeicherte Fehlermeldungen gehören nicht
zur Antwort.

Eine Prüfung braucht den Scope `domains:verify`. Er ist ein eigener Scope, weil
eine Prüfung den gespeicherten Zustand der Domain neu schreibt und eine
verifizierte Domain Richtung `failed` bewegen kann; ein Schlüssel, der nur den
Status liest, kann also keine starten. Schlüssel, die vor diesem Scope angelegt
wurden, haben ihn nicht: Lege einen Schlüssel mit ihm an.

## Antwort

```json
{
	"data": [
		{
			"id": "k57d0main0000000000000000000000",
			"domain": "news.example.com",
			"status": "failed",
			"lastCheckedAt": "2026-11-21T07:30:00.000Z",
			"records": [
				{
					"purpose": "dkim",
					"type": "CNAME",
					"host": "s1._domainkey.news.example.com",
					"value": "s1.dkim.owlat.example",
					"priority": null,
					"state": "wrong",
					"foundValue": "old.dkim.example.net",
					"optional": false
				},
				{
					"purpose": "dmarc",
					"type": "TXT",
					"host": "_dmarc.news.example.com",
					"value": "v=DMARC1; p=none",
					"priority": null,
					"state": "missing",
					"foundValue": null,
					"optional": false
				}
			]
		}
	]
}
```

- `status` ist `registering`, `pending`, `verified` oder `failed`. Nur eine
  verifizierte Domain kann senden.
- `records` listet jeden zu veröffentlichenden Eintrag: `spf`, jeden
  `dkim`-Schlüssel, `dmarc` und `mail_from` für den Return-Path-Host, der die
  Bounces empfängt. Die Liste ist leer, solange die Domain noch registriert
  wird.
- `host` ist der volle Name des Eintrags. Ein `mail_from`-Eintrag kann auf
  einer Return-Path-Domain außerhalb deiner Domain liegen; veröffentliche ihn
  dort, wo `host` es sagt.
- `priority` ist bei einem `MX`-Eintrag gesetzt, sonst `null`.
- `state` ist, was die letzte Prüfung gefunden hat: `found` mit dem erwarteten
  Wert, `wrong` (dort steht ein anderer Wert, zu sehen in `foundValue`),
  `missing` oder `unchecked` (noch keine Prüfung, oder DNS hat nicht
  geantwortet).
- `optional` ist `true` für einen Eintrag, den die Domain nicht braucht: den
  optionalen zweiten DKIM-Schlüssel (Ed25519, `k=ed25519`), den eine Domain
  auf dem eingebauten MTA haben kann. Sein `state` entscheidet nie über
  `status`; zähl ihn also nicht als fehlend. Bei jedem anderen Eintrag `false`.

Die Liste ist nicht seitenweise: Eine Instanz hat eine Handvoll
Absenderdomains.

## Wann sich die Zustände ändern

Die Zustände stammen aus der letzten Prüfung, zu sehen in `lastCheckedAt`
(`null` vor der ersten). Owlat prüft jede Domain, die einmal verifiziert war,
täglich neu. Eine Domain, die noch eingerichtet wird, wird erneut geprüft,
solange ihre Zeile auf der Seite der Absenderdomains aufgeklappt ist, oder wenn
du eine Prüfung anforderst.

## Prüfung anfordern

Nach dem Veröffentlichen forderst du eine neue Prüfung der Domain über ihren
Namen oder ihre `id` an:

```http
POST /api/v1/domains/news.example.com/verify
```

```json
{
	"data": {
		"id": "k57d0main0000000000000000000000",
		"domain": "news.example.com",
		"status": "failed",
		"lastCheckedAt": "2026-11-21T07:30:00.000Z",
		"requestedAt": "2026-11-23T15:30:00.000Z"
	}
}
```

- Die Antwort ist `202`: Die Prüfung läuft im Hintergrund, weil das Nachschlagen
  aller Einträge bei einem langsamen Nameserver länger dauern kann, als eine
  Anfrage darf. `status` und `lastCheckedAt` sind der Stand vor der Prüfung.
- Frag `GET /api/v1/domains` ab, bis `lastCheckedAt` der Domain bei oder nach
  `requestedAt` liegt, meist nach wenigen Sekunden. Jede Prüfung der Domain,
  die zu einem Ergebnis kommt, setzt `lastCheckedAt`, es kann also eine andere Prüfung zuerst gelandet sein,
  etwa eine von der Seite der Absenderdomains; die Zustände sind so oder so
  aktuell. Gibt DNS gar keine Antwort,
  ändert die Prüfung nichts und `lastCheckedAt` bleibt stehen; frag später
  erneut an.
- Eine Prüfung pro Domain und Minute, egal welcher Schlüssel fragt. Eine zweite
  Anfrage vorher bekommt `429` mit `Retry-After` und `data.reason`
  `domain_check_rate_limited`.
- Ein Name oder eine ID, die keine Absenderdomain dieser Instanz ist, bekommt
  `404`. Eine Domain, die noch registriert wird, hat noch keine Einträge zum
  Prüfen und bekommt `409` mit `data.reason` `domain_registering`.
