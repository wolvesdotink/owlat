Veröffentlichte transaktionale Vorlagen an einen Empfänger senden.

## Endpunkt

| Methode | Pfad                             | Zweck                         |
| ------- | -------------------------------- | ----------------------------- |
| `POST`  | `/api/v1/transactional`          | Sendung einreihen             |
| `GET`   | `/api/v1/transactional/{sendId}` | Stand einer Sendung abfragen  |

## Authentifizierung

Beide Routen erfordern einen API-Key im `Authorization`-Header mit dem Scope
`transactional:send`. Anfragen ohne gültigen Key mit diesem Scope werden mit
`401`/`403` abgelehnt.

## Request-Body

Gib entweder `transactionalId` oder `slug` an.

```json
{
	"slug": "order-confirmation",
	"email": "john@example.com",
	"dataVariables": {
		"firstName": "John",
		"orderNumber": "ORD-12345"
	},
	"language": "en",
	"attachments": [
		{
			"filename": "invoice.pdf",
			"url": "https://example.com/invoices/12345.pdf",
			"contentType": "application/pdf"
		}
	]
}
```

Felder:

- `transactionalId` oder `slug` (erforderlich, eines von beiden)
- `email` (erforderlich)
- `dataVariables` (optionales flaches Objekt; jeder Wert ist ein String, eine Zahl, ein Boolean oder `null`)
- `language` (optionaler Sprachcode, z. B. `en`, `de`, `en-US`)
- `attachments` (optionales Array) — Dateianhänge, die der E-Mail beigefügt werden

### Anhänge

Jedes Anhang-Objekt hat die folgenden Felder:

| Feld          | Typ    | Erforderlich                  | Beschreibung                                    |
| ------------- | ------ | ----------------------------- | ----------------------------------------------- |
| `filename`    | string | Ja                            | Der Dateiname, der dem Empfänger angezeigt wird |
| `content`     | string | Entweder `content` oder `url` | Base64-kodierter Dateiinhalt                    |
| `url`         | string | Entweder `content` oder `url` | URL, von der die Datei abgerufen wird           |
| `contentType` | string | Nein                          | MIME-Typ (z. B. `application/pdf`, `image/png`) |

**Limits:**

- Maximal **10 Anhänge** pro E-Mail
- Maximal **10 MB** (10 MiB, 10.485.760 Bytes) Gesamtgröße der Anhänge, gezählt als dekodierte Bytes von `content`. Dateien, die du per `url` angibst, werden später abgerufen und zählen nicht dazu.
- Sende `content` als einfaches Base64 ohne Zeilenumbrüche. Diese Route nimmt einen Request-Body bis 14.081.056 Bytes an: das 10-MiB-Budget als Base64 plus 100.000 Bytes für alles andere. Alle Felder außer dem `content` der Anhänge (auch `dataVariables`) müssen in diese 100.000 Bytes passen, dieselbe Grenze wie bei jedem anderen API-Endpunkt. Ein größerer Body wird mit `400` abgelehnt, bevor er vollständig gelesen ist.
- Ein ungültiger Anhang lehnt die ganze Anfrage ab, bevor etwas gespeichert wird, und die Dateien einer abgelehnten Anfrage werden gelöscht.

## Antwort

Angenommene Sendungen liefern den Status „queued“ zurück:

```json
{
	"data": {
		"status": "queued",
		"email": "john@example.com",
		"transactionalEmailId": "j57...",
		"slug": "order-confirmation",
		"contactId": "j58...",
		"contactCreated": true,
		"language": "en"
	}
}
```

> `transactionalEmailId` ist die ID der **Sendung**, die für diese Anfrage angelegt wurde, nicht
> die ID der Vorlage. Jeder `email.*`-Webhook für diese Sendung trägt sie als `sendId`, und
> `GET /api/v1/transactional/{sendId}` liest ihren Status. `slug` ist der Slug der Vorlage, auch
> wenn die Anfrage die Vorlage per `transactionalId` benannt hat.

`queued` heißt, dass die Sendung angenommen wurde, nicht, dass sie schon raus ist. Ist die Zustellung
eine Zeit lang pausiert (der Sicherheits-Circuit für die Zustellung ist offen oder der Mailserver
startet neu), wird die Anfrage trotzdem angenommen und die Sendung wartet. Sie geht raus, sobald die
Zustellung weiterläuft, oder schlägt nach vier Tagen mit einem Fehlercode fehl, der die Ursache nennt:
`DELIVERY_HOLD_EXPIRED` oder `MTA_UNREACHABLE`. Eine Sendung, die endgültig fehlschlägt, löst einmal
den Webhook `email.failed` aus und zeigt `failed` in der Statusabfrage; eine Sendung, die nur wartet,
löst nichts aus.

## Sendestatus

`GET /api/v1/transactional/{sendId}` liefert, wo eine Sendung steht. `sendId` ist die
`transactionalEmailId`, mit der der Sendeaufruf geantwortet hat.

```json
{
	"data": {
		"sendId": "j57...",
		"status": "failed",
		"email": "john@example.com",
		"templateId": "j59...",
		"slug": "order-confirmation",
		"language": "en",
		"queuedAt": "2026-11-02T09:00:00.000Z",
		"sentAt": null,
		"deliveredAt": null,
		"openedAt": null,
		"clickedAt": null,
		"bouncedAt": null,
		"complainedAt": null,
		"failedAt": "2026-11-06T09:00:00.000Z",
		"bounceType": null,
		"errorCode": "MTA_UNREACHABLE",
		"errorMessage": "The mail server could not be reached before the delivery deadline passed"
	}
}
```

- `status` ist einer von `queued`, `sent`, `failed`, `delivered`, `opened`, `clicked`, `bounced`
  oder `complained`.
- Zeitstempel sind ISO 8601 und `null`, bis die Sendung diesen Schritt erreicht.
- `errorCode` und `errorMessage` sind nur gesetzt, wenn `status` `failed` ist. Verzweige anhand von
  `errorCode`; die Nachricht ist für Menschen gedacht.
- `bounceType` ist `hard` oder `soft`, sobald ein Bounce gemeldet wurde.
- `templateId` und `slug` sind `null`, sobald die Vorlage gelöscht wurde.
- Die `dataVariables` der Sendung werden nie zurückgegeben.
- Eine ID, die keine über diese API angelegte Sendung benennt, liefert `404` `not_found`: eine
  unbekannte oder fehlerhafte ID, aber auch eine E-Mail aus einer Kampagne oder Automatisierung
  oder eine, deren Kontakt gelöscht wurde.

Um Ergebnisse ohne Polling zu erfahren, abonniere mit einem Webhook `email.failed`,
`email.delivered` und `email.bounced` und ordne die Ereignisse über `sendId` zu.

## Idempotente Wiederholungen

Sende einen `Idempotency-Key`-Header, damit du eine Sendung nach einem Timeout oder einem `5xx`
gefahrlos wiederholen kannst:

```http
Idempotency-Key: 3f0c1d9e-6c2b-4a51-9a3e-2f6d1b7c8e90
```

- Der Schlüssel besteht aus 1 bis 255 druckbaren ASCII-Zeichen ohne Leerzeichen, etwa einer UUID
  oder deiner eigenen Bestellnummer. Er gilt für deine Organisation.
- Die erste Anfrage mit einem Schlüssel wird normal verarbeitet. Eine Wiederholung **derselben**
  Anfrage mit diesem Schlüssel innerhalb von 24 Stunden stellt nichts in die Warteschlange, liefert die erste Antwort
  (gleicher Status und Body) und trägt den Header `Idempotent-Replayed: true`.
- Verwendest du den Schlüssel für eine **andere** Anfrage (anderer Body oder anderer Endpunkt),
  wird sie mit `409` `conflict` (`reason: "idempotency_conflict"`) abgelehnt und bewirkt nichts.
- Wurde der Kontakt, den die erste Anfrage betraf, inzwischen gelöscht, wird eine Wiederholung
  innerhalb der 24 Stunden mit `409` `conflict` (`reason: "idempotency_erased"`) abgelehnt und
  bewirkt nichts: Die Anfrage wurde schon ausgeführt, aber ihre Antwort nannte die gelöschte Person
  und wird nicht mehr aufbewahrt.
- Eine abgelehnte Anfrage (zum Beispiel `404` oder `400`) oder eine, die vor dem Ausführen
  fehlschlug, speichert nichts; eine Wiederholung mit demselben Schlüssel führt sie erneut aus.
- Nach 24 Stunden kannst du den Schlüssel für eine neue Anfrage verwenden.
- Ohne den Header wird wie bisher jede Anfrage verarbeitet.

## Reihenfolge der Sprachauflösung

1. Explizites `language` in der Anfrage
2. Bevorzugte Sprache des Kontakts (sofern der Empfänger existiert)
3. Standardsprache der Vorlage
4. Fallback-Standard

## Validierungs- und Zustellprüfungen

- Die Funktion **Transactional API** muss unter **Einstellungen → Features**
  aktiviert sein; solange sie aus ist, werden Anfragen mit `403`
  (`reason: "feature_disabled"`) abgelehnt
- Die Vorlage muss existieren und den Status `published` haben; eine `transactionalId`, die keine
  Vorlage benennt, auch eine fehlerhafte, wird mit `404` abgelehnt
- Die Vorlage muss gerenderten HTML-Inhalt besitzen
- Die Versanddomain muss verifiziert sein
- `dataVariables` werden, sofern vorhanden, gegen das Schema der Vorlage validiert
- Jede Variable, die die E-Mail ohne Fallback verwendet (`{{orderNumber}}`
  statt `{{giftNote|''}}`), muss mitgeschickt werden, außer die E-Mail markiert
  sie als **optional**. Eine fehlende oder `null` gesetzte Pflichtvariable wird
  mit `400` abgelehnt, das sie nennt; eine optionale bleibt leer oder zeigt
  ihren Fallback. Eine Variable markierst du im Editor der E-Mail unter
  **Versand > Datenvariablen** als optional
- Der Send muss in die [Versandlimits für Transaktionsmails](/api#rate-limits)
  passen, die der Instanz-Admin festlegt; ein Send über einem Limit wird mit
  `429` abgelehnt
