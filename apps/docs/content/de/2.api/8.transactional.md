Veröffentlichte transaktionale Vorlagen an einen Empfänger senden.

## Endpunkt

| Methode | Pfad                             | Zweck                        |
| ------- | -------------------------------- | ---------------------------- |
| `POST`  | `/api/v1/transactional`          | Sendung einreihen            |
| `GET`   | `/api/v1/transactional`          | Sendungen auflisten          |
| `GET`   | `/api/v1/transactional/{sendId}` | Stand einer Sendung abfragen |

## Authentifizierung

Jede Route erfordert einen API-Key im `Authorization`-Header mit dem Scope
`transactional:send`. Anfragen ohne gültigen Key mit diesem Scope werden mit
`401`/`403` abgelehnt.

## Request-Body

Gib entweder `transactionalId` oder `slug` an.

```json
{
	"slug": "order-confirmation",
	"email": "john@example.com",
	"dataVariables": {
		"firstName": "John",
		"orderNumber": "ORD-12345"
	},
	"language": "en",
	"attachments": [
		{
			"filename": "invoice.pdf",
			"url": "https://example.com/invoices/12345.pdf",
			"contentType": "application/pdf"
		}
	]
}
```

Felder:

- `transactionalId` oder `slug` (erforderlich, eines von beiden)
- `email` (erforderlich)
- `dataVariables` (optionales flaches Objekt; jeder Wert ist ein String, eine Zahl, ein Boolean oder `null`)
- `language` (optionaler Sprachcode, z. B. `en`, `de`, `en-US`)
- `attachments` (optionales Array) — Dateianhänge, die der E-Mail beigefügt werden

### Anhänge

Jedes Anhang-Objekt hat die folgenden Felder:

| Feld          | Typ    | Erforderlich                  | Beschreibung                                    |
| ------------- | ------ | ----------------------------- | ----------------------------------------------- |
| `filename`    | string | Ja                            | Der Dateiname, der dem Empfänger angezeigt wird |
| `content`     | string | Entweder `content` oder `url` | Base64-kodierter Dateiinhalt                    |
| `url`         | string | Entweder `content` oder `url` | URL, von der die Datei abgerufen wird           |
| `contentType` | string | Nein                          | MIME-Typ (z. B. `application/pdf`, `image/png`) |

**Limits:**

- Maximal **10 Anhänge** pro E-Mail
- Maximal **10 MB** (10 MiB, 10.485.760 Bytes) Gesamtgröße der Anhänge, gezählt als dekodierte Bytes von `content`. Dateien, die du per `url` angibst, werden später abgerufen und zählen nicht dazu.
- Sende `content` als einfaches Base64 ohne Zeilenumbrüche. Diese Route nimmt einen Request-Body bis 14.081.056 Bytes an: das 10-MiB-Budget als Base64 plus 100.000 Bytes für alles andere. Alle Felder außer dem `content` der Anhänge (auch `dataVariables`) müssen in diese 100.000 Bytes passen, dieselbe Grenze wie bei jedem anderen API-Endpunkt. Ein größerer Body wird mit `400` abgelehnt, bevor er vollständig gelesen ist.
- Ein ungültiger Anhang lehnt die ganze Anfrage ab, bevor etwas gespeichert wird, und die Dateien einer abgelehnten Anfrage werden gelöscht.

## Antwort

Angenommene Sendungen liefern den Status „queued“ zurück:

```json
{
	"data": {
		"status": "queued",
		"email": "john@example.com",
		"transactionalEmailId": "j57...",
		"slug": "order-confirmation",
		"contactId": "j58...",
		"contactCreated": true,
		"language": "en"
	}
}
```

> `transactionalEmailId` ist die ID der **Sendung**, die für diese Anfrage angelegt wurde, nicht
> die ID der Vorlage. Jeder `email.*`-Webhook für diese Sendung trägt sie als `sendId`, und
> `GET /api/v1/transactional/{sendId}` liest ihren Status. `slug` ist der Slug der Vorlage, auch
> wenn die Anfrage die Vorlage per `transactionalId` benannt hat.

`queued` heißt, dass die Sendung angenommen wurde, nicht, dass sie schon raus ist. Ist die Zustellung
eine Zeit lang pausiert (der Sicherheits-Circuit für die Zustellung ist offen oder der Mailserver
startet neu), wird die Anfrage trotzdem angenommen und die Sendung wartet. Sie geht raus, sobald die
Zustellung weiterläuft, oder schlägt nach vier Tagen mit einem Fehlercode fehl, der die Ursache nennt:
`DELIVERY_HOLD_EXPIRED` oder `MTA_UNREACHABLE`. Eine Sendung, die endgültig fehlschlägt, löst einmal
den Webhook `email.failed` aus und zeigt `failed` in der Statusabfrage; eine Sendung, die nur wartet,
löst nichts aus.

## Sendestatus

`GET /api/v1/transactional/{sendId}` liefert, wo eine Sendung steht. `sendId` ist die
`transactionalEmailId`, mit der der Sendeaufruf geantwortet hat.

```json
{
	"data": {
		"sendId": "j57...",
		"status": "failed",
		"email": "john@example.com",
		"templateId": "j59...",
		"slug": "order-confirmation",
		"language": "en",
		"queuedAt": "2026-11-02T09:00:00.000Z",
		"sentAt": null,
		"deliveredAt": null,
		"openedAt": null,
		"clickedAt": null,
		"bouncedAt": null,
		"complainedAt": null,
		"failedAt": "2026-11-06T09:00:00.000Z",
		"bounceType": null,
		"bounceCause": null,
		"errorCode": "MTA_UNREACHABLE",
		"errorMessage": "The mail server could not be reached before the delivery deadline passed"
	}
}
```

- `status` ist einer von `queued`, `sent`, `failed`, `delivered`, `opened`, `clicked`, `bounced`
  oder `complained`.
- Zeitstempel sind ISO 8601 und `null`, bis die Sendung diesen Schritt erreicht.
- `errorCode` ist nur gesetzt, wenn `status` `failed` ist. Verzweige anhand davon; die Nachricht
  ist für Menschen gedacht.
- `errorMessage` sagt, warum die Sendung nicht angekommen ist: bei `failed` der Grund des
  Fehlschlags, bei `bounced` die Antwort des empfangenden Servers (zum Beispiel
  `550 5.1.1 User unknown`). Sonst ist es `null`, ebenso bei einem Bounce, dessen Meldung keinen
  Text enthielt.
- `bounceType` ist `hard` oder `soft`, sobald ein Bounce gemeldet wurde.
- `bounceCause` sagt wie der Webhook `email.bounced`, wen der Bounce betrifft: `recipient`, wenn
  die Adresse abgelehnt wurde (ein Hard Bounce sperrt sie), `sender`, wenn der Empfänger die
  sendende IP oder Domain abgelehnt hat (die Adresse bleibt, sperre sie also auch bei dir nicht).
  Ohne Bounce ist es `null`, ebenso bei einem Bounce, den eine Serverversion erfasst hat, die die
  Ursache noch nicht speicherte.
- `templateId` und `slug` sind `null`, sobald die Vorlage gelöscht wurde.
- Die `dataVariables` der Sendung werden nie zurückgegeben.
- Eine ID, die keine über diese API angelegte Sendung benennt, liefert `404` `not_found`: eine
  unbekannte oder fehlerhafte ID, aber auch eine E-Mail aus einer Kampagne oder Automation
  oder eine, deren Kontakt gelöscht wurde.

Um Ergebnisse ohne Polling zu erfahren, abonniere mit einem Webhook `email.failed`,
`email.delivered` und `email.bounced` und ordne die Ereignisse über `sendId` zu.

## Sendungen auflisten

`GET /api/v1/transactional` listet die Sendungen, die diese API angelegt hat, die neueste zuerst.
Jeder Eintrag hat die Felder des [Sendestatus](#sendestatus).

| Parameter | Bedeutung                                                                                                                   |
| --------- | --------------------------------------------------------------------------------------------------------------------------- |
| `email`   | Nur Sendungen an diese Adresse, exakt verglichen nach Trimmen und Kleinschreibung.                                          |
| `status`  | Nur Sendungen in diesem Zustand: `queued`, `sent`, `failed`, `delivered`, `opened`, `clicked`, `bounced` oder `complained`. |
| `since`   | ISO-8601-Zeitstempel: nur Sendungen, die ab diesem Zeitpunkt eingereiht wurden. Standard: 30 Tage vor `until`.              |
| `until`   | ISO-8601-Zeitstempel: nur Sendungen, die davor eingereiht wurden. Standard: jetzt.                                          |
| `limit`   | Sendungen pro Seite, höchstens 100. Standard: 25.                                                                           |
| `cursor`  | Der `pagination.cursor` der vorigen Seite.                                                                                  |

```json
{
	"data": [
		{
			"sendId": "j57...",
			"status": "bounced",
			"email": "ada@example.com",
			"bounceType": "hard",
			"bounceCause": "recipient",
			"errorMessage": "550 5.1.1 The email account that you tried to reach does not exist",
			"...": "die übrigen Felder des Sendestatus"
		}
	],
	"pagination": { "limit": 25, "cursor": null, "isDone": true }
}
```

- Filtere nach `email` oder nach `status`, nicht nach beidem. Eine Anfrage mit beidem wird mit
  `400` abgelehnt, ebenso ein leeres `email` oder `status`. Um die fehlgeschlagenen Sendungen an eine Adresse zu finden, liste nach `email`
  und prüfe jeden `status`.
- Das Fenster von `since` bis `until` ist höchstens 30 Tage lang; ein längeres wird mit `400`
  abgelehnt. Ältere Sendungen erreichst du, indem du `until` zurücksetzt.
- `pagination` hat kein `totalItems`. Gib `cursor` mit denselben Filtern mit; ein Cursor mit
  anderen Filtern wird mit `400` abgelehnt. Eine Sendung, die beim Blättern neu eingereiht wird,
  verschiebt die späteren Seiten nicht.
- Die Liste enthält die Sendungen, die die Statusroute lesen kann, und keine anderen: die
  Sendungen aller API-Keys, aber keine E-Mail aus einer Kampagne oder Automation und keine, deren
  Kontakt gelöscht wurde.

## Eine fehlende E-Mail finden

Wenn jemand sagt, eine E-Mail deiner Anwendung sei nie angekommen:

1. Liste die Sendungen an diese Adresse:
   `GET /api/v1/transactional?email=ada@example.com`. Eine leere Liste heißt, dass in den letzten
   30 Tagen keine Sendung angelegt wurde. Prüfe, ob deine Anwendung `POST /api/v1/transactional`
   aufgerufen hat und was die Antwort war.
2. Lies den `status` der neuesten Sendung:
   - `queued`: Owlat hat sie noch nicht übergeben. Eine Sendung wartet, solange die Zustellung
     pausiert, und schlägt nach vier Tagen fehl.
   - `sent` oder `delivered`: Der empfangende Server hat sie angenommen. Bitte den Empfänger, im
     Spam-Ordner nachzusehen.
   - `bounced` mit `bounceCause` `recipient`: Die Adresse wurde abgelehnt, und `errorMessage` enthält
     die Antwort des Servers. Ein `hard` Bounce heißt, dass die Adresse nicht existiert: Frag nach
     einer richtigen, denn Owlat lehnt weitere Sendungen an sie ab (`recipient_blocked`). Einen
     `soft` Bounce (zum Beispiel ein volles Postfach) kannst du später wiederholen.
   - `bounced` mit `bounceCause` `sender`: Der Empfänger hat die sendende IP oder Domain abgelehnt,
     nicht die Adresse. [`GET /api/v1/status`](/api/status) und das Deliverability Center zeigen,
     was zu beheben ist.
   - `failed`: `errorCode` nennt die Ursache, `errorMessage` erklärt sie.
   - `complained`: Der Empfänger hat sie als Spam markiert.
3. Um alle Fehlschläge auf einmal zu finden, liste stattdessen nach Status:
   `GET /api/v1/transactional?status=failed&since=2026-11-23T08:00:00Z`.

## Idempotente Wiederholungen

Sende einen `Idempotency-Key`-Header, damit du eine Sendung nach einem Timeout oder einem `5xx`
gefahrlos wiederholen kannst:

```http
Idempotency-Key: 3f0c1d9e-6c2b-4a51-9a3e-2f6d1b7c8e90
```

- Der Schlüssel besteht aus 1 bis 255 druckbaren ASCII-Zeichen ohne Leerzeichen, etwa einer UUID
  oder deiner eigenen Bestellnummer. Er gilt für deine Organisation.
- Die erste Anfrage mit einem Schlüssel wird normal verarbeitet. Eine Wiederholung **derselben**
  Anfrage mit diesem Schlüssel innerhalb von 24 Stunden stellt nichts in die Warteschlange, liefert die erste Antwort
  (gleicher Status und Body) und trägt den Header `Idempotent-Replayed: true`.
- Verwendest du den Schlüssel für eine **andere** Anfrage (anderer Body oder anderer Endpunkt),
  wird sie mit `409` `conflict` (`reason: "idempotency_conflict"`) abgelehnt und bewirkt nichts.
- Wurde der Kontakt, den die erste Anfrage betraf, inzwischen gelöscht, wird eine Wiederholung
  innerhalb der 24 Stunden mit `409` `conflict` (`reason: "idempotency_erased"`) abgelehnt und
  bewirkt nichts: Die Anfrage wurde schon ausgeführt, aber ihre Antwort nannte die gelöschte Person
  und wird nicht mehr aufbewahrt.
- Eine abgelehnte Anfrage (zum Beispiel `404` oder `400`) oder eine, die vor dem Ausführen
  fehlschlug, speichert nichts; eine Wiederholung mit demselben Schlüssel führt sie erneut aus.
- Nach 24 Stunden kannst du den Schlüssel für eine neue Anfrage verwenden.
- Ohne den Header wird wie bisher jede Anfrage verarbeitet.

## Reihenfolge der Sprachauflösung

1. Explizites `language` in der Anfrage
2. Bevorzugte Sprache des Kontakts (sofern der Empfänger existiert)
3. Standardsprache der Vorlage
4. Fallback-Standard

## Validierungs- und Zustellprüfungen

- Die Funktion **Transactional API** muss unter **Einstellungen → Features**
  aktiviert sein; solange sie aus ist, werden Anfragen mit `403`
  (`reason: "feature_disabled"`) abgelehnt
- Solange der Versand auf der Instanz ausgesetzt oder gesperrt ist, werden
  Anfragen mit `403` (`reason: "abuse_blocked"`) abgelehnt. `data` im Fehler
  enthält außerdem `status` (`suspended` oder `banned`), `since` (eine
  ISO-8601-Zeit oder `null`, wenn keine hinterlegt ist), `detail`, den mit
  der Sperre hinterlegten Grund (oder `null`), und `lift`, wie sie endet, in
  der Form von `sendingHold.lift` des [Status](/api/status)-Endpunkts. Die
  Meldung sagt, ob sie sich von selbst aufhebt. Aufheben kann sie ein
  Plattform-Admin in der Operator-Konsole
- Die Vorlage muss existieren und den Status `published` haben; eine `transactionalId`, die keine
  Vorlage benennt, auch eine fehlerhafte, wird mit `404` abgelehnt
- Die Vorlage muss gerenderten HTML-Inhalt besitzen
- Die Versanddomain muss verifiziert sein
- `dataVariables` werden, sofern vorhanden, gegen das Schema der Vorlage validiert
- Jede Variable, die die E-Mail ohne Fallback verwendet (`{{orderNumber}}`
  statt `{{giftNote|''}}`), muss mitgeschickt werden, außer die E-Mail markiert
  sie als **optional**. Eine fehlende oder `null` gesetzte Pflichtvariable wird
  mit `400` abgelehnt, das sie nennt; eine optionale bleibt leer oder zeigt
  ihren Fallback. Eine Variable markierst du im Editor der E-Mail unter
  **Versand > Datenvariablen** als optional
- Der Send muss in die [Versandlimits für Transaktionsmails](/api#rate-limits)
  passen, die der Instanz-Admin festlegt; ein Send über einem Limit wird mit
  `429` abgelehnt

## Ablehnungsgründe

Ein abgelehnter Send trägt einen Code in `error.data.reason`. Verzweige auf den
Code, nicht auf die Nachricht: Die Nachricht ist für Menschen und kann sich
ändern. Die SDKs geben ihn als `reason` (JavaScript) und `getReason()` (Java)
heraus. Neue Gründe können dazukommen; einen unbekannten behandelst du nach
seinem Status.

| `reason`                 | Status | Was zu tun ist                                                                                                                         |
| ------------------------ | ------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `feature_disabled`       | `403`  | Ein Admin schaltet **Transactional API** unter **Einstellungen → Features** ein.                                                       |
| `abuse_blocked`          | `403`  | Versand gesperrt. `data.lift` sagt, ob sie sich selbst aufhebt; ein Plattform-Admin hebt sie in der Operator-Konsole auf.               |
| `no_delivery_provider`   | `422`  | Die Instanz hat keinen Zustellprovider. Ihr Betreiber richtet den eingebauten MTA, Resend oder SES ein ([Self-Hosting](/developer/self-hosting)). |
| `recipient_blocked`      | `422`  | Die Adresse ist schon einmal gebounct oder hat sich beschwert. Nicht erneut senden; entferne sie unter **Zielgruppe > Unterdrückungen** nur, wenn du weißt, dass sie wieder funktioniert. |
| `template_not_found`     | `404`  | Prüfe `slug` oder `transactionalId`: Keine Vorlage trägt ihn.                                                                          |
| `template_not_published` | `422`  | Öffne die E-Mail unter **Versand > Transaktional** und klicke auf **Veröffentlichen**.                                                 |
| `template_no_content`    | `422`  | Die E-Mail hat kein gerendertes HTML. Öffne sie, speichere sie und veröffentliche sie erneut.                                          |
| `sender_not_configured`  | `422`  | Lege unter **Versand > Transaktional** einen Absender fest (**Ändern** neben **Sendet von**) oder einen Standardabsender unter **Einstellungen > Allgemein**. |
| `domain_unverified`      | `422`  | Die Domain des Absenders ist nicht verifiziert. Verifiziere sie unter **Einstellungen > Technik > Versanddomains**.                    |
| `invalid_variables`      | `400`  | Eine Datenvariable fehlt, ist `null` oder hat den falschen Typ; die Nachricht nennt sie. Schicke einen Wert des Typs, den die E-Mail festlegt. Eine Variable, die du nicht immer hast, kannst du im Editor der E-Mail als optional markieren. |
| `recipient_rate_limited` | `429`  | Zu viele Sends dieser E-Mail an diese Adresse. Versuche es nach `Retry-After` erneut; der Instanz-Admin legt das Limit unter **Einstellungen > API** fest. |
| `daily_send_limit`       | `429`  | Dieser Key hat sein Tageslimit erreicht. Versuche es nach `Retry-After` (der nächsten Mitternacht UTC) erneut oder bitte den Instanz-Admin, es unter **Einstellungen > API** anzuheben. |
| `idempotency_conflict`   | `409`  | Der `Idempotency-Key` wurde für eine andere Anfrage verwendet. Nimm für eine neue Anfrage einen neuen Key.                              |
| `idempotency_erased`     | `409`  | Die Anfrage lief schon, aber ihr Kontakt wurde inzwischen gelöscht. Nimm nur dann einen neuen Key, wenn du erneut senden willst.        |
